= ADR 0052: A Failed HLS Copy Falls Back to an Encode, and Original Changes to Auto Whenever It Must Encode

== Status

Accepted

This decision changes a rule that link:0013-stream-decision-architecture.adoc[ADR 0013], link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019], link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036], link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] and link:0049-capability-declarations-list-entries-and-an-output-fits-one-entry.adoc[ADR 0049] state.
Those ADRs end playback in Original and in a fixed quality after a format error during an HLS copy.
Each of those ADRs now points to this decision.
This decision also replaces the rule of link:0050-viewer-limits-bind-copies-and-quality-tiers-are-picture-boxes.adoc[ADR 0050] that an encode in Original is one variant without a label.
Every encode that Original reaches now plays in Auto.
ADR 0050 still decides when Original copies, and ADR 0050 still decides how the viewer's limits bound every encode.
ADR 0050 now points to this decision too.
This decision also narrows the rule of ADR 0037 that a copied variant that runs short is a format error.
When the whole source has ended, playback now ends normally at the real end (<<decision-short-copy>>).
link:0045-clients-direct-play-covered-files-and-use-platform-players.adoc[ADR 0045] keeps its fallback from direct play to HLS at original quality.

NOTE: link:0055-a-viewers-audio-delay-is-a-playback-session-parameter-and-the-server-shifts-the-audio-renditions.adoc[ADR 0055] changes Original's order when an applied audio delay is not 0.
Original then skips direct play whenever one capability entry accepts an HLS copy that can apply the delay.
Every format attempt keeps the audio delay and the audio sync correction, and a change of either spends no format attempt.

NOTE: A playback session can start at a start position (<<decision-start-position>>).
Each format attempt starts at the start position until the player reports that playback moved from it.
This amends link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019]'s first job attempt, which starts at the start segment instead of segment 0.
It also amends link:0045-clients-direct-play-covered-files-and-use-platform-players.adoc[ADR 0045]: a direct-play stream session carries the start position, and the client seeks the file there.

NOTE: link:0013-stream-decision-architecture.adoc#encode-range[ADR 0013] decides which encodes keep 10 bits or a PQ or HLG range.
The encode that follows a failed HDR copy keeps the source's range under that rule.
ADR 0013 also decides what follows a failed hardware encoder whose PQ or HLG encode no software encoder can continue in that range: Auto changes format within its format-attempt budget, and a fixed quality changes to an 8-bit SDR encode at the same fixed quality (link:0013-stream-decision-architecture.adoc#hardware-failure-range[ADR 0013]).
This ADR said that every encode is 8-bit SDR until https://github.com/streamarr/streamarr-server/issues/397[streamarr/streamarr-server#397] added HDR10 encodes, and an edit of 2026-11-11 replaces that text.
ADR 0013 also decides that a failure that the server attributes to an encoded lower variant beside a copy withdraws the lower variants and counts no format attempt (link:0013-stream-decision-architecture.adoc#lower-variant-failure[ADR 0013]).
This ADR listed such a variant's `SEGMENT_CAP_EXCEEDED` failure among the failures that move Auto from a copy to an encode, and an edit of 2026-11-13 replaces that text (<<decision-fallback>>).

NOTE: This ADR decided a notice that appeared over the playing video for a few seconds after each fallback.
An edit of 2026-11-11 replaces that notice with a caution symbol on the quality control and a message at the top of the quality picker (<<decision-caution>>).
The same edit adds a format change for an HDR range that the server could not keep (<<decision-hdr-not-kept>>), and a caution symbol on the audio control after a refused audio switch (<<decision-audio-switch-refused>>).

== Context

The viewer picks a playback choice when a stream session starts.
Original is the playback choice that plays the source at its own quality (ADR 0045).
Auto is the playback choice in which the player adapts quality to bandwidth across the variants.
A fixed quality is a playback choice that names one quality, such as 720p, and keeps that quality (link:0050-viewer-limits-bind-copies-and-quality-tiers-are-picture-boxes.adoc[ADR 0050]).
Each client shows the playback choices in a quality control.
The quality control is one of the player controls.
It opens the quality picker, which lists the playback choices.
Original sits at the top of the quality picker.
The player controls show over the video while the viewer uses them, and they hide after a few seconds without input.
iOS and the web client start in Auto.
tvOS starts in Original.

Direct play means that the server sends the source file itself (ADR 0045).
A stream copy passes the source video through unchanged.
An HLS copy is an HLS stream session whose video is a stream copy.
An encode is video that the worker encodes.
In Original, the server direct-plays a file that the client capability declaration covers.
Otherwise, Original plays an HLS copy when one capability entry accepts the copy (ADR 0049).
Otherwise, ADR 0050 decides that Original plays an encode of one variant, bounded by the viewer's limits.
The server today plays Original as copy-only instead.
When no capability entry accepts a copy, the server refuses to start and asks the viewer to set Quality to Auto or to try another device.

A format error is a player error that concerns the media format itself, not the network or the server.
A format attempt is one output format that the server chooses within a playback session.
A playback session is the logical span of one viewing of a media title.
Each playback session has a format-attempt budget that limits how many format attempts the playback session uses (https://github.com/streamarr/streamarr-server/issues/401[streamarr/streamarr-server#401]).
Before this decision, the default budget was two format attempts: the initial format plus one more.

Before this decision, Original recovered from one format error only.
After a format error during direct play, the server fell back to HLS at original quality (ADR 0045).
After a format error during an HLS copy, playback ended with a typed error.
ADR 0013 ended playback in Original when a copy lacked its parameter sets.
ADR 0019 ended playback in Original after a copy's output mismatch.
ADR 0037 ended playback in Original when a copied variant ran short.
In Auto, ADR 0037 moved a copied variant that runs short to an encode, which pads past the real end with the last frame and silence.
ADR 0049 accepted that a rejected copy of a stream with an unknown codec level or frame rate ends playback in Original.
The reason given was that Original is a manual choice, and the server never silently replaces a manual choice.
A fixed quality can also play an HLS copy, when the source fits the fixed quality's picture box and the viewer's other limits (ADR 0050).
A format error during that HLS copy also ended playback, because a fixed quality never changed format automatically.

Auto recovers from a failed Dolby Vision copy in a fixed order (streamarr/streamarr-server#401).
For Dolby Vision profiles 8.1, 8.4, 10.1 and 10.4, and for profile 7 that the worker converts to profile 8.1 (https://github.com/streamarr/streamarr-server/issues/651[streamarr/streamarr-server#651]), Auto first tries the copy with Dolby Vision stripped and then an encode.
The copy with Dolby Vision stripped plays the same video stream on its PQ or HLG base (ADR 0049).
Dolby Vision profiles 5 and 10.0 have no compatible base, so Auto goes straight from the Dolby Vision copy to an encode.
An encode keeps a PQ or HLG range only under the conditions of link:0013-stream-decision-architecture.adoc#encode-range[ADR 0013], and it is SDR otherwise.

A player can refuse a copy that the client declared.
A client capability declaration is evidence, not a guarantee (ADR 0049).
AVPlayer can refuse a stream because of the playlist or the packaging rather than the decoder.
AVPlayer can refuse an HEVC level that the `CODECS` attribute names.
tvOS can refuse an HDR variant while the display is not in an HDR mode.
Streamarr has not measured these refusals.
tvOS starts in Original, so an Apple TV viewer meets a refused copy as an error.

A viewer can also get SDR of an HDR source while expecting HDR.
In a fixed quality, the viewer can choose HDR, and the encode of a fixed quality is SDR when it cannot keep the source's range (link:0013-stream-decision-architecture.adoc#hdr-choice[ADR 0013]).
Auto gives HDR up for SDR after a failed PQ or HLG encode (link:0013-stream-decision-architecture.adoc#encode-range[ADR 0013]).
A TV that leaves its HDR mode changes the picture in a way that the viewer can see.
Streamarr keeps the viewer in HDR for as long as the video can play in HDR.
When the video cannot, SDR is better than no video.

== Decision

[[decision-fallback]]
=== In Original, a format error during an HLS copy falls back to an encode

In Original, the server tries up to four outputs in this order:

. direct play, when the client capability declaration covers the file (ADR 0045);
. an HLS copy at original quality, when one capability entry accepts the copy (ADR 0049);
. the copy with Dolby Vision stripped, after a failed Dolby Vision copy (<<decision-dolby-vision>>);
. an encode.

The server skips every step that the declaration, the probe's property issues or the copy rules rule out.
A file that the declaration does not cover for direct play therefore starts with the HLS copy.
A file that the server cannot copy starts with the encode, which plays in Auto (<<decision-start>>).

After a format error during the HLS copy, the server starts a new format attempt that encodes the video, unless the copy with Dolby Vision stripped comes first (<<decision-dolby-vision>>).
The new format attempt has its own stream session, playlist and initialization segment, as every format attempt does.
The same failures that move Auto from a copy to an encode move Original from the HLS copy to the encode:

* a format error that the player reports for the copy;
* a copy's output mismatch, such as a copy whose decoder configuration record lacks its parameter sets (ADR 0013 and ADR 0019);
* a copied variant that runs short while some source stream still has media after the copy's last segment (<<decision-short-copy>>);
* a job attempt that fails with `SEGMENT_CAP_EXCEEDED` in a stream session with merged segments, which every replacement attempt would repeat (link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc#decision-segment-list[ADR 0037]);
* the worker's typed failure to convert a Dolby Vision profile 7 RPU during the copy (https://github.com/streamarr/streamarr-server/issues/651[streamarr/streamarr-server#651]).

In Auto, a failure that the server attributes to an encoded lower variant beside a copy withdraws the lower variants instead.
A lower variant's job attempt that fails with `SEGMENT_CAP_EXCEEDED` is such a failure.
The withdrawal counts no format attempt.
A new stream session that lists the copy alone replaces the stream session, and the copy plays on (link:0013-stream-decision-architecture.adoc#lower-variant-failure[ADR 0013]).
When the copy does not fit the upload budget, the new stream session plays an encode that leaves the failed lower variant's encode out, as ADR 0013 decides.

The fallback applies whether the viewer picked Original or the client started in Original.

The fallback needs an encode that the client accepts.
Some sources cannot be encoded, for example a source with no usable output frame rate (https://github.com/streamarr/streamarr-server/issues/446[streamarr/streamarr-server#446]).
When the server cannot make an encode that the client accepts, no fallback to an encode exists.
A format error during the HLS copy then ends playback with the typed terminal error, as Auto's recovery does when no eligible replacement exists (streamarr/streamarr-server#401).
The one exception is a failed Dolby Vision copy whose copy with Dolby Vision stripped is eligible: that copy still plays first (<<decision-dolby-vision>>).

*Why:* An error leaves the viewer with no action to take, while the server can still play the title.
The viewer picked Original to watch the title at its best quality, not to give up on the title when that quality fails.
Every failure in the list above is a failure of the copy that an encode avoids.

[[decision-budget]]
=== The default budget is four format attempts, and each fallback spends one

The default format-attempt budget is four format attempts: the initial format plus three more.
Four format attempts hold each of Original's four outputs for a Dolby Vision source: direct play, the Dolby Vision HLS copy, the copy with Dolby Vision stripped and the encode.
The budget stays configurable.

The encode after the HLS copy counts as one format attempt against the playback session's format-attempt budget.
The copy with Dolby Vision stripped after a failed Dolby Vision copy also counts as one format attempt.
A new stream session does not reset the budget or the playback session's format-failure history.
When a configured budget has no room for the next output, playback ends with the typed terminal error, as Auto's recovery does (streamarr/streamarr-server#401).

*Why:* tvOS starts in Original and direct-plays every file that its declaration covers.
Under a budget of two, direct play and the HLS copy used both format attempts, so a refused copy on tvOS still ended playback.
Under a budget of three, a Dolby Vision file that the declaration covers would spend the budget on direct play and the two copies, so a refused stripped copy would still end playback.
Some video is better than no video, so the default budget lets every Original reach the encode.

[[decision-auto]]
=== When Original plays an encode, the playback choice is Auto

Every encode that Original reaches is a format attempt in Auto.
That holds for the encode after the HLS copy, and for an encode that Original starts with (<<decision-start>>).
The server tells the client that the playback choice changed from Original to Auto.
The client then shows Auto as the selected choice in its quality control, and the quality control carries the caution symbol (<<decision-caution>>).

Auto's own rules then apply to the encode:

* The viewer's limits bound the encode, as ADR 0050 decides for Auto.
* The server offers Auto's encoded quality ladder of quality tiers (ADR 0050).
The playlist lists the variants in Auto's order, and the first variant starts first (link:0008-server-generated-hls-playlists.adoc[ADR 0008], link:0044-encoder-headroom-and-the-preset-scale.adoc[ADR 0044]).
* The ladder offers no copy.
After a failed HLS copy, the failed copy stays in the playback session's format-failure history, so the server does not choose the failed copy again for the encode's ladder.
* A format error during the encode starts Auto's recovery within the budget that remains (streamarr/streamarr-server#401).
For example, Auto may then give up HDR for SDR.
* The client hides the HDR toggle, as it does in Auto.

Changing the playback choice to Auto uses no format attempt beyond the encode.
From Auto, the viewer can pick any playback choice again.
A pick of Original starts Original afresh (<<decision-repick>>).

*Why:* After the change, the stream is Auto's ladder, so the quality control describes the stream that actually plays.
A quality control that still showed Original would claim the source's own quality while an encode plays.
The server never silently replaces a manual choice (ADR 0013).
The selected Auto, the caution symbol and its message make this replacement visible.

[[decision-start]]
=== An Original that starts with an encode plays the encode in Auto

Original starts with an encode when the server rules out both direct play and the HLS copy.
That happens, for example, when no capability entry accepts a copy of the source, or when a property issue rules out a copy.
The server then plays the encode in Auto, as it plays the encode after a failed HLS copy (<<decision-auto>>).
The client's quality control shows Auto and carries the caution symbol (<<decision-caution>>).
The encode is the playback session's first format attempt, so the change to Auto spends no format attempt.
The same holds when direct play fails and the server rules out the HLS copy: the encode that follows plays in Auto.
The rule applies whether the viewer picked Original or the client started in Original.

*Why:* Some video is better than no video.
When the device cannot play the original video, the server switches the player to Auto, whether the server learns that from the declaration or from a failed copy.
Refusing to start, as the server does today, gives the viewer an error for a title that the server can still play.
An encode under the Original label would claim the source's own quality while a converted picture plays.

[[decision-fixed-quality]]
=== In a fixed quality, a format error during an HLS copy falls back to an encode at the same fixed quality

After a format error during a fixed quality's HLS copy, the server starts a new format attempt that encodes the video at the same fixed quality, unless the copy with Dolby Vision stripped comes first (<<decision-dolby-vision>>).
The same failures that move Original from the HLS copy to the encode qualify (<<decision-fallback>>).
The encode follows the rules of ADR 0050 for a fixed quality's encode.
The fixed quality's picture box, the viewer's other limits and one capability entry bound its single variant.
The encode counts as one format attempt against the playback session's format-attempt budget (<<decision-budget>>).
The failed copy stays in the playback session's format-failure history.
When the server cannot make an encode that the client accepts, the format error ends playback with the typed terminal error (<<decision-fallback>>).

The playback choice stays the fixed quality, and the client keeps that fixed quality selected in its quality control.
The quality control carries the caution symbol, and the quality picker shows the message for a fixed quality's converted version (<<decision-caution>>).
When the failed copy was HDR and the encode cannot keep that range (link:0013-stream-decision-architecture.adoc#encode-range[ADR 0013]), the encode is SDR.
The message already tells the viewer that a converted version is playing, so the change to SDR is not silent.
The server tells the client that the encode is SDR, and the client's HDR toggle then shows SDR.
A fixed quality changes format after no other format error, so a format error during the encode ends playback with the typed terminal error.

*Why:* A fixed quality promises a picture size, not a copy.
An encode at the same fixed quality keeps that promise, while an error leaves the viewer with no video.
Switching to Auto would drop the size that the viewer picked.
An SDR picture at the chosen size is better than no picture, because some video is better than no video.
The caution symbol and its message tell the viewer that a converted version is playing, so the server does not replace the copy silently (ADR 0013).

[[decision-dolby-vision]]
=== In Original and in a fixed quality, a failed Dolby Vision copy first falls back to the copy with Dolby Vision stripped

Original and a fixed quality follow Auto's order for a failed Dolby Vision copy (streamarr/streamarr-server#401).
The order applies to Dolby Vision profiles 8.1, 8.4, 10.1 and 10.4, and to profile 7 that the worker converts to profile 8.1.
It applies when one capability entry accepts the copy's PQ or HLG base, so the client declares the base range.
In Original, the server then tries direct play, the Dolby Vision HLS copy, the copy with Dolby Vision stripped and the encode, in that order.
In a fixed quality, the server tries the Dolby Vision copy, the copy with Dolby Vision stripped and the encode at the same fixed quality.
The server skips every step that the declaration, the probe's property issues or the copy rules rule out.

Two failures of the Dolby Vision copy lead to the copy with Dolby Vision stripped:

* a format error that the player reports for the Dolby Vision copy;
* the worker's typed failure to convert a Dolby Vision profile 7 RPU during the copy (streamarr/streamarr-server#651).

A copy's output mismatch and a copied variant that runs short go straight to the encode, as in Auto, because the copy with Dolby Vision stripped copies the same video stream and would fail in the same way.
Profiles 5 and 10.0 have no compatible base, so a failed Dolby Vision copy of either goes straight to the encode.

The copy with Dolby Vision stripped is a new format attempt with its own stream session, playlist and initialization segment.
It counts as one format attempt against the playback session's format-attempt budget (<<decision-budget>>).
The failed Dolby Vision copy stays in the playback session's format-failure history.
The playback choice stays Original or the fixed quality, and the client keeps that choice selected in its quality control.
The quality control carries the caution symbol with the Dolby Vision message (<<decision-caution>>), and the quality picker marks the selected choice (<<decision-marking>>).
In a fixed quality, the HDR toggle keeps showing HDR, because the copy plays on the source's HDR base.
A format error during the copy with Dolby Vision stripped falls back to the encode, as a format error during any HLS copy does.
In Original, the playback choice then changes to Auto (<<decision-auto>>).
In a fixed quality, the encode keeps the same fixed quality (<<decision-fixed-quality>>).

*Why:* The copy with Dolby Vision stripped keeps the source's pixels, picture size and PQ or HLG base, and it costs no encoder capacity.
An encode costs worker capacity, and it gives up HDR whenever it cannot keep the range (link:0013-stream-decision-architecture.adoc#encode-range[ADR 0013]).
Stripping Dolby Vision needs only a bitstream rewrite (link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc#decision-bitstream-rewrites[ADR 0036]), not an encode.
The stripped copy still plays the source's own video stream at the source's own size, so Original keeps its promise of the source's own quality, apart from the Dolby Vision information.
A quality control that switched to Auto would describe a ladder that does not play.
The caution symbol, its message and the mark make the loss of Dolby Vision visible, so the server does not replace the copy silently (ADR 0013).

[[decision-short-copy]]
=== A copy that runs short after the whole source has ended ends playback normally

A copied variant runs short when the source ends before the media segments that the copy's playlist advertises (ADR 0037).
When every source stream has ended by the copy's last segment, playback ends at the real end as a normal end.
The server starts no encode and spends no format attempt.
The client ends playback at the real end itself, as it does at the end of the media title.
The quality control carries no caution symbol, and the quality picker shows no mark.
The server starts no job attempt past the real end.

The normal end is part of the stream session's current state, and the server keeps it until the stream session ends.
The state names the real end's position.
The server publishes the state when the copy runs short, and a recovery query returns it, so a late or missed event does not lose it (link:0042-graphql-subscriptions-run-over-websocket-until-token-expiry.adoc[ADR 0042]).
The normal end takes precedence over every failure in that stream session.
The server answers a failure report for that stream session with the normal end, never with a fallback or with the typed terminal error.
The server holds a segment request past the real end and never answers it with `503 Service Unavailable`.
The held request ends when the client ends playback or when the stream session ends.
A player that reaches the real end before the client learns of it therefore waits there instead of failing, and the client then ends playback.
This is the one held segment request that link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019]'s producer liveness does not bound, because no producer can make that segment.

When some source stream still has media after the copy's last segment, such as audio that runs on after the video, the short copy is a format error.
The fallbacks of this decision then apply: Original and a fixed quality fall back to the encode, which pads to the advertised end (ADR 0037).
The same rule holds in Auto, where the short copy that is a format error starts Auto's recovery (streamarr/streamarr-server#401).

*Why:* When the whole source has ended, an encode adds only a frozen frame and silence (https://github.com/streamarr/streamarr-server/issues/511[streamarr/streamarr-server#511]).
The viewer would see a caution symbol, a change to Auto and a new stream session during the credits, for nothing that the viewer could watch.
A request past the real end breaks hls.js, AVPlayer and WebKit's native player, so the client must end playback itself.
A refusal of that request would race with the client's normal end, so the server holds the request, and a player that waits does not fail.

[[decision-caution]]
=== While playback continues but differs from the viewer's choice, the quality control carries a caution symbol, and the quality picker explains it

Playback can continue while what plays differs from the playback choice that the viewer picked.
The server then names the difference as the playback session's format change.
While the playback session names a format change, the client shows a caution symbol on its quality control.
The caution symbol is the alert triangle that the quality picker's mark also uses (<<decision-marking>>).
The caution symbol sits on a corner of the quality control.
The caution symbol shows only while the player controls show, and it hides with them.
The caution symbol never brings up the player controls.
Nothing appears over the playing video while playback continues.

While the quality control carries the caution symbol, the quality picker shows a message at its top.
The message shows as soon as the quality picker opens.
The viewer does not need to hover over a row or focus a row to read the message.
The quality picker also marks the playback choice whose output differed (<<decision-marking>>).
A quality control that carries the caution symbol always opens its quality picker, even when the quality picker offers fewer than two playback choices.

The server names six format changes.
The client shows one message for each case:

[cols="3,2,3",options="header"]
|===
|What happened |Format change |Message

|Original changed to Auto after its HLS copy failed (<<decision-fallback>>).
|`COPY_FAILED`
|This video couldn't play in its original form, so Quality changed to Auto.

|Original changed to Auto after direct play failed and the server ruled out the HLS copy (<<decision-start>>).
|`DIRECT_PLAY_FAILED`
|This video couldn't play in its original form, so Quality changed to Auto.

|Original started with an encode, which plays in Auto (<<decision-start>>).
|`STARTED_WITH_ENCODE`
|This video couldn't play in its original form, so Quality changed to Auto.

|A fixed quality's HLS copy failed, and an encode plays at the same fixed quality (<<decision-fixed-quality>>).
|`COPY_FAILED`
|This video couldn't play in its original form at this quality, so a converted version is playing.

|A Dolby Vision copy failed, and the copy with Dolby Vision stripped plays, in Original or in a fixed quality (<<decision-dolby-vision>>).
|`DOLBY_VISION_STRIPPED`
|This video couldn't play in Dolby Vision, so the HDR version is playing.

|The viewer switched audio tracks during direct play, the server ruled out the HLS copy, and Original changed to Auto.
|`AUDIO_TRACK_SWITCHED`
|The audio track you chose plays in a converted version, so Quality changed to Auto.

|A fixed quality with HDR chosen started in SDR (<<decision-hdr-not-kept>>).
|`HDR_NOT_KEPT`
|This video couldn't play in HDR at this quality, so it's playing in SDR.

|A fixed quality's PQ or HLG encode continued in SDR during playback (<<decision-hdr-not-kept>>).
|`HDR_NOT_KEPT`
|This video couldn't stay in HDR at this quality, so it's playing in SDR.

|Auto gave HDR up for SDR (<<decision-hdr-not-kept>>).
|`HDR_NOT_KEPT`
|This video couldn't stay in HDR, so it's playing in SDR.
|===

The client picks the message from the format change and from the playback choice that the viewer picked.
For `HDR_NOT_KEPT` in a fixed quality, the client also reads whether an earlier format attempt of the playback session played HDR.
Each message says what happened in one sentence.
A message asks nothing of the viewer, because the quality picker already shows what the viewer can pick.
A message names no internal concept, such as a worker, an encoder, a format attempt, a copy or a transcode.
"A converted version" is the viewer's word for an encode.
A message names no cause, so a message never blames the viewer's device when the file or the server forces the change.
Every client names its quality control Quality, so the messages use that name.

The playback session names one format change at a time.
A later format change replaces an earlier one, and the client then shows the later format change's message.
For example, when the copy with Dolby Vision stripped also fails in Original, `COPY_FAILED` replaces `DOLBY_VISION_STRIPPED`.
The server names `HDR_NOT_KEPT` only while the playback session names no other format change (<<decision-hdr-not-kept>>).

When the viewer picked Auto, the server names only `HDR_NOT_KEPT`.
Auto promises no particular format, so Auto's other recoveries still play what the viewer picked, and they raise no caution symbol.
The fallback from direct play to the HLS copy raises no caution symbol, because that HLS copy plays the source's own video.
A copy that runs short after the whole source has ended raises no caution symbol, because playback ends normally (<<decision-short-copy>>).

The selected choice is the playback choice that the quality control shows as selected.
The caution symbol on the quality control goes when the viewer picks a playback choice other than the selected choice, and the picked playback choice plays as the viewer picked it.
A pick of another playback choice starts a new playback session, and the new playback session names no format change until what plays differs again (<<decision-repick>>).
A pick of the selected choice starts nothing and clears nothing, so the caution symbol stays.
For example, after Original changes to Auto, a pick of Auto keeps the caution symbol.
The caution symbol also goes when the viewer leaves the media title.
Opening the quality picker does not clear the caution symbol.

A screen reader announces the message once, politely, when the caution symbol appears or when its message changes.
The announcement does not move focus.
The announcement comes even while the player controls are hidden.
The quality control's accessible name or accessible description carries the message, so a screen reader reads the message with the quality control.
A screen reader also reads the message when the quality picker opens.

The caution symbol and the mark use the design system's caution color, a yellow.
The triangle's shape carries the meaning, so color is never the only signal.
The caution symbol never uses the error red, because the video still plays.
Each client draws the caution symbol, the message and the mark with the design system's components (https://github.com/streamarr/streamarr-ux/pull/30[streamarr/streamarr-ux#30]).

Only playback that has stopped shows over the video.
The client then shows its failed state, with a way to try again.

*Why:* A notice over the playing video covers the picture for a change that needs no action from the viewer.
The caution symbol waits in the place where the viewer chooses quality.
The viewer reads the reason after opening the quality picker, so the reason never disappears before the viewer reads it.
A caution symbol that showed while the player controls are hidden would sit over the picture for the rest of the viewing.
Opening the quality picker changes nothing that plays, so the caution symbol stays, and the viewer can read the message again.
A stream that plays is never restarted to clear the caution symbol.
A restart for a pick of the selected choice would interrupt the video.
The new playback session would also start without the format-failure history, so the new playback session could try the failed output again.
A quality control that could not open would hide the reason that only its quality picker shows.
A message that blamed the device would be false whenever the file or the server forces the change, for example through a property issue or a stream that ends early.
Playback that has stopped needs the viewer to act, so only the failed state shows over the video.

[[decision-hdr-not-kept]]
=== The server names HDR that it could not keep as the format change `HDR_NOT_KEPT`

The server names the format change `HDR_NOT_KEPT` when a format attempt plays SDR of a source whose compatible base is PQ or HLG, in either of two cases:

* the viewer chose HDR in a fixed quality;
* an earlier format attempt of the playback session played PQ or HLG.

Three forms reach `HDR_NOT_KEPT`:

. A fixed quality with HDR chosen starts in SDR, because the fixed quality's encode cannot keep the source's range (link:0013-stream-decision-architecture.adoc#hdr-choice[ADR 0013]).
. A fixed quality's PQ or HLG encode continues in SDR, because its hardware encoder failed and no software encoder can continue the encode in that range (link:0013-stream-decision-architecture.adoc#hardware-failure-range[ADR 0013]).
The SDR encode is a new format attempt at the same fixed quality, and the SDR encode counts against the playback session's format-attempt budget.
. Auto gives HDR up for SDR, after a format error during a PQ or HLG encode or after such a hardware encoder failure (link:0013-stream-decision-architecture.adoc#encode-range[ADR 0013]).

In each form, the playback choice stays selected, and the quality picker marks that playback choice (<<decision-marking>>).
In a fixed quality, the client's HDR toggle shows SDR.

The server names `HDR_NOT_KEPT` only while the playback session names no other format change.
A fixed quality's failed HDR copy whose encode plays SDR therefore keeps `COPY_FAILED` (<<decision-fixed-quality>>).
An Original that changed to Auto keeps its earlier format change when Auto later gives HDR up.

*Why:* Streamarr keeps the viewer in HDR for as long as the video can play in HDR.
When the video cannot, SDR is better than no video, so the server plays SDR instead of ending playback.
A viewer who chose HDR and sees SDR learns the reason, so the server does not replace the manual choice silently (ADR 0013).
In Auto, the viewer chose no range.
A TV that leaves its HDR mode still changes the picture in a way that the viewer can see, so Auto names the loss of HDR too.
The message of an earlier format change already tells the viewer that a converted version plays, so `HDR_NOT_KEPT` does not replace that message.

[[decision-audio-switch-refused]]
=== A refused audio switch during direct play puts the caution symbol on the audio control

During direct play, the viewer can switch to another audio track.
On a player that cannot select an audio track inside a directly played file, the switch replaces the direct-play stream session with an HLS stream session (link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043]).
The server can refuse that switch with a typed error, for example when no worker can take the HLS stream session.
Direct play then continues with the audio track that played before.
The client shows the caution symbol on its audio control, the player control that opens the audio picker.
The audio picker shows this message at its top:

[quote]
The audio track you chose couldn't play, so the audio didn't change.

The caution symbol on the audio control follows the rules of the caution symbol on the quality control, except for the pick that clears the caution symbol (<<decision-caution>>).
The caution symbol on the audio control goes when the viewer picks any audio track, the audio track that plays included.
The caution symbol on the audio control also goes when the viewer leaves the media title.
The server names no format change for a refused switch, because the format did not change.
The client keeps the caution symbol from the server's typed error.

*Why:* Playback continues, so a notice over the video would interrupt the viewer for a change that the audio picker can explain.
The refusal answers the viewer's own request for another audio track, so the caution symbol belongs on the audio control, not on the quality control.
Without the caution symbol, the viewer would hear the old track and could not tell why.
A pick of the audio track that plays restarts nothing, so that pick clears the caution symbol without interrupting the video.
A pick of the selected quality choice could clear the caution symbol only with a restart (<<decision-caution>>).

[[decision-marking]]
=== The quality picker marks a playback choice whose output differed from that playback choice

The quality picker marks the playback choice whose output differed from that playback choice, and the mark explains why.
The mark is the same alert triangle as the caution symbol.

* After Original changes to Auto, the quality picker marks Original, and Auto is the selected choice.
That holds after a failed HLS copy, after a failed direct play whose HLS copy the server rules out, after an audio switch during direct play that needs an encode, and when Original starts with an encode.
* After the fallback to the copy with Dolby Vision stripped, the quality picker marks the selected choice, Original or the fixed quality, which stays selected.
* After a fixed quality's fallback to an encode, the quality picker marks the fixed quality, which stays selected.
* After the server could not keep HDR, the quality picker marks the selected choice, the fixed quality or Auto, which stays selected (<<decision-hdr-not-kept>>).

The quality picker shows no mark after the fallback from direct play to the HLS copy, because that HLS copy plays the source's own video.
The mark stays until the viewer leaves the media title, or until the marked choice plays as the viewer picked it.
The mark can therefore outlast the caution symbol.
For example, after Original changes to Auto, a viewer who picks a fixed quality that plays as picked sees no caution symbol, and Original keeps its mark.
The mark's explanation is the message of its case (<<decision-caution>>).
Every viewer can reach the mark's explanation, including through a screen reader.
Each client decides how the mark's explanation appears (streamarr/streamarr-web#29, streamarr/streamarr-apple#60).

*Why:* The caution symbol goes once the viewer picks another playback choice that plays as the viewer picked it.
The mark keeps the reason beside the playback choice whose output differed.
A viewer who sees the mark beside Original knows that Original may fall back again before picking it.

[[decision-repick]]
=== A viewer who picks Original again starts Original afresh

After the playback choice changed to Auto, the viewer can pick Original again while watching the same media title.
The server then tries Original from the top, as a fresh request.
It tries direct play, the HLS copy, the copy with Dolby Vision stripped and the encode in that order, and skips every step that the declaration, the probe's property issues or the copy rules rule out.
The pick is the viewer's own choice, not format recovery, so it spends no format attempt, even when the budget is used up.
The server handles the pick as it handles reopening the media title: Original starts with the full format-attempt budget and without the earlier format-failure history.
A fallback after the pick follows this decision again, with its caution symbol and its mark.

*Why:* tvOS can refuse an HDR master during a display mode switch and play the same master a moment later, so a refusal earlier in the session does not show that the master never plays.
Epic streamarr/streamarr-server#399 already starts fresh when the viewer reopens the media title.
A pick that skipped every failed output would send the viewer straight back to Auto and to the same caution symbol.
A pick that spent a format attempt could end playback with the typed terminal error, although the viewer only asked to try again.

[[decision-start-position]]
=== A playback session can start at a start position

The start position is where the viewer wants playback to begin, in seconds from the start of the media.
A client usually sends the viewer's resume position as the start position.
The client sends the start position when it creates the playback session, as `startPositionSeconds` in the input of `createPlaybackSession`.
The start position is optional.
Without a start position, playback starts at the beginning of the media, as before.

The server accepts a start position of 0 or more that lies before the stream session's media end (link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc#decision-media-end[ADR 0037]).
The server refuses every other start position with the typed error `StartPositionOutOfRangeError` (link:0026-mutation-payloads-and-error-channels.adoc[ADR 0026]).
The server refuses a negative start position before it reads the media file.

An HLS stream session starts at the start segment.
The start segment is the media segment that holds the start position on the stream session's own segment timeline.
For a copy, each segment opens at its keyframe (ADR 0037), so a start position just before that keyframe lies in the segment before it.
For an encode, the start segment comes from the plain segment grid.
The first-listed variant's first job attempt starts at the start segment, and no job attempt starts at segment 0 (ADR 0019).
The multivariant playlist marks the start position with `EXT-X-START`, with `TIME-OFFSET` set to the start position and `PRECISE=YES`.
RFC 8216bis section 4.4.2.2 lets a multivariant playlist carry the tag.
A tag in the multivariant playlist should not appear in the media playlists that it lists, so no media playlist repeats the tag.
With `PRECISE=YES`, the player starts in the segment that holds the start position and renders no sample that presents before it.

A direct-play stream session carries the start position, and the server returns the start position with the stream session.
The client seeks the source file to the start position.
The server serves the same byte ranges as before.

The start position belongs to the playback session.
Every later format attempt starts at the start position too, until the player reports a playback position for a ready format attempt in a whole second other than the start position's second.
After that report, the next format attempt starts at the beginning of the media, as before, and the client seeks the new stream session itself.
A format attempt that fails before the player reports a position keeps the start position.
Every stream session returns its own start position as `startPositionSeconds`.

*Why:* Before this decision, a resumed title started its first job attempt at segment 0.
The player fetched segment 0, and then the client seeked to the resume position.
The server stopped the job attempt at segment 0 and started another at the resume segment.
Every resumed title paid for one wasted job attempt, one relocation and the delay of both.
A start position lets the first job attempt start where the viewer resumes.
The playlist tag tells the player where to begin, so the player requests the start segment first.
A replacement that keeps the start position avoids the same waste after a format error during startup.
A replacement after the player has moved does not keep the start position, because the start position no longer describes where the viewer is.

[[explicitly-deferred]]
=== Explicitly deferred

* Where the tvOS player hosts its player controls, and therefore where the Apple client draws the caution symbol and the message.
The Apple client builds the caution symbol after that decision.
* Whether a format error that the player reports during a fixed quality's PQ or HLG encode gives HDR up for SDR, as a hardware encoder failure does (<<decision-hdr-not-kept>>).
Today that format error ends playback with the typed terminal error (<<decision-fixed-quality>>).

== Consequences

* In Original, a refused HLS copy no longer ends playback under the default budget.
The quality control shows Auto and carries the caution symbol.
* In a fixed quality, a refused HLS copy no longer ends playback under the default budget.
The fixed quality stays selected, and the quality control carries the caution symbol.
* Nothing appears over the playing video while playback continues.
A viewer who does not bring up the player controls sees the caution symbol only when the player controls next show.
A screen reader announces the message at once.
* A viewer who chose HDR in a fixed quality gets SDR with the caution symbol when the server cannot keep the range, at the start or after a hardware encoder failure (<<decision-hdr-not-kept>>).
Playback ends only when no format attempt remains or no worker can take the SDR encode.
* In Auto, a change from HDR to SDR now raises the caution symbol and marks Auto.
Auto's other recoveries stay unannounced.
* A refused audio switch during direct play puts the caution symbol on the audio control, and the client keeps that state itself, because the playback session names no format change for it.
* With the default budget of four format attempts, a file that starts with direct play reaches the encode.
For a Dolby Vision source whose copy with Dolby Vision stripped is eligible, direct play is the first format attempt, the Dolby Vision HLS copy is the second, the copy with Dolby Vision stripped is the third, and the encode is the fourth.
A format error during that encode then ends playback with the typed terminal error, because no format attempt remains for Auto's recovery.
Any other file that starts with direct play keeps one format attempt for Auto's recovery after the encode.
* The default budget holds for every playback choice, so Auto's recovery also gets a fourth format attempt.
For a Dolby Vision profile 8.1, 8.4, 10.1 or 10.4 source, Auto then keeps one format attempt after the encode that follows the copy with Dolby Vision stripped (streamarr/streamarr-server#401).
* A playback session can spend four format attempts before the typed terminal error, so a viewer may wait through up to three failed starts before the error.
* In Original and in a fixed quality, a refused Dolby Vision copy of profile 8.1, 8.4, 10.1 or 10.4, or of converted profile 7, keeps HDR and the source's picture through the copy with Dolby Vision stripped, and it costs no worker capacity.
The quality control carries the caution symbol with the Dolby Vision message, and the selected choice stays.
* tvOS starts in Original, so every tvOS stream that starts with an encode now starts with Auto selected and the caution symbol on the quality control.
* A viewer who picks Original again can meet the same failure, the same caution symbol and the same change to Auto again.
Each such pick costs another failed start and, after a failed copy, another encode.
* Original never plays an encode.
The rules of ADR 0050 for an encode in Original, one variant without a label, no longer apply, because that encode is Auto's ladder.
* The encode starts on Auto's first variant, which is the variant whose average bitrate is nearest 2000 kb/s.
The picture can therefore start below the source's size and then climb.
* The encode costs worker capacity that the copy did not cost.
* Under ADR 0049, a stream with an unknown codec level or frame rate can reach a player that refuses the copy.
In Original and in a fixed quality, that refusal now costs a format attempt and a converted picture instead of ending playback.
* A copied variant that runs short after the whole source has ended now ends playback normally at the real end, in every playback choice.
The player never reaches the advertised end, so the client must stop it there.
* A copied variant that runs short while some source stream still has media is detected near the real end of the source.
In Original and in a fixed quality, the quality control then carries the caution symbol near the end, and the encode pads to the advertised end (ADR 0037).
* After the fallback, the viewer's limits bound the stream, because Auto honors them (ADR 0050).
* A resumed title starts its first job attempt at the start segment, so the server no longer encodes or copies segment 0 for a viewer who resumes.
* A client that sends a start position must not seek an HLS stream session to the same position again, or the player can request a segment that lies before the start segment and cause a relocation.
* A replacement after the player moved starts at the beginning of the media, so the client must seek that replacement to the viewer's position.
* The server's answer when a stream session starts, and its answer to a format failure, must carry the playback choice that plays and the playback session's format change, so that the client can show Auto, the caution symbol and the right message.
The playback session keeps its format change until the playback session ends.
The answer must also carry the encode's dynamic range, so that the client's HDR toggle shows SDR after an SDR fallback.
* The server must keep the normal end of a copy that runs short after the whole source has ended as stream session state, publish it, return it from a recovery query and answer failure reports with it, so that the client can end playback at the real end.
The server holds a segment request past that real end until the client ends playback or the stream session ends.
* Each client must show the caution symbol on its quality control and the message at the top of its quality picker, and each client must switch its quality control to Auto when Original changes to Auto.
Each client must also mark the playback choice whose output differed, with an explanation.
In a fixed quality, and after the fallback to the copy with Dolby Vision stripped, each client must keep the selected choice.
Each client must let a quality control that carries the caution symbol open, even when the quality control offers fewer than two playback choices.
* Each client removes the notice that it showed over the video for these cases.

== Rejected Alternatives

* Ending playback after an HLS copy's format error, the earlier rule, gives the viewer an error for a title that the server can still play.
tvOS starts in Original, so most Apple TV viewers would meet that error.
* Falling back silently while the quality control still shows Original would replace a manual choice without telling the viewer.
ADR 0013 forbids a silent replacement.
* Showing the caution symbol while the quality control still shows Original would leave the quality control describing a stream that does not play.
* Refusing to start Original when the server must encode, as the server does today, gives the viewer an error for a title that the server can still play.
* Playing an encode in Original as one variant without a label, as ADR 0050 decided, would keep Original selected while a converted picture plays.
* Encoding one variant at the source's size under the Auto label would show Auto while the player has only one variant, so the player cannot adapt quality.
* Asking the viewer to try Auto after Original fails, the epic's earlier deferred idea, stops playback until the viewer acts.
* Skipping every failed output when the viewer picks Original again would send the viewer straight back to Auto, and it would keep a refusal that does not repeat, such as tvOS's refusal during a display mode switch, for the rest of the viewing.
* Charging the viewer's pick of Original against the format-attempt budget would end playback when the viewer asks to try again.
* Marking Original with a line of text such as "Didn't play on this device" would blame the device, which is false when the file forces the encode.
* A notice over the playing video that disappears after a few seconds, the earlier rule, covers the picture for a change that needs no action from the viewer.
The reason is gone once the notice disappears.
* A message that says "This device couldn't play the original video" would be false when a property issue or a stream that ends early forces the encode.
* Clearing the caution symbol when the viewer opens the quality picker would hide a difference that still plays, and the viewer could not read the message again.
* Starting a new playback session when the viewer picks the selected choice would clear the caution symbol, but the restart would interrupt a stream that plays, and the new playback session could try the failed output again.
* Clearing the caution symbol in the client alone when the viewer picks the selected choice would contradict the playback session, which still names the format change.
* Showing the caution symbol while the player controls are hidden would put a symbol over the picture for the rest of the viewing.
* Showing the explanation only beside a hovered or focused row would make the viewer find the marked row before learning what happened.
* Coloring the caution symbol in the error red would tell the viewer that playback failed, while the video still plays.
* Announcing every recovery in Auto would raise the caution symbol for changes that the viewer cannot see.
* Ending a fixed quality's playback when the server cannot keep HDR would give the viewer an error, although SDR at the chosen size can play.
* Naming `HDR_NOT_KEPT` in place of an earlier format change would replace a message that already tells the viewer that a converted version plays.
* Showing a refused audio switch on the quality control would put the reason away from the audio control that the viewer used.
* Starting the encode beside every copy as a standby stream costs worker capacity for every copy that plays.
Epic streamarr/streamarr-server#399 starts another format only after a qualifying format error.
* Keeping the earlier rule for a fixed quality, so that a format error during its HLS copy still ends playback, gives the viewer an error for a title that the server can still play at the size the viewer picked.
* Switching a fixed quality to Auto after a failed HLS copy would drop the size that the viewer picked, although an encode at that size can play.
* Keeping the default budget at two format attempts, and letting the budget bind, would end playback on tvOS whenever a file that starts with direct play also fails its HLS copy.
* A default budget of three format attempts would end playback on tvOS whenever a Dolby Vision file that starts with direct play also fails both copies.
* Falling back from a failed Dolby Vision copy straight to the encode in Original and in a fixed quality would cost worker capacity, and it would give up HDR whenever the encode cannot keep the range (link:0013-stream-decision-architecture.adoc#encode-range[ADR 0013]).
The copy with Dolby Vision stripped keeps the source's pixels and HDR base.
* Switching Original to Auto after the fallback to the copy with Dolby Vision stripped would show a ladder in the quality control while the source's own video stream plays.
* Falling back to an encode that pads when a copy runs short after the whole source has ended would show the viewer a caution symbol and a change to Auto during the credits, for a frozen frame and silence.
* Skipping the HLS copy after a failed direct play, so that a budget of two reaches the encode, would give up the source's own video whenever only direct play fails.
The HLS copy still plays the source's own video, and it can play where direct play cannot, for example when the player refuses the source container.

* Leaving the start to the client, the earlier behavior, starts every resumed title with a wasted job attempt at segment 0 and a relocation.
* Marking the start in every media playlist instead of the multivariant playlist would repeat the same tag in each media playlist.
RFC 8216bis section 4.4.2.2 prefers one tag in the multivariant playlist, and AVPlayer and hls.js 1.6 both read the tag there.
* Marking the start with `PRECISE=NO` would play the media from the start of the start segment, up to one segment before the start position.
* Starting a replacement at the latest reported playback position would follow a position that the player reports only in whole seconds and only from time to time.
The client knows the viewer's exact position and seeks the replacement itself.
* Changing the byte ranges of a direct-play stream session would change the source file that the player reads.
The player seeks within the file on its own.
