== Context

Streaming negotiates source media (ffprobe) against client capabilities (StreamingOptions).
Each stream type -- video, audio, subtitle -- needs an independent decision.

These independent decisions compose into a TranscodeDecision that drives FFmpeg command construction and HLS playlist generation.

The rest of this section describes the system before this amendment.
The video decision is implicit.
A codec family and a compatibility flag stand in for the video decision.
The server copies the video whenever the client names the source codec.
Otherwise, the server encodes the video.
The Apple TV app names `h264` and `hevc`.
The server therefore copies every HEVC source to the Apple TV app, including HDR sources.
Every client counts as naming `h264`.
Every client therefore receives a copy of a 10-bit H.264 source.
Tone mapping converts HDR brightness and color into the smaller SDR range.
PQ (perceptual quantizer) and HLG (hybrid log-gamma) are the two HDR transfer characteristics.
An encode keeps the source's bit depth and transfer characteristic.
A 10-bit source becomes 10-bit H.264.
An encode of an HDR source keeps the source's PQ or HLG transfer characteristic.
The worker does not tone-map that encode.
An encode of a Dolby Vision profile 5 source comes out teal.
A codec string is the RFC 6381 value that names a stream's codec, codec profile and level, such as `avc1.640028`.
A variant's `CODECS` attribute lists the codec strings of the variant's streams.
The playlist's codec strings are constants.
These constants often disagree with the media.
The stored probe cannot tell 8-bit from 10-bit or SDR from HDR.
The stored probe also ignores a source's rotation and container cropping.

== Decision

=== Each stream type has its own decision record

Model each stream type as a decision record: AudioDecision (COPY/TRANSCODE/NONE), SubtitleDecision (EXCLUDE/BURN_IN/SIDECAR/HLS/EMBED), and VideoDecision.
VideoDecision replaces the implicit codec family and compatibility flag.
VideoDecision records whether the video is copied or encoded.
VideoDecision also holds the planned output that link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] defines.

Stream decisions compose into TranscodeDecision -> TranscodeMode -> FfmpegCommandBuilder.
Pipeline: probe -> decide per stream -> compose -> resolve mode -> build command.
Burning in a subtitle turns the video into an encode.
A stream session that burns in an image subtitle therefore follows every encode rule in this ADR.
The transcode job carries the video decision to the worker.
The video decision holds the source's dynamic range and the planned output's dynamic range.
The video decision also holds each variant's codec profile, tier, level and codec string.
The worker follows the video decision and never works those values out again.
link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] leaves the field names of the job contract to the implementation.

The video decision reads facts that probe version 4 and later store.
link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032]'s rules for probe versions govern those facts.
Those facts include the dynamic range, bit depth, chroma subsampling, rotation, container cropping, output frame rate and codec string of the video stream.
From probe version 5 on, the video decision also reads the video stream's typed codec profile.

=== Every video encode produces 8-bit 4:2:0 SDR

Every encode's planned output is 8-bit 4:2:0 SDR.
The planned output uses BT.709 color in limited range.
The planned output's dynamic range has an SDR compatible base.
A compatible base is the standard picture format that a player could use without the advanced HDR information.
HDR10+ and Dolby Vision are absent from the planned output.
The server chooses how the worker converts the source to the planned output.
The worker builds its filters from the two dynamic ranges in the transcode job.
The worker never chooses a conversion on its own.
The worker tone-maps when the planned output is SDR and the source's compatible base is PQ, HLG or none.
The worker converts a source whose compatible base is SDR or unspecified to 8 bits without tone mapping.
The worker never tone-maps a stream copy.
Tone mapping uses the mobius curve with a 1000-nit peak.
The worker never uses another tone curve.
The worker tone-maps with the `tonemapx` filter of the pinned FFmpeg build that ADR 0029 describes.
<<gpu-stages>> decides when a GPU tone mapper replaces `tonemapx`.
A reference processing unit (RPU) holds the per-frame Dolby Vision picture-adjustment instructions.
Before tone mapping, the worker reshapes a Dolby Vision profile 5 source with the source's RPUs.
When such a source's RPUs start their samples, the worker first reorders the RPUs (<<reshape-rpus-starting-samples>>).
An encode of a Dolby Vision profile 7 or 8.x source reads only the Dolby Vision base layer and ignores the source's RPUs.
`tonemapx` leaks memory on every reshaped Dolby Vision profile 5 frame.
Streamarr accepts that leak.
The leaked memory returns when the job attempt's FFmpeg process exits.
Each replacement attempt starts a fresh FFmpeg process.
The tone-mapping work (https://github.com/streamarr/streamarr-transcode-worker/issues/26[streamarr/streamarr-transcode-worker#26]) watches worker memory while a full-length Dolby Vision profile 5 film encodes.

*Why:* Before this amendment, the worker encoded every 10-bit HEVC source to 10-bit H.264 (High 10) in 13 of 13 encodes.
Firefox refused High 10 in 21 of 21 runs.
WebKit's native player and AVPlayer refused PQ-tagged H.264 in 16 of 16 runs.
The tone-mapped output was 8-bit BT.709 in limited range.
The tone-mapped Dolby Vision profile 5 output lost its teal cast.
The tone-mapping filter treats an untagged input as PQ.
The filter therefore darkened an untagged SDR source to a mean luma of 41 instead of 106.
Evidence: <<evidence-sdr-output>>, <<evidence-tone-mapping>>.

[[reshape-rpus-starting-samples]]
=== The worker reorders the RPUs of a profile 5 stream whose RPUs start their samples, so that the encode reshapes it

The RPU of a picture belongs after that picture, in the same sample.
Some muxers start a new sample at each RPU, so each RPU sits at the start of the next picture's sample.
Probe version 5 reports such a stream with `rpu_starts_sample` set to `PRESENT` (link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036]).
FFmpeg's HEVC decoder reads an RPU only when the RPU is the last NAL unit of the packet that it decodes.
For such a stream, the decoder therefore hands `tonemapx` no RPUs, and the encode keeps the color cast of an unreshaped profile 5 picture.

The worker reshapes such a stream with the stream's own RPUs.
The job attempt runs two FFmpeg processes, joined by a pipe:

* The first FFmpeg copies the source into MPEG-TS, with the attempt's seek and the same timestamps as a single FFmpeg.
* The worker reads that MPEG-TS and moves each RPU that starts a sample to the front of the sample, ahead of the access unit delimiter that the MPEG-TS muxer writes.
The move keeps every MPEG-TS packet's size and place, so no timestamp and no other stream changes.
* The second FFmpeg encodes the reordered MPEG-TS with the usual filters.
Its HEVC parser ends each access unit at a delimiter, so each RPU becomes the last NAL unit of the picture before it, which is the picture that the RPU belongs to.
* The second FFmpeg trims the video at the attempt's start, because MPEG-TS does not carry an MP4 edit list.
* When the job encodes audio, the first FFmpeg encodes it, and the second FFmpeg copies it.
The first FFmpeg's seek then trims the audio as a single FFmpeg's seek does, and every source audio codec works.

The worker takes an RPU that starts a sample to belong to the picture before it, as the muxers that start a sample at each RPU write it.

The worker chooses this path from the source dynamic range in the transcode job.
The path changes only the order of the NAL units that reach the decoder, not the conversion that the server chose.
The server's video decision does not change.
The job attempt runs two FFmpeg processes only when all four conditions hold:

* The job encodes the video.
* The source's compatible base is none.
* The source's Dolby Vision is present, and its `rpu_starts_sample` is `PRESENT`.
* The output audio is none, AAC, AC-3 or E-AC-3, which MPEG-TS carries.

Every other job attempt runs one FFmpeg process with the same command as before.

A stop asks the first FFmpeg to quit, and the second FFmpeg then ends at the end of its input.
A stall, a failure or a forced end ends both processes.
The attempt reports the second FFmpeg's failure first, then a failure to move the bytes between the two processes, then the first FFmpeg's failure.
Neither process writes a temporary file.

*Why:* On a profile 5 sample whose RPUs start their samples, the worker's encode without the reorder gave a mean Cr of 62.7 over the first 3 frames.
With the reorder, the mean Cr was 122.3, the same as the encode of the same sample muxed correctly.
128 is neutral on that 8-bit scale.
After a seek, the reordered encode matched the correctly muxed sample after the same seek.
Every media segment held the same packets and timestamps as the encode of the correctly muxed sample, except the duration of the stream's last audio frame.
Evidence: <<evidence-reshape>>.

[[gpu-stages]]
=== A job attempt that encodes on the GPU also decodes, scales and tone-maps on the GPU

An encoder backend is the encoder that a worker runs for a codec family, together with whether that encoder runs on hardware or in software.
When a job attempt encodes with a hardware encoder backend, the worker also decodes, scales and tone-maps that job attempt on the GPU.
Decoding still follows the hardware-decode rule of link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037].
ADR 0037's hardware-decode rule sends AVI sources to software decode.
The same rule sends codecs that the hardware decoder lacks or decodes wrongly to software decode.
A GPU tone mapper replaces the CPU `tonemapx` filter only after a measurement shows that the GPU tone mapper's output matches the `tonemapx` output with the mobius curve at a 1000-nit peak.
The GPU tone mapper keeps the mobius curve and the 1000-nit peak.
Until that measurement passes, the worker tone-maps the job attempt on the CPU with `tonemapx`.

=== Every encode forces a codec profile, level and tier that the server chooses

The server computes each variant's codec profile and level.
H.265 (HEVC) and AV1 also signal a tier, Main or High.
The tier sets the highest bitrate that a level allows.
The server chooses the tier for H.265 and AV1.
Every encode forces the codec profile, the level and, for H.265 and AV1, the tier.
The codec profile is High for H.264, Main for H.265 and Main for AV1.
The server computes the H.264 level from ITU-T H.264 Table A-1.
The server computes the H.265 level from Annex A of ITU-T H.265.
The server computes the AV1 level from Annex A of the AV1 specification.
All three computations use the output picture size after cropping and rotation, and the exact output frame rate.
The H.264 computation also uses the variant's maximum bitrate and buffer size, because Table A-1 limits both.
For example, 1080p60 needs H.264 level 4.2, H.265 level 4.1 and AV1 level 4.1.
720p60 needs H.264 level 3.2.
The HEVC encode work (https://github.com/streamarr/streamarr-server/issues/58[streamarr/streamarr-server#58]) checks the H.265 computation against libx265, as the measurements below checked the H.264 and AV1 computations.

Each encoder handles a forced level that is too low in its own way.
libx264 writes the forced level and only warns.
SVT-AV1 writes the forced level without any message.
libx265 refuses to start, so the job attempt fails.
The server's level computation must therefore be right for every encoder.

*Why:* A level table of about 60 lines predicted the level that each encoder chose on its own in 89 of 89 libx264 encodes and 85 of 85 SVT-AV1 encodes.
When the worker forced the codec profile and level, the encoders wrote exactly the requested values in 174 of 174 encodes.
At 1080p60, libx265 refused to start when forced to level 3.1 or level 4.
Evidence: <<evidence-levels-and-codec-strings>>.

=== An encode's codec string is forced, and a copy's comes from the probe

The probe computes the exact codec string of every video and audio stream from the stream's decoder configuration record.
Probe version 4 stores these codec strings, as link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] records.
A stream copy's codec string is the codec string that the probe computed for the source stream.
An encode's codec string follows from the encode's forced codec, codec profile, level, tier and bit depth.
Examples are `avc1.6400LL` and `av01.0.LLM.08`.
In both examples, `LL` stands for the computed level.
In the AV1 example, `M` stands for the Main tier and `08` stands for 8 bits.
The playlist builds each variant's `CODECS` attribute from these codec strings and never from a constant.
The server never delays the playlist to read a codec string from an initialization segment.
The transcode job carries each variant's codec string to the worker.
The worker reads every initialization segment that it produces.
The worker fails the job attempt when an initialization segment's codec string differs from the codec string in the transcode job (https://github.com/streamarr/streamarr-transcode-worker/issues/25[streamarr/streamarr-transcode-worker#25]).
The forced-value check confirms that an encoder writes exactly the values that the transcode job forces.
libx264 and SVT-AV1 passed the forced-value check.
Before the server encodes with libx265 or a hardware encoder, that encoder must pass the same forced-value check.
The NVENC work (https://github.com/streamarr/streamarr-transcode-worker/issues/56[streamarr/streamarr-transcode-worker#56]) runs the forced-value check for NVENC.
The VideoToolbox work (https://github.com/streamarr/streamarr-transcode-worker/issues/57[streamarr/streamarr-transcode-worker#57]) runs the forced-value check for VideoToolbox.
Issue https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14] runs the forced-value check for the remaining hardware encoders.
An H.265 encode's codec string also names the encode's sample-entry tag.
The sample-entry tag is the four-character code that names a track's coding format in an MP4 file, such as `hvc1` or `hev1`.
link:0009-h264-plus-av1-codec-strategy.adoc[ADR 0009] lets the server encode H.265 only after https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18] makes the worker write `hvc1`.
The Dolby Vision configuration record is the `dvcC` or `dvvC` box that declares a stream's Dolby Vision profile.
Every video copy runs with FFmpeg's `-strict unofficial` option.
The `-strict unofficial` option keeps the Dolby Vision configuration record wherever the pinned FFmpeg build allows the record.
The pinned build drops the record from every 10-bit Dolby Vision profile 8.2 copy.
The pinned build also drops the record from every Dolby Vision profile 5 copy whose sample-entry tag is `hev1`.
Streamarr accepts both losses.

*Why:* The constant strings matched the produced media in 6 of 59 video copies.
Strings computed from the decoder configuration record matched 54 of 59 video copies and 42 of 42 audio copies.
The 54 video matches included all 50 H.264 and HEVC copies.
Evidence: <<evidence-levels-and-codec-strings>>.

=== The worker alone chooses a copy's sample-entry tag

The tag rule is the rule that picks the sample-entry tag of a copy.
The tag rule lives only in the worker.
Until the worker chooses the HEVC sample-entry tag of every copy (https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18]), a copy of an MP4 or MOV source keeps the source's sample-entry tag.
The Dolby Vision retags in <<dolby-vision-copy-tags>> are the only exceptions.
A copy of HEVC from Matroska, MPEG-TS or a raw stream carries `hev1`.
The copy's codec string names the tag that the copy carries.
Any change to the tag rule, such as the change in https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18], increments the probe version.
A rescan then updates every stored codec string under link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032]'s rules for probe versions.
A tag rule that is ready before probe version 4 is released becomes part of probe version 4.

[[dolby-vision-copy-tags]]
=== A Dolby Vision copy carries its base layer's sample-entry tag

Dolby Vision profiles 8.2 and 9 have an SDR compatible base.
A profile 8.2 stream carries HEVC.
A profile 9 stream carries H.264.
A copy of a source whose sample-entry tag is `dvh1` carries the sample-entry tag `hvc1`.
The server encodes a source whose sample-entry tag is `dvhe` until https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18] lets the worker write that copy as `hvc1`.
A copy of a Dolby Vision profile 9 source whose sample-entry tag is `dva1` carries the sample-entry tag `avc1`.
The server encodes a source whose sample-entry tag is `dvav` until https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18] lets the worker copy that source.
If the `avc1` copy fails a check on a real device, the server encodes Dolby Vision profile 9 sources instead.
Over HLS, every HEVC copy of a Dolby Vision source with an SDR compatible base carries `hvc1`, whatever the client declares.
This `hvc1` rule stays in force after the interim copy rule ends.

A decoder configuration record is the box that holds a stream's codec parameters, such as `avcC` for H.264 or `hvcC` for HEVC.
A retagged Dolby Vision copy's codec string comes from the decoder configuration record of the Dolby Vision base layer.
The probe computes that codec string under the sample-entry tag that the copy carries.
For example, a copy of a `dva1` source carries `avc1`.
That copy's codec string comes from the source file's own `avcC`.
The codec string never comes from the Dolby Vision sample-entry tag.
The probe runs in the worker, so the probe computes the codec string with the worker's own tag rule.

The playlist entry of a Dolby Vision copy with an SDR compatible base carries a `CODECS` attribute built from the base layer's sample-entry tag.
That playlist entry declares `VIDEO-RANGE=SDR` explicitly.
That playlist entry carries no `SUPPLEMENTAL-CODECS` attribute.

*Why:* In a headless check, a Dolby Vision profile 8.2 copy under `dvh1` played in 0 of 3 runs in AVPlayer, in WebKit's native player, and in hls.js in Chrome and in Firefox.
The same copy under `hvc1` played in 3 of 3 runs in every headless player that decodes HEVC.
A Dolby Vision profile 9 copy under `dva1` failed in 4 of 6 headless player setups, in 0 of 3 runs each.
The same copy under `avc1` played in 18 of 18 runs across the six headless player setups.
No player took a Dolby Vision path for a profile 8.2 or 9 copy, even with the configuration record and `SUPPLEMENTAL-CODECS`.
Evidence: <<evidence-dolby-vision-copies>>.

=== The server switches to an encode when a copy lacks its parameter sets

Parameter sets are the units that a decoder needs before the first picture: the SPS and PPS, and for HEVC also the VPS.
An `hvc1` or `avc1` sample entry tells a player that the decoder configuration record holds those parameter sets.
The worker checks the record of every `hvc1` or `avc1` copy.
When the record lacks those parameter sets, the worker fails the job attempt as an output mismatch and uploads nothing (https://github.com/streamarr/streamarr-transcode-worker/pull/80[streamarr/streamarr-transcode-worker#80]).
The worker never encodes the stream in place of the copy.
In Auto, the server then starts a new format attempt that encodes the video.
The new format attempt has its own stream session, playlist and initialization segment.
The new decision covers the whole stream session's video, because a copy and an encode use different segment lists.
The server starts this format attempt itself, and the attempt counts against the playback session's format-attempt budget.
In Original, the server does not switch to an encode, and playback ends with a typed error.

*Why:* An `hvc1` or `avc1` copy whose record holds no parameter sets does not play.
Only the server can change a decision, so only the server can switch the copy to an encode.
A new stream session keeps one rule: a playlist describes only its own stream session's output.
The old playlist already advertised the copy's codec string, so it cannot describe the encode.
Original is a manual choice, and the server never silently replaces a manual choice with a different output.

=== A stream copy carries no planned output range yet

At first, only an encode's planned output holds a dynamic range.
A copy's planned output holds no dynamic range until https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] settles one.
link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] forbids `UNSPECIFIED` in a planned output.
For a copy of an untagged source, `UNSPECIFIED` is the only honest value.
The produced copy still passes the source's HDR features through unchanged, as link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] requires.
The playlist entry of a Dolby Vision copy with an SDR compatible base still declares `VIDEO-RANGE=SDR`.
The playlist takes that `SDR` value from the source's compatible base.
The copy's planned output still holds no dynamic range.

=== Until the playlist can describe HDR copies, only SDR sources are copied

The interim copy rule decides when the server copies a source's video.
The interim copy rule applies to every client until the playlist can describe HDR copies.
Issue https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] makes the playlist's HDR attributes truthful, so that the playlist can describe HDR copies.
Issue https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] builds on the client-declared dynamic ranges of https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395].

* Copy the video only when all six conditions hold.
** The source's compatible base is SDR or unspecified.
** The source carries no Dolby Vision compatibility identifier that disagrees with the source's signaled transfer.
The Dolby Vision compatibility identifier is the value in the Dolby Vision configuration record that names the base format that the stream claims.
** The source's video stream has no other `MediaFileProbePropertyIssue` that rules out a copy.
link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] decides which issues rule out a copy.
A Dolby Vision profile 9 stream in which an RPU starts a sample has such an issue.
** The source's codec profile is not `UNSPECIFIED`.
This condition applies to a stored outcome of probe version 5 or later.
A probe version 4 outcome stores no codec profile.
** The source is not H.264, or the source is 8-bit 4:2:0 H.264.
** The client names the source's codec, as the server already requires.
* Encode every other source to 8-bit SDR.
The worker tone-maps the encode when the source's compatible base is PQ, HLG or none.

The interim copy rule takes effect only after the pinned worker image contains three changes.
Issue https://github.com/streamarr/streamarr-transcode-worker/issues/22[streamarr/streamarr-transcode-worker#22] makes every encode 8-bit.
Issue https://github.com/streamarr/streamarr-transcode-worker/issues/26[streamarr/streamarr-transcode-worker#26] adds tone mapping.
Issue https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18] adds the Dolby Vision retags that <<dolby-vision-copy-tags>> decides.

The interim copy rule is not the only condition for a copy.
The server copies the video only once the server knows the source's keyframe positions, as link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] decides.
A merged-slot segment list builds media segments from 3 s slots and merges a slot without a source keyframe into the segment before that slot.
Until https://github.com/streamarr/streamarr-server/issues/512[streamarr/streamarr-server#512] adds merged-slot segment lists, one more condition applies to a stream session that also encodes a variant.
In such a stream session, the server encodes a variant that the interim copy rule would copy when the source's keyframes do not fit the 3 s grid of link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037].

Issue https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395] sets a default for a client that declares nothing.
That default is H.264 High profile at 8 bits in SDR.
The rule keeps that default's SDR limit for the codec names that clients send today.
For H.264, the rule also keeps that default's 8-bit 4:2:0 limit.
The rule applies link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036]'s answer for a client that declares no dynamic range.
A Dolby Vision or HDR10+ source permits only an SDR encode when its compatible base is PQ, HLG or none.
PQ and HLG sources without Dolby Vision or HDR10+ also permit only an SDR encode.
Dolby Vision profiles 8.2 and 9 have a valid SDR compatible base.
The interim copy rule therefore copies a Dolby Vision source with an SDR compatible base, which means a profile 8.2 or 9 source.
Such a copy carries the base layer's sample-entry tag, as <<dolby-vision-copy-tags>> decides.
In a headless check, such copies played in every player that decodes the base layer's codec.
The server never copies a Dolby Vision source whose compatibility identifier disagrees with its signaled transfer, such as Dolby Vision profile 7 tagged as SDR.
The server encodes such a source and interprets the source's signaled transfer, as link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] decides.
This refusal stays in force after the interim copy rule ends.
The refusal of a malformed Dolby Vision profile 9 stream also stays in force after the interim copy rule ends.
The refusal of an `UNSPECIFIED` codec profile also stays in force after the interim copy rule ends.
The server cannot check an unknown codec profile against what a client can decode.
The Apple TV app receives no HDR copies until https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] makes the playlist's HDR attributes truthful.
Until then, the server encodes HDR HEVC sources to SDR for the Apple TV app.
At first, those SDR encodes use H.264.
Those SDR encodes use HEVC once link:0009-h264-plus-av1-codec-strategy.adoc[ADR 0009]'s HEVC preference takes effect (https://github.com/streamarr/streamarr-server/issues/58[streamarr/streamarr-server#58]).
This amendment defers HDR copies to the Apple TV app on purpose.

Probe version 5 reads the first frames of the chosen video stream (ADR 0036).
From probe version 5 on, the compatible base of a Dolby Vision profile 5 stream is none, whatever the stream's signaled transfer says.
The probe identifies profile 5 from the configuration record, or from the first RPU header when the stream has no configuration record.
This rule covers a profile 5 stream without a configuration record that signals BT.709.
This rule also covers a profile 5 stream in MPEG-TS without the Dolby Vision descriptor.
The probe finds such a stream's RPUs even when FFmpeg's HEVC decoder ignores them, because the probe also parses the NAL units of the packets (ADR 0036).
The interim copy rule therefore encodes each such stream, and the worker tone-maps the encode.
When the stream's RPUs start their samples, the worker reorders the RPUs before the encode (<<reshape-rpus-starting-samples>>).
Dolby Vision profile 10.0, which is AV1 with no compatible base, follows the same rule, so the server encodes a profile 10.0 stream.
Probe version 5 also finds the Dolby Vision profile 9 files from a known faulty muxer, in which an RPU starts a sample.
Such a file ends with a sample that holds no picture.
The server encodes such a file.
A file whose stored outcome comes from probe version 4 keeps the version 4 decisions until the server stores the file's probe version 5 outcome (link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032]).

*Why:* No playlist can yet describe an HDR copy truthfully to a client that declares no range.
WebKit's native player and AVPlayer refused PQ and Dolby Vision profile 8.1 copies in a variant that the playlist declared SDR.
When the playlist declared the variant PQ or HLG, AVPlayer without an HDR display refused the variant.
WebKit's native player timed out on that variant.
Evidence: <<evidence-copies>>.

[[explicitly-deferred]]
=== Explicitly deferred

* The HDR output choice (https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396], https://github.com/streamarr/streamarr-server/issues/397[streamarr/streamarr-server#397] and https://github.com/streamarr/streamarr-transcode-worker/issues/27[streamarr/streamarr-transcode-worker#27]).
This choice covers the Original quality option, the user's HDR choice, and 10-bit or HDR encodes.
* A copy's typed codec profile and level, and a copy's planned output range (https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396]).
* Client-declared dynamic ranges (https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395]).
Client-declared dynamic ranges alone do not bring back HDR copies.
* HDR copies, including HDR copies to the Apple TV app, once the playlist's HDR attributes are truthful (https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396]).
HDR copies end the interim copy rule.
* Dolby Vision copies with a PQ or HLG compatible base, and the playlist attributes of those copies, including `SUPPLEMENTAL-CODECS`.
Issue https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395] decides when such a copy carries those attributes.
Issue https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] builds those attributes.
* How a job attempt on the reshape path plays when the attempt starts after the end of the source's audio (<<reshape-rpus-starting-samples>>).
Such an attempt fails today.
* Reshaping a profile 5 stream whose RPUs start their samples when the job copies FLAC, ALAC or Opus audio, names no audio codec, or writes an audio codec that MPEG-TS does not carry.
Such a job runs one FFmpeg process, and its output keeps the color cast of an unreshaped picture.
* Copies of a Dolby Vision profile 5 source under `hev1` for clients that declare Dolby Vision (https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395]).
Such a copy becomes a `dvhe` copy once a measurement shows that the `dvhe` copy plays.
Otherwise the server encodes such a source.
* Choosing the HEVC sample-entry tag of every copy, and copying sources whose sample-entry tag is `dvhe` or `dvav` (https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18]).

== Consequences

* Decision records are pure domain objects.
* Mode resolution considers all stream decisions (e.g. subtitle burn-in promotes REMUX -> FULL_TRANSCODE).
* New stream types follow the same pattern.
* TranscodeReason tracking can be added as metadata on each decision later.
* Encodes no longer produce High 10 or PQ-tagged H.264.
Firefox refuses High 10.
Apple's players refuse PQ-tagged H.264.
* With libx264, encoding a 10-bit or HDR source costs less than before.
The 8-bit output saves more than tone mapping costs.
With SVT-AV1, the cost stays about the same.
* A variant's codec profile, tier and level depend only on the variant.
Every job attempt of the variant therefore forces the same values.
The initialization segment then stays identical across job attempts, as link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] requires.
* When an encoder ignores a forced value, the worker fails the job attempt.
The playlist therefore never advertises a false codec string for an encode.
* A libx265 encode whose forced level is too low fails the job attempt, because libx265 refuses to start.
* A full-length Dolby Vision profile 5 encode grows each FFmpeg process's memory until the job attempt ends.
* An encode of a profile 5 stream whose RPUs start their samples runs two FFmpeg processes.
When the source is read at real time, the first media segment arrives about 1.4 s later than from one FFmpeg process.
* The last audio frame of a job attempt on the reshape path declares a whole AAC frame, because MPEG-TS drops the encoder's trim of that frame.
About 9 ms of encoder padding then plays at the very end of the title.
* An attempt on the reshape path that starts after the end of the source's audio fails.
MPEG-TS carries the audio's parameters only in the audio's packets, so the encoding FFmpeg finds an audio stream with no parameters.
Before this amendment, such an attempt played with the color cast.
* The transcode job names no source codec, so the worker's conditions do not check that the source is HEVC.
An H.264 Dolby Vision stream whose probe found no transfer, and whose RPUs start their samples, has no compatible base and meets the conditions.
The worker's reorder leaves such a stream's packets unchanged, so the output is the same, at the cost of the second FFmpeg process.
* An encode of a profile 5 stream whose RPUs FFmpeg's HEVC decoder ignores for another reason, such as an RPU that it cannot parse, still keeps the color cast of an unreshaped picture.
Under the interim copy rule, the server never copies a profile 5 stream.
* A Dolby Vision copy with an SDR compatible base plays as SDR in every measured player.
* A 10-bit Dolby Vision profile 8.2 copy loses its configuration record under the pinned FFmpeg build.
In the measured players, the lost record changed nothing.
* A Dolby Vision profile 5 copy under `hev1` also loses its configuration record under the pinned FFmpeg build.
The record is the only Dolby Vision signal in such a copy's initialization segment.
Without the record, such a copy plays teal.
* A source whose compatible base is PQ, HLG or none plays as SDR on every client until the deferred HDR output choice is built.
* A source whose codec profile is `UNSPECIFIED` always plays through an encode.
A source in a video codec whose codec profiles the worker contract does not name always has an `UNSPECIFIED` codec profile.
* The playlist advertises a copy's codec string before any job attempt runs.
A failed copy therefore costs the player one switch to a new playlist.

The probe can compute the exact codec string.
* No interim copy rule before clients declare dynamic ranges: HDR copies fail in Apple's players when the playlist declares the copies SDR.
* A narrower interim rule that stops copying only Dolby Vision profile 5 and 10-bit H.264: the narrower rule would still copy PQ and HLG sources.
No playlist can describe such copies truthfully to a client that declares nothing.
* Moving the HDR playlist attributes into https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395], so that HDR copies return with client-declared dynamic ranges: https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] makes the playlist's HDR attributes truthful.
HDR copies wait for https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396].
* Declaring `VIDEO-RANGE=PQ` or `VIDEO-RANGE=HLG` on copies today: on macOS 26.6.2 with no HDR display, AVPlayer refused 4 of 4 such variants.
WebKit's native player timed out on 4 of 4 such variants.
The same variants played when the playlist declared them SDR.
* Copying HLG sources to clients that name the codec: the HLG copies played.
The playlist could not state the copies' HLG range.
AVPlayer without an HDR display refuses a variant declared `VIDEO-RANGE=HLG`.
WebKit's native player times out on that variant.
* Leaving tone mapping to the worker's discretion: link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] requires the server to choose every change to the source.
The worker would also probe the source a second time.
* The bt2390 tone curve at the same 1000-nit peak, or the bt2390 curve as a fallback if the mobius curve showed a color cast: above the peak, the bt2390 curve folds back and maps brighter input to darker output.
A highlight brighter than 1000 nits therefore renders darker than a 1000-nit highlight.
With the pinned build's filter, the bt2390 curve mapped a 983-nit PQ gray to luma 235.
The same curve mapped a 10,000-nit PQ gray to luma 168.
Streamarr chose the mobius curve with no condition.
* The hable tone curve: the hable curve makes pictures darker overall.
Below the peak, the hable curve gave a mean luma of 76.9 on a PQ source, against 92.9 for the mobius curve on the same source.
* Copying a Dolby Vision profile 7 source tagged SDR: the source makes contradictory claims.
The server never copies such a source, as link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] decides.
* Copying no Dolby Vision source with an SDR compatible base until the worker chooses the HEVC tag of every copy (https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18]), or encoding every such source with a `dvh1` or `dvhe` tag until then: the retag makes `dvh1` copies play now.
In a headless check on macOS against the pinned worker image, a `dvh1` profile 8.2 copy played in 0 of 3 runs in each of AVPlayer, WebKit's native player, and hls.js in Chrome and in Firefox.
Written as `hvc1`, the same copy played in 3 of 3 runs in every player that decodes HEVC.
* Keeping `dva1` on a Dolby Vision profile 9 copy: in the same kind of headless check, the `dva1` copy failed in 4 of 6 player setups, in 0 of 3 runs each.
The `avc1` copy played in 18 of 18 runs across the six player setups.
* Choosing the HEVC tag of a Dolby Vision copy with an SDR compatible base from the client's declaration, after a tvOS check: the tag is settled now.
Every client receives `hvc1`.
* Encoding every Dolby Vision profile 9 source while the interim copy rule applies, or having the worker drop a trailing sample that holds no picture: probe version 5 finds the malformed files.
The server encodes only those files.
* Getting the pinned build's validity check for the configuration record relaxed upstream, building FFmpeg ourselves, or re-inserting the configuration record in the worker: for profile 8.2, the record changed nothing measured.
With the record restored, and even with `SUPPLEMENTAL-CODECS`, AVPlayer, Safari and an iPhone Air still showed SDR.
* Reading the first frame's RPU header in probe version 4, or encoding every Dolby Vision stream that has no configuration record: probe version 5 reads the RPU header instead.
A Dolby Vision stream without a configuration record keeps link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036]'s rule for the compatible base.
* Applying the refusal of an `UNSPECIFIED` codec profile to probe version 4 outcomes: a probe version 4 outcome stores no codec profile.
The server would then encode every source until the re-scan stored each file's probe version 5 outcome.
* `SUPPLEMENTAL-CODECS` on Dolby Vision copies with an SDR compatible base: adding the attribute changed nothing measurable in any headless player.
The attribute stays open in case a later need appears.
* Applying the HEVC tag rule in the server as well as in the worker: the tag rule would then live in two places.
* Keeping tone mapping on the CPU while the GPU decodes, scales and encodes, or using the GPU only to encode: when a job attempt encodes on the GPU, the worker runs every stage that the GPU can run on the GPU.
Tone mapping moves to the GPU once the GPU tone mapper matches the CPU output.
* Having the worker encode a stream whose copy fails the record check: the job's video decision and codec string would then no longer describe the worker's output.
* Encoding in place in the same stream session and making the player reload its playlist: the old playlist's `CODECS` attribute would no longer match the media until the player reloads.
* Predicting the failure from probe data: the worker cannot tell in advance which sources yield a record without parameter sets.
* Reordering a profile 5 stream's RPUs with a bitstream filter of the pinned FFmpeg build: no filter in that build moves a NAL unit.
The `dovi_rpu` filter looks only at the last NAL unit of a packet.
The `filter_units` filter can delete NAL units, but deleting the RPUs removes the reshape.
* Patching FFmpeg's HEVC decoder so that it reads an RPU anywhere in its sample: Streamarr runs the pinned Jellyfin build unchanged, and link:0029-pin-jellyfin-ffmpeg-releases.adoc[ADR 0029] defers an FFmpeg build pipeline of Streamarr's own.
* Fixing the colors after decoding, with a filter: the decoder has already discarded the RPUs, and nothing after the decoder can rebuild the per-frame reshape.
The first RPU header that the probe stores tells only the Dolby Vision profile and holds no reshape.
* Moving each RPU to the end of its own sample in a fragmented MP4 copy: an RPU that starts a sample belongs to the picture before it.
The move would give each picture the RPU of the picture before it.
Moving an RPU into the previous sample changes the sizes and offsets of both samples.
This design was never run in the pinned FFmpeg build.
* A raw HEVC stream between the two FFmpeg processes: a raw stream carries neither the source's timestamps nor its audio.
* A Matroska stream between the two FFmpeg processes: the pinned build's Matroska muxer writes millisecond timestamps and drops the decoding timestamps.
* A NUT stream between the two FFmpeg processes: the pinned build's NUT demuxer restores neither the decoding timestamps nor the durations, and its muxer refuses a negative presentation timestamp.
* Seeking in the second FFmpeg with an output `-ss` option: FFmpeg subtracts that time from every output timestamp, so the attempt's timeline would no longer match a single FFmpeg's timeline.
The second FFmpeg trims instead.
An input seek cannot run on a pipe.

== Evidence

Unless a measurement names another date and version, every measurement used the pinned worker image with FFmpeg 8.1.2 on a 10-core host.
The encoders were libx264 and SVT-AV1.
One level check also used libx265.
The players were hls.js 1.7.0 in Chromium, Chrome, Firefox and WebKit, plus WebKit's native player and AVPlayer on macOS 26.6.2.
These six player setups ran headless.
No headless player ran with an HDR display.
The sources covered HDR10, HDR10+, HLG from an iPhone, Dolby Vision profiles 5, 7 (base layer), 8.1, 8.2, 8.4 and 9, 10-bit SDR with an untagged transfer characteristic, and 8-bit SDR.

[[evidence-sdr-output]]
=== 8-bit SDR output

* Before this amendment, the worker encoded every 10-bit HEVC source to H.264 High 10 (13 of 13).
* Firefox's `MediaSource.isTypeSupported` returned false for `avc1.6E00xx` in 21 of 21 runs.
hls.js therefore dropped the variant.
* WebKit's native player and AVPlayer failed PQ-tagged High 10 in 16 of 16 runs with `CoreMediaErrorDomain -12927`.
The PQ transfer characteristic in a variant that the playlist declared SDR triggered the failure.
Converting to 8 bits alone therefore does not fix the failure.
* All 14 tone-mapped outputs (7 sources, 2 encoders) were 8-bit 4:2:0.
All 14 used BT.709 color in limited range.
None carried the static HDR boxes `mdcv` and `clli` or a Dolby Vision configuration record.
* The mean chroma offsets (Cb and Cr) of the HDR10 and HLG encodes were measured against Apple's own SDR rendering of the same source.
The offsets of an HDR10 encode moved from −32 and −12 before tone mapping to −7.3 and −3.1 after tone mapping.
The offsets of tone-mapped HLG stayed within 1.5 code values.
The Dolby Vision profile 5 offsets were measured against the rendering of the Dolby Vision profile 8.1 version of the same master.
These offsets moved from −35 and −44 to −9.5 and −11.3.
The Dolby Vision profile 5 teal cast disappeared.
* The tone-mapped libx264 output played from every source in Chromium, Chrome, WebKit with hls.js, WebKit's native player and AVPlayer.
Firefox played 6 of 7.
Firefox's one failure matched a separate, intermittent Firefox failure on H.264 with muxed AAC.
That separate failure also occurs without tone mapping.
* The following sentences give libx264's cost in CPU seconds per media second at the 1080p variant, before and after this amendment's change.

From a 2160p Dolby Vision profile 5 source, the cost fell from 12.60 to 10.19.
From an iPhone HLG source, the cost fell from 15.26 to 7.52.
SVT-AV1 cost about the same as before.

[[evidence-tone-mapping]]
=== Tone mapping

* On 1080p PQ and HLG sources, tone mapping cost at most 0.1 CPU seconds per media second more than a plain 8-bit conversion.
Reshaping Dolby Vision profile 5 added about 1.1 to 1.2 CPU seconds per media second at 1080p60.
* Against the Dolby Vision profile 8.1 version of the same master, the reshaped Dolby Vision profile 5 encode scored 32.7 dB peak signal-to-noise ratio (PSNR).
Without the reshape, the Dolby Vision profile 5 encode scored 14.8 dB.
* The tone-mapping filter treats an untagged input as PQ.
On a 10-bit SDR source with an untagged transfer characteristic, the filter gave a mean luma of 41 instead of 106.
* With tone mapping, one 1080p variant that libx264 encoded at its default preset, `medium`, ran at 1.20–1.43× real time from 1080p60 HDR sources.
The same variant ran at 0.90–1.01× real time from 2160p60 sources.
A four-variant ladder from 60 fps HDR sources ran at 0.35–0.56× real time, with or without tone mapping.
* The bt2390 curve at 1000 nits mapped a 983-nit PQ gray to luma 235.
The bt2390 curve mapped a 10,000-nit gray to luma 168.
The mobius curve clips at 235 instead of folding.
* Below the peak, mobius and bt2390 gave the same brightness (mean luma 92.9 and 92.1).
The hable curve gave a mean luma of 76.9.
* The color, player and seek checks ran with the bt2390 curve.
Mobius was compared only for brightness.
The tone-mapping work (https://github.com/streamarr/streamarr-transcode-worker/issues/26[streamarr/streamarr-transcode-worker#26]) therefore repeats the color and player checks with the mobius curve.
* `tonemapx` leaked about 3.2 KB per reshaped Dolby Vision profile 5 frame.
By calculation from that rate, a two-hour film at 24 fps would grow one FFmpeg process by about 0.55 GB.
* On 2026-10-27, FFmpeg in the pinned worker image decoded the first 3 frames of a raw profile 5 HEVC stream and tone-mapped them with the worker's filter.
The stream is the one that ADR 0032's frame-facts evidence rewrote so that each RPU sat ahead of the next picture instead of after its own picture.
The mean Cr of the unchanged stream's output was 122.4 on an 8-bit scale whose neutral value is 128.
The mean Cr of the rewritten stream's output was 62.6, the same as for the stream with every RPU removed.

Each RPU then sat in the next frame's sample, and the last sample held only an RPU and no picture.
A copy of that stream failed at the end of the stream in Chromium and Firefox.
The same copy played in 0 of 3 runs in WebKit with hls.js.
The same stream muxed correctly played in 3 of 3 runs in all six player setups.
