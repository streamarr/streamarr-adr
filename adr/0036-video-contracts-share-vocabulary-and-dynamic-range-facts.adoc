= ADR 0036: Video Contracts Share One Vocabulary and Preserve Dynamic-Range Facts

== Status

Proposed

This draft records the agreed dynamic-range structure and the rules to preserve source facts and report problems separately.
The server, worker, and client contracts still need answers to the open questions listed below.

== Context

https://github.com/streamarr/streamarr-server/issues/399[The playback capabilities epic] requires the playlist to describe the media that the worker produces.
A codec name alone does not describe a stream's codec profile, level, bit depth, color properties, or dynamic range.
If the server chooses an output from incomplete source or capability details, the client may fail to decode the video.
The worker may also process colors incorrectly, or the playlist may advertise a format that differs from the media segments.

The probe describes the source, the client reports what the player can accept, and the server chooses the output.
The server, workers, and clients must use the same meanings for the properties they share.
https://github.com/streamarr/streamarr-adr/issues/15[Vocabulary issue #15] tracks the work to define those meanings before the dependent contracts use them.

A video stream can contain both HDR10+ and Dolby Vision information.
An enum that allows only one HDR format would need extra values to describe streams that contain both formats.
The picture's color properties can also disagree with the compatible base that the Dolby Vision information claims.
The probe records what the source contains.
Check whether the source properties are valid and agree with one another.
Separately, check whether a particular player can play the source.

Streamarr already defines variants, renditions, stream sessions, transcode decisions, and stored probe results.
This ADR builds on those definitions.
Use other projects' terms to compare meanings; rename an established Streamarr concept only when the rename solves a specific problem.

== Decision

=== Preserve the established domain language

Use the existing definitions and link to the ADRs that define each concept.

[cols="1,3",options="header"]
|===
|Existing concept |Meaning

|Variant and rendition
|link:0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018] uses variant for an option in the bitrate and resolution ladder.
ADR 0018 reserves rendition for alternate HLS tracks, such as audio languages.

|Stream session and dispatch attempt
|ADR 0018 defines the stream session that manages playback at runtime and the identities for worker jobs and dispatch attempts.
An attempt to dispatch a job to a worker differs from an attempt to try another format within one logical playback session.

|Transcode decision
|link:0013-stream-decision-architecture.adoc[ADR 0013] combines independent decisions for each stream.
The planned explicit video decision extends that architecture.

|Probe result and stream properties
|link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] defines how to store container and stream properties, retain unknown properties after a successful probe, record terminal probe errors, and use `probe_version`.

|Metadata
|ADR 0032 reserves the unqualified term metadata for descriptive TMDB data.
Use probe properties and stream properties for technical facts.
When discussing an external format, name the format in terms such as Dolby Vision metadata.
|===

Keep the existing `StreamingOptions`, `VideoQuality`, `TranscodeMode`, `ContainerFormat`, `MediaProbe`, and `MediaSourceRef` names.
The user can choose Auto, Original, or a fixed quality.
The transcode mode describes how the worker processes the media to produce the selected output.
Write codec profile or Dolby Vision profile when referring to either video property, because link:0024-identity-authority-by-relationship.adoc[ADR 0024] already defines a viewing profile.
Keep the units that the worker contract already uses, including bits per second for bitrate and seconds for seek position.

=== Describe source tracks, client capabilities, and output separately

Use the same meanings for shared properties in the records below, but keep each record's purpose distinct.

[cols="1,3",options="header"]
|===
|Record |What the record describes

|Source description
|Describe the individual media track that the probe found.
Keep the source facts unchanged when the server chooses a playback output.

|Client capability declaration
|Describe the combinations that the current player and delivery path can accept.
Include any relevant display constraints.
The server uses the reported capabilities to choose an output, but playback can still fail.

|Planned output
|Describe the output that the server chooses from the source facts, client capabilities, verified worker capabilities, and the user's playback choice.

|Produced output
|Describe the media that the worker produces.
The worker must produce the output that the server selected or report a failure.
The playlist must describe the produced media.
|===

The planned explicit `VideoDecision` belongs within the existing `TranscodeDecision` defined by ADR 0013.
The source and output can have different dynamic ranges.
The proposed fields `sourceDynamicRange` and `outputDynamicRange` would record those two values.
The field names remain open until the video-decision contract is final.

=== Describe dynamic range with one shared structure

Use `VideoDynamicRange` as the shared type and `dynamicRange` as the field on an individual video stream.
In this ADR, video stream means a media track, not the stream session that manages playback at runtime.
Use the same type to describe a source video stream and an output video stream, even when the source and output have different values.

Use the following agreed structure.
The TypeScript example shows the fields and values; the example does not choose a wire format or require an implementation language.

[source,typescript]
----
type Presence = "UNSPECIFIED" | "ABSENT" | "PRESENT";

type VideoDynamicRange = {
  compatibleBase: "UNSPECIFIED" | "NONE" | "SDR" | "HDR10" | "HLG";
  hdr10Plus: Presence;
  dolbyVision: {
    presence: Presence;
    profile: number | null;
    level: number | null;
    baseLayerCompatibilityId: number | null;
    baseLayer: Presence;
    enhancementLayer: Presence;
    rpu: Presence;
  };
};
----

`compatibleBase` describes the standard picture format that a player could use without the advanced HDR information.
`NONE` means the stream has no standard compatible base.
`UNSPECIFIED` means the compatible base is unknown.
The `compatibleBase` value does not guarantee that a device can play the source bytes unchanged.
The worker may need to transform the source before the player can use the compatible base.
The server must explicitly choose that change, and the worker must support the change.

`hdr10Plus` records whether HDR10+ information is present, independently of Dolby Vision.
Both `hdr10Plus` and `dolbyVision.presence` may be `PRESENT` in the same stream.
The nested `dolbyVision` object records the Dolby Vision profile, level, and base-layer compatibility identifier.
The object also records whether the base layer, enhancement layer, and picture-adjustment instructions are present.
The `rpu` field records whether those Dolby Vision picture-adjustment instructions are present.

Use `Presence` to distinguish information that remains unknown from information that the probe found or confirmed absent.
If the probe cannot check for a feature, do not report the feature as absent.
Leave unknown numeric fields absent or null; do not substitute zero when zero has a defined meaning.
The Dolby Vision profile and level describe Dolby Vision signaling.
Keep the Dolby Vision profile and level separate from the codec's profile and level.

Derive the broad HDR or SDR label shown to users from the detailed description.
Do not store another label that can change independently of the detailed facts.
Keep uncertainty visible when the description is incomplete or inconsistent.
The open questions below include how to derive that label.

Keep the typed Protobuf contract that ADR 0018 defines, and keep zero as the explicit unspecified value in enums.
The protocol and generated clients must distinguish an unknown numeric value from a known value.
The TypeScript examples do not permit replacing the worker's Protobuf messages with JSON.
Choose protocol field numbers, generated names, and storage columns when implementing the contract, after answering the open questions about what the properties mean.

=== Preserve source facts and report problems separately

Use `MediaFileProbePropertyIssue` for a problem found when checking the container or stream properties reported by a media-file probe.
The term covers container properties and properties of any stream type, including video, audio, and subtitles.
A probe can succeed while the reported properties contain problems.
Keep `MediaFileProbePropertyIssue` distinct from `ProbeFailure`, which reports a failed probe attempt.
Include `Probe` in the name so readers do not mistake the issue for a problem with a filename, path, or stored `MediaFile` record.

Preserve the source facts that the probe observed.
Check the source facts and record any specific problems separately from the observed facts.
Distinguish missing information from information that contradicts another observed fact.
ADR 0032 already allows a probe to succeed when some properties remain unknown.
An incomplete description alone does not require the probe to report a terminal error.

Check the specific Dolby Vision profile and the properties that the profile requires.
Some valid profiles have an SDR fallback base, so a stream can legitimately contain both Dolby Vision information and an SDR base.
When claims conflict, record which claims disagree and keep the original observed facts.

Choose how to process colors from the actual picture signal that the selected playback path uses.
Do not tone-map from HDR to SDR solely because Dolby Vision information is present.
Check whether source properties are valid separately from whether a particular player, container, delivery path, and display can handle the source.
If a malformed stream plays on one player, another player may still fail to handle the stream safely.

The server chooses usable playback paths under the Auto and manual rules recorded in epic #399.
A problem found while checking source facts does not add a new reason to try another format automatically.
Only Auto can automatically change format after an explicit playback error that concerns the format.
Manual and Original choices remain fixed, even when a platform selects Original by default.
When the rules permit a replacement, the server explicitly chooses the new output and leaves the source description unchanged.
The probe can recognize Dolby Vision in a source; this ADR does not add support for Dolby Vision output.

=== Examples show how to use the shared terms

The examples below apply the agreed meanings.
The examples leave the client-capability and validation-result schemas open.

The following source has an HDR10-compatible base, HDR10+, and Dolby Vision Profile 8.1.
The example assumes that the relevant probe facts agree.

[source,typescript]
----
const sourceDynamicRange: VideoDynamicRange = {
  compatibleBase: "HDR10",
  hdr10Plus: "PRESENT",
  dolbyVision: {
    presence: "PRESENT",
    profile: 8,
    level: 6,
    baseLayerCompatibilityId: 1,
    baseLayer: "PRESENT",
    enhancementLayer: "ABSENT",
    rpu: "PRESENT",
  },
};
----

A client that reports HDR10 support does not necessarily support every combination of Dolby Vision, HDR10+, container, and delivery path.
The server may consider an HDR10 output only when the user's playback choice permits HDR10 and a worker can make the required changes to the source.
The server must explicitly choose the output.
The source description still records both HDR features even when the output contains neither enhancement.

[cols="2,3",options="header"]
|===
|Situation |How the system must respond

|Auto encounters an explicit format error, and the server chooses an eligible SDR replacement.
|Keep the original source description.
Set the output's `compatibleBase` to `SDR`.
Set `hdr10Plus` and `dolbyVision.presence` to `ABSENT`.
For an output known to contain no Dolby Vision, set the output's Dolby Vision numeric details to null and set its layer/RPU flags to `ABSENT`.
The worker converts the media as required, and the playlist describes SDR.
Count the replacement against the same playback-session attempt budget.

|The user requests a fixed quality and HDR output, but the server cannot provide that output.
|Keep the source properties unchanged.
The server cannot silently substitute SDR or another quality.
The epic tracks the open question of how the client should explain the failure to the user.

|The probe cannot determine whether HDR10+ or Dolby Vision information is present.
|Use `UNSPECIFIED` for unknown presence values, and leave unknown numeric details absent or null.
Do not infer SDR or mark enhancements absent solely because information is missing.
The probe can succeed while some properties remain unknown.

|The source reports Dolby Vision Profile 7 alongside SDR transfer and color properties.
|Keep the observed profile, layer, and color properties.
Record which properties conflict, and choose how to process colors from the picture signal that the playback path actually uses.
Do not tone-map solely because Dolby Vision information is present.
The problem code and the rules for deciding which playback paths remain usable are still open.

|A valid Dolby Vision profile has an SDR-compatible base.
|Keep both the Dolby Vision details and the SDR-compatible base in the source description.
The compatible base describes how to interpret the underlying picture without the advanced HDR information; the base does not describe the complete Dolby Vision picture.
The rules that derive the broad HDR label must account for the specific profile.
|===

=== Answer the open questions before finalizing the contracts

The questions below remain open.
The questions do not add agreed fields or requirements.

* Decide which codec names to use, how to express codec profiles and levels, and how to represent bit depth and chroma.
Define color primaries, transfer characteristics, matrix coefficients, and color range.
Reuse established names and units where those names and units already exist.
* Define how to derive `compatibleBase` from observed color properties and Dolby Vision claims, including cases where the claims conflict.
Define how to distinguish confirmed `NONE` from `UNSPECIFIED`.
Keep one answer for the compatible base instead of storing duplicates that can change independently.
* Define how to derive the broad HDR or SDR label when the description is complete, incomplete, conflicting, or unfamiliar.
Include sources known to have HDR when the HDR kind remains unknown.
Keep source facts even when those facts prevent a simple display label.
* Define the fields of `MediaFileProbePropertyIssue`, including how to identify the affected container or stream properties.
Decide which problem codes and severities to use, where to store and report problems, and which playback paths each problem rules out.
The agreed design does not include a generic setting to allow invalid streams.
* Define which combinations and limits a client can report for codec, profile, level, bit depth, dynamic-range features, container, player, and display.
The contract must describe how a supported value for one property constrains the values of other properties.
Do not assume that a client supports every combination of the values in separate lists unless the contract explicitly gives the lists that meaning.
* Finalize the explicit video-decision fields, decide how to encode the fields on the wire, and map the fields to the generated server, worker, and client types.
Keep unknown numeric values distinct from known values, and keep source properties distinct from the selected output properties.

https://github.com/streamarr/streamarr-server/issues/394[Server probe #394], https://github.com/streamarr/streamarr-server/issues/395[client capabilities #395], and https://github.com/streamarr/streamarr-server/issues/396[explicit video decision #396] depend on this shared vocabulary.
This draft does not meet those issues' prerequisites until the required definitions are complete.
Publish the protocol from the server repository first.
Implement the published contract in the worker, then update the server's pinned worker image as the epic requires.
When adding stored probe properties, follow ADR 0032's `probe_version` rules.

Explicitly deferred:

* Defer Dolby Vision output support.
Keep the work to recognize Dolby Vision in source files in scope.
* Leave codec preferences to the epic's planned work on verified encoders and codec choice.
That work will amend link:0009-h264-plus-av1-codec-strategy.adoc[ADR 0009].
* Keep the playback rules already recorded in the epic, including retry limits, how to allocate the quality ladder, and client controls.
The issues dedicated to those rules track the work to implement them.
* Keep the existing stream-session, variant, rendition, probe, and transcode-decision names unless a rename solves a specific problem.
Do not rename those concepts solely to match another project.

== Consequences

* The server, worker, and clients use shared properties with the same meanings, while each component keeps its own responsibilities.
Keep source, capability, and output records distinct; one record cannot replace another.
* The shared structure preserves simultaneous HDR features and unknown values without adding an enum value for every combination.
Define rules that derive and check the properties for each profile.
Use representative media examples to check those rules.
* When a problem arises, the original source facts remain available to explain why the server chose an output or why playback failed.
Record the problem separately from the source facts.
The open questions include how to record each problem and how each problem affects which playback paths the server can choose.
* When the server chooses SDR output, the source description keeps the HDR facts that the probe found.
The server cannot silently change a manual choice, and the playlist must describe the actual output that the server selected.
* This Proposed ADR records the agreed terms and structure and lists the questions that remain open.
The draft does not claim that the contracts or application behavior already exist.
* Amend ADR 0013's video-decision section when implementing #396.
Continue to follow the existing ADR definitions and the order of work recorded in the epic.

== Rejected Alternatives

* A single HDR boolean discards the format details that the server needs to choose an output and explain that choice.
* An enum that allows only one HDR format needs additional values for streams that combine Dolby Vision and HDR10+ and cannot retain all the source details on its own.
* Broad and detailed HDR labels can disagree if either label can change independently; derive the broad label from the detailed facts and the results of checking those facts.
* If missing information becomes confirmed absence or SDR, the source record loses the uncertainty that ADR 0032 preserves.
* If Dolby Vision alone triggers tone mapping, the worker ignores the picture signal and the specific profile.
* If one successful player test establishes support for all players, the server ignores differences between players and delivery paths.
* If Streamarr copies another project's glossary without a specific reason to rename its concepts, readers must learn new names without gaining clearer meanings.
