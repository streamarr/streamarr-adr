= ADR 0029: Pin Jellyfin FFmpeg Releases and Resolve Updates Before Building

== Status

Accepted

NOTE: Since link:0033-transcode-worker-is-a-separate-service.adoc[ADR 0033], the buildpack, lock, notices, and smoke tests described here live in the `streamarr-transcode-worker` repository.
The server image ships no FFmpeg.

An amendment to this ADR pins a second FFmpeg build for native macOS workers (<<decision-macos-pin>>).
The amendment brings hardware decode of seek attempts and the NVENC and VideoToolbox encoders into scope (<<decision-hardware>>).
The amendment also records how tests guard each upgrade of a pinned FFmpeg build (<<decision-upgrade-guard>>).

== Context

Streamarr runs FFmpeg as a subprocess (link:0004-processbuilder-over-jni.adoc[ADR 0004]) and requires H.264, AV1, and recoverable HLS behavior (link:0009-h264-plus-av1-codec-strategy.adoc[ADR 0009], link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019]).
The previous binary provider retained only a rolling window of daily builds, so a pinned dependency could disappear without a source change.
CI also installed distribution FFmpeg for smoke tests, exercising a different runtime from the shipped image.
Jellyfin publishes numbered FFmpeg releases with media-server patches and portable GPL binaries for both supported Linux architectures.
Its packaging revision is a fourth numeric version component, not a prerelease indicator.

An upgrade of the pinned FFmpeg build can change the initialization segment and the media segments that the worker produces from the same source file.

VideoToolbox is Apple's hardware video framework.
Only a process that runs natively on macOS can reach VideoToolbox.
A container on a Mac runs in a Linux virtual machine.
The FFmpeg build in the Linux worker image therefore cannot reach VideoToolbox on a Mac.
NVDEC is the hardware video decoder of NVIDIA GPUs.
NVENC is the hardware video encoder of NVIDIA GPUs.

== Decision

Consume exact numbered Jellyfin FFmpeg releases through the existing Cloud Native Buildpack, keeping ProcessBuilder and the application codec contracts unchanged.
Renovate owns one release-tag file and uses the GitHub releases datasource with regex versioning that compares the packaging revision numerically as a stable build component.
Keep FFmpeg updates isolated and reviewed rather than automerged.
Require Dependency Dashboard approval for major-version updates.

Generate a checked-in lock from published release metadata containing the full package version, fork source commit, portable GPL asset names, and SHA-256 digests for Linux amd64 and arm64.
Require both architecture assets before accepting an update and verify every downloaded archive against its locked digest before extraction.
Validate runtime identity, GPL/nonfree build flags, and required HLS capabilities; ship bundled-component notices, corresponding-source access instructions, and an SBOM alongside the binaries.
The flag check rejects `--enable-nonfree`; it does not exclude stripped FDK-AAC from Jellyfin's GPL binary.
Bind the reviewed notice inventory to the locked source revision and both binary digests, and reject stale redistribution materials before packaging.
The runtime banner omits Jellyfin's packaging revision, so the artifact checksum identifies the exact package build.

Separate dependency resolution from ordinary builds.
Validate the lock offline on every CI run and before publishing; query upstream metadata when FFmpeg resolution inputs change.
Run application smoke tests against the locked runtime, and verify both architecture images and their HLS recovery behavior for packaging changes.

Use a narrowly privileged synchronization workflow for Renovate updates.
Execute only trusted base-branch resolver code, treat the proposed tag as data, and generate the lock before minting write credentials.
Use a short-lived GitHub App token to create a signed commit containing only that lock, with an atomic expected-head check that rejects concurrent branch changes.
Include the App's commit identity in Renovate's ignored authors so generated commits do not prevent future updates.
Unprivileged PR CI may execute the proposed resolver to test changes to that resolver.

[[decision-macos-pin]]
=== A pinned macOS FFmpeg build serves native macOS workers

Streamarr supports native macOS workers on Apple silicon.
A native macOS worker runs directly on macOS, outside any container.
A native macOS worker can therefore use VideoToolbox.
https://github.com/streamarr/streamarr-transcode-worker/issues/54[streamarr/streamarr-transcode-worker#54] packages the worker for macOS and runs the worker natively.
This ADR pins a macOS FFmpeg build for native macOS workers, beside the FFmpeg build in the Linux worker image.
The macOS pin covers Apple silicon (arm64) only.
A native macOS worker is supported only with a server that runs natively on the same Mac.
The native macOS worker reaches the server over loopback.

[[decision-hardware]]
=== Hardware decode of seek attempts and the NVENC and VideoToolbox encoders are in scope

A seek attempt is a job attempt that starts FFmpeg at a point after the start of the source.
A seek attempt can decode in hardware.
On a native macOS worker, the hardware decoder is VideoToolbox.
On a Linux worker with an NVIDIA GPU, the hardware decoder is NVDEC.
link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] decides which seek attempts decode in hardware.
https://github.com/streamarr/streamarr-transcode-worker/issues/55[streamarr/streamarr-transcode-worker#55] adds hardware decode of seek attempts.
https://github.com/streamarr/streamarr-transcode-worker/issues/56[streamarr/streamarr-transcode-worker#56] adds the NVENC encoders.
https://github.com/streamarr/streamarr-transcode-worker/issues/57[streamarr/streamarr-transcode-worker#57] adds the VideoToolbox encoders.
ADR 0037 lists the checks that each hardware encoder backend must pass before a worker encodes with that backend.

[[decision-upgrade-guard]]
=== Committed fixtures guard each upgrade of the pinned FFmpeg build

FFmpeg's test sources are built-in source filters that synthesize video and audio signals.
The worker repository holds committed test fixtures that FFmpeg's test sources generate.
The worker's CI runs tests against those fixtures with the pinned FFmpeg build of the Linux worker image.
An upgrade of the Linux worker image's pinned FFmpeg build must pass those tests.
The tests follow link:0005-tdd-and-behavior-testing.adoc[ADR 0005] and assert the worker's produced output, not how the worker invokes FFmpeg.

FATE, the FFmpeg Automated Testing Environment, is FFmpeg's own test suite with its own set of real sample media files.
CI runs no FATE job.
The full FATE sample suite stays outside every repository.
Only local test runs use the full FATE sample suite.
Every committed fixture is generated, never copied from the FATE samples.
A test case that needs a FATE sample runs only locally.

FFmpeg's test sources cannot generate Dolby Vision video.
One small Dolby Vision profile 8.2 fixture is therefore the only committed fixture that FFmpeg's test sources do not generate.
Profile 8.2 carries Dolby Vision metadata on an HEVC stream whose compatible base is SDR.
x265 is an HEVC encoder.
`dovi_tool` is a tool that writes Dolby Vision metadata into an HEVC stream.
x265 and `dovi_tool` generate the Dolby Vision fixture once.
The worker repository commits the generated Dolby Vision fixture.
The worker's CI makes a stream copy of the Dolby Vision fixture.
The CI tests check four facts about the copy.

* The tests check the sample entry that the copy carries after the retag.
The retag writes the sample entry of a Dolby Vision copy whose compatible base is SDR as `hvc1` or `avc1` (link:0013-stream-decision-architecture.adoc[ADR 0013]).
* The tests check that every frame of the copy carries an RPU.
An RPU (reference processing unit) holds one frame's Dolby Vision metadata.
* The tests check whether the copy carries the Dolby Vision configuration record.
* The tests check the codec string of the copy.
The codec string is the value that names a stream's codec, codec profile and level in an HLS playlist.

Tests of Dolby Vision color and tone mapping run only locally, against real Dolby Vision samples.

PGS (Presentation Graphic Stream) is the bitmap subtitle format of Blu-ray discs.
VobSub is the bitmap subtitle format of DVDs.
FFmpeg's test sources cannot generate PGS subtitles.
Tests of PGS subtitles therefore run only locally, against real PGS samples.
Image-subtitle burn-in draws a bitmap subtitle, such as a PGS or VobSub subtitle, into the encoded video picture.
Tests of image-subtitle burn-in also run only locally, against real PGS and VobSub samples, like the PGS tests.

The worker's CI has no VideoToolbox or NVIDIA hardware.
The hardware-decode rules of ADR 0037 depend on how FFmpeg's decoders behave.
Each upgrade of a pinned FFmpeg build therefore re-runs the tests on the hardware-decode seek fixtures in a local test run.
The local run uses a Mac with VideoToolbox for the macOS FFmpeg build and a host with an NVIDIA GPU for the Linux worker image's FFmpeg build.
Each upgrade of a pinned FFmpeg build also re-runs the NVENC and VideoToolbox encoder checks in the same local run.
The encoder checks record the keyframes that each encoder produces.
The encoder checks compare the initialization segment of a variant's first job attempt with the initialization segments of the variant's replacement attempts.
The encoder checks also run the output check of https://github.com/streamarr/streamarr-transcode-worker/issues/25[streamarr/streamarr-transcode-worker#25].
The output check compares the codec, codec profile and level of the produced output with the job's decision.

=== Explicitly deferred

* A Streamarr-owned permanent binary/source archive and independent build pipeline.
* New codec selection behavior.
* The remaining hardware encoders, VAAPI, QSV, AMF and RKMPP, stay deferred to https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14] until hardware exists to verify them.
* Hardware decode on Intel and AMD GPUs (QSV and VAAPI) also stays deferred to https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14].
* Workers on another host outside a service mesh (link:0035-worker-uses-spring-boot-and-mesh-transport-security.adoc[ADR 0035]) wait for https://github.com/streamarr/streamarr-server/issues/509[streamarr/streamarr-server#509].
A worker outside a service mesh needs mutual TLS and a decision on how workers authenticate.
* This ADR leaves open whether an upgrade of the macOS FFmpeg build must pass the committed-fixture tests in CI or only in a local run on a Mac.

== Consequences

Dependency age alone no longer invokes a daily-build retention policy, and normal lock validation does not depend on the release API being available.
Binary downloads still depend on upstream availability; numbered releases are not a permanent-retention or immutability guarantee.
Jellyfin's versioned `repo.jellyfin.org/files/ffmpeg/linux/` mirror provides a second upstream source; automatic fallback is deferred.
Neither download channel supplies portable-tarball signatures or a permanent-retention promise.
A deleted asset fails the build, and a replaced asset fails checksum verification rather than silently changing the runtime.
Rebuilds independent of both upstream channels require an owned archive; caches do not provide that guarantee.
Streamarr accepts Jellyfin's patch and release cadence and retains responsibility for reviewing security updates, redistribution obligations, and runtime compatibility.
The privileged updater changes only after trusted resolver changes merge, while ordinary PR CI can validate a resolver migration before merge.

The committed fixtures cover the cases that FFmpeg's test sources can generate.
One generated fixture also covers a stream copy of Dolby Vision profile 8.2.
CI downloads no FATE samples.
Only a local test run checks an FFmpeg upgrade against PGS subtitles, image-subtitle burn-in, and Dolby Vision color and tone mapping.

Streamarr reviews the upgrades of two pinned FFmpeg builds instead of one.
A ServerAdmin who wants VideoToolbox runs both the server and the worker natively on one Apple silicon Mac.

An upgrade of the Linux worker image's FFmpeg build needs a local run on a host with an NVIDIA GPU.
An upgrade of the macOS FFmpeg build needs a local run on an Apple silicon Mac.
CI alone cannot accept either upgrade.

== Rejected Alternatives

* Refresh daily-build pins more frequently — postpones the retention failure without removing the dependency on an expiring artifact.
* Use a floating latest asset or distribution package — loses a reviewed runtime identity and dev/test/production parity.
* Treat the packaging suffix as SemVer prerelease — can suppress stable Jellyfin packaging fixes in Renovate.
* Query release metadata on every build — adds a live resolution dependency to builds whose inputs have not changed.
* Add a CI job that fetches a subset of the FATE samples whenever the pinned FFmpeg build changes — the committed fixtures guard upgrades instead, and the FATE samples stay local.
* Run a CI job that fetches a subset of the FATE samples beside the committed fixtures — the committed fixtures alone guard upgrades, and the FATE samples stay local.
* Commit FATE sample files as fixtures — the FATE samples stay outside every repository, and every committed fixture is generated.
* Keep every Dolby Vision test local — one small generated fixture lets CI guard the retag, the RPUs, the configuration record and the codec string.
* Keep the Dolby Vision tests local and add the four checks of the Dolby Vision copy to the local suite — the four checks belong in CI, because one small generated fixture covers them.
* Defer native macOS workers in link:0033-transcode-worker-is-a-separate-service.adoc[ADR 0033] and decode seek attempts in hardware only with NVDEC on Linux — Streamarr supports native macOS workers now, with their own pinned FFmpeg build.
