= ADR 0052: A Failed HLS Copy Falls Back to an Encode, and Original Changes to Auto Whenever It Must Encode

== Status

Proposed

This decision changes a rule that link:0013-stream-decision-architecture.adoc[ADR 0013], link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019], link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036], link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] and link:0049-capability-declarations-list-entries-and-an-output-fits-one-entry.adoc[ADR 0049] state.
Those ADRs end playback in Original and in a fixed quality after a format error during an HLS copy.
Each of those ADRs now points to this decision.
This decision also replaces the rule of link:0050-viewer-limits-bind-copies-and-quality-tiers-are-picture-boxes.adoc[ADR 0050] that an encode in Original is one variant without a label.
Every encode that Original reaches now plays in Auto.
ADR 0050 still decides when Original copies, and ADR 0050 still decides how the viewer's limits bound every encode.
ADR 0050 now points to this decision too.
link:0045-clients-direct-play-covered-files-and-use-platform-players.adoc[ADR 0045] keeps its fallback from direct play to HLS at original quality.

== Context

The viewer picks a playback choice when a stream session starts.
Original is the playback choice that plays the source at its own quality (ADR 0045).
Auto is the playback choice in which the player adapts quality to bandwidth across the variants.
A fixed quality is a playback choice that names one quality, such as 720p, and keeps that quality (link:0050-viewer-limits-bind-copies-and-quality-tiers-are-picture-boxes.adoc[ADR 0050]).
Each client shows the playback choices in a quality control, such as a quality menu.
Original sits at the top of that menu.
iOS and the web client start in Auto.
tvOS starts in Original.

Direct play means that the server sends the source file itself (ADR 0045).
A stream copy passes the source video through unchanged.
An HLS copy is an HLS stream session whose video is a stream copy.
An encode is video that the worker encodes.
In Original, the server direct-plays a file that the client capability declaration covers.
Otherwise, Original plays an HLS copy when one capability entry accepts the copy (ADR 0049).
Otherwise, ADR 0050 decides that Original plays an encode of one variant, bounded by the viewer's limits.
The server today plays Original as copy-only instead.
When no capability entry accepts a copy, the server refuses to start and asks the viewer to set Quality to Auto or to try another device.

A format error is a player error that concerns the media format itself, not the network or the server.
A format attempt is one output format that the server chooses within a playback session.
A playback session is the logical span of one viewing of a media title.
Each playback session has a format-attempt budget that limits how many format attempts the playback session uses (https://github.com/streamarr/streamarr-server/issues/401[streamarr/streamarr-server#401]).
Before this decision, the default budget was two format attempts: the initial format plus one more.

Before this decision, Original recovered from one format error only.
After a format error during direct play, the server fell back to HLS at original quality (ADR 0045).
After a format error during an HLS copy, playback ended with a typed error.
ADR 0013 ended playback in Original when a copy lacked its parameter sets.
ADR 0019 ended playback in Original after a copy's output mismatch.
ADR 0037 ended playback in Original when a copied variant ran short.
ADR 0049 accepted that a rejected copy of a stream with an unknown codec level, codec tier or frame rate ends playback in Original.
The reason given was that Original is a manual choice, and the server never silently replaces a manual choice.
A fixed quality can also play an HLS copy, when the source fits the fixed quality's picture box and the viewer's other limits (ADR 0050).
A format error during that HLS copy also ended playback, because a fixed quality never changed format automatically.

A player can refuse a copy that the client declared.
A client capability declaration is evidence, not a guarantee (ADR 0049).
AetherEngine, an open-source playback engine for Apple platforms, records several cases in which AVPlayer refuses a stream because of the playlist or the packaging rather than the decoder.
AetherEngine records that AVPlayer refuses an HEVC level that the `CODECS` attribute names.
AetherEngine also records that tvOS refuses an HDR variant while the display is not in an HDR mode.
Rivulet, an open-source tvOS media client that uses AetherEngine, plans a transcode as the fallback for every route that plays the source directly.
Rivulet also falls back to that transcode after a load hangs for 60 seconds.
Streamarr read both projects' source code and measured neither.
tvOS starts in Original, so an Apple TV viewer meets a refused copy as an error.

== Decision

[[decision-fallback]]
=== In Original, a format error during an HLS copy falls back to an encode

In Original, the server tries up to three outputs in this order:

. direct play, when the client capability declaration covers the file (ADR 0045);
. an HLS copy at original quality, when one capability entry accepts the copy (ADR 0049);
. an encode.

The server skips every step that the declaration, the probe's property issues or the copy rules rule out.
A file that the declaration does not cover for direct play therefore starts with the HLS copy.
A file that the server cannot copy starts with the encode, which plays in Auto (<<decision-start>>).

After a format error during the HLS copy, the server starts a new format attempt that encodes the video.
The new format attempt has its own stream session, playlist and initialization segment, as every format attempt does.
The same failures that move Auto from a copy to an encode move Original from the HLS copy to the encode:

* a format error that the player reports for the copy;
* a copy's output mismatch, such as a copy whose decoder configuration record lacks its parameter sets (ADR 0013 and ADR 0019);
* a copied variant that runs short (ADR 0037);
* the worker's typed failure to convert a Dolby Vision profile 7 RPU during the copy (https://github.com/streamarr/streamarr-server/issues/651[streamarr/streamarr-server#651]).

The fallback applies whether the viewer picked Original or the client started in Original.

The fallback needs an encode that the client accepts.
Some sources cannot be encoded, for example a source with no usable output frame rate (https://github.com/streamarr/streamarr-server/issues/446[streamarr/streamarr-server#446]).
When the server cannot make an encode that the client accepts, no fallback exists.
A format error during the HLS copy then ends playback with the typed terminal error, as Auto's recovery does when no eligible replacement exists (streamarr/streamarr-server#401).

*Why:* An error leaves the viewer with no action to take, while the server can still play the title.
The viewer picked Original to watch the title at its best quality, not to give up on the title when that quality fails.
Every failure in the list above is a failure of the copy that an encode avoids.

[[decision-budget]]
=== The default budget is three format attempts, and the fallback to the encode spends one

The default format-attempt budget is three format attempts: the initial format plus two more.
Three format attempts hold each of Original's three outputs: direct play, the HLS copy and the encode.
The budget stays configurable.

The encode after the HLS copy counts as one format attempt against the playback session's format-attempt budget.
The encode's stream session does not reset the budget or the playback session's format-failure history.
When a configured budget has no room for the encode, playback ends with the typed terminal error, as Auto's recovery does (streamarr/streamarr-server#401).

*Why:* tvOS starts in Original and direct-plays every file that its declaration covers.
Under a budget of two, direct play and the HLS copy used both format attempts, so a refused copy on tvOS still ended playback.
Some video is better than no video, so the default budget lets every Original reach the encode.

[[decision-auto]]
=== When Original plays an encode, the playback choice is Auto

Every encode that Original reaches is a format attempt in Auto.
That holds for the encode after the HLS copy, and for an encode that Original starts with (<<decision-start>>).
The server tells the client that the playback choice changed from Original to Auto.
The client then shows Auto as the selected choice in its quality control.
A client without a quality control shows the notice alone (<<decision-notice>>).

Auto's own rules then apply to the encode:

* The viewer's limits bound the encode, as ADR 0050 decides for Auto.
* The server offers Auto's encoded quality ladder of quality tiers (ADR 0050).
The playlist lists the variants in Auto's order, and the first variant starts first (link:0008-server-generated-hls-playlists.adoc[ADR 0008], link:0044-encoder-headroom-and-the-preset-scale.adoc[ADR 0044]).
* The ladder offers no copy.
After a failed HLS copy, the failed copy stays in the playback session's format-failure history, so the server does not choose the failed copy again for the encode's ladder.
* A format error during the encode starts Auto's recovery within the budget that remains (streamarr/streamarr-server#401).
For example, Auto may then give up HDR for SDR.
* The client hides the HDR toggle, as it does in Auto.

Changing the playback choice to Auto uses no format attempt beyond the encode.
From Auto, the viewer can pick any playback choice again.

*Why:* The quality control is a second sign, beside the notice, that the viewer watches a converted version.
After the change, the stream is Auto's ladder, so the quality control describes the stream that actually plays.
A quality control that still showed Original would claim the source's own quality while an encode plays.
The server never silently replaces a manual choice (ADR 0013), and the notice and the quality control make this replacement visible.

[[decision-start]]
=== An Original that starts with an encode plays the encode in Auto

Original starts with an encode when the server rules out both direct play and the HLS copy.
That happens, for example, when no capability entry accepts a copy of the source, or when a property issue rules out a copy.
The server then plays the encode in Auto, as it plays the encode after a failed HLS copy (<<decision-auto>>).
The client shows the notice, and its quality control shows Auto (<<decision-notice>>).
The encode is the playback session's first format attempt, so the change to Auto spends no format attempt.
The same holds when direct play fails and the server rules out the HLS copy: the encode that follows plays in Auto.
The rule applies whether the viewer picked Original or the client started in Original.

*Why:* Some video is better than no video.
When the device cannot play the original video, the server switches the player to Auto, whether the server learns that from the declaration or from a failed copy.
Refusing to start, as the server does today, gives the viewer an error for a title that the server can still play.
An encode under the Original label would claim the source's own quality while a converted picture plays.

[[decision-fixed-quality]]
=== In a fixed quality, a format error during an HLS copy falls back to an encode at the same fixed quality

After a format error during a fixed quality's HLS copy, the server starts a new format attempt that encodes the video at the same fixed quality.
The same failures that move Original from the HLS copy to the encode qualify (<<decision-fallback>>).
The encode follows the rules of ADR 0050 for a fixed quality's encode.
The fixed quality's picture box, the viewer's other limits and one capability entry bound its single variant.
The encode counts as one format attempt against the playback session's format-attempt budget (<<decision-budget>>).
The failed copy stays in the playback session's format-failure history.
When the server cannot make an encode that the client accepts, the format error ends playback with the typed terminal error (<<decision-fallback>>).

The playback choice stays the fixed quality, and the client keeps that fixed quality selected in its quality control.
The client shows the notice without its sentence about Auto (<<decision-notice>>).
When the failed copy was HDR and the device cannot play an HDR encode, the encode is SDR.
The notice already tells the viewer that a converted version is playing, so the change to SDR is not silent.
A fixed quality changes format after no other format error, so a format error during the encode ends playback with the typed terminal error.

*Why:* A fixed quality promises a picture size, not a copy.
An encode at the same fixed quality keeps that promise, while an error leaves the viewer with no video.
Switching to Auto would drop the size that the viewer picked.
An SDR picture at the chosen size is better than no picture, because some video is better than no video.
The notice tells the viewer that a converted version is playing, so the server does not replace the copy silently (ADR 0013).

[[decision-notice]]
=== The client shows a short notice

When Original changes to Auto, the client shows this notice:

[quote]
This device couldn't play the original video, so a converted version is playing.
Quality is now set to Auto.
To choose another quality, open quality settings.

The notice appears over the playing video for a few seconds and then disappears by itself.
The notice neither pauses playback nor asks the viewer to act.
The notice names no internal concept, such as a worker, a format attempt, a copy or a transcode.
Each client may adapt the words "quality settings" to the name of its own quality control.

The client shows the same notice when Original starts with an encode.
The words stay true then, because the device could not play the original video in that case either.

After the fallback in a fixed quality, the quality control still shows the fixed quality.
The client therefore shows the notice without the sentence "Quality is now set to Auto.":

[quote]
This device couldn't play the original video, so a converted version is playing.
To choose another quality, open quality settings.

The client shows no notice after the fallback from direct play to the HLS copy.
That HLS copy still plays the source's own video, so a notice about a converted version would be false.

[[explicitly-deferred]]
=== Explicitly deferred

* This decision does not say what happens when the viewer picks Original again after the playback choice changed to Auto, in the same playback session.
https://github.com/streamarr/streamarr-server/issues/399[Epic streamarr/streamarr-server#399] keeps that question open.
* This decision does not say whether Original or a fixed quality tries the copy with Dolby Vision stripped before the encode, as Auto does for Dolby Vision profiles 8.1, 8.4, 10.1 and 10.4 (streamarr/streamarr-server#401).
Until that question closes, Original and a fixed quality fall back from a failed Dolby Vision copy to the encode.

== Consequences

* In Original, a refused HLS copy no longer ends playback under the default budget.
The viewer sees the notice, and the quality control shows Auto.
* In a fixed quality, a refused HLS copy no longer ends playback under the default budget.
The viewer sees the notice, and the fixed quality stays selected.
* With the default budget of three format attempts, a file that starts with direct play reaches the encode.
Direct play is the first format attempt, the HLS copy is the second, and the encode is the third.
A format error during that encode then ends playback with the typed terminal error, because no format attempt remains for Auto's recovery.
A file that starts with the HLS copy keeps one format attempt for Auto's recovery after the encode.
* The default budget holds for every playback choice, so Auto's recovery also gets a third format attempt.
For a Dolby Vision profile 8.1, 8.4, 10.1 or 10.4 source, Auto then reaches the encode after the copy with Dolby Vision stripped fails (streamarr/streamarr-server#401).
* A playback session can spend three format attempts before the typed terminal error, so a viewer may wait through one more failed start before the error.
* tvOS starts in Original, so every tvOS stream that starts with an encode now starts with the notice and with Auto selected.
* Original never plays an encode.
The rules of ADR 0050 for an encode in Original, one variant without a label, no longer apply, because that encode is Auto's ladder.
* The encode starts on Auto's first variant, which is the variant whose average bitrate is nearest 2000 kb/s.
The picture can therefore start below the source's size and then climb.
* The encode costs worker capacity that the copy did not cost.
* Under ADR 0049, a stream with an unknown codec level, codec tier or frame rate can reach a player that refuses the copy.
In Original and in a fixed quality, that refusal now costs a format attempt and a converted picture instead of ending playback.
* A copied variant that runs short is detected near the real end of the source.
In Original and in a fixed quality, the viewer then sees the notice near the end, and the encode pads to the advertised end (ADR 0037).
* After the fallback, the viewer's limits bound the stream, because Auto honors them (ADR 0050).
* The server's answer when a stream session starts, and its answer to a format failure, must carry the playback choice that plays, so that the client can show the notice and Auto.
In a fixed quality, the answer must also tell the client that an encode replaced a failed copy, so that the client can show the notice.
* Each client must show the notice and switch its quality control to Auto.
In a fixed quality, each client must show the notice without its sentence about Auto and keep the fixed quality selected.

== Rejected Alternatives

* Ending playback after an HLS copy's format error, the earlier rule, gives the viewer an error for a title that the server can still play.
tvOS starts in Original, so most Apple TV viewers would meet that error.
* Falling back silently while the quality control still shows Original would replace a manual choice without telling the viewer.
ADR 0013 forbids a silent replacement.
* Showing the notice while the quality control still shows Original would leave the quality control describing a stream that does not play.
* Refusing to start Original when the server must encode, as the server does today, gives the viewer an error for a title that the server can still play.
* Playing an encode in Original as one variant without a label, as ADR 0050 decided, would keep Original selected while a converted picture plays.
* Encoding one variant at the source's size under the Auto label would show Auto while the player has only one variant, so the player cannot adapt quality.
* Asking the viewer to try Auto after Original fails, the epic's earlier deferred idea, stops playback until the viewer acts.
* Starting the encode beside every copy as a standby stream costs worker capacity for every copy that plays.
Epic streamarr/streamarr-server#399 starts another format only after a qualifying format error.
* Keeping the earlier rule for a fixed quality, so that a format error during its HLS copy still ends playback, gives the viewer an error for a title that the server can still play at the size the viewer picked.
* Switching a fixed quality to Auto after a failed HLS copy would drop the size that the viewer picked, although an encode at that size can play.
* Keeping the default budget at two format attempts, and letting the budget bind, would end playback on tvOS whenever a file that starts with direct play also fails its HLS copy.
* Skipping the HLS copy after a failed direct play, so that a budget of two reaches the encode, would give up the source's own video whenever only direct play fails.
The HLS copy still plays the source's own video, and it can play where direct play cannot, for example when the player refuses the source container.
