= ADR 0033: The Transcode Worker Is a Separate Service and Repository, and the Server Runs No FFmpeg

== Status

Accepted

== Context

link:0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018] introduced outbound transcode workers in the server's repository and jar.
One Maven module builds both, and one image exposes `web` and `worker` process types.
Local playback runs FFmpeg inside the server.
Remote workers are optional.

Issue #248 proposed restoring a Maven reactor to exclude authentication, persistence, and web code from the worker jar, with a repository split deferred until the wire contract stabilized.
Three dependencies complicate that split.
The server's local execution path and the worker share the FFmpeg command builder, process manager, and capability detection.
The server's remote playback and recovery tests construct the real worker in-process.
Both sides generate stubs from one proto file.

The goal is an independently deployable and scalable worker in its own repository.
Moving all FFmpeg execution to workers removes the server's dependency on the engine.
The two repositories can then share the Protobuf contract without publishing a shared engine artifact or maintaining a Maven reactor.

== Decision

Run the transcode worker as a separate service in the `streamarr/streamarr-transcode-worker` repository, published as the `streamarr/streamarr-transcode-worker` image.
The server executes no FFmpeg.

=== Execution

Transcoding and probing both run on workers.
Remove the server's local transcode executor, engine wiring, FFmpeg health indicator, and `streaming.remote.enabled` switch.
Retain `TranscodeExecutorHealthIndicator` to report worker connectivity.
It reports `DOWN` when no workers are connected and continues to affect `/actuator/health`.
Every playback needs a worker, including compatible media that FFmpeg remuxes into HLS (link:0007-transcode-first-with-smart-remux.adoc[ADR 0007]).

The file-processing pipeline requests probes over the worker session, outside the playback path, as defined in link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032].
The worker resolves the source through the same `MediaSourceRef` and mount mapping used for transcoding.
It advertises probe support at registration, and the server sends probe requests only to workers advertising that capability.
Probe capabilities identify the Streamarr probe result contract versions the worker can produce, as defined in ADR 0032.
A worker that advertises probing validates its configured probe executable before registration.
The server requests a supported `probe_version` and accepts a result only for the version carried by the probe request.
A worker without probe support can still transcode.

=== Media access

Source media resides on filesystem storage supplied by the deployment.
The server and eligible workers mount the same media tree through their configured source namespace mappings.
Local mount paths may differ.

Multi-node installations require storage that supports concurrent reads from every eligible worker node.
Workers mount source media read-only.
Each worker uses separate writable storage for temporary transcode output.

The deployment chooses the storage backend.
Worker scaling remains bounded by available storage and network throughput.
Node-local media restricts worker placement to nodes where that media is available.

=== Health checks

Workers expose liveness and readiness through the standard gRPC health-checking protocol on a dedicated port.
The health service uses plaintext and separate service names for liveness and readiness.
Kubernetes probes reach this port on the worker's Pod IP.
The port serves only health checks.
The server never dials it for worker control or health checks.
Readiness requires successful initialization and an active session accepted by the server.
A worker remains ready while all execution slots are occupied.
Liveness checks local process health.
It does not depend on server connectivity.
The Kubernetes worker Deployment configures both probes.
The server continues to assign jobs through the worker session using advertised capabilities and available slots.
Kubernetes readiness does not control job dispatch.

Server liveness and readiness remain independent of worker availability.
The server Deployment uses `/actuator/health/liveness` for startup and liveness probes and `/actuator/health/readiness` for readiness probes.
Neither group includes `TranscodeExecutorHealthIndicator`.
Configuration tests preserve this exclusion, which Spring Boot's default group membership provides today.
The server's Service must remain reachable so workers can establish sessions when no workers are connected.

=== Kubernetes installations

Kubernetes installations run workers in a separate Deployment.
Worker pods connect to the server's Service over mutual TLS, including when they run on the same node as the server.
Worker replicas scale independently of the server and have their own resource requests and node placement.
The server Deployment runs one replica, as defined in link:0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018].
It uses stop-before-start replacement (`Recreate`), as required by link:0027-library-work-claimed-in-database-single-instance.adoc[ADR 0027].
Multiple server replicas remain deferred.

A colocated worker may run as a sidecar for small installations.
It shares the server's Pod and uses the loopback listener.
This arrangement couples its replica count and node placement to the server.

=== Listener configuration

The loopback and mutual-TLS worker-session listeners each require explicit enablement.
The default Compose configuration enables the loopback listener.
The Kubernetes example enables only the mutual-TLS listener.
Enabling mutual TLS requires an externally issued certificate, private key, and trust bundle.
The server refuses to start if neither worker-session listener is enabled.
The `dev` profile enables the loopback listener.

Worker-session listener ports and the worker health port are configurable.
Tests may request port `0` and retrieve the bound port after startup.
Shared configuration for full application tests enables loopback on an ephemeral port.
Narrow test contexts that omit listener configuration do not start a listener.

=== Colocated installations

Colocated workers share the server's network namespace.
Docker Compose uses `network_mode: service:<server>`.
The optional Kubernetes sidecar shares the server's Pod.
The plaintext gRPC listener accepts the worker's connection on the server's loopback interface.
The worker reads its id from the environment.
The listener requires no credential and trusts callers that can reach the loopback interface.
The bind address is fixed and non-configurable.
An integration test verifies that the listener binds only to loopback and is unreachable through the server's non-loopback addresses.
A caller presenting an existing worker id replaces that worker's connection and abandons its jobs, so the loopback restriction is part of the trust boundary.
Tests reach the loopback listener from the test JVM through the contract stubs.
Container-based tests use the mutual-TLS listener.
Workers outside the server's network namespace use mutual TLS with externally issued identities, as decided in ADR 0018.

=== Contract ownership and rollout

The server repository owns the proto file and keeps the Buf lint and breaking-change checks.
On merge to main, the server repository publishes the module to the Buf Schema Registry as `buf.build/streamarr/transcode`.
The worker consumes it as a module dependency or generated Java SDK, without keeping a copy of the proto.

Contract changes are additive, and the server deploys support for them before workers are upgraded.
The server dispatches a new operation only after a worker advertises support for it.
This capability check applies to every new operation: schema compatibility alone does not establish that a worker implements a command.
Today's worker logs unknown commands without replying.

=== Tests cross the boundary through images

The server's remote playback and recovery tests use Testcontainers to run the published worker image, pinned to an immutable version tag.
They connect over the mutual-TLS listener using test-issued certificates.
A scripted `ffmpeg` mounted into the container injects faults at specific segments.
Tests select the script through the worker's existing FFmpeg path environment variable.
The worker's own tests run against a scripted fake control plane built from the contract stubs.

=== Repository split

Move the FFmpeg buildpack, lock, notices, and smoke tests defined in link:0029-pin-jellyfin-ffmpeg-releases.adoc[ADR 0029] together into the worker repository.
Hardware acceleration examples and device passthrough target the worker.
Preserve the worker's history with `git filter-repo`.
The worker remains a plain Java process.
Adopt a framework only when the implementation requires one.

=== Implementation order

The loopback listener, worker health checks, and repository and registry setup can proceed alongside ADR 0032.
Probe relocation depends on ADR 0032 being complete.

. Implement ADR 0032.
. Add the loopback listener and probe operation, then remove local execution while the worker is still in the server repository.
. Add worker health endpoints and configure the Kubernetes probes.
. Publish the worker contract to the Buf Schema Registry after its organization, module, and publication credentials are configured.
. Move the packages in a structural change while the worker is still in the server repository.
. Populate the worker repository with preserved history, its build, CI, and tests against a fake control plane.
Move the FFmpeg buildpack, lock, notices, and smoke tests together.
. Publish the first worker image.
. Update server tests and deployment examples to use the published worker image, then remove the relocated code and build assets from the server repository.

Once this ADR is accepted and a replacement implementation epic exists, close issue #248 as superseded.
The replacement epic tracks completion of the repository split.

Explicitly deferred:

* Direct access to object-storage backends, including S3-compatible services.
Issue #77 explores Apache OpenDAL as a possible implementation.
* A worker-free delivery path for compatible media, such as serving the file as-is.
* Multiple control-plane replicas, as already deferred in ADR 0018.
* Worker-to-client or object-store segment delivery.
* An in-process worker mode inside the server.
* Making aggregate health independent of worker availability.

== Consequences

* A single-node installation runs two processes.
The default Compose file includes a colocated worker.
The Kubernetes example uses a separate worker Deployment.
Local development needs a worker container for playback and scans.
* All installations use the same worker execution path, so single-node use also exercises remote dispatch and recovery.
* Changes to FFmpeg handling are released with the worker.
* Cross-repository changes require coordinating contract publication, capability support, and the worker image used by server tests.
* The server's in-process worker tests become container tests, and a scripted `ffmpeg` replaces the fake process manager.
* A worker must implement and advertise a new operation before the server dispatches it.
Probing is the first such operation.
* This ADR supersedes ADR 0018's local execution decision (one engine, two execution adapters), optional distributed transcoding, and single image with separate process types.
It also narrows ADR 0018's no-inbound-port statement to allow a worker port solely for orchestrator health checks.
ADR 0018's live playback authority, outbound mutual-TLS sessions, workload identity, `MediaSourceRef`, and contract rules remain in force.
* link:0004-processbuilder-over-jni.adoc[ADR 0004]'s single image with and without GPU now describes the worker image.
* link:0020-tmdb-reachability-does-not-gate-aggregate-health.adoc[ADR 0020]'s aggregate-health deferral now concerns worker connectivity through `TranscodeExecutorHealthIndicator`.
The local FFmpeg contributor is removed, while worker connectivity continues to affect aggregate health.

== Rejected Alternatives

* A Maven reactor in the server repository, as issue #248 proposed — separates the jars but retains a shared engine that would need its own publication process after a repository split.
* Publishing the engine and contract as Maven artifacts on Maven Central, GitHub Packages, or JitPack — adds artifact publication and dependency coordination.
Only the worker needs the engine.
The contract is published through Buf.
* Copying the proto into the worker repository with a drift check — requires synchronizing two copies when both repositories can use the published module.
* A separate proto repository — adds a repository and release workflow for a contract owned by one server.
* Keeping the engine in both repositories — requires duplicating FFmpeg command and process-management changes.
* Server-issued identities for the colocated worker — requires certificate issuance inside the application, contrary to ADR 0018's decision to use external issuers.
* A pre-shared token or other credential on the loopback listener — adds secret provisioning and rotation to an installation that explicitly trusts callers with access to the loopback interface.
* Probing on the playback path — adds a worker round trip and process startup to every playback start while leaving library scans without probe data.
* A configurable bind address for the plaintext listener — an externally reachable listener with no credential lets any caller register as a worker or replace one, and tests do not need it.
* Relying on additive schemas alone for rollout — older workers can decode envelopes containing new commands without implementing those commands or returning a result.
* Keeping ffprobe in the server — requires the FFmpeg buildpack and runtime pin in both repositories.
* Publishing the worker as a Maven artifact for in-process server tests — adds a publication workflow solely for tests when the worker image already provides a deployable artifact.
