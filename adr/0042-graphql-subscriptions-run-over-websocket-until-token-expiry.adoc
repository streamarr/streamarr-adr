= ADR 0042: GraphQL Subscriptions Keep Queried Screens Current over WebSocket until Token Expiry

== Status

Proposed

== Context

A normal query or mutation response already supplies the state needed to display a Streamarr screen.
Library status (https://github.com/streamarr/streamarr-server/issues/411[#411]), Profile watch state (https://github.com/streamarr/streamarr-server/issues/165[#165]) and library contents (https://github.com/streamarr/streamarr-server/issues/166[#166]) need subsequent changes pushed to open clients.
The server, web client and Apple client need shared subscription conventions, just as link:0026-mutation-payloads-and-error-channels.adoc[ADR 0026] defines mutation conventions.
WebSocket with `graphql-transport-ws` provides a supported transport across Spring for GraphQL, Apollo Client and Apollo iOS.
link:0016-authentication-mechanisms-and-session-security.adoc[ADR 0016] bounds authority by access-token expiry even when a connection remains open.

== Decision

=== Initial state and live updates

* Ordinary queries and mutation responses populate screens; explicit, purpose-specific subscriptions keep them current through useful typed payloads.
  Reuse the same entity types and cache identities, and provide the data needed to update lists and visible aggregates without a query after each event.
* Accept the small query-to-registration gap.
  A subscription has no universal initial snapshot, readiness handshake, durable replay or exactly-once guarantee.
  Recovery reloads current state through ordinary queries.
* Use ordinary normalized caching.
  Do not require revisions or stale-response guards on every entity or response.
  A delayed response may overwrite newer displayed fields; stronger consistency requires a justified feature-specific contract.
* Apply updates automatically.
  Inserting within a loaded list range grows it, removing shrinks it without backfilling, and filter, sort and authoritative aggregate changes update the view.
  Keep the current library's subscriptions through library-to-movie-to-library navigation.
* Keep subscriptions running when a browser tab is hidden, subject to platform suspension.
  Revalidate silently after reconnect, return online or return to the foreground, including the retained library view.
  Temporary interruptions add no connection-status indicator.
* Publish committed changes as they happen without default batching or coalescing.
  Transactional publication occurs after commit; the domain event remains independent of the GraphQL payload.

The shared server and client rules, per-field contract and verification requirements are in link:../docs/graphql-subscription-conventions.md[GraphQL subscription conventions].

=== Transport, authority and recovery

* Subscriptions use `graphql-transport-ws` over a shared WebSocket on `/graphql`.
  Queries and mutations remain on HTTP; HTTP and server-sent-event subscriptions are refused.
* The opening HTTP handshake authenticates with the existing access cookie or Bearer token and retains the origin check.
  A token does not travel in `connection_init`.
  Authorize each subscription and its data through the service-layer contract in link:0025-cedar-decides-authorization.adoc[ADR 0025].
* At the opening token's expiry, stop data delivery and close the socket with a documented, client-tested signal.
  Do not send `complete` for active operations first: completion ends them in the client and prevents normal restoration.
  Coordinate session renewal before opening the replacement socket, then restore still-desired subscriptions and revalidate.
* Retry recoverable connection failures without an attempt limit, using the transport's retry machinery with capped exponential backoff and jitter.
  Start with a cap of approximately 30 seconds as client configuration.
  Preserve fatal-error handling and stop obsolete recovery on logout, permanent authentication failure, cancellation or identity change.
* Normal scope completion and permanent subscription refusal remain terminal.
  If an operation error is documented as recoverable, its consumer recreates the operation explicitly; socket reconnection alone does not revive completed or errored operations.
* Domain failures are ordinary data, such as a library becoming `UNHEALTHY`.
  Subscription refusal and execution/source failures use sanitized GraphQL errors with documented codes; subscriptions do not copy mutation `userErrors` into every result.

=== Resource limits and deployment

* Bound queues and transport resources, and never make publishing wait for a slow subscriber.
  Terminate the affected operation or connection on overflow and recover through revalidation.
  Do not promise that a shared socket failure affects only one subscription.
* Cancellation, completion, expiry and disconnection release all subscription resources.
  Keep required reactive adaptation at the GraphQL boundary; virtual threads remain the application concurrency model.
* Changes initially reach subscribers through the one active server process required by link:0027-library-operations-are-durable-jobs.adoc[ADR 0027].
  Horizontal deployment requires shared event distribution and resolution of the other single-instance assumptions, beyond the transport choice.

Explicitly deferred:

* A durable event history or resumable change cursor.
* Universal atomic query/subscription startup, entity revisions, deletion tombstones or cross-transport ordering guards.
* Additional subscription transports, periodic polling fallback and speculative coalescing.

== Consequences

* An open page receives live changes without reloading after each event, while recovery uses familiar query and cache mechanisms.
* Clients reconnect at least once per opening access-token lifetime while subscriptions remain needed.
  Refreshing an HTTP cookie does not reauthenticate an existing WebSocket.
* Best-effort current state accepts a missed startup change and stale-response overwrites until a later update or revalidation.
  It does not claim historical completeness.
* Payload design includes list membership, sorting, pagination and visible aggregates where the feature promises them; Apollo entity normalization does not maintain those automatically.
* The web and Apple transports need tests for expiry, reconnection and operation termination because their library defaults differ.
* A reverse proxy must pass WebSocket upgrades on `/graphql`.

== Rejected Alternatives

* Polling as the routine update path — avoid recurring requests and update delay; recovery queries remain appropriate.
* Server-sent events or multipart HTTP subscriptions — add transport and client work without a shared supported path across the selected server and Apple stack.
* The older `subscriptions-transport-ws` protocol — replaced by `graphql-transport-ws`.
* Universal snapshot/readiness and highest-revision protocols — their complexity is not justified by the accepted live-screen consistency requirement.
* An ID-only invalidation stream followed by a query for every event — ordinary updates should carry the data needed by the UI.
* Completing every operation before closing an expired socket — tells clients the operations are finished instead of temporarily disconnected.
* Unlimited buffering or waiting for a slow client — permits unbounded memory growth or delays the publishing operation.
