= ADR 0037: The Worker Delivers Fragmented MP4 Segments From FFmpeg's Standard Output, and HLS Media Segments Are fMP4 Only

== Status

Accepted

NOTE: link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043] amends this decision.
Once the server delivers audio renditions, a variant's media segments carry video alone.
Each audio rendition then has its own initialization segment.
Until then, the server keeps serving multiplexed variants as this decision describes.

This decision supersedes the container clause of link:0009-h264-plus-av1-codec-strategy.adoc[ADR 0009] ("H.264 uses MPEGTS container" and "container format is determined by codec choice").
This decision changes one consequence of link:0008-server-generated-hls-playlists.adoc[ADR 0008].
FFmpeg no longer writes segments to disk.
This decision left ADR 0009's codec-preference clause alone.
An amendment to ADR 0009 has since settled that clause for the playback capabilities epic (https://github.com/streamarr/streamarr-server/issues/399[streamarr/streamarr-server#399]).
Under that amendment, an encode uses the first of AV1, HEVC and H.264 that the client declares and that a worker-verified encoder can encode.

== Context

This section describes the system before the changes required by this decision.
References to the previous worker mean the worker before this decision, which asks FFmpeg's HLS muxer to write segment files.

The transcode worker runs FFmpeg under `ProcessBuilder` (link:0004-processbuilder-over-jni.adoc[ADR 0004]).
FFmpeg's HLS muxer writes each segment to a directory.
The worker uploads each segment over the gRPC session that link:0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018] and link:0033-transcode-worker-is-a-separate-service.adoc[ADR 0033] describe.
FFmpeg never signals that a segment is complete, so the worker infers that the segment is complete by checking whether FFmpeg has renamed the segment file or exited.
The worker checks the directory and the process every 50 ms, but at different moments, so the result depends on the order in which FFmpeg renames the file and exits.
In worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/36[#36], FFmpeg renamed the last segment and exited between the two reads.
The worker then reported a successful attempt as `TRANSCODE_FAILED` while the segment sat on disk.
Reviewers of the fix in worker PR https://github.com/streamarr/streamarr-transcode-worker/pull/38[#38] found a second bug.
After the worker asks FFmpeg to stop, FFmpeg flushes a final segment.
The worker uploads that segment after sending `JobAttemptStopped`.
The server rejects that upload, and the worker reports a failure for an attempt it has already reported as stopped.
Five open-source media and live-streaming servers that watch FFmpeg's output directory hit the same last-segment race.

The research compared five designs for delivering segments.
This decision chooses the design in which the worker reads fragmented MP4 (fMP4) from FFmpeg's standard output.
Rejected Alternatives explains why this decision rejects the other designs.
Standard output provides one ordered channel.
FFmpeg writes every fragment in order.
The reader reaches end of file only after it has read the last byte from the pipe.
The kernel pipe blocks FFmpeg when the reader falls behind.
`Process.waitFor` returns the exit code.
The HLS muxer decides where a segment ends, and it measures each cut from the first packet of its own run.

A job attempt is one dispatch of a variant's job to a worker, with its own FFmpeg process and outcome.
A replacement attempt replaces an earlier job attempt for the same variant under link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019]'s recovery.
The server advertises fixed segment intervals, but the worker relies on the HLS muxer's cuts without checking whether those cuts match the advertised intervals.
The server picks stream copy, which passes the source video through unchanged, whenever the client supports the source video codec (`TranscodeDecisionService`).
The server sends an `align_keyframes_to_segments` flag that neither the server nor the worker reads.
No probe field carries keyframe spacing.
The server builds the media playlist from the probed duration alone.
Every `EXTINF` is exactly the configured period, 6 s by default.
Media time is presentation time on the timeline that every attempt of a stream session shares.
The playlist defines segment `i` as media time `[i × period, (i + 1) × period)`, and the boundaries `k × period` form the grid.
The server never reads a per-segment duration from an upload.
For every start, seek, resume and replacement attempt, the server requests a seek to segment index times period and sends that index as `start_sequence_number`, the start sequence number.
The worker does not discard media that a stream-copy seek emits before the requested segment.
The start-0 attempt is the job attempt whose start sequence number is 0.
The server sends the probed frame rate on every job attempt, or 0 when the probe found no usable rate.
`SegmentUploadMetadata` carries `content_length_bytes` and the segment name, and no timing field.
The server caps a segment at 128 MiB, the segment cap.
It admits at most 8 concurrent uploads per worker and 64 MiB of buffered upload bytes fleet-wide.
The server reclaims an upload older than 120 s only when it checks whether it can accept a later upload.
The worker sends chunks in a plain `onNext` loop with no `isReady` check.
It starts its 5 s acknowledgment timer only after the last chunk and sets no gRPC deadline, so a stalled receiver never times the worker out.
The worker advertises a slot count to the server and never enforces it.
The server frees an attempt's slot when it sends `StopVariant`, before the worker has stopped that attempt.
On the stop path, the worker writes `q`, FFmpeg's quit command, to FFmpeg's standard input and sends `JobAttemptStopped` after a bounded wait.
On the forced-kill path it sends that message without waiting for the process to exit.
Worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/40[#40] requires the new producer to bound those waits and its memory, and requires the worker to enforce its slot count.

ADR 0009 ties H.264 to MPEG-TS, and the server selects MPEG-TS for every codec except AV1 and HEVC.
Tests construct H.264/fMP4 decisions to check command lines and decoding, but those tests do not play the output in a real player.
The previous worker has never served H.264 in fMP4 in production.
The server's fMP4 container accepts every audio codec its MPEG-TS container accepts, plus FLAC, Opus and ALAC.
Apple's authoring rules require fMP4 for HEVC, AV1, FLAC and ALAC and permit either container for H.264.
MPEG-TS needs a workaround for copying multichannel AAC that fMP4 does not need.
ADR 0019 already decides that the worker retries a failed segment upload with bounded back-off.
Worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/1[#1] (transferred from streamarr-server issue https://github.com/streamarr/streamarr-server/issues/253[#253]) tracks that work, which the previous worker does not implement.
ADR 0019 also rejects Low-Latency HLS blocking playlist reload as the way a client waits for a segment.
The media layer of moq-dev, a Media over QUIC (MoQ) project, consumes keyframe-aligned fragments read from FFmpeg's standard output, the unit this decision produces.

The playback capabilities epic (issue https://github.com/streamarr/streamarr-server/issues/399[#399], with the vocabulary in ADR 0036) predates this decision, and several of its sub-issues touch the same ground.
Issue https://github.com/streamarr/streamarr-server/issues/66[streamarr/streamarr-server#66] adds keyframe timestamps to the probe.
With them the server can derive copy-mode segment boundaries, advertise real durations and seek to a boundary keyframe.
Issue https://github.com/streamarr/streamarr-server/issues/398[streamarr/streamarr-server#398] makes each worker advertise, per codec family, the encoder it will really use.
Issue https://github.com/streamarr/streamarr-server/issues/396[#396] with worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/25[#25] makes the video decision explicit and has the worker assert the produced output against it.
Worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18] tags HEVC output `hvc1`, and issue https://github.com/streamarr/streamarr-server/issues/497[streamarr/streamarr-server#497] closes libx265's GOPs so that every forced keyframe is an IDR frame.
The epic requires H.264 for every stream session until the client declares its codecs, so switching H.264 to fMP4 affects every stream session that exists at this point.
ADR 0036 distinguishes an attempt to dispatch a job from a format attempt, which tries another format.
A format attempt under issue https://github.com/streamarr/streamarr-server/issues/401[#401] is a new variant with its own initialization segment.
A replacement attempt serves the same variant and must keep that variant's initialization segment.
The server chooses workers for replacement attempts by source namespace alone.
Each worker chooses its encoder backend, the encoder it actually runs for a codec family, locally.
A replacement attempt can therefore run on a worker whose H.264 encoder writes different parameter sets.
fMP4 keeps those parameter sets in the initialization segment, whereas MPEG-TS carried them in-band with every keyframe.

== Decision

=== One producer per job attempt reads FFmpeg's standard output

The worker runs FFmpeg under `ProcessBuilder` and directs the mp4 muxer to write to `pipe:1` with `-movflags cmaf+delay_moov+skip_trailer+frag_keyframe+frag_discont`.
The FFmpeg arguments that this Decision sets form the recipe.
A producer module in the worker's `engine` package owns that process, reads its standard output and observes its exit.
The producer imports no gRPC protocol types.
Its reader is the loop that reads the pipe.
The producer parses top-level ISOBMFF boxes.
`ftyp` and `moov` form the initialization segment.
Each `moof` and the `mdat` that follows it form one fragment.
The worker change removes the HLS muxer, the output directory, the predicted file names, the directory poll and the liveness poll.
The server keeps generating every playlist (ADR 0008).
The worker sets no `min_frag_duration`, so a keyframe normally starts a fragment.
The worker sets `-frag_duration`, the fragmentation target, from its configuration.
The fragmentation target defaults to 250 ms.
The measurements in the Evidence appendix used a fragmentation target of 1 s unless they state another value.
The worker, not the muxer, decides where a segment ends.
The worker passes `-max_interleave_delta 10000000`, FFmpeg's default of 10 s, rather than inheriting it.
This interleave bound is how long the muxer holds one stream's packets while it waits for another stream's.
The <<decision-audio,closing rule>> relies on it, so an FFmpeg upgrade cannot change it silently.
The worker passes `-copyts -avoid_negative_ts disabled` and adds `-start_at_zero`.
The worker must also pass `-discard none` on every input.
Together these flags place media time zero at the source container's start time.
That start time is the first timestamp of the container's earliest stream.
On an MPEG-TS source, `-start_at_zero` alone measures media time zero from the earliest stream that the job attempt maps.
Two attempts that map different streams would then disagree on media time zero.
With `-discard none`, media time zero stays at the container's earliest stream, whatever streams the job attempt maps.
link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043] measured the shift on an MPEG-TS source.
Mapping English alone put media time zero 170.7 ms later than mapping all three of the source's languages.
The worker does not pass `-discard none` yet.
Every attempt uses this origin, whether it starts from zero or seeks into the source.
The producer keeps the timestamps that FFmpeg writes, with one exception.
The producer snaps copied audio with fixed-length frames to its codec's encoder frame grid (<<decision-audio,audio rule>>).
When it copies AAC audio, the worker adds `-bsf:a aac_adtstoasc`, because `delay_moov` stops the mp4 muxer from inserting that filter on its own.
When an attempt encodes video, the worker passes `-r:v:0` with the output frame rate (<<decision-frame-rate>>) and sets no `-fps_mode`.
It computes its frame-count GOP, the keyframe interval it gives the encoder in frames, from the same rate (<<decision-gop,GOP sizing>>).
FFmpeg's automatic mode then selects the constant-rate path.
Under `-copyts`, FFmpeg selects an internal variant of that path that keeps the first timestamp.
The pipe thus carries the HLS muxer's constant-rate frames.
Frame-count keyframes land on the period.
A seek does not pad from zero.
A test replays a recorded fixture and checks that output after a seek under these flags starts at the seek point, so an FFmpeg upgrade cannot silently change this behavior.
The worker refuses a video encode that carries no output frame rate with `JOB_ATTEMPT_FAILURE_INVALID_SPECIFICATION`, since it can neither pass a rate to `-r:v:0` nor count a GOP without one.
The server never dispatches such a job.
link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] decides how the server handles a stream session whose output frame rate the frame-rate rule refused.
Otherwise the server would spend ADR 0019's recovery budget dispatching jobs that every worker would refuse.

*Why:* `-copyts` alone put a source that begins at 12 s into segment 2 for a job asking for segment 0.
Explicit `cfr` padded 720 duplicate frames after a seek to 30 s.
A 250 ms fragmentation target completed a seek's first segment 0.16 s sooner than a 1 s target.
That figure is the median of 18 paired runs, with a range of 0.09 to 0.27 s.
The runs timed the encoder alone for a 1080p libx264 seek at the `faster` preset, with 3 s segments and the pinned FFmpeg 8.1.2.
A 100 ms target saved only 0.03 s more than a 250 ms target.
Parsing four fragments per media second instead of one cost under 0.1 % of FFmpeg's CPU time.
Evidence: <<evidence-channel>>, <<evidence-timeline>>, <<evidence-frame-rate>>, https://github.com/streamarr/streamarr-transcode-worker/issues/53[streamarr/streamarr-transcode-worker#53].

[[decision-frame-rate]]
=== The frame-rate rule chooses the output frame rate

The output frame rate is the rate at which every encode of a file's chosen video stream runs.
The frame-rate rule chooses the output frame rate.
The worker's probe job runs the rule once per file, as link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] records.
The rule picks from a list of standard rates.
The list holds 10, 12, 12.5, 15, 23.976, 24, 25, 29.97, 30, 47.952, 48, 50, 59.94 and 60 frames per second, each as an exact fraction.
For example, the list holds 23.976 as 24000/1001.

A video stream declares two rates: its average rate, `avg_frame_rate`, and its base rate, `r_frame_rate`.
When the two declared rates agree on a listed rate, the rule keeps that rate.
When a Matroska file carries per-stream statistics tags, those tags must also agree with that rate before the rule keeps it.

Otherwise the rule measures the motion rate, the frame rate at which the video's motion actually runs.
A packet scan reads the packet times of the first 30 s of media and measures the motion rate from them.
The scan trusts a timing pattern only when that pattern recurs.
The rule then snaps the motion rate to the list:

* A rate below 10 becomes 10.
* A rate from 60 to 60.3 counts as 60.
* Above 60.3, the rule divides the rate evenly down to a listed rate: 100 becomes 50, 90 becomes 30, 72 becomes 24 and 119.88 becomes 59.94.
* Otherwise the rule takes the nearest listed rate.

When the scan finds fewer than 2 frames, the rule snaps the average rate to the list instead.
When the average rate is not usable, the rule snaps the base rate.
The rule refuses to choose a rate only when the scan finds fewer than 2 frames and neither declared rate is usable.

The output frame rate stays an exact fraction from the probe to the worker's `-r:v:0` argument.
No step converts it to a decimal.

*Why:* The rule was modeled on the packet times of 1,622 video streams.
300 of them came from a library sample, 1,253 from FFmpeg's test suite and 69 from local sources.
The earlier rule snapped the average rate to the list.
Under the earlier rule, some variable-frame-rate MP4 and Matroska files dropped 9 to 70 % of their frames, because an output rate below the motion rate makes FFmpeg drop frames to keep a constant rate.
Under the frame-rate rule, those files drop no frames.
The frame-rate rule refuses 3 of the test-suite streams, against 13 under the earlier rule, and it refuses none of the library sample.
294 of the 300 library files keep their declared rate, so about 2 % of files need a packet scan.
On the six library files that needed a scan, the scan read 8 to 113 MB and took 58 to 336 ms with the files cached.
Evidence: https://github.com/streamarr/streamarr-transcode-worker/issues/24[streamarr/streamarr-transcode-worker#24].

[[decision-segment-list]]
=== Every variant of a stream session shares one segment list

A stream session's segment list gives the start of every media segment that the stream session's playlists advertise.
Segment `N`'s interval runs on the zero-based timeline from segment `N`'s start up to, but not including, segment `N + 1`'s start.
The last segment's interval runs to the end of the media.
Every variant of the stream session shares the segment list.
The segment list is the one boundary rule for the whole system.
The server's playlists, the worker's forced keyframes and the producer's grouping all follow the same segment list.

Encoded variants use 3 s media segments.
A slot is one 3 s step of media time, so slot `k` covers `[k × 3 s, (k + 1) × 3 s)`.
A stream session that only encodes uses the plain 3 s grid as its segment list, so segment `N` starts at `N × 3 s`.
A stream session with a copied variant builds its segment list from 3 s slots once the source's keyframe positions are known.
In that segment list, a slot that holds no source keyframe merges into the segment before it.
A merged segment therefore spans several slots.
A stream copy advertises each segment's real duration.
The stream session's encoded variants place their keyframes at the segment list's starts.
In a stream session with merged segments, the server sends the segment list's starts with each job attempt, so that the worker forces keyframes and groups samples on the server's list.
Once merged segment lists arrive, every stream session therefore uses 3 s slots.
The period is a stream session's slot length: 3 s, or 6 s in a stream session that keeps 6 s segments under the interim rule below.
On a plain grid, segment `N` starts at `N × period`.

AVPlayer on the Apple TV 4K playing 3 s segments is the merge gate for 3 s segments (issue https://github.com/streamarr/streamarr-server/issues/504[streamarr/streamarr-server#504]).
Streamarr predefines no fallback length.
If the merge gate fails, further research chooses the segment length.

The server offers a stream copy only once it knows the source's keyframe positions (ADR 0032), and the server encodes the video until then.
A stream copy uses those keyframe positions for its segment boundaries, its playlist durations and its seeks.

Merged segment lists arrive with issue https://github.com/streamarr/streamarr-server/issues/512[streamarr/streamarr-server#512].
Until then, an interim rule chooses each stream session's segments:

* A stream session whose every variant is a stream copy keeps 6 s segments on the plain 6 s grid.
* A stream session with any encoded variant uses the plain 3 s grid.
* The server offers a stream copy only when every interval of the stream session's grid holds a source keyframe, except the final interval.
Otherwise the server encodes that variant instead.
In a stream session with an encoded variant, the server therefore encodes the copied variant when the source's keyframes do not fit the 3 s grid.
* When the grid's final interval holds no source keyframe, that interval joins the segment before it in every variant of the stream session.
The stream session then advertises one segment fewer than the grid holds, and its last segment runs to the end of the media.
That last segment can last up to twice the period: 12 s on the 6 s grid and 6 s on the 3 s grid.
The playlist's target duration covers that segment, as RFC 8216 requires.

*Why:* 3 s segments let a player start and seek sooner, because the producer encodes half as much media before the segment that the player waits for is complete.
With 1080p libx264 at the `faster` preset, the decode-only early-start seek (<<decision-seek>>), the pinned FFmpeg 8.1.2 and 1 s fragments, a seek completed its first segment 1.28 s after FFmpeg started at 3 s segments, against 1.95 s at 6 s segments.
Each of those figures is the median of 12 runs on two open-license films, and the runs timed the encoder alone.
macOS AVPlayer also played against a fixture server that released each segment when a modeled producer would finish that segment.
That fixture server listed 480p first and served over a 10 Mb/s link, with 3 sessions per cell.
There, playback started in 1.18 s at 3 s segments against 1.68 s at 6 s segments, and a far seek took 3.03 s against 4.94 s.
AVPlayer made no error, abandoned no request and never rebuffered in its 51 sessions at 3, 4 and 6 s segments.
macOS AVPlayer abandons a segment request when no byte has arrived after one target duration, so at 3 s segments the server must hold every segment request for less than 3 s.
The merge gate checks that risk on the Apple TV, a primary client.
A stream copy's segments can start only at source keyframes.
On a plain 3 s grid, more sources would therefore leave an interval without a keyframe, and the server would encode those sources instead of copying them.
Merged segment lists let every stream session use 3 s slots without encoding more sources.
The interim rule exempts the final interval because AAC priming can carry an ordinary source just past a period boundary.
An AAC encoder adds priming samples, so a container runs about 23 ms longer than its video.
FFmpeg's `lavfi` test source, given 36 s of video and AAC audio, makes a file that measures 36.023 s.
That file's final 6 s grid interval runs from 36 s to 36.023 s and holds no keyframe.
Without the exemption, the server would encode that file although every full interval holds a keyframe.
Streamarr adopts the exemption to learn how players handle the longer last segment, and will revisit it if players mishandle that segment.
Evidence: https://github.com/streamarr/streamarr-server/issues/504[streamarr/streamarr-server#504], https://github.com/streamarr/streamarr-server/issues/512[streamarr/streamarr-server#512], https://github.com/streamarr/streamarr-server/pull/534[streamarr/streamarr-server#534].

=== Every encoder forces the boundary keyframes from a list

The worker forces a keyframe at every segment boundary for every encoder, including SVT-AV1 and the hardware encoders that the previous worker controls through a frame-count GOP alone.
The worker continues to disable scene-cut keyframes for libx264 through `-sc_threshold`.
Issue https://github.com/streamarr/streamarr-server/issues/497[streamarr/streamarr-server#497] will set libx265's scene-cut behavior along with its other GOP arguments.
A scene-cut keyframe adds another keyframe inside an interval, and the producer groups that keyframe's fragment into the same segment.
FFmpeg's `-force_key_frames` has two modes: a list of absolute times, or an expression evaluated against the time since the attempt's first frame.
The worker forces the boundaries with the list, never an expression.
`-force_key_frames:0` receives the start of every segment from the start sequence number up to, but not including, the variant's media segment count.
On a plain grid, segment `k` starts at `k × period`, in whole seconds.
Every attempt thus forces the same frame at each boundary it shares with another attempt.
FFmpeg chooses the first frame at or after that boundary on the zero-based timeline.
The list starts at the start sequence number, because FFmpeg consumes at most one entry per frame and would force an extra keyframe for each entry before the attempt's first frame.
The worker ends the list early at the last entry that keeps the argument within Linux's per-argument limit.
The server sends the count on every job attempt in `TranscodeExecution.media_segment_count`, a new, additive field number 5.
The server computes this count with the same code that counts the playlist's `EXTINF` entries.
On a plain grid, that code converts the probed duration to whole milliseconds, divides it by the period expressed in milliseconds, and rounds the quotient up.
With merged segments, the count is the number of segments in the segment list.
Zero is not a valid count, and it is also what the worker reads from a server that omits the field.
The worker refuses a job whose count is zero, or whose start sequence number is not below its count, with `JOB_ATTEMPT_FAILURE_INVALID_SPECIFICATION`.
Such a job asks for a segment the playlist does not advertise, and in a video encode (`VIDEO_TRANSCODE` or `FULL_TRANSCODE`) its list would be empty, which FFmpeg's option parsing rejects.
The worker keeps no expression as a fallback, because Streamarr has no production instances.

*Why:* Under an expression, 202 of 360 shared boundaries fell one or two frames apart.
Under the list, none of 372 shared boundaries differed.
A list from zero reaches the argument limit only after 22,463 boundaries at a 3 s period, or 18.7 hours.
At a 6 s period, it reaches the limit after 21,370 boundaries, or 35.6 hours.
Evidence: <<evidence-keyframe-list>>.

[[decision-gop]]
=== The worker extends the GOP only for keyframe-verified encoders

To verify an encoder's keyframes, record this recipe under the pinned FFmpeg (ADR 0029) at a fractional frame rate, both from the start and after a seek.
An encoder is keyframe-verified only when the recordings show all three behaviors:

* Every forced keyframe comes out as a sync sample.
* The encoder restarts its GOP count at each forced keyframe.
* Every forced keyframe starts a closed GOP, as does the keyframe the GOP places when a recording deliberately suppresses one forced keyframe.

A keyframe starts a closed GOP when no later frame in decode order references a frame before it.
The keyframe's picture type must guarantee this independence.
The keyframe must be an H.264 or HEVC IDR picture, or a shown AV1 key frame.
An HEVC CRA picture may be followed in decode order by RASL pictures, which precede it in presentation order and reference the GOP before it.
A decoder that starts at a CRA picture must discard them, so a segment that starts there does not decode on its own.
A CRA picture never qualifies, even when no RASL picture follows it.
The encoder may place RASL pictures after any CRA picture.
The mp4 muxer marks the CRA picture as a sync sample in both cases.
libx264 and SVT-AV1 are keyframe-verified.
`h264_videotoolbox` and `hevc_videotoolbox` are keyframe-verified with B-frames off.
With B-frames on, neither encoder is keyframe-verified.
SVT-AV1 stays keyframe-verified despite upstream bug https://gitlab.com/AOMediaCodec/SVT-AV1/-/work_items/2385[#2385] in the pinned runtime (worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/42[#42]), because that bug stalls or reorders output rather than dropping a forced keyframe.
The stall watchdog of the <<decision-waits,four waits>> and the short-sample rule for <<decision-untrusted-output,untrusted output>> fail each affected attempt so that the server can replace it under ADR 0019.
Worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/42[#42] will update the selected runtime to a version that includes the fix.
libx265 is not keyframe-verified.
Under its default open GOP, its forced keyframes are CRA pictures.
When a recording suppressed a forced keyframe, libx265's GOP placed a CRA picture that was followed by a RASL picture.
libx265 qualifies only after its GOPs are closed under issue https://github.com/streamarr/streamarr-server/issues/497[streamarr/streamarr-server#497] and a new recording shows that both its forced keyframes and its GOP's backstop keyframe are IDR pictures.
Every other hardware encoder must pass the same recording checks before it is keyframe-verified (<<decision-hardware-encoders>>).

The worker sets each encoder's frame-count GOP by whether that encoder is keyframe-verified.
For a keyframe-verified encoder, the worker multiplies the period by the output frame rate, rounds the result up, and adds one frame to obtain the extended GOP.
On a plain grid, that GOP never fires while forcing works, and if a forced keyframe were dropped it would place a keyframe one or two frames later, inside the same interval.
A merged segment spans several slots, so that GOP can place keyframes inside a merged segment, between the segment list's starts.
Those keyframes start no segment, because the worker groups samples on the server's segment list.
For every other encoder, the worker multiplies the period by the output frame rate and rounds the result down to obtain the floored GOP.
Even if the encoder ignores forced keyframes, that GOP still places one keyframe inside every interval and never skips a segment.
Under the floored GOP every segment holds at least one keyframe, and most hold two.
The floored GOP keeps a keyframe in every interval for libx265 but does not close its GOPs.
Closing those GOPs requires the changes tracked by issue https://github.com/streamarr/streamarr-server/issues/497[streamarr/streamarr-server#497].
Past the list's last entry, only the GOP places keyframes.
The floored GOP still puts a keyframe in every interval.
With the extended GOP, keyframes drift away from the segment starts until an interval holds no keyframe.
The producer then fails the attempt with `SKIPPED_SEGMENT_NUMBER` (<<decision-grouping,grouping>>).
The server dispatches a replacement attempt from the skipped segment under ADR 0019, and that attempt starts a new list at the skipped segment's boundary.

*Why:* The floored GOP added a second keyframe beside the forced one at 13 of 15 boundaries.
The extended GOP produced only forced keyframes in all twelve runs.
libx265's backstop was a CRA picture followed by RASL pictures in three of four recordings.
The VideoToolbox encoders were recorded on an Apple M1 Max with macOS 26.6.2 and FFmpeg 8.1.2 for macOS on arm64, from the start and after a seek, at 23.976 and 29.97 fps.
With B-frames off, every forced keyframe in 176 recordings was a sync sample: 4,155 of 4,155 for H.264 and 4,345 of 4,345 for HEVC.
Each of those keyframes was an IDR picture with no leading pictures, and each encoder restarted its GOP count there.
With `-bf 2`, HEVC's forced keyframes became CRA pictures followed by RASL pictures.
VideoToolbox also placed IDR keyframes of its own at frames that differed between attempts, and none of them displaced a forced keyframe.
Evidence: <<evidence-gop>>, <<evidence-svt-av1>>, https://github.com/streamarr/streamarr-transcode-worker/issues/57[streamarr/streamarr-transcode-worker#57].

[[decision-hardware-encoders]]
=== Hardware encoder backends join one at a time, after three checks

Streamarr adds hardware encoder backends one at a time.
NVENC (https://github.com/streamarr/streamarr-transcode-worker/issues/56[streamarr/streamarr-transcode-worker#56]) and VideoToolbox (https://github.com/streamarr/streamarr-transcode-worker/issues/57[streamarr/streamarr-transcode-worker#57]) are added now.
The VAAPI, QSV, AMF and RKMPP encoders stay deferred to https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14] until hardware exists to verify them.
A worker encodes with a hardware encoder backend only after that backend passes three checks:

. The backend's recordings pass the keyframe recording checks (<<decision-gop>>), so the backend joins the keyframe-verified list.
. Every job attempt on the backend with the same encoder settings writes a byte-identical initialization segment.
. The backend's initialization segments pass the worker's output check (https://github.com/streamarr/streamarr-transcode-worker/issues/25[streamarr/streamarr-transcode-worker#25]).
Each initialization segment carries the codec string, codec profile, level and tier that the job decided.

No worker encodes with VideoToolbox before two more checks pass.
A timing check measures how long each VideoToolbox encoder takes to complete a seek's first media segment at the chosen segment length.
A second Mac must write the same parameter sets (SPS and PPS) as the first Mac for the same encoder settings.

*Why:* The server serves a variant's stored initialization segment with every later attempt's segments, so a backend whose initialization segment changes between attempts breaks replacement attempts.
The output check stops a backend from writing a codec string, profile, level or tier that differs from what the playlist advertises.
VideoToolbox's recordings made no timed runs, and only one Mac was measured.
The parameter sets depend on the encoder's settings, and `-realtime 1` alone changed the H.264 SPS and the HEVC VPS, SPS and PPS.
Evidence: https://github.com/streamarr/streamarr-transcode-worker/issues/56[streamarr/streamarr-transcode-worker#56], https://github.com/streamarr/streamarr-transcode-worker/issues/57[streamarr/streamarr-transcode-worker#57].

[[decision-independent-segments]]
=== Keyframe-verified variants carry `EXT-X-INDEPENDENT-SEGMENTS`

The `EXT-X-INDEPENDENT-SEGMENTS` tag tells a player that it can decode each media segment without the segments before it.
The tag is true only when every media segment starts with a keyframe that opens a closed GOP, as a keyframe-verified encoder's segments do.
The server writes the tag in the multivariant playlist when every video variant of the stream session comes from a keyframe-verified encoder.
Otherwise the server writes the tag only in the media playlists of the variants that come from a keyframe-verified encoder.
A stream copy never carries the tag, because a source keyframe can open a GOP whose pictures reference earlier pictures.
A variant from libx265 does not carry the tag while libx265 is off the keyframe-verified list.

*Why:* Without the tag, Safari's native player also requested the two segments before a seek target.
With the tag, it requested only the segment that holds the target.
A test server released each segment when the measured libx264 encode speed would have produced that segment.
The test used a 10-core arm64 host, a four-variant ladder and a 25 Mb/s link, and each figure is the median of 3 sessions.
With the tag, Safari's native seek fell from 11.0 s to 6.9 s at 6 s segments, and from 5.8 s to 3.9 s at 3 s segments.
AVPlayer's seeks did not change, and neither did hls.js at 6 s segments.
At 3 s segments, the tag moved hls.js's share of time at 1080p in both directions, and no one found a cause.
Apple's HLS authoring specification asks for the tag in the multivariant playlist (item 9.11).
When the multivariant playlist lacks the tag, item 9.12 requires it in each media playlist whose segments are independent.
A tag on a variant whose segments are not independent would let a player start decoding in the middle of a GOP.
Evidence: https://github.com/streamarr/streamarr-server/issues/398[streamarr/streamarr-server#398].

[[decision-seek]]
=== Encoded replacement attempts use the decode-only early-start seek

Preroll is media that an attempt's seek emits before the attempt's first media segment.
The producer discards preroll because this media belongs to earlier segments.
A stream-copy seek emits preroll because it lands on the keyframe at or before its target.
A stream-copy attempt targets its first segment's own first source keyframe, which the stored keyframe positions give (issue https://github.com/streamarr/streamarr-server/issues/66[streamarr/streamarr-server#66]).
A junction is a boundary where one attempt's segment follows another attempt's segment.
A replacement attempt's first junction is where its first segment follows the start-0 attempt's segment before it.

An attempt that encodes video with a start sequence number above zero uses the decode-only early-start seek.
The server chooses the source keyframe that the attempt reads from.
That keyframe is the last source keyframe at or before the first segment's start minus 0.5 s.
The server finds that keyframe in the stored keyframe positions.
The server sends that keyframe's decode time as the job's seek position, or a position a margin before that decode time.
The server sends the decode time rather than the presentation time, because a keyframe's presentation time can lie after its decode time.
The demuxer then starts reading at that keyframe in every container.
The job's seek position has sub-second precision.
The worker reads from the seek position with `-noaccurate_seek`.
The worker treats an MPEG-TS source like every other source.
The worker decodes the media from that keyframe up to the first segment's start, but the worker does not encode that media.
The attempt thus feeds its encoder the same source frames as the start-0 attempt from its first segment's start onward.
The server no longer sends the requested segment's boundary as the seek position.
The worker no longer computes a seek position of its own.

A file without a usable container index has no stored keyframe positions until its keyframe scan finishes (link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032]).
Until that scan finishes, the server sends a fixed, generous read-back instead of a keyframe.
The read-back is a seek position a fixed distance before the first segment's start.
The worker decodes the media from that seek position up to the first segment's start, and the worker does not encode that media either.

*Why:* A seek to the boundary itself can lose the frame that the start-0 attempt repeats there, and can land late on an MPEG-TS source.
Such a seek put 20 of 36 recorded replacement attempts one or two frames off and left an audio gap that stalled Chromium with hls.js.
A recorded variable-frame-rate MP4 has no frame between 23 s and 31 s.
An accurate seek to 24 s discarded the frame at 23 s and started segment 5 at 31.031 s.
A `-noaccurate_seek` read from the source keyframe at 22.022 s passed the frame at 23 s to the encoder and forced segment 5's keyframe at 30.030 s, as the start-0 attempt did.
The earlier seek one period early also aligned every recorded junction, but that seek encoded a whole period that the producer then discarded.
With 1080p libx264 at the `medium` preset and 6 s segments, the decode-only early-start seek completed its first segment about 3.0 s after FFmpeg started.
The seek one period early took about 5.0 s.
The paired difference was −2.00 s over 18 seeks, on two open-license films with three seek points each and 1 s fragments, timing the encoder alone.
That time matters because macOS AVPlayer, against a fixture server, abandoned a segment request when no byte had arrived after one target duration.
Evidence: <<evidence-early-seek>>, https://github.com/streamarr/streamarr-server/issues/502[streamarr/streamarr-server#502].

[[decision-hardware-decode]]
=== Seek attempts decode in hardware behind a leading-picture filter

A seek attempt is a job attempt whose start sequence number is above zero.
A seek attempt that encodes video decodes the source in hardware: on VideoToolbox on macOS, and on NVDEC on Linux.
A keyframe's leading pictures follow the keyframe in decode order but precede the keyframe in presentation order, and leading pictures can reference pictures before the keyframe.
A leading-picture filter runs on the compressed packets before the hardware decoder.
The filter drops the leading pictures of the keyframe at which the seek starts reading.
The filter treats the first keyframe that the demuxer delivers as that keyframe.
The filter keeps every packet that carries no presentation timestamp.
An attempt that starts at zero runs without the filter.
The worker decodes AVI sources in software.
The worker also decodes in software any codec that the hardware decoder lacks or decodes wrongly.
MPEG-4 Part 2 is such a codec on both platforms.
A worker without VideoToolbox or NVDEC decodes in software.
Hardware decode on Intel and AMD GPUs (QSV and VAAPI) stays deferred to https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14].

*Why:* After a seek onto an H.264 open-GOP keyframe, FFmpeg submits that keyframe's leading pictures, which reference the GOP before the keyframe.
VideoToolbox rejected one such picture and then every non-I picture until a keyframe without leading pictures arrived, so up to 240 frames went missing.
With the filter, VideoToolbox decoded 146 of 146 junctions frame-exact with no decoder error, and 696 of 696 open-GOP seeks.
A DVD VOB file, and an MPEG-TS file that stamps a presentation time only on keyframes, carry packets without a presentation timestamp.
On those sources, a filter that dropped such packets kept 11 of 1,742 frames.
At the start of one of FFmpeg's test samples, the filter dropped 2 leading B pictures that the decoder could decode, so an attempt that starts at zero runs without the filter.
NVDEC's H.264 and HEVC output was bit-identical to software decoding, with 0 of 32,633 frames different, so attempts decoded either way join exactly.
PSNR, the peak signal-to-noise ratio, measures how close one picture is to another, and a higher PSNR means a closer match.
NVDEC decoded MPEG-4 Part 2 without an error, but its B pictures averaged 31.9 dB PSNR against software decoding over 479 B pictures, and the worst B picture scored 15.4 dB.
VideoToolbox cannot decode MPEG-4 Part 2.
The filter never drops a packet in an AVI file, so open-GOP H.264 in AVI still failed on VideoToolbox in 5 of 8 seeks.
On an Apple M1 Max with FFmpeg 8.1.2 for macOS, one 1080p replacement attempt that encoded with `h264_videotoolbox` used 0.84 to 0.97 s of CPU with hardware decoding and the filter, against 4.26 to 4.28 s with software decoding.
On an RTX 5090 with the pinned worker image's FFmpeg 8.1.2, hardware decoding cut one 1080p libx264 attempt's CPU time from 19.26 s to 16.47 s, as the median of 5 runs.
Evidence: https://github.com/streamarr/streamarr-transcode-worker/issues/55[streamarr/streamarr-transcode-worker#55].

[[decision-grouping]]
=== A segment's video opens at the first keyframe at or after its boundary

Segment `N` covers its interval in the stream session's segment list (<<decision-segment-list>>), exactly as the playlist defines it, for the initial attempt and every replacement attempt.
Segment `N` opens at the first video keyframe at or after segment `N`'s start, inside one of FFmpeg's fragments if need be.
That keyframe must lie inside the segment's interval.
A stream copy cannot produce a segment whose interval holds no keyframe.
The server applies the same rule to the stored keyframe positions (issue https://github.com/streamarr/streamarr-server/issues/66[streamarr/streamarr-server#66]).
A stream copy's playlist therefore advertises each segment's real duration, and a stream-copy seek starts at its first segment's own first keyframe.

The producer reads every sample of the video track and the sound track.
For each sample it reads the decode time, the duration, the size, the flags, the composition offset and the sample's bytes in the `mdat`.
Those facts come from each `trun` entry, with the `tfhd` and `trex` defaults for any value the entry omits.
A track's first decode time is the `tfdt`, read as a signed 64-bit value, because the first audio `tfdt` is the unsigned wrap of a negative time.
A sample's presentation time is its decode time plus its composition offset, in the track's timescale, with no edit list applied.
A `trun` of version 1 carries signed composition offsets, and a `trun` of version 0 carries unsigned ones.
Whether a video sample is a sync sample, a keyframe, comes from its flags.
Every audio sample is a sync sample, and an audio sync flag never opens a segment.
The producer never compares a raw `tfdt` with a segment's start.
It never places a segment boundary at a fragment's end computed from its sample durations.

Video is grouped by keyframe, not by fragment.
A keyframe opens the segment whose interval contains its presentation time, unless that segment is already open.
A non-sync video sample always joins the open segment, because a segment can only begin at a video keyframe.
When a keyframe opens a segment in the middle of a fragment, the video samples before it belong to the segment it closes.
A segment's video is therefore every video sample from its opening keyframe up to the keyframe that opens the next segment, in arrival order.
A fragment without a video track adds no video, and its audio samples follow the <<decision-audio,audio rule>>.
The producer discards video samples whose segment number is below the start sequence number, because they are preroll and their segment belongs to another attempt.
A segment that runs past its interval is not itself a failure.
A stream copy's playlist advertises the real duration of each such segment.

The producer fails the attempt with the named reason `SKIPPED_SEGMENT_NUMBER` when a keyframe skips a segment number.
The attempt's output then holds no keyframe inside the skipped interval, so this attempt can never deliver that segment.
In a stream copy the source has no keyframe inside the skipped interval, so no replacement attempt can deliver the missing segment.
An encode skips a number only when its keyframes drift away from the segment starts, past the end of its list or through an encoder fault.
The replacement attempt from the skipped segment forces a keyframe there.
The producer detects the skip when it reads the keyframe that follows the skipped interval.
The video samples before that keyframe in its fragment still join the open segment.
The producer adds neither that keyframe, nor any video after it, nor any sample of a later fragment to a segment.
The audio samples of that keyframe's fragment still join the segments whose intervals hold their start.
The skip closes the open segment and every segment still waiting for its audio.
The producer delivers those segments, in order, before it records the failure.
Each of them is correctly numbered, and its video is complete.

*Why:* Grouping every keyframe's fragment by absolute time reproduced the HLS muxer's cuts on all three fixtures: the NTSC copy, the irregular copy and the variable-frame-rate encode.
A fixed `min_frag_duration` gave 7 and 9 fragments for 11 segments on the last two.
At a 1 s target the muxer cut at the first packet after the target, with measured fragment spans of 1.001 s for H.264 and 1.033 s for SVT-AV1.
The closing fragment therefore follows the boundary by about one target in media time rather than one whole segment.
In a stream-copy replacement attempt with encoded audio, FFmpeg's first fragment ran from 28.028 s and held the boundary keyframe at 30.030 s as its 49th sample.
Grouping by whole fragments started segment 5 at 32.032 s and left a 2 s hole, and opening at that keyframe closed the hole in every player.
Evidence: <<evidence-grouping>>, <<evidence-keyframe-inside>>.

[[decision-audio]]
=== Each audio sample joins the segment whose interval holds its start

An audio sample belongs to the segment whose interval holds its presentation time, whichever fragment carried it.
On a plain grid, that segment is `floorDiv(presentation time, period × timescale)`.
FFmpeg's fragments do not respect the grid for audio.
libx264 output carries the audio just before a boundary in the fragment that opens the next segment.
SVT-AV1 output without B-frames carries the audio just after a boundary in the last fragment of the segment before it.
The producer therefore holds an audio sample for a later segment until it closes that segment.
Audio before media time zero is dropped in audio renditions (for AAC, the priming frame).
Multiplexed variant segments keep that audio.
In a multiplexed variant, an attempt whose start sequence number is 0 therefore keeps the AAC priming frame in segment 0.
link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043] states both rules in the same words.
In every other attempt, an audio sample below the start sequence number is preroll, and the producer discards it.
When the output ends, the last segment also takes every audio sample after its interval.
A late audio sample is one that arrives after the producer has closed its segment.
The producer drops a late audio sample, counts it and continues the attempt.
It never moves a late sample into a later segment.
The producer fails the attempt with the named reason `PRESENTATION_TIME_REGRESSED` when an audio sample starts before the audio sample that arrived before it.

The producer snaps copied audio with fixed-length frames to its codec's encoder frame grid.
The encoder frame grid holds the frame start times that FFmpeg's own encoder for the same codec writes on media time.
The snap moves the whole track by one constant amount.
The producer does not snap copied audio whose frames vary in length, such as FLAC with variable block sizes.

Segment `N`'s end is segment `N + 1`'s start, which is `(N + 1) × period` on a plain grid.
Open segment `N` closes once a keyframe at or after segment `N`'s end has arrived and either of two facts holds:

* An audio sample has arrived whose presentation time is at or after segment `N`'s end.
* The decode end of the latest video sample has run past segment `N`'s end by 1 s plus the video's lead.

When the initialization segment declares no sound track, the keyframe alone closes the segment.
End of file closes every segment still open or waiting for its audio.
While the audio lasts, an audio sample shows how far the audio has arrived.
A fragment without audio past a boundary does not show that the audio before that boundary has all arrived.
FFmpeg writes no sign that one stream has ended before the whole input ends.
Once the audio ends, only the video shows how far the audio has arrived.
Within the interleave bound, the muxer writes each audio sample beside the video around it.
The muxer interleaves the streams on the input's decode times.
With B-frames, the mp4 muxer shifts the video's output decode times by the encoder's reordering delay.
The video's decode end therefore leads the audio beside it by that delay.
The video's lead is the most that the decode end of the latest video sample has run ahead of an audio sample that the producer holds, at the moment that sample arrives.
A dropped late sample or a preroll sample does not count.
The 1 s margin covers the remaining interleaving lag and one fragmentation target.
Once the audio stops, the muxer holds the video for up to the 10 s interleave bound while it waits for audio.
The worker's 1 s margin follows that wait.
The 1 s margin is a safety net, because every stream that the probe shows ending early is padded (<<decision-early-ends>>).
The fragmentation target measurably shortens the lag before the closing keyframe arrives, but it is a target, not a guarantee.

*Why:* Placing audio by the fragment that carried it made a stream-copy replacement attempt from an MPEG-TS source repeat ten AAC frames (213 ms) that the previous segment already held.
Chromium then dropped 7 video frames at that junction in every run.
Placing each sample by its start removed that overlap, and Chromium lost no frame there.
A copy whose AAC frames outlast its video frames wrote a keyframe fragment without audio at 6.006 s and an audio sample from 5.964 s in the next fragment.
Apart from an audio encoder's final frames, an audio sample trailed the video written before it by at most 0.162 s in every recording.
That figure includes the video's lead, which was two frames, 0.083 s, in most recordings at 23.976 fps.
A stream copy of a source with one frame per second and libx264's B-frames put the video's decode end 2 s ahead of the audio beside it.
With the 1 s margin alone, the attempt dropped 47 audio samples, about 1 s of audio that had not ended.
With the video's lead added to the margin, the attempt dropped none.
With the margin, the segments after a 20 s audio track's end arrived at the same pace as with the previous producer, which never waited for audio.
An AAC encoder emits a frame only once it receives the next input, so FFmpeg flushes its last two frames only when the whole input ends.
In a 180 s encode whose audio ended at 20 s, those two frames arrived at 169 s, long after their segment was delivered.
With the video copied, the muxer stops holding the video 10 s after the audio's last packet.
Between 8 and 29 more AAC frames, about 0.2 to 0.6 s, then arrived late, and the count varied from run to run.
No margin short of the whole output covers either case.
In a measurement of switches between AAC audio renditions, copied AAC from a Matroska file started 16 samples off the encoder's grid.
Without the snap, those switches moved the audio offset by −46 to +60 ms.
With the snap, the offset stayed within −12 to +9 ms, about the measurement's own ±10 ms jitter.
For typical sources the snap moves a track by under 0.7 ms.
For audio that starts in the middle of a codec frame, the snap moves the track by at most half a frame: 10.7 ms for AAC, and 16 ms for AC-3 and E-AC-3.
Both amounts lie inside the ITU-R BT.1359 and EBU R37 tolerances for the timing of sound against picture.
Evidence: <<evidence-one-fragment>>, <<evidence-early-audio>>, https://github.com/streamarr/streamarr-server/issues/503[streamarr/streamarr-server#503].

[[decision-one-fragment]]
=== Each media segment is delivered as one `moof` and one `mdat`

The producer rebuilds every media segment from its samples.
It never concatenates FFmpeg's fragments into a segment.
The rebuilt segment is one `moof` followed by one `mdat`.
The `moof` holds an `mfhd` and then one `traf` for each track with samples in the segment, video first.
The `mfhd` sequence number derives from the segment number alone, never from a counter local to the attempt.
Identical input therefore gives identical bytes in every attempt.
Each `traf` holds a `tfhd` with `default-base-is-moof`, a version 1 `tfdt`, and a version 1 `trun` with a data offset.
The `trun` gives every sample its own duration, size, flags and composition offset.
The `mdat` holds the samples in that order, each track's samples in decode order.
The priming frame's negative `tfdt` is written as FFmpeg writes it, as the 64-bit two's complement.
The rebuilt samples keep FFmpeg's bytes, composition offsets and sync flags.
The rebuilt samples also keep FFmpeg's decode times and durations, except for copied audio with fixed-length frames, which the producer snaps to its codec's encoder frame grid.
The initialization segment passes through unchanged, with one exception: the worker removes the SEI arrays from every `hvc1` decoder configuration record (https://github.com/streamarr/streamarr-transcode-worker/pull/80[streamarr/streamarr-transcode-worker#80]).
A copy's record can otherwise hold SEI messages from the attempt's first keyframe, so two attempts that start at different keyframes would write different initialization segments.
The samples keep their SEI messages.
The segment cap applies to the rebuilt segment.

*Why:* Firefox treats each `moof` as its own media segment.
FFmpeg's segment 0 held six `moof` boxes, and its first audio sample is the priming frame at −1024 ticks.
Firefox resets its append state at the next audio frame, after it has inserted the first `moof`'s video.
It then drops the rest of the segment's video until the next keyframe, 6 s later.
With one `moof`, Firefox processes the whole segment's video before its audio, so the reset costs nothing.
Firefox with hls.js then started all 48 runs from 0 on MP4 sources, against none with FFmpeg's fragments.
Evidence: <<evidence-one-fragment>>.

[[decision-untrusted-output]]
=== The producer fails an attempt on output it cannot trust

The producer checks every box size against the segment cap before it allocates the box, and it fails the attempt on a box that exceeds the cap.
It fails the attempt with the named reason `TRUNCATED_OUTPUT` when the pipe ends inside a box header, inside a box body, or after a `moof` with no `mdat`.
In a video encode the producer fails the attempt with the named reason `SHORT_VIDEO_SAMPLE` when a video sample is shorter than half the nominal frame duration at the output frame rate.
It reads that duration from `trun` or from the `tfhd` and `trex` defaults.
Such a sample marks a packet whose decode time FFmpeg rewrote after the encoder emitted it out of order, and the segments may not decode even though FFmpeg exits 0.
A stream copy is exempt, because a variable-frame-rate source's own sample durations vary.
A short sample does not close the open segment, unlike a skipped segment number.
The fragment that holds the sample would join or close that segment, and the producer does not judge which samples of an out-of-order output still decode.
The replacement attempt therefore encodes that segment again.
Some failures lie in FFmpeg's output itself: it is truncated, malformed or over the segment cap, skips a segment number, or holds a short video sample.
When the producer detects one of these failures, or fails to read the pipe, it first checks whether a complete segment is already being uploaded.
If so, the producer lets that upload finish before it records the failure.
If the producer records a stop while it waits, the attempt stops instead.
The producer records a failed upload, a stall or an unexpected error at once and cancels any upload in flight.

*Why:* In the SVT-AV1 study, such a sample appeared only where FFmpeg logged a non-monotonic decode time.
In 2 of the 10 pinned-runtime failures, FFmpeg exited 0 with undecodable segments.
Evidence: <<evidence-svt-av1>>.

=== Each closed segment is uploaded once, under back-pressure

The producer holds the open segment in memory, bounded by the segment cap, together with any closed segment still waiting for its audio.
It starts a segment's upload only after it closes the segment.
The upload contract does not change.
The worker sends the metadata message with `content_length_bytes` before sending the chunks.
It then waits for the server to acknowledge the segment.
The worker sends the next chunk only when the gRPC stream reports `isReady`.
The reader admits a box only when the box's bytes and the output the producer already holds fit within the producer's budget of two segment caps.
It hands over a closed segment only once the server has acknowledged the previous one.
Otherwise the reader stops reading, and the pipe blocks FFmpeg.
The reader waits for room only while an upload is in flight, because only a delivery frees room.
When the next box does not fit and no upload is in flight, the producer fails the attempt at once with `SEGMENT_CAP_EXCEEDED`.
This back-pressure loses nothing.
The worker never skips or drops a fragment because the server has already advertised each segment to on-demand clients.

*Why:* MoQ's importer likewise skips no fragment.
For the tracks it publishes, the importer publishes every fragment or fails.
Only its live consumer skips a stale or missing group.
Evidence: <<evidence-channel>>.

=== An attempt completes only when four facts hold

An attempt completes only when four facts hold, in whatever order they arrive:

* The pipe reached end of file on a box boundary, with no `moof` still waiting for its `mdat`.
* FFmpeg exited with status 0.
* The server acknowledged every segment the producer closed, with no segment number skipped.
* The attempt is still active.

The producer fails the attempt when FFmpeg exits with a non-zero status, or when the server has not acknowledged every closed segment.
It also fails the attempt when the <<decision-waits,exit wait>> expires.
If FFmpeg exits with status 0 but produces no media segment, the attempt also fails, as it did with the previous worker.
A completed attempt means that FFmpeg finished cleanly and the server accepted everything FFmpeg produced.
The worker uses the media segment count to refuse a job that asks for no advertised segment, to end its list of forced keyframes, and to check whether the source ended before the last advertised segment.
When an encoded variant's source ends early, the worker pads the remaining advertised segments and reports the early end (<<decision-early-ends>>).
The worker still does not fail the attempt.
If a client requests an advertised segment that no attempt produced, the server's delivery coordinator starts recovery under ADR 0019.
The same rules apply when rounding the probed duration caused the playlist to advertise a final segment past the source's end.

[[decision-early-ends]]
=== Encoded output plays to the advertised end when a stream or the source ends early

These rules apply to a stream that the probe shows ending at least one segment before another stream of the same source.

* When an audio track ends at least one segment before the video, that audio track is encoded and padded with silence to the video's end.
The track is encoded even when the stream session copies the video.
An attempt that starts after the audio track's end encodes generated silence for that track.
Every attempt therefore carries the same tracks, and no playlist needs `EXT-X-GAP`.
An attempt that carries only generated silence writes the same initialization segment as the variant's other attempts, because the server's comparison stays strict.
* When the video ends at least one segment before the audio, the video is encoded and holds its last frame until the audio ends.
The video is encoded even when the stream session would otherwise copy it.

Padding every encoded attempt's audio stays rejected under Rejected Alternatives.

A source can also end before the media segments that the playlist advertises, for example when the file is shorter than its probe says.
When that happens, the worker fills an encoded variant's advertised segments past the real end with the last frame and silence.
Every advertised segment is served, and the player ends at the advertised end.
For an encoded variant, "source ended early" is a typed report, not a failure.
The attempt delivers every advertised segment, padded past the real end, and the report names the last segment that holds source frames.
The server never starts an attempt past that segment.
A padded segment answers a request past the real end.
When no padded segment is stored yet, the server starts an attempt at the last segment that holds source frames, and that attempt pads forward.

Padding past a source's real end applies to encoded variants only.
A stream copy cannot be padded in its own codec.
An encoded tail cannot join a stream copy either, because the server refuses an attempt whose initialization segment differs.
A copied variant that runs short is therefore a format error.
In Auto, the format recovery of https://github.com/streamarr/streamarr-server/issues/401[streamarr/streamarr-server#401] moves playback to an encoded stream session, which pads.
In Original, playback ends at the real end with an error.
ADR 0032 trusts a container index only when the probe can read the last keyframe that the index lists.
That check keeps a copy playlist from advertising past the real end, so this rule is a backstop.

*Why:* A count of each file's last packets covered a 300-file library sample.
In 10 of those files an audio track ended at least 3 s before the video, and in 5 it ended at least 6 s before the video.
Those thresholds are one segment at 3 s and at 6 s segments, and the gaps ran from 3.5 s to 24.9 s.
In 6 files of the same sample, the video ended at least 3 s before the audio, with gaps from 3.1 s to 237 s.
Without padding, AVPlayer ended playback where the multiplexed audio ended in 12 of 12 runs, and WebKit's native player did so in 8 of 8 runs.
That source was an 84 s video whose audio ends at 20 s, in 6 s segments.
In a 64 s video with 84 s of audio, no keyframe opened the segments after the video's end.
Answering 404 for those segments broke hls.js, AVPlayer and WebKit's native player.
With a padded source standing in for the worker, a held last frame played to 84 s in hls.js in four browsers, in WebKit's native player and in AVPlayer, with two runs each.
With audio renditions, AVPlayer played to the end with silence padding and with `EXT-X-GAP`, in 3 runs each, but `EXT-X-GAP` left hls.js stuck on the iPhone.
Evidence: https://github.com/streamarr/streamarr-server/issues/511[streamarr/streamarr-server#511].

=== A stop ends the attempt for good

A stop changes what the producer admits, not what the server has already committed.
When the worker stops an attempt, the producer records the stop under its own lock, then writes `q` to FFmpeg and cancels any upload in flight.
The reader then drains the pipe to end of file and discards everything it reads, including the partial fragment FFmpeg flushes on `q`.
The producer delivers nothing after a stop.
Canceling an upload does not roll back a segment that the server has already committed.
When the server commits a segment, its attempt fence decides whether to publish that segment (ADR 0019).
The stop's grace period specifies how long FFmpeg may take to exit after the worker writes `q`.
After writing `q`, the worker waits for FFmpeg to exit within that grace period.
If FFmpeg has not exited when the grace period expires, the worker sends SIGKILL and waits until the process exits.
The worker sends `JobAttemptStopped` only after it has observed the process exit, on both paths, so that message always means the process is gone.

The producer settles every outcome only after FFmpeg has exited and no upload is in flight.
The worker reports the outcome to the server only after the producer settles it, so no upload follows that report.
The worker settles an attempt's outcome once, under its own monitor.
The attempt keeps whichever outcome the producer records first.
A stop already in progress prevents the worker from also completing or failing the attempt, and the worker never reports a failure that the producer observes after the stop.
When the producer recorded that the attempt completed or failed before it recorded the stop, the worker answers `StopVariant` with that outcome instead of `JobAttemptStopped`.
If the worker has already reported that outcome, the stop draws no further message.
The worker can send messages for other attempts on its control stream while it waits for a stopped attempt's FFmpeg process to exit.
Each job attempt's messages stay in order, but the messages of different attempts do not.
A replacement attempt's `JobAttemptStarted` can reach the server before the `JobAttemptStopped` of the attempt it replaces.

*Why:* Draining the pipe lets FFmpeg finish its flush inside the grace period, where a pipe nobody reads would hold FFmpeg until the forced kill.

[[decision-waits]]
=== Four waits bound an attempt's progress

Four waits bound an attempt's progress, and a stop takes precedence over each.
Three have their own configured bounds, and the exit wait reuses the stop's grace period.

* An encoder-stall watchdog fails the attempt when no byte has arrived from the pipe within the stall threshold while the reader was reading.
It measures liveness only by bytes on standard output, never by standard error or by the process being alive.
When the watchdog fires, the worker sends FFmpeg SIGTERM and waits for the process to exit.
If FFmpeg has not exited when the stop's grace period expires, the worker sends SIGKILL and waits until the process exits.
* A readiness wait fails the upload when the gRPC stream has not reported `isReady` within its bound.
* For each upload, the worker starts the acknowledgment deadline when it sends the first byte.
The upload fails if the server has not acknowledged the segment when that deadline expires.
* An exit wait starts once the pipe has ended and the server has acknowledged the last segment.
FFmpeg must then exit within the stop's grace period.
This wait watches the process, not the pipe.
If FFmpeg has not exited when this wait expires, the producer fails the attempt with the named reason `PROCESS_DID_NOT_EXIT` and ends FFmpeg as it ends a stalled process.
If the output is truncated, the producer keeps the `TRUNCATED_OUTPUT` failure even if FFmpeg also exceeds the exit deadline.
A stop recorded during this wait takes precedence over both `TRUNCATED_OUTPUT` and `PROCESS_DID_NOT_EXIT`.

Back-pressure from the server therefore pauses the encoder-stall watchdog but never exempts the attempt from every bound.

*Why:* A blocking pipe read cannot time out on its own.
A hung FFmpeg keeps printing its progress line and exits on neither `q` nor SIGTERM.
The watchdog stops when the reader finishes reading the output, so only the exit wait catches an FFmpeg process that hangs after its last byte.
Evidence: <<evidence-svt-av1>>.

=== A producer and a worker each admit memory within a budget

Each producer holds at most two segment caps of FFmpeg's output plus one fixed scratch buffer.
It reserves each box's bytes against that budget before it allocates the box, and it never holds a whole fragment twice.
Before it builds the samples a `moof` describes, it also reserves a fixed heap cost for each of them against both budgets.
A `trun` can describe a sample in one byte, so counting box bytes alone would let a crafted source fill the heap.
Before it writes a rebuilt segment's `moof`, it reserves that `moof`'s bytes against both its own budget and the worker's budget.
When its own budget cannot hold that `moof`, the producer fails the attempt with `SEGMENT_CAP_EXCEEDED`.
The worker enforces the slot count it advertises.
A job that arrives while every slot holds an active job attempt fails with `JOB_ATTEMPT_FAILURE_STARTUP_FAILED` before FFmpeg starts.
`JOB_ATTEMPT_FAILURE_STARTUP_FAILED` says that this worker could not start the attempt.
`JOB_ATTEMPT_FAILURE_INVALID_SPECIFICATION` would instead say that no worker could run the job.
The contract has no failure value specifically for a worker whose slots are full.
The worker's segment memory stays within one worker-wide budget of the slot count times two segment caps.
Every producer counts against that budget until it releases its segments, even after the producer starts stopping.
FFmpeg's own memory, the kernel pipe buffer and gRPC's flow-control window sit outside that budget.
The container runtime bounds those resources.

*Why:* A hung FFmpeg can take the grace period and a forced kill to exit.
A burst of seeks can stop attempts faster than their FFmpeg processes exit.
Evidence: <<evidence-svt-av1>>.

=== Tests substitute the process

Tests substitute the process, not the producer.
Production uses `ProcessBuilder`.
The worker-session tests supply a scripted `Process`.
The real producer and its grouping and ordering rules run in every test.
Tests replay recorded fixtures to verify that the producer groups fragments by the stream session's segment list.
They compare every delivered sample with the recording's own samples: its bytes, decode time, duration, composition offset and sync flag.
A test checks that a stream-copy replacement attempt delivers exactly the start-0 attempt's bytes for every segment both deliver.
The fixtures README in the worker repository, cited in References, lists each recording and the behavior it verifies.

The recorder identifies the picture that starts each keyframe.
It reads the NAL unit type for H.264 and HEVC, and the frame header for AV1.
The tests therefore check that libx264 produces IDR pictures, SVT-AV1 produces shown key frames and libx265 produces CRA pictures in these fixtures.
Both the recorder and CI's check fail when a keyframe of a keyframe-verified encoder does not start a closed GOP.
For every fixture the recorder also runs the HLS muxer, records each segment whose cut differs from the segment list, and records why the cuts differ.
The HLS muxer's cuts are a comparison, not the reference.
CI reads the committed recordings, derives their expected results without running FFmpeg, and fails when a recorded expectation disagrees with the results derived from the bytes.
Smoke and image tests run real FFmpeg.
A smoke test runs more than 1000 one-second segments through each software encoder to show that no interval is ever skipped.
It runs SVT-AV1 at a parallelism of one so that upstream bug https://gitlab.com/AOMediaCodec/SVT-AV1/-/work_items/2385[#2385] cannot fail it.
The server's scripted FFmpeg test fixture writes a recorded fMP4 stream to standard output instead of writing segment files.

*Why:* The HLS muxer measures from the run's first packet, not from zero.
When the first packet carries audio, the pinned FFmpeg can interpret that packet's timestamp in video ticks rather than audio ticks.
Evidence: <<evidence-grouping>>.

=== HLS media segments are fMP4 only

The container no longer follows the codec.
The server serves every variant as multiplexed fMP4 in an HLS version 6 playlist with an `EXT-X-MAP` tag.
Multiplexed fMP4 carries a video `traf` and an audio `traf` in a single `moof`.
The output keeps the `cmaf` muxer flag as part of the measured recipe and claims no CMAF conformance.
CMAF restricts a track to one media type, so the flag does not make this output CMAF, and strict CMAF stays outside this contract.
H.264 moves from MPEG-TS to fMP4.
The server change removes the codec-to-container rule, the `.ts` code paths, the MPEG-TS audio rules and the multichannel-AAC copy workaround.
The 10 s timestamp offset that `-max_delay` causes in MPEG-TS output disappears with the container.
The worker rejects a job that requests `CONTAINER_FORMAT_MPEG_TS` and reports `JOB_ATTEMPT_FAILURE_INVALID_SPECIFICATION`.
The container stops being a decision.
The server's `ContainerFormat` type and the worker's counterpart type go away with MPEG-TS, their second value.
The segment extension, the playlist version, the `EXT-X-MAP` tag and the audio codec set become facts of HLS delivery rather than a choice per variant.
The explicit video decision of https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] carries no container.
The worker contract still carries its container field, and the server always sends fMP4.
Under ADR 0033's wire-compatibility rule, a later change may remove the field and reserve its number and name.
A future container would be a new decision, not a revived enum value.
The `hvc1` tag from https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18] applies to the mp4 muxer unchanged.
The producer's parser reads the sample entry from `moov`.
https://github.com/streamarr/streamarr-transcode-worker/issues/25[streamarr/streamarr-transcode-worker#25] should add the check here to confirm that the produced output matches the video decision.
Codec eligibility stays a client capability decision, and choosing fMP4 removes a packaging branch and adds no decoder.
Direct play never touches the worker, so this decision does not affect it.

Every attempt of a variant produces the same initialization segment, or init, so the server serves the stored init alongside every later attempt's segments, as ADR 0019 assumes.
A test checks that recorded fixtures contain byte-identical inits across a start-0 attempt and an attempt that seeks, for both encoded video and stream copy.
That identity holds only within one encoder backend, so a replacement attempt must run on the backend of the attempt that produced the init.
If a replacement attempt uploads an init that differs from the stored init, the server rejects the attempt with a named failure.
The server adds this comparison as part of this decision.
Every attempt that copies audio writes a byte-identical init.
The server's byte-for-byte comparison stays strict.
The comparison never ignores a field that FFmpeg treats as advisory, such as a bitrate field.
The worker contract does not need to change.
The server will restrict replacement attempts to the same backend when workers advertise their encoders (issue https://github.com/streamarr/streamarr-server/issues/398[streamarr/streamarr-server#398]).
The <<explicitly-deferred,deferred list>> records that work separately.
Once workers advertise their encoders, the server records the first attempt's backend on the variant and dispatches replacement attempts only to workers that advertise the same encoder for that codec family.

Before merging the server pull request, test fMP4 delivery with real players.
Play H.264 with stereo and 5.1 AAC, uninterrupted and across a replacement attempt, in the web player's hls.js, in WebKit natively and in AVPlayer.
Include segments whose inner fragments begin with non-sync samples, which the `-frag_duration` target produces, and a variable-frame-rate source encoded with SVT-AV1.
Use the previous worker's MPEG-TS output as the control.
For every combination of stream and player that passes with the MPEG-TS control, fMP4 delivery must also pass.
Use MPEG-TS for the control because the previous worker serves H.264 in MPEG-TS, and that delivery path hid a junction audio gap that fMP4 exposes.
Every real-player check that this decision requires also runs on the Apple TV 4K and on the SHIELD TV Pro, because both are primary clients.

*Why:* The encoded runs produced byte-identical inits across start 0 and seeks to 30 s and 60 s.
The stream-copy runs also produced byte-identical inits across those start points, but their init differed from the encoded runs' init.
In the server's player check the fMP4 stack and the MPEG-TS control each passed 210 of 234 runs, with matching results for every combination of stream and player.
The remaining failures are AV1 in WebKit and AVPlayer, which the test host's native decoders reject on both stacks.
With an earlier worker image, the server refused a seek in a stream session that copied AAC from an MPEG-TS source.
FFmpeg's advisory bitrate fields differed between the two attempts' inits.
Worker pull request https://github.com/streamarr/streamarr-transcode-worker/pull/50[streamarr/streamarr-transcode-worker#50] made those fields identical, and https://github.com/streamarr/streamarr-server/issues/502[streamarr/streamarr-server#502] adds the server's end-to-end test of that fix.
Evidence: <<evidence-init>>, <<evidence-players>>.

=== The producer delivers fragments to a protocol adapter

An adapter turns the producer's fragments into one delivery protocol's units.
The producer delivers the initialization segment first.
The producer then delivers each fragment with every sample of its video and sound tracks.
Each sample carries its decode time, presentation time, duration, flags and bytes.
A fragment may carry audio alone.
The HLS adapter opens each segment's video at its keyframe, places each audio sample by its start, rebuilds each segment as one `moof` and one `mdat`, and uploads it once.
A future MoQ adapter would run FFmpeg with `separate_moof` and a much smaller fragmentation target, as the moq-dev demo does.
It would publish each fragment as a frame within a group, behind the same producer interface.

=== Rollout

Merge the changes in this order:

. Merge the server change that adds `media_segment_count` to `TranscodeExecution` and sends it on every job attempt.
The previous worker ignores the new field, and the new worker refuses a job without it.
. Merge the worker's standard-output producer.
. Merge the server change that switches HLS to fMP4, updates the worker image, replaces the scripted FFmpeg test fixture, and records the real-player checks.
These four changes belong in one server pull request.

Between the second and third steps, a server built from `main` fails H.264 jobs against the new worker image, and this decision accepts that window.
Worker PR https://github.com/streamarr/streamarr-transcode-worker/pull/38[streamarr/streamarr-transcode-worker#38] served as the interim fix for issue https://github.com/streamarr/streamarr-transcode-worker/issues/36[streamarr/streamarr-transcode-worker#36] until the worker adopted the producer.

*Why:* Streamarr has no production instances.

=== Explicitly deferred

* Restrict ADR 0019 replacement attempts to the same encoder backend (issue https://github.com/streamarr/streamarr-server/issues/398[streamarr/streamarr-server#398]).
Until workers advertise their encoders, the server rejects differing inits without requiring the same backend at dispatch time.
* Add Low-Latency HLS parts and a contract for uploading parts.
A part's length stays unknown until the part ends, and ADR 0019 rejects LL-HLS blocking reload as the way a client waits for a segment.
* Transport and publish media through MoQ.
This ADR does not adopt MoQ, its transport or its live retention policy.
* Retry uploads from the retained segment (worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/1[#1]).
Until the worker supports these retries, a failed upload fails the attempt, and the server dispatches a replacement attempt within the budget ADR 0019 sets.
Once the worker supports retries, the producer retains the closed segment while it retries failed uploads with bounded back-off.
The producer releases the segment after the server acknowledges it.
The server must accept repeated uploads idempotently.
The worker can retry through the same producer interface without adding a buffer.
* Align an encoded replacement attempt's AAC frames with the frames of the attempt before it.
Placing each audio sample by its start removes the copied-audio overlap at a junction.
It keeps an encoded-audio step under one AAC frame only while both attempts' audio runs continuously across the boundary.
The producer does not measure or correct that step, and the worker change's real-player check measured −16 ms at both stream-copy junctions with encoded audio.
A source, sample rate or encoder that left a longer gap could again stall Chromium.
fMP4 reaches Media Source Extensions without the MPEG-TS remux that hid those gaps.
* Encode with the VAAPI, QSV, AMF and RKMPP hardware encoders, and decode in hardware on Intel and AMD GPUs through QSV and VAAPI (https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14]).
These backends wait until hardware exists to verify them.
* Adopt a runtime whose SVT-AV1 fixes upstream bug https://gitlab.com/AOMediaCodec/SVT-AV1/-/work_items/2385[#2385] (worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/42[#42]).
The worker takes FFmpeg as a pinned prebuilt release under ADR 0029, and no SVT-AV1 release contains commit `ae2658e5` yet.
* Check whether different FFmpeg builds produce byte-identical inits.
The init carries the muxer's version string, so a stream session that outlives a worker image upgrade could receive a replacement attempt whose init differs from the one the server serves.
The measurements did not cover a stream session that spans a worker image upgrade.
* Continue forcing keyframes after an attempt reaches the end of its list.
The worker could end each attempt at its list's last boundary, so that the server starts a replacement attempt with a new list when a client requests a later segment.
This approach would avoid the repeated period that Consequences describes, but it would require a replacement attempt.
Reading the list from a file stays rejected under Rejected Alternatives.
* Measure whether each producer and the worker stay within their memory budgets under production conditions.
The proofs of concept measured pacing and one retention budget, but did not measure whether each producer and the worker as a whole stay within the budgets this decision requires.
* Use a fragmentation target shorter than 250 ms.
A later experiment may still adopt a shorter target, and this decision does not rule one out.

== Consequences

* One ordered channel replaces two side channels.
The race between the directory and the exit cannot occur.
No step rescans, drains or reconciles after exit.
* The worker gains an ISOBMFF box parser, a sample reader, a grouper on the absolute timeline, a segment writer and strict end-of-file rules, each with its own tests.
It loses `awaitSegment`, the liveness poll, the 50 ms constant and the output directory.
* With no media on disk, the worker needs no segment base path and no code that cleans that path up.
* The worker, not FFmpeg's muxer, decides where a segment ends.
Tests verify this rule against recorded fixtures so that an FFmpeg upgrade under ADR 0029 cannot silently merge or split segments.
* A stream-copy replacement attempt now starts on the advertised segment boundary, because the producer discards the preroll fragment.
Its audio starts with the first sample at or after the boundary, so it no longer repeats audio that the previous segment holds.
From an MPEG-TS source that repeat had been ten AAC frames, and Chromium dropped 7 video frames at the junction.
The previous worker starts the replacement attempt's first segment one keyframe early, which the server never noticed because it reads no segment timing.
* An encoded replacement attempt feeds its encoder the start-0 attempt's source frames from its first segment's start onward, whatever the source's frame spacing and container.
The worker no longer encodes media that the producer discards, so a seek's first segment completes sooner.
* The encoder starts at the first segment without having encoded any earlier frame, which costs picture quality at the start of that segment.
VMAF is a perceptual video quality score.
Over libx264 at 1080p and 720p, on three sources with three boundaries each and 6 s segments, the first second of that segment scored on average 1.8 VMAF below an uninterrupted encode.
The whole segment scored 0.7 below, and the difference was gone by the third second.
The worker before this decision had the same cost.
SVT-AV1 showed no difference while it stayed under its bitrate cap.
* The attempt encodes no audio before its first segment either.
The player checks in the Evidence measured junction audio under the seek one period early and under the seek to the boundary, not under the decode-only early-start seek.
The merge gate of issue https://github.com/streamarr/streamarr-server/issues/502[streamarr/streamarr-server#502] requires every junction to play in real players without a stall, a hole or a repeated picture.
* A seek attempt on a worker with VideoToolbox or NVDEC decodes in hardware, which leaves more of the worker's CPU for encoding.
* A segment closes about one fragmentation target after its boundary in media time.
With the previous worker, FFmpeg renames the segment file at the boundary itself.
Wall-clock delivery further depends on encoder speed and on back-pressure from the server.
A segment also waits for the first audio sample past its end, or for its video to run 1 s past its end, which delayed no measured segment.
The worker's configuration sets the fragmentation target, which no longer shapes the delivered segment.
Every media segment carries one `moof`, as the HLS muxer's segments did.
* The producer rewrites every `moof`, so its segments match FFmpeg's samples, not FFmpeg's bytes.
Tests compare delivered samples with the recording's samples.
* Firefox with hls.js now starts streams whose segment 0 begins with the AAC priming frame.
With FFmpeg's fragments, 40 of 42 such runs from 0 failed fatally before playing.
* A stream-copy replacement attempt whose first fragment holds the boundary keyframe inside it now delivers its first segment whole.
With the previous producer, that segment lost 2 s of video, and Chromium, WebKit and AVPlayer each lost 24 to 26 frames at the junction.
With rebuilt segments, none of them lost a frame there.
* A source whose audio or video ends at least one segment early plays to its end in every player, because the early-ending stream is encoded and padded.
A stream session that copies such a source's video still encodes an early-ending audio track, and it encodes early-ending video.
* An encoded variant delivers every advertised segment, even past a source's real end, and a copied variant that runs short becomes a format error.
* A source whose audio ends before its video delivers every segment at the pace of its video.
When the attempt encodes that audio, the producer drops the frames FFmpeg flushes after their segment was delivered.
That is the last 2 AAC frames when the video is encoded, and up to about 0.6 s of audio, varying between runs, when the video is copied.
* Snapping copied audio with fixed-length frames moves each such track by one constant amount.
That amount is under 0.7 ms for typical sources and at most half a codec frame for audio that starts in the middle of a frame.
* Rebuilding each segment made a stream copy's first segment arrive 33 to 40 ms after the init, against 17 ms, in a newly started process.
The measurements did not isolate the cause, and the delay did not grow at the audio's end.
* Each producer holds up to two segment caps in memory.
One segment awaits acknowledgment while the producer assembles the next.
The previous worker instead keeps the closed segment on disk while it uploads that segment.
The worker holds at most the slot count times two segment caps.
* Variable-frame-rate sources are still padded to a constant rate.
The worker now uses the output frame rate instead of FFmpeg's guess.
The frame-count GOP and the output rate therefore cannot disagree.
* Every encoder receives time-based keyframes, so segment boundaries stop drifting with the GOP.
* A variable-frame-rate file whose average rate lies below its motion rate now encodes at its motion rate, so the encode keeps every frame.
* Encoded variants cut 3 s segments, so the producer encodes half as much media before the segment that a starting or seeking player waits for.
At 3 s segments the server must hold every segment request for less than 3 s, because macOS AVPlayer abandons a request after one target duration without a byte.
* Until merged segment lists arrive, a stream session that only copies keeps 6 s segments, and a copied variant in a stream session that also encodes is encoded when its keyframes do not fit the 3 s grid.
Once merged segment lists arrive, every stream session uses 3 s slots, and a stream copy's playlist advertises segments of different lengths.
* In a stream session with a copied variant, every variant's last segment can last up to twice the period when the grid's final interval holds no source keyframe.
* The server encodes a source until it knows the source's keyframe positions, so a file without a usable container index is encoded until its keyframe scan finishes.
* A keyframe-verified encoder's segments hold one keyframe instead of the two that most segments hold under the floored GOP.
Other encoders keep the extra keyframe until they are verified.
libx265 can qualify after the changes tracked by issue https://github.com/streamarr/streamarr-server/issues/497[streamarr/streamarr-server#497].
NVENC and VideoToolbox qualify through their own checks (https://github.com/streamarr/streamarr-transcode-worker/issues/56[streamarr/streamarr-transcode-worker#56], https://github.com/streamarr/streamarr-transcode-worker/issues/57[streamarr/streamarr-transcode-worker#57]), and https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14] keeps VAAPI, QSV, AMF and RKMPP.
* A worker encodes with a hardware encoder backend only after the backend passes the keyframe recording checks, the initialization-segment check and the output check.
* Safari's native player fetches only the target segment when it seeks in a variant from a keyframe-verified encoder.
* The extended GOP alone no longer guarantees a keyframe in every interval.
If an encoder stopped honoring forced keyframes altogether, its GOP would drift away from the segment starts until an interval held no keyframe, as it does past the end of the list.
The producer would then fail that attempt with `SKIPPED_SEGMENT_NUMBER` instead of misnumbering segments.
Tests check the recordings to catch that regression when FFmpeg is updated under ADR 0029.
* Under the extended GOP the forced keyframes alone place every boundary that the list holds, on the first frame at or after that boundary in every attempt.
A junction between two attempts at any listed boundary after a replacement attempt's first junction therefore neither drops nor repeats a frame.
The expression had put shared boundaries one or two frames apart, and the floored GOP's extra keyframe had hidden that difference.
* The worker contract gains `TranscodeExecution.media_segment_count`, the advertised count.
When merged segment lists arrive with https://github.com/streamarr/streamarr-server/issues/512[streamarr/streamarr-server#512], the worker contract also gains the segment list's starts.
The server still handles requests for advertised segments that the worker did not produce, under ADR 0019.
* An FFmpeg command line carries its keyframe times in one argument, up to Linux's per-argument limit, and FFmpeg parses that argument in no measurable time.
* SVT-AV1 attempts in the pinned runtime still fail under CPU contention, as the study found.
The stall watchdog and the short-sample rule turn a hung FFmpeg or undecodable segments into a failed attempt that ADR 0019 replaces.
Both rules stay after the runtime update tracked by worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/42[#42], because they cover every encoder.
* When a media file outlasts its list and a keyframe-verified encoder's attempt fails with `SKIPPED_SEGMENT_NUMBER`, the replacement attempt starts a new list at the skipped segment's start.
Its first segment repeats about one period of media that the last drifted segment already held.
ADR 0019's recovery cannot withdraw that repeat once the server has published it.
* Switching H.264 to fMP4 removes the parameter sets that MPEG-TS carried in each media segment.
The server instead serves the stored init with later segments and, once workers advertise their encoders, requires replacement attempts to use the backend that produced that init.
* The upload loop gains `isReady` flow control, a readiness bound and an acknowledgment deadline.
The worker starts enforcing the slot count it advertises.
* AAC stream copies gain an explicit `aac_adtstoasc` filter that the HLS muxer inserted on its own.
Without this filter, every MPEG-TS source with AAC fails to copy under the new muxer flags.
* MPEG-TS disappears end to end, and the container as a type goes with it rather than surviving with one value.
ADR 0036's list of names to keep drops `ContainerFormat`.
H.264 playback changes container, and the server pull request carries the player evidence for that change.
* H.264 in hls.js loses the MPEG-TS remux that hid timestamp gaps, so a junction audio gap longer than one AAC frame now reaches Chromium as a hole.
Placing each audio sample by its start removes the copied-audio overlap at a junction.
The producer does not align an encoded replacement attempt's AAC frames with the frames of the attempt before it (<<explicitly-deferred>>).
* The server and worker changes must follow the rollout order above.
One server pull request switches the container, updates the worker image, replaces the scripted FFmpeg fixture, and records the player checks.
* A stop can no longer end in a forced kill because the reader sat blocked in an upload.
The producer must both drain the pipe and cancel the upload.
* A MoQ proof of concept needs `separate_moof`, a smaller fragmentation target and a publisher adapter, not a second producer.

== Rejected Alternatives

* A producer that watches the output directory with inotify and treats exit as an event removes the race by ordering the two facts.
It still keeps two channels, needs a polling fallback on macOS, and the pipe would replace it anyway.
* A pull-style producer with a `next()` method leaves the read loop with the caller, and a fake producer would have to duplicate the ordering rules.
* Exit and segment-arrival callbacks on the existing process manager leave the stop logic in the worker under a different lock.
The worker would still upload a segment that FFmpeg flushed during a stop.
* A loopback HTTP receiver inside the worker, which several live-streaming servers use and the first proof of concept measured, would have to rebuild every delivery guarantee that FFmpeg's HTTP output lacks.
It would also give the worker a listening port that ADR 0033 reserves for health checks.
* FFmpeg `PUT`ing segments straight to the server adds a second transport beside gRPC.
The server would fence attempts by a URL token instead of by the connection that owns them.
FFmpeg's HTTP client would handle TLS.
This approach offers no per-segment retry.
* Having the server read segments from storage the worker shares moves the same two-channel race onto the server and across a network filesystem.
ADR 0018 and ADR 0019 already defer that design.
* Cutting one fragment per segment with `-min_frag_duration` just under the period matches the HLS muxer only at a constant frame rate with keyframes exactly one period apart.
No fixed minimum holds for arbitrary keyframe spacing.
* Setting `-min_frag_duration` to exactly the segment period merged two segments at 23.976 fps in the first proof of concept.
* Checking each fragment's raw `tfdt` against segment number times period rejected valid segment starts.
Decode time differs from presentation time by the composition offset.
A 144-frame period is 6.006 s, and the first audio `tfdt` wraps negative.
* Keeping a stream-copy replacement attempt's preroll fragment in its first segment reproduces the previous worker's overlap of one keyframe interval with the previous attempt.
* Seeking an encoded replacement attempt exactly to its first boundary leaves no preroll to discard.
That seek drops frames at the first junction on variable-frame-rate and MPEG-TS sources.
It also left an audio gap that stalled Chromium with hls.js.
A 1 s margin still dropped frames on MPEG-TS sources whose keyframes are 2 s apart.
* Seeking an encoded replacement attempt one period early, and encoding that period for the producer to discard, aligned every recorded junction.
A 1080p seek's first segment then took about 5.0 s to complete instead of about 3.0 s.
* Having the worker compute its own read-back for an encoded seek ignores where the source's keyframes are, and FFmpeg's MPEG-TS demuxer starts at the next keyframe after its target.
* A fixed, generous read-back for every file decodes more media before the first segment than a known keyframe needs.
The read-back therefore serves only until an index-less file's keyframe scan finishes.
* Handling stream sessions whose attempts run on different worker versions, by adding the worker version to the affinity key or a recipe version to the worker's capabilities, handles a case that cannot occur while Streamarr has no production instances.
* Decoding every seek in software, or only the seeks of open-GOP sources, keeps the CPU cost of software decoding.
That cost was 4.26 to 4.28 s against 0.84 to 0.97 s for one 1080p replacement attempt on the M1 Max.
* Keeping software decode on Linux until https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14] would delay a decoder whose H.264 and HEVC output already matched software decoding bit for bit.
* Running NVDEC without the leading-picture filter would give the two platforms different recipes, while the filter changed no NVDEC output frame in 77 pairs of runs.
* Failing the attempt before closing the open segment when a fragment skips a number discards a complete, correctly numbered segment.
In a stream copy every replacement attempt would fail at the same fragment, so none could deliver it, and in an encode a replacement attempt would encode it again.
* Requiring recorded fixtures to match the HLS muxer's cuts would make the tests enforce that muxer's first-packet origin, which misaligns a stream-copy replacement attempt.
The tests would also enforce behavior that reads the reference timestamp in the wrong time base and that FFmpeg's development branch has already changed.
* Concatenating FFmpeg's fragments byte for byte into each segment keeps about `period / target` `moof` boxes per segment.
Firefox treats each `moof` as its own media segment, so an audio discontinuity after the first `moof` drops the rest of the segment's video until the next keyframe.
Concatenation also leaves each audio sample in whatever segment its fragment joins, which repeated ten AAC frames at a stream-copy junction from an MPEG-TS source.
A 250 ms fragmentation target without rebuilding still lost the rest of the replacement attempt's first segment at every junction in Firefox's raw Media Source Extensions.
* Dropping or shortening the AAC priming frame in multiplexed variant segments fixes only segment 0 in Firefox.
Any audio jump beside continuous video in a segment of several `moof` boxes still drops the rest of that segment's video.
It would also shift timestamps that FFmpeg wrote.
This rejection covers multiplexed variant segments only.
ADR 0043 drops audio before media time zero in audio renditions.
* Closing a segment when the first fragment past its boundary arrives, with or without audio, closed a segment before its last audio sample arrived.
That happened where AAC frames outlast video frames and FFmpeg cut a keyframe fragment without audio.
* Closing a segment only once an audio sample past its end arrives holds every segment after the audio's end until the output ends.
Those held segments then outgrow the producer's budget, and a replacement attempt from the first of them meets the same limit.
* Grouping video by whole fragments misses a boundary keyframe that FFmpeg writes inside a fragment.
`delay_moov` writes nothing until every track has a sample, so a stream copy whose encoded audio starts at the seek point puts that keyframe mid-fragment.
* Failing the attempt on a late audio sample fails every attempt that encodes audio ending long before its video.
Each replacement attempt meets the same flush at the end of its input, so none could complete.
* Padding the audio to the video's length and stopping at the shortest stream would change every encoded attempt's audio.
It cannot apply to copied audio, and FFmpeg still gives no signal that a stream has ended.
This rejection covers padding every attempt's audio.
An audio track that the probe shows ending at least one segment early is still encoded and padded (<<decision-early-ends>>).
* Marking the segments after an audio track's end with `EXT-X-GAP` left hls.js stuck on the iPhone.
* Padding a copied audio track with silence in its own codec, without encoding the track, would join encoder-made silence to copied frames.
An attempt that starts after the track's end would carry only that silence, and its initialization segment would differ from the copied one, which the server refuses.
* Ending the stream at the video's end would drop the remaining audio, up to 237 s of it in the library sample.
* Closing segments without a keyframe, as audio-only segments, when the source ends early breaks the rule that every segment's video opens at a keyframe.
* Leaving an early end unreported lets the server start replacement attempts past the source's end, and those attempts can never deliver the missing segments.
* Answering 404 for the advertised segments past a source's real end broke hls.js, AVPlayer and WebKit's native player.
* Carrying each audio track's end time to the worker, so that a segment never waits for audio, adds a contract field for a wait that padding already removes for every track the probe shows ending early.
* Closing a segment on a fragment's computed end, its start plus its sample durations, closed a segment before its last fragment arrived on a variable-frame-rate stream copy.
* A worker margin of 10 s would add a second 10 s wait after the muxer's own wait.
The longer margin would save no audio, because no margin short of the whole output covers the audio that arrives late.
* Adopting 100 ms fragments now, or testing Firefox at 100 ms first, would gain only 0.03 s per seek beyond what 250 ms fragments save.
* Measuring the parsing cost of 125 ms fragments inside the 250 ms change would study a target that can save at most 0.125 s per segment, so that measurement waits for a later experiment on shorter fragments.
* Anchoring the audio snap at the track's probed start keeps a copied track on its own grid, not on the grid that encoded tracks use.
* Encoding every selected audio track gives up every audio copy to remove an offset that a constant shift of under 0.7 ms removes for typical sources.
* Leaving copied audio unsnapped let switches between AAC renditions move the audio offset by −46 to +60 ms.
* Ignoring FFmpeg's advisory bitrate fields when the server compares inits would weaken a strict check to hide a difference that the worker can remove.
* Cutting a fragment at every frame, so that the closing signal arrives within one frame, multiplies the `moof` count by the frame rate for a gain that the `-frag_duration` target already delivers.
* Passing `-fps_mode:v:0 cfr` to keep the HLS muxer's constant-rate behavior padded duplicate frames from time zero after a seek.
The HLS muxer's behavior is an internal variant that `-copyts` selects and that the command line cannot request.
* Leaving frame synchronization to the mp4 muxer's default, or passing `-fps_mode:v:0 vfr` for every encoder, keeps each source frame's own timing.
That suits time-based forced keyframes but stretches a frame-count GOP until segment numbers lack a keyframe.
* Choosing `vfr` for encoders that use time-based keyframes and a forced rate for encoders that use frame-count GOPs worked in the measurements.
It adds a second rule without improving on one forced rate that reproduces the previous worker's output for every encoder.
* Carrying the frame rate as a double cannot hold a rate such as 24000/1001 exactly, so the rate that reaches `-r:v:0` would differ from the rate that the rule chose.
* Having the worker convert a double to the nearest fraction repeats a choice that the probe job has already made, and the conversion can pick a different fraction.
* The frame-rate rule without the packet scan keeps snapping a variable-frame-rate file's average rate, which dropped 9 to 70 % of the frames of some files.
* Keeping 6 s segments for encoded variants makes the producer encode twice as much media before the segment that a starting or seeking player waits for.
A 1080p seek's first segment completed 1.95 s after FFmpeg started at 6 s segments, against 1.28 s at 3 s segments.
* Moving encoded variants to 4 s segments saves less of that time.
The same seek's first segment completed in 1.50 s at 4 s segments.
Over a 10 Mb/s link, AVPlayer's far seek took 3.44 s at 4 s segments, against 3.03 s at 3 s segments.
* Predefining 4 s as the length to use if the merge gate fails would choose a length before the Apple TV run shows why 3 s failed.
* Choosing a segment length for each stream session gives every stream session its own period to measure and test.
Merged segment lists already fit every source's keyframes into 3 s slots.
* Cutting 2 s segments failed four separate measures in simulated playback sessions.
AVPlayer logged error −12318, "Segment exceeds specified bandwidth", in 2 of 6 sessions.
A 2 s segment's peak bitrate reached 1.161 times the advertised `BANDWIDTH`, above Apple's limit of 1.10.
WebKit kept 1080p in only 4 of 15 sessions, and hls.js in Chromium held 1080p for 3 % of the time.
At equal VMAF, 2 s segments needed 6.0 to 16.4 % more bitrate than 6 s segments, against 2.9 to 7.7 % more for 3 s segments.
* Measuring the library's keyframe spacing before choosing a stream copy's segment length would delay a choice that the spacing no longer decides.
Merged segment lists let every stream session use 3 s slots without encoding more sources, whatever the spacing is.
* Requiring a source keyframe in the grid's final interval as well, the interim rule that this decision first accepted, would encode ordinary sources.
AAC priming makes a container run about 23 ms past its video.
A source whose video ends on a period boundary therefore leaves a final interval of about 23 ms, and that interval holds no keyframe.
* Writing `EXT-X-INDEPENDENT-SEGMENTS` for every variant would claim independence for stream copies and libx265, whose segments can start with an open GOP.
* Never writing `EXT-X-INDEPENDENT-SEGMENTS` would keep Safari's native player fetching two extra segments before every seek target.
* Recording the VideoToolbox encoders only in https://github.com/streamarr/streamarr-transcode-worker/issues/14[streamarr/streamarr-transcode-worker#14] would keep them off the keyframe-verified list that the worker reads.
* Deferring the VideoToolbox encoders would leave a Mac worker's hardware encoder unused, although both encoders already pass the recording checks.
* Adding VAAPI, QSV, AMF and RKMPP now, each on its own or all in one change, would add backends that no available hardware can verify.
* Waiting for the encoded-seek work before adding NVENC and VideoToolbox would delay both backends, although their three checks do not depend on that work.
* Keeping the rounded-up frame-count GOP as the only source of keyframes, as the previous worker does for SVT-AV1 and hardware encoders, lets keyframes drift until an interval holds none.
Waiting for a replacement attempt to produce the missing segment would stall playback each time.
The extended GOP is safe only because forced keyframes, not the GOP, place every boundary.
* Keeping the floored GOP for every encoder adds a second keyframe and a one-frame fragment beside most boundaries.
It guards against a failure that the keyframe verification recordings rule out and that `SKIPPED_SEGMENT_NUMBER` would still name.
* Verifying keyframes on sync samples alone would admit libx265.
Its forced keyframes are CRA sync samples, and its backstop keyframe carried a RASL picture.
The sync flag cannot distinguish an open GOP from a closed one.
* A GOP of exactly the rounded-up number of frames fires on the same frame as a forced keyframe after a gap of that length.
A recording cannot then show whether the encoder honored the forced keyframe or reached its GOP limit.
* Keeping the expression `gte(t,n_forced*period)` measures every boundary from the attempt's first frame, because FFmpeg gives an expression no absolute time.
It put shared boundaries one or two frames apart, and on sources whose first frame is after zero it put the start-0 attempt's own boundaries one frame late.
* Anchoring the expression with a predicted first frame, `gte(t+T0,(n_forced+k)*period)`, requires the first output frame's time before FFmpeg runs.
The worker cannot know that time in advance because it depends on the source's frame times and where the demuxer starts reading after the seek.
* Measuring each forced keyframe from the previous one, `gte(t,prev_forced_t+period)`, is a frame-count GOP in another form, so it drifts, misaligns replacement attempts, and would skip a segment after about 1000.
* A fixed horizon gives every job the same number of boundaries without changing the contract.
The server already defines the segment list and computes the count it advertises.
Adding a field for that count costs little before production.
* Having the worker probe the source's duration before each attempt to end the list adds a process and its latency to every start and replacement attempt.
The new probe can also disagree with the probe behind the advertised count.
* Reading the list from a file with `-/force_key_frames:0` lifts the argument limit.
It also restores a per-attempt file on disk after this decision removes the output directory.
The worker must create that file and remove it on every exit path.
Standard input carries the stop command, and `ProcessBuilder` passes FFmpeg no other descriptor.
* Serving a replacement attempt's own init mid-playlist would tolerate a backend change, but it needs per-attempt inits and playlist changes that ADR 0008 does not generate.
* Switching H.264 to the `avc3` sample entry, so that parameter sets travel in-band, would tolerate a backend change, but it has no evidence on AVPlayer.
* Zeroing each attempt's timeline at its own first fragment gives a replacement attempt a different origin from the initial attempt, so the same segment number would name different media.
* Having the worker probe the source's start time and subtract it duplicates what `-start_at_zero` already does inside FFmpeg.
* Exempting the upload wait from every bound, on the grounds that back-pressure is not a stall, leaves an attempt that a silent receiver can hold forever.
* Waiting indefinitely for FFmpeg to exit after its output ends lets a process that hangs after its last byte hold the attempt until a stop arrives.
No other watchdog watches the process once the reader has finished reading the output.
* Keeping MPEG-TS behind a worker capability flag changes nothing for the server, which would stop requesting MPEG-TS anyway, and both repositories would have to keep two container paths correct.
* Keeping a one-value `ContainerFormat` type as a slot for a future container preserves a decision that no code makes.
A future container would need its own ADR, and its type can return then.
* None of the surveyed projects parses FFmpeg's playlist or its `EXT-X-ENDLIST` tag as the completion signal.
This approach duplicates a playlist the server already generates.
It also retains a filesystem side channel.
* Scraping FFmpeg's log for segment events turns a log line into a contract, and a log line is not one.

== Evidence

Each group below holds the measurements behind one part of the Decision.
The References section identifies the committed recordings and the measurements whose recordings were not committed.

[[evidence-channel]]
=== Delivery channel and prior art

* Of the five open-source servers that hit the last-segment race, one now rescans the output directory after FFmpeg exits (2026).
* One replaced its polling watcher in 2020 so that FFmpeg pushes each segment to the server over HTTP.
* One never fixed the race.
* Two independent throwaway proofs of concept measured the HTTP receiver and the standard-output design against FFmpeg 8.1.2 in the pinned worker image.
* The second proof of concept added 17 timing cases, 13 gRPC scenarios and a playback matrix on real decoders.
* FFmpeg's HTTP output never reads the response status.
`libavformat/http.c` substitutes a 200.
* It never re-sends a segment the receiver dropped.
* It exits with status 0 even after a rejected upload.
* It exits before a slow receiver has read everything FFmpeg wrote.
* moq-mux's demo runs FFmpeg with `separate_moof` and a 1 ms `-frag_duration`, so its fragments are sample-sized.
* moq-mux's importer closes a group only when it observes the next boundary.
* Keyframes alone do not define that importer's groups.
The importer starts a new group on every track, including audio, at each segment boundary.
* For that importer, a `styp` box or an explicit cut marks a boundary as well as a video keyframe does.
* MoQ's importer skips no fragment.
For the tracks it publishes, the importer publishes every fragment or fails.
* MoQ's live consumer skips stale or missing groups.

[[evidence-grouping]]
=== Fragmentation and grouping

* The HLS muxer cuts at the first keyframe whose presentation time, measured from the run's first packet, reaches the period times the segment count.
`hlsenc.c` compares `pkt->pts - vs->start_pts` against `recording_time * number`.
* In the pinned FFmpeg that first packet can be audio.
`hlsenc.c` keeps the first audio packet's `pts` in audio ticks unless a video packet's raw `pts` is smaller, and subtracts it in the video time base.
Its reference therefore depends on the audio sample rate.
* FFmpeg's development branch (checked at commit `a6e5d5f`) already rescales both to microseconds, so the HLS muxer's cut points would move with an FFmpeg update.
* The mp4 muxer with `frag_keyframe` cuts at a keyframe when the time since the previous fragment reaches `min_frag_duration`, measured from the previous fragment rather than from any target.
* With a constant frame rate and a forced keyframe at every period, the two rules agree.
The first proof of concept confirmed that agreement at 23.976 fps for encode, stream copy and a seek.
* A 66 s stream copy has keyframes at 0, 6.5, 12, 18, 24.5, 30, 36.5, 42, 48, 54.5 and 60 s.
There `min_frag_duration` just under 6 s produced 7 fragments where the HLS muxer produced 11 segments.
The 5.5 s gap from 6.5 s to 12 s can never satisfy a 5.958 s minimum.
* On a variable-frame-rate encode with the worker's own forced keyframes, the same recipe produced 9 fragments where the HLS muxer produced 11 segments.
* With `min_frag_duration` set to exactly the period, FFmpeg merged two segments even at a constant 23.976 fps, because the forced-keyframe gap fell one frame short.
* Setting no minimum and grouping fragments by absolute presentation time reproduced the HLS muxer's cut points on all three fixtures.
Those were 90 fragments into 30 segments for the NTSC copy, 11 into 11 for the irregular copy, and 11 into 11 for the variable-frame-rate encode.
* The pinned FFmpeg decoded every grouped playlist.
* The recorded fixtures of worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/39[#39] force keyframes with the list.
In those fixtures, grouping matches the HLS muxer tick for tick on a constant-rate encode and on a stream copy whose first frame is at zero.
The recorder lists every other difference and explains its cause.
* The variable-frame-rate encode in those fixtures still yields 11 segments for 11, but its first frame is at 41.7 ms, and the HLS muxer measures from it.
The list forces the first frame at or after each boundary, which comes before that boundary plus 41.7 ms.
The HLS muxer therefore cuts only at the next forced keyframe, and from segment 1 on its segment numbers run one behind the grid's.
* An encoded replacement attempt from segment 5 forces the same frames as the start-0 attempt, so its segments match the start-0 attempt's HLS output.
The HLS muxer's own run of that attempt's seek to 24 s measures from its first frame at 24.024 s and runs one segment behind from segment 7 on.
* At 23.976 fps a 144-frame period is 6.006 s, so fragment decode times do not land on the nominal grid.
* The `cmaf` flag writes negative composition offsets that shift `tfdt` by two frames.
* The first audio `tfdt` is the unsigned wrap of −1024 ticks.
* A check of `tfdt` against segment number times period rejected 23 of 30 valid segment starts.
* On a variable-frame-rate stream copy with B-frames, a fragment that starts at 6.0 s carries durations that sum to 12.0 s, yet the next fragment starts at 11.9 s.
A worker that closed the segment on that computed end would close it before its last fragment arrived.
* The only reliable boundary signal is the next fragment's own start.
FFmpeg emits a fragment only when it closes it, so the worker learns that a segment is complete one fragment late.
* With a 1 s `-frag_duration` and `frag_keyframe`, the mp4 muxer still cut at every keyframe and also cut every 1.001 s.
The muxer produced 91 fragments over 90 s at 23.976 fps.
* A stream copy with 2.002 s keyframes gave 90 fragments under the same bound.
* Every fragment that did not begin at a keyframe began with a non-sync sample.
* At a 1 s target the muxer cuts at the first packet after the target.
Measured spans were 1.001 s for H.264 and 1.033 s for SVT-AV1.
* Fragments without a video track appear only after the last video sample.
There may be none, one, or several such fragments.
The muxer emits one per target of audio that outlasts the video.
* On the 90 s fixture that tail was three AAC samples at 89.941 s.
* Audio that outlasts video by 5 s produced five such fragments.
* A video-only tail appears when video outlasts audio.
* `delay_moov` folds audio that starts before the video into the first fragment, so no fragment without video ever precedes the first segment.
* On a 10 s-GOP stream copy the sync-first fragments fell in segment numbers 0, 1, 3, 5, 6, 8, 10, 11 and 13, with the first skip at 20.02 s.

[[evidence-timeline]]
=== Timeline origin, seeks and preroll

* `-copyts` keeps the source's own timestamp origin.
A source whose timestamps begin at 12 s put its first fragment at 12 s, in segment 2, for a job that asked for segment 0.
* The HLS muxer hides that origin by measuring from the run's first packet.
* `-start_at_zero` subtracts the source container's start time under `-copyts`, and that start time does not move with `-ss`.
* With `-start_at_zero`, the same source's first fragment started at 0 for stream copy and for encode.
* With `-start_at_zero`, an encoded seek to 30 s started at 30.030 s.
* With `-start_at_zero`, a stream-copy seek to 30 s started at 28.028 s, on the keyframe at or before the requested time, so that fragment is preroll.
* The container's start time is the earliest stream's first timestamp.
On MPEG-TS sources it is the AAC priming frame, 21 ms before the first video frame, so video starts at 0.021 s (copy) or 0.042 s (encode) rather than at 0.
* Two MPEG-TS remuxes of the same content starting at 1.46 s and at 3601.38 s produced byte-identical outputs.
* MPEG-TS input seeking lands on the next keyframe after the target, not the one at or before it.
* `-ss 30` on an MPEG-TS source started video at 30.051 s (copy) and 30.072 s (encode), while audio still started near 30 s.
* On a 10 s-GOP MPEG-TS source, `-ss 25` started video at 30.07 s with five seconds of audio before it.
* Under `delay_moov`, a stream copy of AAC from an MPEG-TS source exits 255 with "Malformed AAC bitstream detected".
* Adding `-bsf:a aac_adtstoasc` fixes that copy and leaves copies from MP4 and MKV sources byte-identical.
* The previous worker passes `-max_delay 5000000`.
The measurements produced byte-identical mp4 output with and without this flag.
* In MPEG-TS output the same flag moves the first timestamp from 1.4 s to 10.0 s.
* The HLS muxer measures its cut points from a stream-copy seek's preroll keyframe.
With 48 kHz audio, a stream-copy replacement attempt's segments start at 28.028, 34.034 and 40.040 s, while the server advertises them as 30, 36 and 42 s.
* With 8 kHz audio, the HLS muxer took the first audio packet as its reference for the same replacement attempt and read that packet's timestamp in video ticks.
The muxer cut at every 2.002 s keyframe from 28.028 s to 36.036 s, then at 40.040 s and every 6 s after.
The muxer produced 10 segments numbered 5 to 14 with 8 kHz audio, compared with 7 segments with 48 kHz audio.
* With every keyframe as its own fragment, the preroll is a separate fragment that the worker can discard.
* An encoded replacement attempt that seeks exactly to its first boundary starts at 30.030 s with nothing to discard.

[[evidence-init]]
=== Initialization segment identity

* Across start 0, a seek to 30 s and a seek to 60 s, every encode run produced one byte-identical `ftyp`+`moov` of 1327 bytes.
* The stream-copy runs produced byte-identical inits of 1347 bytes across the same start points.
Those inits differed from the encoded runs' inits.
* Each init held zero durations, empty sample tables, a zero edit list and zero `trex` defaults.
* Pairing the start-0 init with a seek run's segments gave the same packets, and the same decoded frames, as that run's own init.
* Encode and stream-copy inits differ in bitrate metadata, and a copy from an MKV source takes the source's 1/1000 time base.
An init is therefore a property of the variant's mode and codec parameters, never of the attempt.
* FFmpeg's demuxer presents every output 2002 ticks (83 ms) after its composition time, uniformly across attempts and independent of the init.
That offset is the negative of the most negative composition offset the `cmaf` flag writes.

[[evidence-frame-rate]]
=== Frame synchronization

* FFmpeg's automatic frame synchronization depends on the muxer.
* The mp4 muxer declares `AVFMT_VARIABLE_FPS`, so automatic mode passes variable frame rates through.
* The HLS muxer does not, so automatic mode picks a constant rate.
Under `-copyts` FFmpeg turns that constant rate into an internal variant that keeps the first timestamp (`fftools/ffmpeg_mux_init.c`, `VSYNC_VSCFR`).
* The same variable-frame-rate source yielded 622 video packets through mp4 and 1976 through HLS.
* The command line cannot request that internal variant, and the explicit `cfr` mode is a different thing.
* After a seek to 30 s, `cfr` padded the output with 720 duplicate frames from time zero.
The output contained 2157 video packets instead of 1437.
* The HLS recipe with automatic mode produced 1437 packets starting at 30.030 s.
* Passing `-r` with the probed frame rate and no `-fps_mode` puts automatic mode back on the constant-rate path, and `-copyts` then selects that same internal variant.
* On an irregular variable-frame-rate source, SVT-AV1 with the worker's frame-count GOP then produced a keyframe every 6.006 s and 1583 video packets, identical to the HLS muxer's output on the same source.
* A seek to 30 s under those flags started at 30.113 s with no padding.
* The same encoder under `-fps_mode vfr` placed keyframes at 0.04, 9.43, 20.35, 30.86, 40.96, 51.30 and 61.23 s, leaving five of eleven segment numbers without a keyframe.
* A GOP counted in frames equals the period only at a constant frame rate.
The previous worker gives SVT-AV1 and the hardware encoders a frame-count GOP and no time-based forced keyframe.
* libx264 with time-based forced keyframes kept a keyframe in every interval under `vfr`.

[[evidence-keyframe-list]]
=== Forced keyframe modes and the list

* `force_key_frames` chooses the frames it forces differently in its two modes (FFmpeg n8.1 `fftools/ffmpeg_enc.c`, `forced_kf_apply`).
* An expression sees `t`, the time since the first frame that reached the encoder, and the counters `n`, `n_forced`, `prev_forced_n` and `prev_forced_t`, which count from that frame as well.
* No expression constant carries an absolute time, so no expression can name a point on the zero-based timeline.
* A list compares each frame's own timestamp with absolute times and consumes at most one entry per frame.
* `-copyts -start_at_zero` places each frame's timestamp on the zero-based timeline whatever `-ss` is.
* Recordings of the recipe under the pinned FFmpeg measured both modes for libx264 and SVT-AV1 at 23.976 and 29.97 fps, with a 6 s period and the extended GOP.
Each encoder ran single-threaded so that runs compare frame for frame.
* The sources were a constant-rate MP4 whose first frame is at zero, a variable-frame-rate MP4 whose first frame is at 41.7 ms, and an MPEG-TS source.
The MPEG-TS source's timestamps begin at 12 s, and its first output frame falls one frame after zero.
* Each source ran from the start and after seeks to 18, 30 and 42 s.
* Under the expression, 202 of the 360 boundaries that a replacement attempt shares with the start-0 attempt began one or two frames apart.
* After a seek to 30 s on the constant-rate source, the expression forced frames 1008, 1152, 1296 and 1440 against the start-0 attempt's 1007, 1151, 1295 and 1439.
* Under the expression, on the two sources whose first frame is after zero, the start-0 attempt itself put 15 of 16 boundaries one frame after the first frame at or after the boundary.
* Under a list of the boundaries from the attempt's start sequence number on, every attempt forced the first frame at or after each boundary, and none of the 372 shared boundaries differed.
* A list that also held boundaries before the attempt's first frame forced one extra keyframe per such entry, on consecutive frames.
* The expression `gte(t+T0,(n_forced+k)*period)` anchors forced keyframes to a predicted first frame.
`T0` is the time of the first output frame at or after the seek position.
`k` is the start sequence number.
This expression aligned the constant-rate source whose first frame is at zero.
* The anchored expression left 80 of 360 shared boundaries one frame apart on the variable-frame-rate and MPEG-TS sources.
* From the start, `gte(t,prev_forced_t+period)` drifted one frame every seven segments at 23.976 fps.
* Under `gte(t,prev_forced_t+period)`, a replacement attempt from 42 s landed one frame off the start-0 attempt at every later boundary.
* Past the list's last entry, segment starts drifted 47.7 ms per segment at 23.976 fps and 39.4 ms at 29.97 fps.
* The first skipped segment number came 126 segments after the last listed boundary at 23.976 fps, and 153 at 29.97 fps.
* A list that ran past the media's end produced byte-identical output.
* Linux caps a single argument to a process at 32 memory pages, including its terminating zero byte.
* In the pinned image a 131,071-byte argument ran and a 131,072-byte one failed with "Argument list too long".
* A list from zero that fits holds 22,771 boundaries at a 2 s period (12.65 h), 22,308 at 4 s (24.8 h) and 21,370 at 6 s (35.6 h).
* FFmpeg parsed the longest of those lists in no measurable time.
* An empty list fails FFmpeg's option parsing ("Invalid keyframe time").
* FFmpeg can also read an option's value from a file (`-/force_key_frames:0`), and it read a 1,000,000-entry list that way in about 150 ms.

[[evidence-svt-av1]]
=== SVT-AV1 study

* Worker issue https://github.com/streamarr/streamarr-transcode-worker/issues/42[#42] records a study that ran SVT-AV1 1,170 times through the recipe with the expression in place of the list.
* The runs used the pinned runtime and a separate FFmpeg 8.0.1 build with SVT-AV1 4.0.1 and 4.1.0, at periods of 1 s and 6 s, under both GOPs.
* In every run whose packets left the encoder in order, every forced keyframe was a shown AV1 key frame, a sync sample and a fragment start.
* In those runs, under the extended GOP, no other keyframe appeared.
* The runtime pinned during these runs, FFmpeg 8.1.2 with SVT-AV1 4.1.0 (ADR 0029), carried upstream SVT-AV1 bug https://gitlab.com/AOMediaCodec/SVT-AV1/-/work_items/2385[AOMediaCodec/SVT-AV1#2385].
* The current pin, the FFmpeg 8.1.3-1 build with SVT-AV1 4.2.0, still carries the bug.
* When the encoder's oldest picture is slow, a later picture overwrites its slot in the packetization reorder queue, and the encoder runs out of output buffers.
* SVT-AV1 4.0.x, 4.1.0 and 4.2.0 all have the bug.
* Its fix, commit `ae2658e5`, is on SVT-AV1's master branch and in no release.
* In interleaved runs under load, the fix took 4.0.1 from 13 failures in 40 to none.
* Under production threading the pinned image failed 10 of 740 runs.
* All 10 failures came among the 420 runs under CPU contention, and none among the 320 without it.
* The GOP does not cause the bug.
At two contended CPUs, 5 of 150 runs failed under the floored GOP.
Under the extended GOP, 4 of 200 runs failed.
* In one failure mode FFmpeg hangs at zero CPU while it keeps printing a progress line whose frame count no longer changes.
* SIGTERM ended none of the hung runs.
* FFmpeg's source shows that `q` cannot end such a hang either.
Both `q` and SIGTERM end FFmpeg's main loop, but the main loop then waits for the stuck encoder thread to exit.
* Only SIGKILL or a fourth signal ends a hung FFmpeg.
* In the other failure mode the encoder emits packets out of decode order, and FFmpeg rewrites each such packet's decode time to the previous one plus one tick.
* The output then carries one-tick video samples, and keyframes of 30 to 150 frames crowd into one or two intervals.
* The producer then fails with `SKIPPED_SEGMENT_NUMBER`, or FFmpeg exits 0 with segments that dav1d cannot decode, as 2 of the 10 pinned failures did.
* Across the 1,170 runs, a video sample shorter than half the nominal frame duration appeared only in runs where FFmpeg logged a non-monotonic decode time.
* Such a sample appeared in every such run except one, which hung before FFmpeg wrote the reordered fragment.
* Of the encoder parameters the study ran, only `-svtav1-params lp=1` avoided the bug, in 90 runs without a failure.
* `lp=1` encodes 1080p at 0.78 times real time, too slow to stream.
* The study ran no other thread count, scene-change detection, lookahead, pinning or prediction structure.
