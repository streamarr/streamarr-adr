= ADR 0036: Video Contracts Share One Vocabulary and Preserve Dynamic-Range Facts

== Status

Accepted

NOTE: link:0045-clients-direct-play-covered-files-and-use-platform-players.adoc[ADR 0045] adds one automatic format change in Original.
When the player cannot play a direct-played file, the server falls back to HLS at original quality.
That HLS stream is a new format attempt.
A direct-played format attempt has no initialization segment.

This ADR records the accepted dynamic-range structure and the rules to preserve source facts and report problems separately.
An amendment adds the facts that probe version 4 reports under this vocabulary (<<decision-probe-version-4>>).
The amendment also decides which playback paths an HDR source permits for a client that declares no dynamic range (<<decision-undeclared-client>>).
That decision holds until clients can declare a dynamic range.
The amendment also decides how a stream copy writes and describes a Dolby Vision source with an SDR compatible base.

A second amendment adds the facts that probe version 5 reports under this vocabulary (<<decision-probe-version-5>>).
Probe version 5 reads the first frames of the chosen video stream before it reports HDR10+ or a Dolby Vision RPU as `ABSENT`.
The second amendment also decides where `MediaFileProbePropertyIssue` lives and which playback paths each issue rules out (<<decision-property-issues>>).
The server derives each issue from the stored probe facts and stores no issue.
The second amendment also decides that the server never copies a Dolby Vision stream whose compatibility identifier disagrees with its signaled transfer.
The server, worker, and client contracts still need answers to the other open questions listed below.
A later amendment to this ADR answers the remaining architectural questions.
The implementation issues resolve the contract questions.

== Context

https://github.com/streamarr/streamarr-server/issues/399[The playback capabilities epic] requires the playlist to describe the media that the worker produces.
A codec name alone does not describe a stream's codec profile, level, bit depth, color properties, or dynamic range.
If the server chooses an output from incomplete source or capability details, the client may fail to decode the video.
The worker may also process colors incorrectly, or the playlist may advertise a format that differs from the media segments.

The probe describes the source, the client reports what the player can accept, and the server chooses the output.
The server, workers, and clients must use the same meanings for the properties they share.
https://github.com/streamarr/streamarr-adr/issues/15[Vocabulary issue #15] tracks the work to define those meanings before the dependent contracts use them.

A video stream can contain both HDR10+ and Dolby Vision information.
An enum that allows only one HDR format would need extra values to describe streams that contain both formats.
The picture's color signaling can also disagree with the base format that the Dolby Vision configuration claims.
The probe records what the source contains.
Whether those properties are valid and agree with one another is one question, and whether a particular player can play the source is a separate one.

Probe versions 1 and 3 report each video stream's codec name, size, frame rate and bitrate.
Neither version reports the bit depth, the chroma subsampling, the rotation or the dynamic range.
Without those facts, the server cannot tell an 8-bit SDR stream from a 10-bit HDR stream.
The server copies the video whenever the client names the source codec.
No client can declare a dynamic range yet.
Issue https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395] adds that declaration.

Streamarr already defines variants, renditions, stream sessions, transcode decisions, and stored probe results.
This ADR builds on those definitions.
Other projects' terms serve as comparison material for those definitions.

== Decision

=== Preserve the established domain language

Use the existing definitions and link to the ADRs that define each concept.

[cols="1,3",options="header"]
|===
|Existing concept |Meaning

|Variant and rendition
|link:0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018] uses variant for an option in the bitrate and resolution ladder.
ADR 0018 reserves rendition for alternate HLS tracks, such as audio languages.

|Stream session and job attempt
|ADR 0018 defines the stream session that manages playback at runtime and the identities for worker jobs and job attempts.
Three kinds of attempt exist, and they are not interchangeable.
A job attempt is one dispatch of a variant's job to a worker.
A replacement attempt is a job attempt that replaces an earlier one for the same variant under link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019]; it keeps the variant's initialization segment, media time and encoder backend (link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037]).
A format attempt is one output format that the server chooses within a playback session, delivered by its own stream session.
An HLS format attempt also has its own initialization segment.
The initial format is the first attempt, and each Auto recovery after a format error adds one, so epic https://github.com/streamarr/streamarr-server/issues/399[#399's] default budget of two means the initial attempt plus one fallback.
A playback session is the logical span of one viewing: it survives replacement stream sessions and holds the format-failure history and the attempt budget, while ADR 0018 keeps `playback` for the token and request surface.
Write the qualified name, because an unqualified "replacement" is ambiguous.

|Transcode decision
|link:0013-stream-decision-architecture.adoc[ADR 0013] combines independent decisions for each stream.
The planned explicit video decision extends that architecture.

|Probe result and stream properties
|link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] defines how to store container and stream properties, retain unknown properties after a successful probe, record terminal probe errors, and use `probe_version`.

|Metadata
|ADR 0032 reserves the unqualified term metadata for descriptive TMDB data.
Use probe properties and stream properties for technical facts.
When discussing an external format, name the format in terms such as Dolby Vision metadata.
|===

Keep the existing `StreamingOptions`, `VideoQuality`, `TranscodeMode`, `MediaProbe`, and `MediaSourceRef` names.
Do not keep `ContainerFormat`: ADR 0037 makes every HLS media segment fragmented MP4 and deletes that type, so the container of delivered media is a fact rather than a decision.
The container of a source file is a probe property named source container, and it never reuses that type.
The user can choose Auto, Original, or a fixed quality.
The transcode mode describes how the worker processes the media to produce the selected output.
Write codec profile or Dolby Vision profile when referring to either video property, because link:0024-identity-authority-by-relationship.adoc[ADR 0024] already defines a Profile as a portable viewing identity.
Keep the units that the worker contract already uses, including bits per second for bitrate and seconds for seek position.

=== Describe source tracks, client capabilities, and output separately

Use the same meanings for shared properties in the records below, but keep each record's purpose distinct.

[cols="1,3",options="header"]
|===
|Record |What the record describes

|Source description
|Describe the individual media track that the probe found.
Keep the source facts unchanged when the server chooses a playback output.

|Client capability declaration
|Describe the combinations that the current player and delivery path can accept.
Include any relevant display constraints.
The server uses the reported capabilities to choose an output, but playback can still fail.

|Planned output
|Describe the output that the server chooses from the source facts, client capabilities, verified worker capabilities, and the user's playback choice.

|Produced output
|Describe the media that the worker produces.
The worker must produce the output that the server selected or report a failure.
The playlist must describe the produced media.
For video delivered as fragmented MP4, the initialization segment carries the codec configuration, the color signaling, the static HDR metadata and the Dolby Vision configuration record, so the worker reads it to assert those properties against the decision (ADR 0037).
HDR10+ metadata and the Dolby Vision RPUs travel in the samples, so asserting them needs sample inspection.
The playlist's codec string must match the initialization segment.
|===

The planned explicit `VideoDecision` belongs within the existing `TranscodeDecision` defined by ADR 0013.
The source and output can have different dynamic ranges.
The proposed fields `sourceDynamicRange` and `outputDynamicRange` would record those two values.
The field names remain open until the video-decision contract is final.

=== Describe dynamic range with one shared structure

Use `VideoDynamicRange` as the shared type and `dynamicRange` as the field on an individual video stream.
In this ADR, video stream means a media track, not the stream session that manages playback at runtime.
Use the same type to describe a source video stream and an output video stream, even when the source and output have different values.
A planned or produced output never holds `UNSPECIFIED`, because the server chooses every value and the worker asserts every value.
Validation enforces that rule, because the shared type permits the value.

Use the following agreed structure.
The TypeScript example shows the fields and values; the example does not choose a wire format or require an implementation language.

[source,typescript]
----
type Presence = "UNSPECIFIED" | "ABSENT" | "PRESENT";

// The Dolby Vision configuration record, kept whole; every value in it is a claim.
type DolbyVisionConfiguration = {
  profile: number;
  level: number;
  baseLayerCompatibilityId: number;
  baseLayer: boolean;
  enhancementLayer: boolean;
  rpu: boolean;
};

type DolbyVision =
  | { presence: "UNSPECIFIED" }
  | { presence: "ABSENT" }
  | {
      presence: "PRESENT";
      declared: DolbyVisionConfiguration | null;
      observedRpu: Presence;
    };

type VideoDynamicRange = {
  compatibleBase: "UNSPECIFIED" | "NONE" | "SDR" | "PQ" | "HLG";
  hdr10Plus: Presence;
  dolbyVision: DolbyVision;
};
----

`compatibleBase` names the standard picture format that a player could use without the advanced HDR information.
The probe derives it when it runs, from the base layer's signaled transfer characteristic and the Dolby Vision claim, and stores it with the probe version so a newer probe can derive it again.
The signaled transfer decides the value: `SDR` for a standard-dynamic-range transfer, `PQ` for SMPTE ST 2084, and `HLG` for ARIB STD-B67.
`PQ` covers both HDR10 and PQ10; whether the static HDR metadata is present is a separate stream property.
`NONE` means the stream has no standard compatible base: Dolby Vision declares none, or the signaled transfer is unspecified while Dolby Vision is present, as in Profile 5.
From probe version 5 on, the `compatibleBase` of a Dolby Vision profile 5 or profile 10.0 stream is `NONE` whatever the signaled transfer says (<<decision-probe-version-5>>).
`UNSPECIFIED` means the probe could not read the transfer and found no Dolby Vision claim.
When the Dolby Vision compatibility identifier disagrees with the signaled transfer, the signaled transfer wins.
The server then derives a `MediaFileProbePropertyIssue` that names both claims (<<decision-property-issues>>).
The `compatibleBase` value does not guarantee that a device can play the source bytes unchanged.
The worker may need to transform the source before the player can use the compatible base.
The server must explicitly choose that change, and the worker must support the change.

`hdr10Plus` records whether HDR10+ information is present, independently of Dolby Vision.
Both `hdr10Plus` and Dolby Vision may be `PRESENT` in the same stream.
`dolbyVision` is a union on `presence`, so the two empty states carry no details.
`PRESENT` means the probe found any of a configuration record, a Dolby Vision sample entry, or an RPU in the samples; `ABSENT` means the probe checked all three and found none; `UNSPECIFIED` means the probe could not check.
Inside `PRESENT`, `declared` holds the configuration record whole or not at all, because the record carries its profile, level, base-layer compatibility identifier and layer flags together, and every value in it is a claim.
`observedRpu` records whether the samples contain the Dolby Vision picture-adjustment instructions, and it is `UNSPECIFIED` when the probe read no frames.
A record that claims RPUs over samples that contain none keeps both facts, and the mismatch is not a `MediaFileProbePropertyIssue` (<<decision-property-issues>>).
A `PRESENT` stream with no record and no observed RPU still counts as Dolby Vision.
The Dolby Vision profile of such a stream could be one with no compatible base.
<<decision-undeclared-client>> decides which playback paths such a stream permits for a client that declares no dynamic range.
The object describes one track; this ADR defers pairing a base-layer track with a separate enhancement-layer track.

Use `Presence` to distinguish information that remains unknown from information that the probe found or confirmed absent.
If the probe cannot check for a feature, do not report the feature as absent.
Leave unknown numeric fields absent or null, and never substitute zero, because zero is a real value for the base-layer compatibility identifier.
The Dolby Vision profile and level describe Dolby Vision signaling.
Keep the Dolby Vision profile and level separate from the codec's profile and level.

Derive the broad HDR or SDR label shown to users from the detailed description.
Do not store another label that can change independently of the detailed facts.
Keep uncertainty visible when the description is incomplete or inconsistent.
The open questions below include how to derive that label.

Keep the typed Protobuf contract that ADR 0018 defines, and keep zero as the explicit unspecified value in enums.
The protocol and generated clients must distinguish an unknown numeric value from a known value.
Map the Dolby Vision union to a `oneof` with an absent arm and a present arm, where no arm set means unspecified, and give every numeric field explicit presence.
Decide that mapping in the first published contract, because moving fields into a `oneof` later is a breaking change.
The TypeScript examples do not permit replacing the worker's Protobuf messages with JSON.
Choose protocol field numbers, generated names, and storage columns when implementing the contract, after answering the open questions about what the properties mean.

[[decision-probe-version-4]]
=== Probe version 4 reports stream-level dynamic-range facts and never reports a per-frame feature as absent

Probe version 4 takes its dynamic-range facts from each video stream's headers and configuration records.
Probe version 4 does not inspect the samples for per-frame HDR information.
link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] lists every fact that probe version 4 stores.
ADR 0032 also governs how probe version 4 results replace version 1 and version 3 results.
This section decides how those facts use this ADR's vocabulary.

* Each video stream reports `dynamicRange` as a `VideoDynamicRange`.
The `compatibleBase` of that `VideoDynamicRange` follows the signaled transfer under the `compatibleBase` rules above.
* `dolbyVision` is `PRESENT` when the probe finds a Dolby Vision configuration record (`dvcC` or `dvvC`) or a Dolby Vision sample entry.
A sample entry is the four-character code in the initialization segment that names a video stream's coding format, such as `dvh1` or `hvc1`.
When `dolbyVision` is `PRESENT`, `declared` holds the whole configuration record.
`declared` is null when the probe found only the sample entry.
`observedRpu` is `UNSPECIFIED`, because the RPUs travel in the samples and probe version 4 does not inspect them.
* When the probe finds neither a configuration record nor a Dolby Vision sample entry, `dolbyVision` is `UNSPECIFIED`.
`dolbyVision` is never `ABSENT` in probe version 4, because `ABSENT` requires the probe to check the samples for RPUs.
* `hdr10Plus` is `UNSPECIFIED`, because HDR10+ information travels only in the samples.
* Each video stream reports its bit depth.
* Each video stream reports its chroma subsampling.
* Each video stream reports the HDR10 static metadata that its container declares.
The HDR10 static metadata is the mastering display color volume and the content light level.
The probe reads the static metadata from the stream side data that an MP4 `mdcv` or `clli` box or the Matroska mastering elements provide.
The probe does not read the SEI messages in the HEVC bitstream.
So a PQ stream without declared static metadata can still be HDR10.
Probe version 4 therefore does not tell HDR10 from PQ10.

When the Dolby Vision compatibility identifier disagrees with the signaled transfer, probe version 4 keeps both facts.
Probe version 4 keeps the whole configuration record and the signaled transfer that decides `compatibleBase`.
No probe version stores a `MediaFileProbePropertyIssue`.
The server derives each issue from the stored facts, including the facts of a probe version 4 outcome (<<decision-property-issues>>).

*Why:* Probe version 4 reads each stream's headers and configuration records.
Probe version 4 does not inspect the samples for per-frame HDR information.
A feature that travels per frame therefore stays unchecked.
Under this ADR, a probe never reports an unchecked feature as absent.
ADR 0032 gives the measurements behind the new facts.

[[decision-probe-version-5]]
=== Probe version 5 reads the first frames of the chosen video stream before it reports a per-frame feature as absent

Probe version 5 reports every fact of probe version 4.
Probe version 5 also reads frames of the chosen video stream.
The chosen video stream is the first video stream that is not an attached picture, such as embedded cover art (ADR 0032).
link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] lists every fact that probe version 5 stores.
ADR 0032 also governs how probe version 5 results replace probe version 4 results.
This section decides how those facts use this ADR's vocabulary.

* The probe reads the first 3 frames of the chosen video stream.
The probe reads fewer frames when the stream holds fewer than 3.
The probe reads no frame of any other stream.
Each video stream reports whether the probe read its first frames.
* For the chosen video stream, `hdr10Plus` and `observedRpu` are `PRESENT` or `ABSENT` when the probe can see the feature in what the probe read.
`ABSENT` means that what the probe read carries no such information.
A feature that the probe cannot see in a codec stays `UNSPECIFIED`.
A video stream whose frames the probe did not read reports `ABSENT` for no feature.
* For HEVC and AV1, the probe finds HDR10+ information and RPUs in the side data that ffprobe reports for each frame.
* FFmpeg's decoders lose some RPUs before ffprobe reports a frame.
FFmpeg's H.264 decoder drops the NAL (network abstraction layer) units of type 28, which carry the RPUs of Dolby Vision profile 9.
FFmpeg's HEVC decoder ignores an RPU that is not the last NAL unit of its sample, and an RPU that it cannot parse.
For H.264 and HEVC, the probe therefore also parses the NAL units of the packets that hold the frames it read.
`observedRpu` is `PRESENT` when either the frames or those packets hold an RPU.
`observedRpu` is `ABSENT` only when the probe could delimit every NAL unit of those packets and found no RPU.
* For the chosen video stream, `dolbyVision` is `ABSENT` when the probe found no configuration record, no Dolby Vision sample entry and no RPU in what the probe read.
* Every other video stream keeps the dynamic-range facts of probe version 4.
For every other video stream, `hdr10Plus` and `observedRpu` stay `UNSPECIFIED`, and `dolbyVision` is never `ABSENT`.
* When the probe finds an RPU, `dolbyVision` keeps the fields of the first RPU's header that tell the Dolby Vision profile.
The probe takes that header from the frames, or from the packets when the frames show no RPU.
For a stream without a configuration record, the probe derives the Dolby Vision profile from those header fields, the way FFmpeg 8.1 guesses the profile.
For HEVC, an RPU header with `vdr_rpu_profile` 0 and `bl_video_full_range_flag` 1 means profile 5.
For AV1, the same header fields mean profile 10.0.
The worker contract spells out the rule for each codec.
An RPU header does not carry the compatibility identifier of profile 8.
The signaled transfer therefore still decides the compatible base of a profile 8 stream without a configuration record.
* Dolby Vision profiles 5 and 10.0 have no compatible base.
Profile 5 is HEVC, and profile 10.0 is AV1.
A picture of either profile is correct only after the player reshapes the picture with the stream's RPUs.
From probe version 5 on, the `compatibleBase` of a profile 5 or profile 10.0 stream is `NONE` whatever the signaled transfer says.
The probe knows profile 5 from the configuration record, or from the first RPU header when the stream has no configuration record.
The probe knows profile 10.0 from a configuration record with profile 10 and compatibility identifier 0, or from the first RPU header when the stream has no configuration record.
This rule covers a profile 5 stream tagged BT.709.
This rule also covers a profile 5 stream in MPEG-TS without the Dolby Vision descriptor.
* When `dolbyVision` is `PRESENT`, the probe also reports whether a sample that the probe read starts with an RPU ahead of the sample's picture.
The RPU of a picture belongs after that picture, in the same sample.
At least one muxer starts a new sample at each RPU, so each RPU sits in the next picture's sample.
The last sample of such a file holds an RPU and no picture.
The probe reads where the RPUs sit from the NAL units of the packets, for H.264 and HEVC.
The probe reports this fact as `UNSPECIFIED` when the probe could not delimit the samples that hold the RPUs, and always for AV1.
* Each video stream reports its codec profile, codec level and codec tier as typed values.
The probe reads those values from the stream's decoder configuration record or sequence header.
The probe never maps ffprobe's profile name.
The probe maps a codec profile that the worker contract does not name to `UNSPECIFIED`.
Keep the codec profile and level separate from the Dolby Vision profile and level, as the rules above require.
* Each video stream reports its color primaries, transfer characteristics, matrix coefficients and color range.
Each value of the primaries, the transfer and the matrix names one ITU-T H.273 code point.
The worker contract numbers its enum values on its own, so an enum value's number need not equal its H.273 code point.
For example, the perceptual quantizer is H.273 code point 16 and enum number 14, and enum number 16 names hybrid log-gamma.
Code that reads or writes a code point maps it to its enum value explicitly and never casts one to the other.
The probe maps a value that the worker contract does not name to `UNSPECIFIED`.
The worker contract carries none of ffprobe's strings for the codec profile or the color properties.
* The probe reads the mastering display and the content light level separately.
When the container declares no mastering display, the probe takes the mastering display from the first frame of the chosen video stream.
When the container declares no content light level, the probe takes the content light level from the first frame of the chosen video stream.
Some streams carry the static metadata only in the SEI messages of their HEVC bitstream.
Every HEVC stream in MPEG-TS or in a raw HEVC file works this way.
The probe marks a value as omitted when the stream carries the value but the probe could not read the value.
FFmpeg's Matroska demuxer drops a MasteringMetadata element when neither its primaries nor its luminance are complete.
When ffprobe reports no mastering display for the chosen video stream of a Matroska file, the probe checks the track for that element itself.
The probe marks the mastering display as omitted when the track holds the element.
A PQ stream is PQ10 when the probe read its first frames and found neither a mastering display nor a content light level, and the probe omitted neither value.
A stream with an omitted value carries static metadata, so that stream is never PQ10.
Probe version 5 therefore tells HDR10 from PQ10.

*Why:* A probe that reads no frames cannot report a per-frame feature as `ABSENT`.
A malformed profile 9 file's first sample holds no RPU, because the muxer moved that RPU into the next sample.
A probe that read only the first frame would report that file's RPUs as `ABSENT`, and could not see where the RPUs sit.
ffprobe cannot observe a profile 9 stream's RPUs when it reads frames, because FFmpeg's H.264 decoder drops the NAL units that carry those RPUs.
ffprobe also misses the RPUs of an HEVC stream whose RPU is not the last NAL unit of its sample, such as a malformed profile 5 stream.
Such a profile 5 stream without a configuration record would read as Dolby Vision `ABSENT`, and the server could copy it with teal colors.
FFmpeg guesses the Dolby Vision profile from the first RPU header when the configuration record is missing.
The pinned ffprobe reports the fields of that header.
ffprobe reports static metadata that only the bitstream carries as side data of the first frame.
For comparison, Jellyfin reads only the first video frame, and sets only a nullable HDR10+ flag from that frame.
ADR 0032 gives the measurements behind the new facts.

[[decision-property-issues]]
=== The server derives each property issue from the stored probe facts when it decides, and stores no issue

The probe reports facts.
The worker contract carries no `MediaFileProbePropertyIssue`.
The server stores the facts under ADR 0032's rules for source snapshots, `probe_version` and guarded publication.
The server derives each `MediaFileProbePropertyIssue` from the stored facts when the server makes a decision that the issue affects, such as the stream decision of link:0013-stream-decision-architecture.adoc[ADR 0013].
The server stores no `MediaFileProbePropertyIssue`.
An issue therefore never outlives the facts that the issue comes from.
When the server stores a file's new probe outcome, the file's issues follow the new facts.
A fix to the rule that derives an issue takes effect at the server's next decision.
A fix to such a rule needs no new probe version and no re-scan.
The server derives an issue from any stored outcome whose probe version reports the facts that the issue needs.

The server derives the following issues.
Each issue lists the playback paths that the issue rules out.

* A Dolby Vision compatibility identifier that disagrees with the signaled transfer.
Dolby Vision profile 7 with SDR transfer and color properties is an example.
The server never copies such a stream, whatever the client declares.
The server encodes such a stream.
The encode interprets the signaled transfer.
So the stream's `compatibleBase` follows the signaled transfer, and ADR 0013 decides from that compatible base whether the worker tone-maps.
From probe version 5 on, a Dolby Vision profile 5 or profile 10.0 stream never has this issue, because its `compatibleBase` is `NONE` whatever its signaled transfer says (<<decision-probe-version-5>>).
* An RPU that starts a sample.
The malformed profile 9 files of <<decision-probe-version-5>> have this issue.
The server never copies such a stream.
The server encodes such a stream.

A configuration record that claims RPUs over frames that hold none is not a `MediaFileProbePropertyIssue`.

*Why:* The probe facts record what the source holds.
A property issue records the server's judgment of those facts.
A judgment stored beside the facts would need a new probe version, or a migration, for every fix to the rule.
A stored judgment could also disagree with the facts that the judgment comes from.
ADR 0032 makes the same choice for handler names.
Under ADR 0032, the server fixes its own rule for handler names without a new probe.
A Dolby Vision stream whose compatibility identifier disagrees with its signaled transfer makes contradictory claims.
The server cannot tell which claim a player would follow.
Before this amendment, the server already encoded such a stream and interpreted the signaled transfer.
Copies of a malformed profile 9 file failed in headless players where the same stream muxed correctly played.
ADR 0013 gives those player measurements.

=== Preserve source facts and report problems separately

Use `MediaFileProbePropertyIssue` for a problem found when checking the container or stream properties reported by a media-file probe.
The term covers container properties and properties of any stream type, including video, audio, and subtitles.
A probe can succeed while the reported properties contain problems.
Keep `MediaFileProbePropertyIssue` distinct from the worker contract's `ProbeFailure`, which reports why a probe attempt failed, and from ADR 0032's persisted `probe_error`, which records a terminal media error.
Include `Probe` in the name so readers do not mistake the issue for a problem with a filename, path, or stored `MediaFile` record.

Preserve the source facts that the probe observed.
Check the source facts and record any specific problems separately from the observed facts.
Distinguish missing information from information that contradicts another observed fact.
ADR 0032 already allows a probe to succeed when some properties remain unknown.
An incomplete description alone does not require the probe to report a terminal error.

Check the specific Dolby Vision profile and the properties that the profile requires.
Some valid profiles have an SDR fallback base, so a stream can legitimately contain both Dolby Vision information and an SDR base.
When claims conflict, record which claims disagree and keep the original observed facts.

Choose how to process colors from the actual picture signal that the selected playback path uses.
Do not tone-map from HDR to SDR solely because Dolby Vision information is present.
Check whether source properties are valid separately from whether a particular player, container, delivery path, and display can handle the source.
If a malformed stream plays on one player, another player may still fail to handle the stream safely.

The server chooses usable playback paths under the Auto and manual rules recorded in epic https://github.com/streamarr/streamarr-server/issues/399[#399].
A problem found while checking source facts does not add a new reason to try another format automatically.
Only Auto can automatically change format after an explicit playback error that concerns the format.
Manual and Original choices remain fixed, even when a platform selects Original by default.
When the rules permit a format attempt, the server explicitly chooses the new output and leaves the source description unchanged.
The probe recognizes Dolby Vision and HDR10+ in a source.
A stream copy passes HDR10+ information through unchanged.
A stream copy also passes the Dolby Vision RPUs through unchanged.
An SDR-base Dolby Vision copy is a stream copy of a Dolby Vision source whose `compatibleBase` is `SDR`.
The worker writes the sample entry of an SDR-base Dolby Vision copy as `hvc1` or `avc1`.
A stream copy keeps the Dolby Vision configuration record only where the pinned FFmpeg build allows the record, as link:0013-stream-decision-architecture.adoc[ADR 0013] decides.
The playlist describes an SDR-base Dolby Vision copy by the copy's base layer.
The playlist entry of an SDR-base Dolby Vision copy takes its `CODECS` attribute from the base sample entry, `hvc1` or `avc1`.
The same playlist entry declares `VIDEO-RANGE=SDR`.
The same playlist entry carries no `SUPPLEMENTAL-CODECS` attribute.
Only the playlist attributes that would announce Dolby Vision on a PQ or HLG base stay deferred.
This ADR defers encoding Dolby Vision or HDR10+ output; it does not defer passing them through.
<<decision-undeclared-client>> decides which playback paths a Dolby Vision source permits for a client that declares no dynamic range.
The server never copies a source with no compatible base to a client that declares no Dolby Vision support.

[[decision-undeclared-client]]
=== A client that declares no dynamic range receives copies only of sources with an SDR or unspecified compatible base

This section decides which playback paths an HDR source permits for a client that declares no dynamic range.
The answer holds until clients declare dynamic ranges under https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395].
Today every client declares none.
A client that declares no dynamic range may receive a stream copy only of a source whose `compatibleBase` is `SDR` or `UNSPECIFIED`.
The source must also carry no Dolby Vision compatibility identifier that disagrees with the source's signaled transfer.
The source must also have no other `MediaFileProbePropertyIssue` that rules out a copy (<<decision-property-issues>>).
Every other source permits only an encode to 8-bit 4:2:0 SDR.
The planned output of that encode has `compatibleBase` set to `SDR`.
The planned output also has `hdr10Plus` and `dolbyVision` set to `ABSENT`.
Apart from those property issues, the answer depends on `compatibleBase` alone.
The source's Dolby Vision profile changes the answer only through `compatibleBase`, as for profiles 5 and 10.0.
The source's HDR10+ presence does not change the answer.
A PQ or HLG source without Dolby Vision or HDR10+ also permits only the SDR encode.
A `PRESENT` Dolby Vision stream whose profile is unknown follows the same `compatibleBase` rule.
When that stream's signaled transfer is unspecified, its `compatibleBase` is `NONE`.
The server therefore encodes that stream.
A Dolby Vision stream whose compatibility identifier disagrees with its signaled transfer permits only the SDR encode, such as Dolby Vision profile 7 with SDR transfer and color properties.
That limit is not interim.
The server never copies such a stream, whatever the client declares (<<decision-property-issues>>).
link:0013-stream-decision-architecture.adoc[ADR 0013] records the copy rule, the SDR encode and its tone mapping, and a copy's planned output.
https://github.com/streamarr/streamarr-server/issues/66[streamarr/streamarr-server#66] adds a probe version that stores keyframe positions.
From that probe version on, link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] lets the server offer a stream copy only after the server knows the source's keyframe positions.
Under this answer, the server copies Dolby Vision profile 8.2 and 9 sources, whose `compatibleBase` is `SDR`.
The server encodes a profile 9 source in which an RPU starts a sample (<<decision-property-issues>>).
ADR 0013 records the player evidence for those copies.

*Why:* No playlist can yet describe an HDR copy truthfully to a player that declared nothing.
ADR 0013 gives the measurements behind this decision.

=== Examples show how to use the shared terms

The examples below apply the agreed meanings.
The examples leave the client-capability and validation-result schemas open.

The following source has a PQ-compatible base, HDR10+, and Dolby Vision Profile 8.1, and the probe read frames and saw the RPUs.
The example assumes that the relevant probe facts agree.

[source,typescript]
----
const sourceDynamicRange: VideoDynamicRange = {
  compatibleBase: "PQ",
  hdr10Plus: "PRESENT",
  dolbyVision: {
    presence: "PRESENT",
    declared: {
      profile: 8,
      level: 6,
      baseLayerCompatibilityId: 1,
      baseLayer: true,
      enhancementLayer: false,
      rpu: true,
    },
    observedRpu: "PRESENT",
  },
};
----

A client that reports HDR10 support declares that it accepts a PQ base with static HDR metadata; it does not necessarily support every combination of Dolby Vision, HDR10+, container, and delivery path.
The server may consider a PQ output only when the user's playback choice permits HDR and a worker can make the required changes to the source.
The server must explicitly choose the output.
The source description still records both HDR features even when the output contains neither enhancement.

=== Answer the open questions before finalizing the contracts

The questions below remain open, and they do not add agreed fields or requirements.
A later amendment to this ADR answers the remaining architectural questions.
<<decision-probe-version-5>> answers what evidence the probe needs before it reports HDR10+ or an RPU as `ABSENT`.
<<decision-property-issues>> answers where each `MediaFileProbePropertyIssue` lives and which playback paths each issue rules out.
<<decision-undeclared-client>> decides which playback paths a Dolby Vision or HDR10+ source permits for a client that declares no dynamic range.
That decision holds until clients declare dynamic ranges.

Architectural questions:

* Define how to derive the broad HDR or SDR label when the description is complete, incomplete, conflicting, or unfamiliar.
Include sources known to have HDR when the HDR kind remains unknown.
Keep source facts even when those facts prevent a simple display label.
* Decide which playback paths a Dolby Vision or HDR10+ source permits for a client that declares a dynamic range but neither Dolby Vision nor HDR10+.
The question includes a `PRESENT` Dolby Vision stream whose Dolby Vision profile is unknown.
Issue https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395] answers this question.
* Define which combinations and limits a client can report for codec, profile, level, bit depth, dynamic-range features, container, player, and display.
The contract must describe how a supported value for one property constrains the values of other properties.
Do not assume that a client supports every combination of the values in separate lists unless the contract explicitly gives the lists that meaning.

Contract questions, resolved inside the implementation issues:

* Define the server's `MediaFileProbePropertyIssue` type, including how to identify the affected container or stream properties, and decide which problem codes and severities to use.
The worker contract carries no issue (<<decision-property-issues>>).
* Finalize the explicit video-decision fields, decide how to encode the fields on the wire under the `oneof` rule above, and map the fields to the generated server, worker, and client types.
Keep unknown numeric values distinct from known values, and keep source properties distinct from the selected output properties.
The existing `StreamingOptions` record mixes the user's choice with client capability facts, and `VideoQuality` has no value for Original; the capability and video-decision issues separate those facts and add the missing choices.

https://github.com/streamarr/streamarr-server/issues/394[Server probe #394], https://github.com/streamarr/streamarr-server/issues/395[client capabilities #395], and https://github.com/streamarr/streamarr-server/issues/396[explicit video decision #396] depend on this shared vocabulary.
This ADR does not meet those issues' prerequisites until the required definitions are complete.
Publish the protocol from the server repository first.
Implement the published contract in the worker, then update the server's pinned worker image as the epic requires.
When adding stored probe properties, follow ADR 0032's `probe_version` rules.

The worker contracts of probe versions 4 and 5 settle how the contracts spell the codec and color values of a video stream.
Probe version 4 defines the bit depth, the chroma subsampling and the static HDR metadata fields.
The static HDR metadata fields are the mastering display, the maximum content light level and the maximum frame-average light level, in the units of the HEVC SEI messages.
Probe version 5 defines the typed codec profile, codec level and codec tier.
Probe version 5 also defines the color primaries, transfer characteristics, matrix coefficients and color range.
Each primaries, transfer and matrix value names an ITU-T H.273 code point, and its enum number need not equal that code point.

Explicitly deferred:

* Defer encoding Dolby Vision or HDR10+ output.
A stream copy still passes HDR10+ information and Dolby Vision RPUs through unchanged.
Recognizing Dolby Vision and HDR10+ in source files stays in scope.
* Defer reading the frames of video streams other than the chosen video stream.
Every other video stream keeps the dynamic-range facts of probe version 4.
* Defer deciding whether a `MediaFileProbePropertyIssue` rules out direct play.
Direct play waits for client capability declarations (link:0045-clients-direct-play-covered-files-and-use-platform-players.adoc[ADR 0045]), and https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395] decides that question.
* Defer showing a `MediaFileProbePropertyIssue` to clients.
ADR 0032 also defers exposing stream properties in GraphQL.
* Defer conversion between Dolby Vision profiles, such as Profile 7 to Profile 8.1.
* Defer distinguishing a full enhancement layer from a minimal one.
The configuration record has no flag that tells the two kinds of enhancement layer apart.
Detection needs the RPUs parsed from frames.
Probe version 5 keeps only the RPU header fields that tell the Dolby Vision profile.
Adding the field later is an additive change.
* Defer pairing a base-layer track with a separate enhancement-layer track; the dynamic-range description covers one track.
* Defer the playlist attributes that announce a PQ or HLG video range.
Also defer the playlist attributes that announce Dolby Vision on a PQ or HLG base.
https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395] decides when a copy carries those attributes.
https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] builds those attributes.
This ADR fixes the facts that those attributes read.
This ADR already decides the playlist entry of an SDR-base Dolby Vision copy.
* Leave codec preference to link:0009-h264-plus-av1-codec-strategy.adoc[ADR 0009].
An amendment to ADR 0009 settles only ADR 0009's codec-preference clause.
ADR 0037 supersedes ADR 0009's container clause, so the codec preference must not reintroduce a container that follows the codec.
* Keep the playback rules already recorded in the epic, including retry limits, how to allocate the quality ladder, and client controls.
The issues dedicated to those rules track the work to implement them.
* Keep the existing stream-session, variant, rendition, probe, and transcode-decision names unless a rename solves a specific problem.
Do not rename those concepts solely to match another project.

== Consequences

* The server, worker, and clients use shared properties with the same meanings, while each component keeps its own responsibilities.
Keep source, capability, and output records distinct; one record cannot replace another.
* The shared structure preserves simultaneous HDR features and unknown values without adding an enum value for every combination.
Define rules that derive and check the properties for each profile.
Use representative media examples to check those rules.
* When a problem arises, the original source facts remain available to explain why the server chose an output or why playback failed.
Record the problem separately from the source facts.
The server derives each problem from the stored facts when the server decides, so a fix to the rule changes the next decision without a new probe version or a re-scan.
* A Dolby Vision stream whose compatibility identifier disagrees with its signaled transfer plays through an encode for every client.
That rule still holds after clients can declare Dolby Vision.
* The upgrade to probe version 5 probes every library again, and each of those probes reads the first frames of the chosen video stream.
* When the server chooses SDR output, the source description keeps the HDR facts that the probe found.
The server cannot silently change a manual choice, and the playlist must describe the actual output that the server selected.
* A stream copy of a Dolby Vision or HDR10+ source delivers the HDR10+ information and the Dolby Vision RPUs unchanged.
The client's declaration decides whether such a copy is eligible.
Until clients declare dynamic ranges, <<decision-undeclared-client>> decides whether the copy is eligible.
An SDR-base Dolby Vision copy still carries the Dolby Vision RPUs.
The playlist entry of an SDR-base Dolby Vision copy describes only the copy's SDR base layer.
* This ADR records the accepted terms and structure and lists the questions that remain open.
It does not claim that the contracts or application behavior already exist.
* Amend ADR 0013's video-decision section when implementing https://github.com/streamarr/streamarr-server/issues/396[#396].
Continue to follow the existing ADR definitions and the order of work recorded in the epic.

== Rejected Alternatives

* A single HDR boolean discards the format details that the server needs to choose an output and explain that choice.
* An enum that allows only one HDR format needs additional values for streams that combine Dolby Vision and HDR10+ and cannot retain all the source details on its own.
* A set of HDR format flags describes combinations but cannot distinguish an unknown feature from an absent one.
* A single Dolby Vision object with a presence flag beside nullable details lets the flag drift from the details, and it cannot record a configuration record that claims RPUs over samples that contain none; the union keeps the record whole and the observed RPU separate.
* Separate source and output dynamic-range types would stop an output from holding `UNSPECIFIED`, but every field would exist twice; validation enforces the rule instead.
* A compatible base edited independently of the signaled transfer and the Dolby Vision claim could drift from both; the probe derives it, and a newer probe version derives it again.
* Broad and detailed HDR labels can disagree if either label can change independently; derive the broad label from the detailed facts and the results of checking those facts.
* If missing information becomes confirmed absence or SDR, the source record loses the uncertainty that ADR 0032 preserves.
* If Dolby Vision alone triggers tone mapping, the worker ignores the picture signal and the specific profile.
* If one successful player test establishes support for all players, the server ignores differences between players and delivery paths.
* If Streamarr copies another project's glossary without a specific reason to rename its concepts, readers must learn new names without gaining clearer meanings.
* A generic setting that allows invalid streams hides which problem the stream has and which playback paths the problem rules out; the design records each problem instead.
* If a stream-level probe reports HDR10+ or Dolby Vision as `ABSENT` when it finds no sign of them, the probe breaks the rule that an unchecked feature is not absent.
A Dolby Vision stream can carry its RPUs only in the samples.
* Announcing Dolby Vision with `SUPPLEMENTAL-CODECS` in an SDR-base Dolby Vision copy's playlist entry changed nothing measurable in any headless player.
The playlist leaves that attribute out unless a later need appears.
* A copy of a Dolby Vision profile 7 stream tagged SDR would trust a source that makes contradictory claims.
The server never copies such a stream, even to a client that declares Dolby Vision.
* An encode of such a stream could interpret the compatibility identifier instead of the signaled transfer.
The server keeps interpreting the signaled transfer, as the server did before the second amendment.
* Probe version 4 could read the RPU header of a Dolby Vision stream's first frame, to find a stream without a configuration record that is really profile 5.
This ADR keeps probe version 4 at stream-level facts instead, and probe version 5 reads the RPU header.
* Encoding every Dolby Vision stream without a configuration record would override the `compatibleBase` rule for those streams.
Probe version 5 identifies profile 5 from the first RPU header instead.
* Letting the signaled transfer decide the `compatibleBase` of a profile 5 stream would give a profile 5 stream tagged BT.709 an SDR compatible base.
The server would then copy that stream, and the copy plays with teal colors.
A profile 10.0 stream has no compatible base either, so the same rule covers it.
* Reading an HEVC stream's RPUs only from the frames that ffprobe decodes would miss an RPU that is not the last NAL unit of its sample.
A malformed profile 5 stream without a configuration record would then read as Dolby Vision `ABSENT`.
* Deriving a `MediaFileProbePropertyIssue` from a configuration record that claims RPUs over frames that hold none.
That issue would rule out no playback path.
* Reading only the first frame, as Jellyfin does, would miss the RPUs of a malformed profile 9 file.
That file's first sample holds no RPU.
* Reading an H.264 stream's RPUs from the frames that ffprobe decodes would report every profile 9 stream's RPUs as `ABSENT`.
FFmpeg's H.264 decoder drops the NAL units that carry those RPUs.
* Storing each `MediaFileProbePropertyIssue` with the probe outcome would need a new probe version, or a migration, for every fix to an issue rule.
A stored issue could also disagree with the facts that the issue comes from.
* Having the worker report property issues would put the issue rules in the worker.
Each fix to an issue rule would then need a new probe version and a re-scan of every library.
* Putting caption detection into probe version 4 would delay https://github.com/streamarr/streamarr-server/issues/501[streamarr/streamarr-server#501], which plays HDR and 10-bit sources as SDR.
Caption detection decodes the video's keyframes.
Probe version 4 reads no frames.
The audio and subtitle stream titles, handler names and hearing-impaired flags come from the same ffprobe pass as the other version 4 facts, so probe version 4 reports all three (ADR 0032).
Each change after probe version 4 that adds a fact increases the probe version when that change merges.
When an upgrade needs new probe data, the server queues a re-scan itself, as ADR 0032 decides.
* Giving no interim answer before clients declare dynamic ranges would keep copying HDR sources to every client.
ADR 0013 records that those copies fail in Apple's players when the playlist declares the copies SDR.
* A narrower interim answer would stop copying only Dolby Vision profile 5 and 10-bit H.264 sources.
The narrower answer would still copy PQ and HLG sources to a client that declares no dynamic range.
