= ADR 0034: Release Please Owns Maven Release Versions

== Status

Proposed

== Context

Release Drafter calculated GitHub release versions independently of the Maven POM.
The latest published GitHub release was `v0.0.10`, while Maven still identified the server as `0.0.1-SNAPSHOT`.
Container metadata used the GitHub release version, so it could disagree with the packaged application.
Sonar's previous-version new-code definition also retained a baseline from 2022 because the Maven version never advanced.
Manual release and snapshot updates would create another maintenance obligation and allow drift to recur.

== Decision

Use Release Please's Maven strategy as the single owner of Maven version changes, changelogs, release tags, and GitHub release metadata.
Run the pinned SDK with a checked-in npm lockfile under `.github/release`, outside the application buildpack's root dependency detection.
Keep one release PR current with `main`, and leave it open until a maintainer chooses to squash-merge it under the existing required-check ruleset and strict base freshness requirement.
Use Release Please's documented merge-to-release lifecycle and default published-release behavior: merging the stable release PR is the single manual gate, after which Release Please tags the merged revision and publishes its GitHub release automatically.
Auto-merge only the development snapshot PRs under the same required checks. Snapshot updates do not create GitHub releases.
Treat each release as a fixed version and source revision. Subsequent work belongs to later release PRs, rather than moving an existing release's tag.
Serialize release reconciliation and reload release state after tagging before preparing the next PR.
Use commit metadata for SemVer decisions, including compatibility with existing structural and behavioral subjects; PR labels do not compute an independent version.
Keep release PR bodies factual, omit author attribution from release notes, and supply an empty squash commit body.
Allow only the release bot to use Release Please's upstream `chore(main): release X` subjects, with an empty squash body. Human subjects retain the repository's structural and behavioral conventions.
Use the native Maven strategy and PR grouping with configured headers, footers, and the version-bearing upstream title format. No custom strategy, title parser, or metadata plugin is required.
The native strategy recognizes snapshot updates, and ordinary `chore:` commits are hidden housekeeping that do not initiate another release.

Authenticate through a dedicated, organization-owned release App installed only on `streamarr/streamarr-server`, with contents, pull-request, and issue write access and no branch-rule bypass.
Use only its `RELEASE_APP_CLIENT_ID` and `RELEASE_APP_PRIVATE_KEY` repository secrets; do not fall back to the FFmpeg App.
Install and test the tooling before minting the App token.
Check that repository auto-merge is enabled before creating releases.
Request auto-merge only for snapshot PRs, using the exact head observed by the workflow so a concurrent head change requires another reconciliation.

Preserve the existing container builds and FFmpeg verification from ADR 0029.
The GitHub release publication event starts image publishing automatically. The release App's token allows that event to trigger the downstream workflow.
Before publishing images, require an already-published GitHub release, a stable SemVer tag whose commit belongs to `main`, and a tagged Maven version equal to the release version.
Build both architectures from that exact commit and use the validated version for image tags and OCI metadata.
Require an already-published GitHub release for manual image publishing retries and apply the same checks; a pre-created draft tag alone is insufficient.
Only the current GitHub release can advance Docker's `latest` tag, so retrying an older release cannot regress it.

Bootstrap from the last published GitHub release and let Release Please create the initial snapshot transition.
Resolve outstanding code-quality findings independently of the version migration.

== Consequences

Version and release-note preparation becomes automatic. A maintainer reviews the proposed version and notes, then merges the release PR after GitHub's required checks pass; publication needs no second approval.
The release tag and GitHub release record the merged stable POM version. Image publishing and the next development snapshot proceed automatically from that baseline.
Existing `behavioral:` and `structural:` subjects produce patch releases without extra labels or body metadata; larger automatic bumps require explicit semantic commit metadata.
The release App has its own installation and credential lifecycle; its keys can be rotated or revoked independently of FFmpeg synchronization.
The FFmpeg App retains its existing contents-only permissions.
The release tooling adds a small locked Node dependency tree, tested in CI and maintained by Renovate.
Existing tags whose POM version disagrees with their release version cannot be republished through the new workflow.

== Rejected Alternatives

* Run Release Drafter and Release Please together — leaves two independent version calculators and release-note owners.
* Require a separate draft-publication approval after merging the release PR — adds a second manual gate where the documented merge-to-release lifecycle already provides release timing control.
* Share the FFmpeg App's credentials — couples two independent automations to the same permissions and key rotation.
* Patch the POM after publishing a GitHub release — the release tag would not record the version of the published Maven artifact.
* Use a build number as Sonar's project version — advances the baseline on every build instead of following the release lifecycle.
