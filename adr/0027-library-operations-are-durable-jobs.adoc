= ADR 0027: Library Operations Are Durable Jobs; a Restart Runs Them Again, and a Stop Leaves the Library Usable

== Status

Accepted

NOTE: This text replaces the first proposal of ADR 0027, "Library Scan and Refresh Are Claimed Atomically in the Database and Run on a Single Instance", which Streamarr never built or accepted.
The ADR keeps its number, and its file name follows the new decision.

== Context

link:0026-mutation-payloads-and-error-channels.adoc[ADR 0026] fixes the contract of `scanLibrary` and `refreshLibrary`: each returns the `Library` node, accepted is not completed, and a client observes `Library.status` afterwards.
ADR 0026 leaves the execution protocol to this ADR.

Library work runs in memory today:

* A scan or a refresh starts on a bare virtual thread, in-memory sets and a per-library mutex decide whether a library is busy, and only a log line reports a failure.
* At startup and at shutdown, a crash-recovery service marks every library left `SCANNING` or `REFRESHING` as `UNHEALTHY`, so a restart discards the work and reports a failure that nobody caused.

https://github.com/streamarr/streamarr-server/issues/418[#418] keeps a scan `SCANNING` until every required result is recorded, so a first scan of a large library runs for hours.
link:0038-scans-remove-media-only-when-files-are-confirmed-missing.adoc[ADR 0038] adds a third kind of library operation, removal of items with missing files, and needs every kind to stop on request and scans to run on a schedule.

Probes already run as durable db-scheduler work, and link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] persists their results; https://github.com/streamarr/streamarr-server/issues/412[#412] moves artwork to db-scheduler as well.
db-scheduler has no notion of a job that owns several scheduled tasks, cannot report when a group of them has finished, and keeps no history of attempts.
A job that spans many tasks therefore belongs to Streamarr.

== Decision

A library operation is a durable job that Streamarr owns.
The mutation that requests it claims the library in its transaction, and one scheduled task runs it.
A restart runs the operation again from the start, and its tasks run in memory.
A stop admits no new tasks, lets running tasks finish, and leaves the library usable.

=== Vocabulary

Library processing is described as Job -> Task -> Step -> Attempt.
This combines the conventional decomposition of jobs into tasks with Spring Batch's distinction between a processing step and an execution of that step.
Spring Batch separates a job's definition, one logical run identified by its parameters, and one execution of that run; a library operation run again after a restart is another execution of the same logical run, and Streamarr does not record executions separately.
In Streamarr, tasks group work for a file, title or library item.

Job:: A requested operation with an overall completion criterion.
A library operation is one kind of job; a transcode job is another, and it has attempts directly, with no tasks or steps.
Library operation:: The job that scans a library, refreshes it, or removes its items with missing files.
Streamarr stores it as a durable row from its claim to its end.
Task:: A distinct portion of a job's work, grouped around one subject: a file in a scan, a title in a refresh, a library item in a removal.
A task is defined by its work, not by the thread that runs it, and it requires one or more steps.
Step:: A logical operation that can be executed and retried independently, such as identify, fetch poster, fetch backdrop, probe, or fetch person or company artwork.
A step keyed by its subject, such as a probe today and artwork after https://github.com/streamarr/streamarr-server/issues/412[#412], can be required by several tasks and jobs; they require it without owning it, and stopping a job never cancels it.
Attempt:: One execution of a retryable unit of work: a step in library processing, and the transcode job itself in transcoding.
Item result:: The latest recorded outcome of a step for a subject (https://github.com/streamarr/streamarr-server/issues/417[#417]).
It carries the id of the operation that it was produced for, if any.
It is not an attempt history: an attempt that crashes records nothing.
Scheduled task:: A persisted db-scheduler task instance, as distinct from its registered task definition: the one that runs each library operation, or a step that must survive a restart.
Streamarr uses the term only at the scheduling boundary.

Streamarr aims to retry each step independently.
It already retries the probe and identify steps independently.
https://github.com/streamarr/streamarr-server/issues/412[#412] will allow Streamarr to retry artwork steps independently.
Streamarr does not use the terms "operation item" or "subtask".
A group of items processed together is a batch, never a page, and library operations have no batches: admission is per task (link:0041-scans-and-refreshes-admit-tasks-through-an-adaptive-limit.adoc[ADR 0041]).

=== Claiming an operation

A library has at most one library operation.
`Library.status` shows the running kind, `SCANNING`, `REFRESHING` or `REMOVING_ITEMS_WITH_MISSING_FILES`, and shows `STOPPING` after a ServerAdmin stops it; `HEALTHY` and `UNHEALTHY` mean that no operation runs.
The mutation that requests an operation claims the library, stores the operation and schedules its scheduled task in one transaction, deciding atomically on the library's row.
An operation therefore never exists without its scheduled task, and a failed transaction claims nothing and returns ADR 0026's top-level `UNAVAILABLE` error.

* A library that does not exist returns `LibraryNotFoundError`.
* An idle library is claimed, and the payload returns it in its busy status.
* A busy library refuses every request for library work with `LibraryBusyError`, which carries the current status and a message that names the running kind, such as "A library scan is already in progress."

The refusal covers an identical request and a stronger one, such as a refresh that replaces artwork while a refresh that keeps artwork runs.
An identical request succeeds only when the server itself runs the operation again after a restart, which users never trigger.
Streamarr never queues library work.
This ADR amends ADR 0026: a busy library rejects even an identical request with `LibraryBusyError`.
Streamarr retires `LIBRARY_WORK_NOT_SCHEDULED` because it claims the library and schedules the operation's task in one transaction.
The rules below replace ADR 0026's earlier rules for compensating when work cannot start and for running on a single server.

Adding a library claims its first scan in the transaction that adds the library, and removing a library returns `LibraryBusyError` while an operation runs.
Each mutation that starts or stops an operation, or changes the scan schedule, has its own typed intent and Cedar action, which the service layer checks through the authorization service (link:0025-cedar-decides-authorization.adoc[ADR 0025]).

=== Running an operation

The claim schedules the operation's one-time scheduled task, inside the claim's transaction, on a scheduler dedicated to library operations.
An operation's execution waits for probes and artwork, so it never runs on, or holds, the scheduler threads that run them.
Every execution walks the library from the start and skips completed work by the normal rules: a scan skips a matched file whose stored facts are current, and a refresh skips a title whose item result for fetching metadata carries the operation's id.
Streamarr keeps no checkpoints.
When an execution ends before the operation ends, the scheduled task runs the operation again: at startup after a graceful shutdown, after a crash once db-scheduler finds the lost scheduled task dead, and with backoff after a failure that the execution could not record.

Tasks run in memory: a scan or a refresh admits each task through ADR 0041's adaptive limit and forks and joins its tasks with structured concurrency; a removal of items with missing files removes one item at a time.
Each task records its outcome in its own transaction, and an execution keeps no result in memory.
A task whose failure is recorded does not fail the operation.
An unexpected failure, or an outcome that cannot be recorded, fails the operation: it admits no further tasks, lets running tasks finish, and ends as failed.

A task requests the subject-keyed steps it needs, such as a probe and, after https://github.com/streamarr/streamarr-server/issues/412[#412], artwork, in the transaction that records its outcome.
Those steps do not belong to the operation: the file watcher, playback and other operations require the same steps, and requests for one subject merge.
A primary artwork request carries the id of the operation that waits for it, and a background artwork request carries none.
When an operation requests primary artwork, it takes over a pending request for the same item and sets that request's operation id to the current operation's id.
The pending request may have no operation id, as with a file-watcher request, or may carry the id of an operation that has ended.
Only one operation runs for a library at a time.
A request from outside an operation, such as an artwork edit, keeps the id that the pending request carries.
Taking over a request that waits to retry runs it again at once, so the operation waits for one fresh attempt, not the backoff.
A request with changed sources or a stronger refresh mode starts a new generation of the request, and an attempt of an older generation records no result.
Each item result carries the operation id that its request carried when the result was recorded, so an operation reads only results produced for it.
A task stays admitted until Streamarr records an outcome for each poster and backdrop that the task requested, so a stop waits only for admitted tasks.
A task or an operation waits by reading recorded results, never for an in-process signal, because a result can arrive after a restart or through a path that sends no signal.

=== Finishing

An operation finishes when every result that its tasks require is recorded, as https://github.com/streamarr/streamarr-server/issues/418[#418] defines: a success or a recorded failure, never an attempt that is still pending.
A scan requires a recorded probe outcome for each file as the scan found it, regardless of who requested the probe.
Scans and refreshes also require primary artwork results.
Primary artwork consists of the posters and backdrops of movies and series, plus the required season and episode artwork.
For each item whose result for fetching metadata carries the operation's id, the operation requires primary artwork results that carry the same operation id.
Those artwork results count whether the artwork was saved, unavailable or failed.
An operation that removes items with missing files requires no result.
A result recorded after the claim proves nothing by its time alone, because artwork requested before the claim can finish after it.
Person and company artwork is background work, which an operation requests and never waits for.
A retry after a recorded failure never holds an operation open either; its result later replaces the recorded failure.

Once the walk is done and every required result is recorded, the finishing steps run in a fixed order.
A scan updates file availability, removes items with missing files when the library's setting allows it (ADR 0038), and recalculates the letter index; a refresh or a removal recalculates the letter index, which takes over https://github.com/streamarr/streamarr-server/issues/447[#447]'s recount after a refresh.
Each finishing step is keyed by the operation's id and is idempotent, so a step that a restart interrupted has the same effect when it runs again.
A finishing step for an operation that has ended does nothing, so a stale execution cannot apply a step to a later operation.
To end an operation, Streamarr sets the library's final status and deletes the operation in one transaction: `HEALTHY` for a finished operation, the library's status from before the claim for a stopped one, and `UNHEALTHY` for a failed one.
A stopped or failed operation skips the finishing steps that it has not started, except that it still recalculates the letter index, because tasks that finished can change titles.

=== Stopping an operation

A ServerAdmin stops an operation with `stopScanningLibrary`, `stopRefreshingLibrary` or `stopRemovingItemsWithMissingFiles`, and the library shows `STOPPING`.
A stop leaves the library usable, as it was before the operation except for the tasks and finishing steps that the operation already finished and the items that it already removed:

* The library returns to the status that it had before the operation was claimed.
* Every library item is either untouched or fully through its foreground steps: identify, fetch poster and fetch backdrop.
* No task is stopped halfway, and the letter index is recalculated.
* A scan stopped before its finishing steps changes no file's availability and removes nothing (ADR 0038).

A stop is not a rollback: it admits no new tasks and lets the tasks already running finish their foreground steps.
It never cancels running work, because cancelling interrupts running tasks and breaks the pooled database connections that they hold.
A graceful stop is meant to take seconds and at most about a minute: only the few admitted tasks drain, and each step has its own timeouts.
Streamarr stores the stop request with the operation.
If the server restarts while the library is `STOPPING`, the new execution completes the stored stop.
The execution admits no tasks and waits until every item whose result for fetching metadata carries the operation's id has primary artwork results that carry the same operation id.
The execution then recalculates the letter index and restores the library's status from before the operation was claimed.
A stop does not wait for probes or background artwork; they keep running, and their results appear afterwards.
A stopped operation requests no new background artwork, and the interface distinguishes a stopped operation from details that are still arriving.

A stop during a scan's finishing removal halts the removal between items: items already removed stay removed, and no item is ever half-removed.
A stop of the running kind returns the library in `STOPPING`, and a repeated stop returns it unchanged while it stops, as ADR 0026's rule for naturally idempotent mutations requires.
A stop of a kind that is not running returns a typed rejection with a helpful message, such as "No library scan is in progress, so there is nothing to stop.", which names the running kind when another kind runs.

Server shutdown drains for a bounded, configured time before it cancels the remaining tasks.
Shutdown is the only path that cancels running work, because the process ends and the operation runs again at startup; the library keeps its busy status until then.

=== Scheduled library scans

Streamarr stores one server-wide scan schedule in its single server-settings row.
The schedule scans every library and defines:

* whether scheduled scans run, on by default and changed with `enableLibraryScanSchedule` and `disableLibraryScanSchedule`;
* an interval in whole hours that divides 24, 24 by default, so scans start at the same times every day;
* a start time, 00:00 by default, in the server's time zone; the schedule stores no zone of its own.

`changeLibraryScanSchedule` changes the interval and the start time, and the next firing moves to match.
A recurring scheduled task runs the schedule, and db-scheduler reschedules it under one identity, so each firing requests one scan operation per library, each a separate job, as a cron schedule creates a separate job for each occurrence.
A firing skips a busy library and never queues a scan for it.
When the server was down at one or more scheduled times, the schedule runs once at startup.
A ServerAdmin turns the schedule on or off or changes it through mutations that the authorization service checks, and the audit trail records that ServerAdmin on the change.
A firing is not a ServerAdmin's request: it requests scans as the System actor, a reserved identity that cannot sign in and holds no Household or Profile, and the audit trail records the System actor on each scheduled scan.
A scheduled scan follows every rule of a scan that a ServerAdmin starts.
Every library operation records who requested it, a ServerAdmin's account or the System actor, and an execution after a restart keeps the original requester.

=== One active server

Exactly one Streamarr server runs against a database at a time, as link:0018-live-playback-authority-and-outbound-workers.adoc[ADR 0018]'s one-replica topology already requires.
Deployments stop the old server before they start the new one, and link:0033-transcode-worker-is-a-separate-service.adoc[ADR 0033]'s server deployment follows this rule.
Stream sessions, the file watcher and caches act within one process and depend on this rule.

A startup guard is deferred.
The guard would hold a session-level PostgreSQL advisory lock for the process lifetime, so that a second server refuses to start with a clear message, and PostgreSQL would release the lock automatically if the holder crashed.
It is deferred because:

* db-scheduler already keeps two servers from running the same library operation, so durable library work does not need the guard;
* what the guard would protect is in-memory state: stream sessions, the file watcher and caches;
* a home server is rarely started twice, and the deployment rule covers that case;
* the guard would have to be removed or reworked if several servers ever run on purpose.

Streamarr revisits the guard before any deployment can run overlapping servers, including rolling updates, not only when horizontal scaling begins.

=== Build order

* The lifecycle ships after https://github.com/streamarr/streamarr-server/issues/412[#412], so that pending artwork survives a restart and an execution after a restart can wait for it.
* Scheduled scans ship after ADR 0038's rules, so that a share that unmounts cannot empty a library overnight.

=== Explicitly deferred

* Durable per-task request rows that record which pending steps each operation requested.
They return when an operation needs membership beyond the operation id that artwork requests and item results carry, such as a per-title status for a single-title refresh (https://github.com/streamarr/streamarr-server/issues/429[#429]) or fix match (https://github.com/streamarr/streamarr-server/issues/430[#430]).
* The single-server startup guard, until a deployment can run overlapping servers.

== Consequences

* A restart no longer turns a busy library `UNHEALTHY`; the operation runs again, and the normal rules skip completed work.
* After a crash, a library stays busy without progress until db-scheduler finds the lost scheduled task dead.
* An execution after a restart waits only for the primary artwork of items that its operation recorded, because artwork requests and item results carry the operation's id.
* Scheduled scans read every library's storage on schedule, even when nothing changed.
* If Streamarr repeatedly fails to commit the transaction that sets the library's final status and deletes the operation, the library stays busy.
The scheduled task runs the operation again with backoff until that transaction commits.

== Rejected Alternatives

* Durable fan-in now, with per-task request rows and dependency tracking between steps — counting completions durably is a protocol of its own, and an operation id on each subject's one request is enough to tell which results an operation waits for.
* Proving completion by the claim time — artwork requested before the claim can finish after it, so a refresh would skip a title it never refreshed or finish on artwork fetched for a weaker request.
* A scheduled task for each task — db-scheduler cannot report when a group finishes and deletes a successful one-time execution, so the operation could not tell when its tasks finished.
* A workflow engine beside db-scheduler — it adds a second durable engine with its own replay model, and a caller could not share a subject-keyed step that another caller requested.
* Queueing a second operation, or upgrading the running operation to a stronger request — a queue needs its own durable state and ordering, the ServerAdmin cannot see when queued work will start, and an upgraded refresh would refresh some titles twice.
* Checkpointing progress inside an operation — a checkpoint must stay valid while files change between executions, and walking the library again reads its current state.
* Cancelling running work on a stop — cancelling interrupts running tasks, breaks the pooled connections that they hold, and leaves items half done.
* Crash-recovery markers that turn interrupted work `UNHEALTHY` at startup — they discard accepted work and report a failure that nobody caused.
* Starting the work in memory after the claim and compensating when it cannot start, as the first proposal did — scheduling the scheduled task in the claim's transaction leaves no gap to compensate.
* Running every missed scheduled scan after downtime — the scans would repeat back to back and find the same state.
* Intervals that do not divide 24, or cron expressions — start times would move from day to day, and cron adds a syntax for one setting.
* Storing a time zone with the schedule — the schedule would disagree with the server's clock and logs.
