= ADR 0013: Stream Decision Architecture

== Status

Accepted

NOTE: Under link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043] (proposed), the stream decision selects every audio track and chooses the text subtitle tracks.
The server delivers each selected track as an HLS rendition.
Each audio track keeps its own copy-or-encode decision inside one audio codec per stream session.
An image subtitle track that the viewer selects is burned into the video.

NOTE: link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] changes where the probe input comes from.
The pipeline's probe step reads persisted container and stream rows; ffprobe runs during library file processing, not at stream creation.

This amendment makes the video decision explicit for its first case.
In that first case, every video encode produces SDR.
The playback capabilities epic (https://github.com/streamarr/streamarr-server/issues/399[streamarr/streamarr-server#399]) delivers this amendment.
Issue https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] completes the video decision for HDR output.
link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] leaves open which playback paths a Dolby Vision or HDR10+ source permits.
This amendment's interim copy rule answers that question for a client that declares no dynamic range.

== Context

Streaming negotiates source media (ffprobe) against client capabilities (StreamingOptions).
Each stream type -- video, audio, subtitle -- needs an independent decision.

These independent decisions compose into a TranscodeDecision that drives FFmpeg command construction and HLS playlist generation.

The rest of this section describes the system before this amendment.
The video decision is implicit.
A codec family and a compatibility flag stand in for the video decision.
The server copies the video whenever the client names the source codec.
Otherwise, the server encodes the video.
The Apple TV app names `h264` and `hevc`.
The server therefore copies every HEVC source to the Apple TV app, including HDR sources.
Every client counts as naming `h264`.
Every client therefore receives a copy of a 10-bit H.264 source.
Tone mapping converts HDR brightness and color into the smaller SDR range.
An encode keeps the source's bit depth and transfer characteristic.
A 10-bit source becomes 10-bit H.264.
An encode of an HDR source keeps the source's PQ or HLG transfer characteristic, and the worker does not tone-map that encode.
An encode of a Dolby Vision profile 5 source comes out teal.
A codec string is the RFC 6381 value that names a stream's codec, codec profile and level, such as `avc1.640028`.
A variant's `CODECS` attribute lists the codec strings of the variant's streams.
The playlist's codec strings are constants.
These constants often disagree with the media.
The stored probe cannot tell 8-bit from 10-bit or SDR from HDR.
The stored probe also ignores a source's rotation.

== Decision

=== Each stream type has its own decision record

Model each stream type as a decision record: AudioDecision (COPY/TRANSCODE/NONE), SubtitleDecision (EXCLUDE/BURN_IN/SIDECAR/HLS/EMBED), and VideoDecision.
VideoDecision replaces the implicit codec family and compatibility flag.
VideoDecision records whether the video is copied or encoded.
VideoDecision also holds the planned output that link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] defines.

Stream decisions compose into TranscodeDecision -> TranscodeMode -> FfmpegCommandBuilder.
Pipeline: probe -> decide per stream -> compose -> resolve mode -> build command.
The transcode job carries the video decision to the worker.
The video decision holds the source's dynamic range and the planned output's dynamic range.
The video decision also holds each variant's codec profile, tier, level and codec string.
The worker follows the video decision and never works those values out again.
link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] leaves the field names of the job contract to the implementation.

The video decision reads facts that only probe version 2 stores.
link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032]'s rules for probe versions govern those facts.
Those facts include the dynamic range, bit depth, chroma subsampling, rotation, output frame rate and codec string of the video stream.

=== Every video encode produces 8-bit 4:2:0 SDR

Every encode's planned output is 8-bit 4:2:0 SDR.
The planned output uses BT.709 color in limited range.
The planned output's dynamic range has an SDR compatible base.
A compatible base is the standard picture format that a player could use without the advanced HDR information.
HDR10+ and Dolby Vision are absent from the planned output.
The server chooses how the worker converts the source to the planned output.
The worker builds its filters from the two dynamic ranges in the transcode job.
The worker never chooses a conversion on its own.
The worker tone-maps when the planned output is SDR and the source's compatible base is PQ, HLG or none.
The worker converts a source whose compatible base is SDR or unspecified to 8 bits without tone mapping.
The worker never tone-maps a stream copy.
Tone mapping uses the mobius curve with a 1000-nit peak.
No other tone curve serves as a fallback.
The worker tone-maps with the `tonemapx` filter of the pinned FFmpeg build that ADR 0029 describes.
An RPU holds the per-frame Dolby Vision picture-adjustment instructions.
Before tone mapping, the worker reshapes a Dolby Vision profile 5 source with the source's RPUs.
An encode of a Dolby Vision profile 7 or 8.x source reads only the Dolby Vision base layer and ignores the source's RPUs.
`tonemapx` leaks memory on every reshaped Dolby Vision profile 5 frame.
Streamarr accepts that leak.
The leaked memory returns when the job attempt's FFmpeg process exits.
Each replacement attempt starts a fresh FFmpeg process.
The tone-mapping work (https://github.com/streamarr/streamarr-transcode-worker/issues/26[streamarr/streamarr-transcode-worker#26]) watches worker memory while a full-length Dolby Vision profile 5 film encodes.

*Why:* Before this amendment, the worker encoded every 10-bit HEVC source to 10-bit H.264 (High 10) in 13 of 13 encodes.
Firefox refused High 10 in 21 of 21 runs.
WebKit's native player and AVPlayer refused PQ-tagged H.264 in 16 of 16 runs.
The tone-mapped output was 8-bit BT.709 in limited range.
The tone-mapped Dolby Vision profile 5 output lost its teal cast.
The tone-mapping filter treats an untagged input as PQ.
The filter therefore darkened an untagged SDR source to a mean luma of 41 instead of 106.
Evidence: <<evidence-sdr-output>>, <<evidence-tone-mapping>>.

=== Every encode forces a codec profile and level that the server computes

The server computes each variant's codec profile and level.
H.265 (HEVC) and AV1 also signal a tier.
The server chooses the tier for H.265 and AV1.
Every encode forces the codec profile, the level and, for H.265 and AV1, the tier.
The codec profile is High for H.264, Main for H.265 and Main for AV1.
The server computes the H.264 level from ITU-T H.264 Table A-1.
The server computes the H.265 level from Annex A of ITU-T H.265.
The server computes the AV1 level from Annex A of the AV1 specification.
All three computations use the output picture size after rotation and the exact output frame rate.
The H.264 computation also uses the variant's maximum bitrate and buffer size, because Table A-1 limits both.
For example, 1080p60 needs H.264 level 4.2, H.265 level 4.1 and AV1 level 4.1.
720p60 needs H.264 level 3.2.
The HEVC encode work (https://github.com/streamarr/streamarr-server/issues/58[streamarr/streamarr-server#58]) checks the H.265 computation against libx265, as the measurements below checked the H.264 and AV1 computations.

Each encoder handles a forced level that is too low in its own way.
libx264 writes the forced level and only warns.
SVT-AV1 writes the forced level without any message.
libx265 refuses to start, so the job attempt fails.
The server's level computation must therefore be right for every encoder.

*Why:* A level table of about 60 lines predicted the level that each encoder chose on its own in 89 of 89 libx264 encodes and 85 of 85 SVT-AV1 encodes.
When the worker forced the profile and level, the encoders wrote exactly the requested values in 174 of 174 encodes.
At 1080p60, libx265 refused to start when forced to level 3.1 or level 4.
Evidence: <<evidence-levels-and-codec-strings>>.

=== An encode's codec string is forced, and a copy's comes from the probe

The probe computes the exact codec string of every video and audio stream from the stream's decoder configuration record.
Probe version 2 stores these codec strings, as link:0032-media-file-probe-results-are-persisted.adoc[ADR 0032] records.
A stream copy's codec string is the codec string that the probe computed for the source stream.
An encode's codec string follows from the encode's forced codec, codec profile, level, tier and bit depth.
Examples are `avc1.6400LL` and `av01.0.LLM.08`, where `LL` stands for the computed level.
The playlist builds each variant's `CODECS` attribute from these codec strings and never from a constant.
The server never delays the playlist to read a codec string from an initialization segment.
The transcode job carries each variant's codec string to the worker.
The worker reads every initialization segment that it produces.
The worker fails the job attempt when an initialization segment's codec string differs from the codec string in the transcode job (https://github.com/streamarr/streamarr-transcode-worker/issues/25[streamarr/streamarr-transcode-worker#25]).
The measurements verified that libx264 and SVT-AV1 write the forced values.
libx265 and each hardware encoder need the same verification before the server encodes with libx265 or that hardware encoder.
Every video copy keeps the source's Dolby Vision configuration record.
The worker preserves that record with FFmpeg's `-strict unofficial` option.

*Why:* The constant strings matched the produced media in 6 of 59 video copies.
Strings computed from the decoder configuration record matched 54 of 59 video copies and 42 of 42 audio copies.
The 54 video matches included all 50 H.264 and HEVC copies.
Evidence: <<evidence-levels-and-codec-strings>>.

=== A stream copy carries no planned output range yet

At first, only an encode's planned output holds a dynamic range.
A copy's planned output holds no dynamic range until https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] settles one.
link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] forbids `UNSPECIFIED` in a planned output.
For a copy of an untagged source, `UNSPECIFIED` is the only honest value.
The produced copy still passes the source's HDR features through unchanged, as link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] requires.

=== Until clients declare dynamic ranges, only SDR sources are copied

This rule holds until clients declare the dynamic ranges they accept (https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395]).

* Copy the video only when all three conditions hold.
** The source's compatible base is SDR or unspecified.
** The source is not H.264, or the source is 8-bit 4:2:0 H.264.
** The client names the source's codec, as the server already requires.
* Encode every other source to 8-bit SDR.
The worker tone-maps the encode when the source's compatible base is PQ, HLG or none.

The interim copy rule takes effect only after the 8-bit encodes (https://github.com/streamarr/streamarr-transcode-worker/issues/22[streamarr/streamarr-transcode-worker#22]) and tone mapping (streamarr/streamarr-transcode-worker#26) ship.

Issue streamarr/streamarr-server#395 sets a default for a client that declares nothing.
That default is H.264 High profile at 8 bits in SDR.
The rule applies that default to the codec names that clients send today.
The rule is the interim answer to link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036]'s open question about which playback paths a Dolby Vision or HDR10+ source permits.
The rule answers that question only for a client that declares no dynamic range.
A Dolby Vision or HDR10+ source permits only an SDR encode when its compatible base is PQ, HLG or none.
PQ and HLG sources without Dolby Vision or HDR10+ also permit only an SDR encode.
Dolby Vision profiles 8.2 and 9 have a valid SDR compatible base.
The rule still copies a Dolby Vision profile 8.2 or 9 source.
A player check must prove that such a copy plays before the interim copy rule ships.
The rule does not decide how the server handles a Dolby Vision source whose claims contradict its picture signalling, such as Dolby Vision profile 7 tagged as SDR.
Issue streamarr/streamarr-server#394 decides that case.
The Apple TV app receives no HDR copies until streamarr/streamarr-server#395.
The server encodes HDR HEVC sources to SDR for the Apple TV app.
link:0009-h264-plus-av1-codec-strategy.adoc[ADR 0009] decides when those SDR encodes use HEVC (streamarr/streamarr-server#58).
This amendment defers HDR copies to the Apple TV app on purpose.

The probe reads a Dolby Vision profile 5 stream in MPEG-TS without the Dolby Vision descriptor as having an unspecified compatible base.
This misreading is a known gap.
The copy rule then either copies the stream or encodes the stream without the reshape.
In both cases, the stream plays teal.
Only a probe that reads RPUs from the frames detects such a stream (https://github.com/streamarr/streamarr-server/issues/394[streamarr/streamarr-server#394]).

*Why:* No playlist can yet describe an HDR copy truthfully to a client that declares no range.
WebKit's native player and AVPlayer refused PQ and Dolby Vision profile 8.1 copies in a variant that the playlist declared SDR.
When the playlist declared the variant PQ or HLG, AVPlayer without an HDR display refused the variant.
WebKit's native player timed out on that variant.
Evidence: <<evidence-copies>>.

[[explicitly-deferred]]
=== Explicitly deferred

* The HDR output choice (https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396], https://github.com/streamarr/streamarr-server/issues/397[streamarr/streamarr-server#397] and https://github.com/streamarr/streamarr-transcode-worker/issues/27[streamarr/streamarr-transcode-worker#27]).
This choice covers the Original quality option, the user's HDR choice, and 10-bit or HDR encodes.
* A copy's typed codec profile and level, and a copy's planned output range (streamarr/streamarr-server#396).
* Client-declared dynamic ranges (streamarr/streamarr-server#395).
Client-declared dynamic ranges replace the interim copy rule.
HDR copies to the Apple TV app return with client-declared dynamic ranges.
* Reading HDR10+ information and RPUs from the frames (streamarr/streamarr-server#394).
Reading RPUs from the frames closes the Dolby Vision profile 5 gap in MPEG-TS.
* The playlist attributes that announce a produced range and supplemental codecs.
link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] already defers these attributes to the epic.
* Choosing the HEVC sample-entry tag of a copy (https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18]).
Until then, a copy keeps the source's sample-entry tag.
The copy's codec string names that tag.
The tag rule lives only in the worker.
Issue streamarr/streamarr-transcode-worker#18 bumps the probe version, so a rescan updates every stored codec string under ADR 0032's rules for probe versions.
If streamarr/streamarr-transcode-worker#18 is ready before probe version 2 ships, probe version 2 includes that tag rule.

== Consequences

* Decision records are pure domain objects.
* Mode resolution considers all stream decisions (e.g. subtitle burn-in promotes REMUX -> FULL_TRANSCODE).
* New stream types follow the same pattern.
* TranscodeReason tracking can be added as metadata on each decision later.
* Encodes no longer produce High 10 or PQ-tagged H.264.
Firefox refuses High 10, and Apple's players refuse PQ-tagged H.264.
* With libx264, encoding a 10-bit or HDR source costs less than before.
The 8-bit output saves more than tone mapping costs.
With SVT-AV1, the cost stays about the same.
* A variant's codec profile, tier and level depend only on the variant.
Every job attempt of the variant therefore forces the same values.
The initialization segment then stays identical across job attempts, as link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] requires.
* When an encoder ignores a forced value, the worker fails the job attempt.
The playlist therefore never advertises a false codec string for an encode.
* A forced H.265 level that is too low fails the job attempt, because libx265 refuses to start.
* A full-length Dolby Vision profile 5 encode grows each FFmpeg process's memory until the attempt ends.
* A source whose compatible base is PQ, HLG or none plays as SDR on every client until the deferred HDR output choice lands.

== Rejected Alternatives

* 10-bit H.264 output (High 10): Firefox refuses High 10.
Before this amendment, the worker produced High 10 from every 10-bit source.
* Constant codec strings: the constant strings matched 6 of 59 video copies.
The constants also stated level 4.0 for 1080p60 encodes that need level 4.2.
* Reading every codec string from the produced initialization segments: the playlist would wait for the slowest variant.
One failed first job attempt would block the playlist.
* Declaring `VIDEO-RANGE=PQ` or `VIDEO-RANGE=HLG` on copies today: AVPlayer without an HDR display refuses the variant.
WebKit's native player times out on the variant.
* Copying HLG sources to clients that name the codec: the HLG copies played.
The playlist could not state the copies' HLG range.
AVPlayer without an HDR display refuses a variant declared `VIDEO-RANGE=HLG`, and WebKit's native player times out on that variant.
* Leaving tone mapping to the worker's discretion: link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036] requires the server to choose every change to the source.
The worker would also probe the source a second time.
* The bt2390 tone curve at the same 1000-nit peak: above the peak, the curve folds back and maps brighter input to darker output.
A highlight brighter than 1000 nits therefore renders darker than a 1000-nit highlight.
* The hable tone curve: the hable curve makes pictures darker overall.

== Evidence

Every measurement used the pinned worker image with FFmpeg 8.1.2, libx264 and SVT-AV1 on a 10-core host.
The players were hls.js 1.7.0 in Chromium, Chrome, Firefox and WebKit, plus WebKit's native player and AVPlayer on macOS 26.6.2.
No player ran with an HDR display.
The sources covered HDR10, HDR10+, HLG from an iPhone, Dolby Vision profiles 5, 7 (base layer), 8.1 and 8.4, 10-bit SDR with an untagged transfer characteristic, and 8-bit SDR.

[[evidence-sdr-output]]
=== 8-bit SDR output

* Before this amendment, the worker encoded every 10-bit HEVC source to H.264 High 10 (13 of 13).
* Firefox's `MediaSource.isTypeSupported` returned false for `avc1.6E00xx` in 21 of 21 runs.
hls.js therefore dropped the variant.
* WebKit's native player and AVPlayer failed PQ-tagged High 10 in 16 of 16 runs with `CoreMediaErrorDomain -12927`.
The PQ transfer characteristic in a variant that the playlist declared SDR triggered the failure.
Converting to 8 bits alone therefore does not fix the failure.
* All 14 tone-mapped outputs (7 sources, 2 encoders) were 8-bit 4:2:0.
All 14 used BT.709 color in limited range.
None carried the static HDR boxes `mdcv` and `clli` or a Dolby Vision configuration record.
* Each encode's mean chroma offsets (Cb and Cr) were measured against Apple's own SDR rendering of the source.
The offsets of an HDR10 encode moved from −32 and −12 before tone mapping to −7.3 and −3.1 after tone mapping.
The offsets of tone-mapped HLG stayed within 1.5 code values.
The Dolby Vision profile 5 offsets were measured against the rendering of the Dolby Vision profile 8.1 version of the same master.
These offsets moved from −35 and −44 to −9.5 and −11.3.
The Dolby Vision profile 5 teal cast disappeared.
* The tone-mapped libx264 output played from every source in Chromium, Chrome, WebKit with hls.js, WebKit's native player and AVPlayer.
Firefox played 6 of 7.
Firefox's one failure matched a separate, intermittent Firefox failure on H.264 with muxed AAC.
That separate failure also occurs without tone mapping.
* At the 1080p variant, libx264 cost these CPU seconds per media second before and after this amendment's change.
From a 1080p HDR10 source, the cost fell from 9.11 to 6.07.
From a 2160p Dolby Vision profile 5 source, the cost fell from 12.60 to 10.19.
From an iPhone HLG source, the cost fell from 15.26 to 7.52.
SVT-AV1 cost about the same as before.

[[evidence-tone-mapping]]
=== Tone mapping

* On 1080p PQ and HLG sources, tone mapping cost at most 0.1 CPU seconds per media second more than a plain 8-bit conversion.
Reshaping Dolby Vision profile 5 added about 1.1 to 1.2 CPU seconds per media second at 1080p60.
* Against the Dolby Vision profile 8.1 version of the same master, the reshaped Dolby Vision profile 5 encode scored 32.7 dB PSNR.
Without the reshape, the Dolby Vision profile 5 encode scored 14.8 dB.
* The tone-mapping filter treats an untagged input as PQ.
On a 10-bit SDR source with an untagged transfer characteristic, the filter gave a mean luma of 41 instead of 106.
* One tone-mapped 1080p libx264 variant ran at 1.20–1.43× real time from 1080p60 HDR sources.
The same variant ran at 0.90–1.01× real time from 2160p60 sources.
A four-variant ladder from 60 fps HDR sources ran at 0.35–0.56× real time, with or without tone mapping.
* The bt2390 curve at 1000 nits mapped a 983-nit PQ grey to luma 235.
The bt2390 curve mapped a 10,000-nit grey to luma 168.
The mobius curve clips at 235 instead of folding.
* Below the peak, mobius and bt2390 gave the same brightness (mean luma 92.9 and 92.1).
The hable curve gave a mean luma of 76.9.
* The color, player and seek checks ran with the bt2390 curve.
Mobius was compared only for brightness.
The tone-mapping work (https://github.com/streamarr/streamarr-transcode-worker/issues/26[streamarr/streamarr-transcode-worker#26]) therefore repeats the color and player checks with the mobius curve.
* `tonemapx` leaked about 3 KB per reshaped Dolby Vision profile 5 frame.
By calculation from that rate, a two-hour film at 24 fps would grow one FFmpeg process by about 0.55 GB.

[[evidence-levels-and-codec-strings]]
=== Levels and codec strings

* When left alone, libx264 and SVT-AV1 each chose the smallest level whose limits fit the output.
* A level table of about 60 lines predicted 89 of 89 libx264 encodes and 85 of 85 SVT-AV1 encodes.
The encodes covered 24 sources at every variant of the ladder.
The encodes ranged from 144p to 2160p and from 2 to 2400 frames per second.
* With the profile and level forced, both encoders wrote exactly the forced values in 174 of 174 encodes.
* Both encoders also wrote a forced level that was too low.
libx264 only warned, and SVT-AV1 said nothing.
* A separate check forced libx265 in the same pinned worker image on a 1080p60 source.
Forced to level 3.1, libx265 refused to start because the picture size exceeded the level.
Forced to level 4, libx265 refused to start because the frame rate exceeded the level.
In both cases FFmpeg wrote no output and exited with an error.
Forced to level 4.1, libx265 wrote level 4.1.
* On every rotated source, the server computed a 1920x1080 variant, but FFmpeg wrote 608x1080.
The level that the encoder chose on its own therefore differed from the prediction.
* Strings computed from the source's decoder configuration record matched 54 of 59 video copies and 42 of 42 audio copies.
The 5 misses were AV1 in IVF or raw OBU files.
The codec-string predictor did not parse the sequence header of those files.
* The server's constant strings matched 6 of 59 video copies.
* Without `-strict unofficial`, none of the 9 Dolby Vision copies kept `dvcC` or `dvvC`.
With the flag, all 9 copies kept the box.
The flag changed no other box on any of the 15 sources.
No encode wrote either box.
* A four-variant ladder's last initialization segment arrived up to 11.1 s after FFmpeg started.
WebKit's native player and AVPlayer request a playlist once and give up after 20.2 s.

[[evidence-copies]]
=== Copies to clients that declare no range

* WebKit's native player and AVPlayer failed the PQ and Dolby Vision profile 8.1 copies in a variant declared SDR.
Both players failed with `-12927`, whether or not the copy kept its Dolby Vision configuration record.
* With `VIDEO-RANGE=PQ` or `VIDEO-RANGE=HLG`, AVPlayer without an HDR display failed 4 of 4 variants with `-1002`.
WebKit's native player timed out on 4 of 4.
The same variants played when the playlist declared them `VIDEO-RANGE=SDR`.
* HLG copies without a `VIDEO-RANGE` attribute played in Chrome, Firefox, WebKit's native player and AVPlayer, in one run each.
* The Dolby Vision profile 5 copy failed in every engine except Chrome.
Chrome played the Dolby Vision profile 5 copy only when the copy lacked its Dolby Vision configuration record.
Chromium, Chrome and Firefox report no decoder for `dvh1`.
* One open-source media server copies a video stream only when the client's declared ranges include the source's range.
That server encodes every HDR source to 8-bit SDR BT.709, and that server's playlist declares SDR.
