= ADR 0030: Credential Attempts Use PostgreSQL Time and Pairing Successes Preserve Failures

== Status

Proposed

== Context

link:0028-credential-attempts-are-journaled-and-throttled-in-postgresql.adoc[ADR 0028] stores credential attempts in a shared PostgreSQL journal.
Resetting failures after every success and taking timestamps from application clocks can exclude failures that should count toward the limit.

Device-pairing guesses share the approver Account's limit, and anyone can issue a pairing code through the public device-code endpoint.
An approver can alternate failed guesses with successful lookups of a self-issued code, repeatedly resetting the failure count before lockout.
Looking up a self-issued pairing code must not clear previous failed guesses.

The journal compares completion times to the latest success to determine which failures count.
If the application instance recording that success has a clock ahead of the instance recording subsequent failures, those failures can appear to precede the success and be ignored until the slower clock catches up.
Serializing writes with an advisory lock cannot correct timestamps sampled from different clocks.

== Decision

`CredentialAttemptPolicy.Limited` specifies whether success resets the target's failures.
`DEVICE_PAIRING_CODE` keeps previous failures after successful lookups and decisions; all other credential kinds reset failures on success.
Completed pairing successes are recorded as `SUCCEEDED` and no longer count as pending attempts.
The standard failure count, failure window, lockout duration, and per-approver scope remain unchanged.

The repository reads reservation and completion timestamps from PostgreSQL.
It calls `clock_timestamp()` inside each journal transaction after acquiring the target's advisory lock, so admission, pending expiry, and completion use the same clock across application instances.
`CURRENT_TIMESTAMP` is fixed at transaction start and can precede a success committed while the transaction waits for the lock.
Callers do not supply journal timestamps.

Reservation and completion keep their short `REQUIRES_NEW` transactions and bounded lock waits.
Verification runs outside these transactions.
A failed database-time query returns credential verification unavailable, as other journal failures do.

== Consequences

* Successful pairing-code checks no longer let an approver reset the failed-attempt count.
* Application clock differences no longer affect journal timestamps. Database host clock corrections can still affect them.
* Reservation and completion each add one database-time query.
* The change requires no schema or stored-data migration.

== Rejected Alternatives

* Reset every credential budget on success — publicly issuable pairing codes make that reset attacker-controlled.
* Depend on synchronized application clocks — a shared lock does not impose ordering on values sampled from different clocks.
* Use transaction-start time — a transaction waiting for the target lock can retain a time earlier than a success committed by the preceding lock holder.
