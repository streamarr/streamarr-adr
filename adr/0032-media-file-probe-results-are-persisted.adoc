= ADR 0032: Media File Probe Results Are Persisted and Playback Reads Them

== Status

Accepted

An amendment to this ADR replaces the probe task protocol with the design that shipped (<<decision-probe-task-protocol>>).
db-scheduler picks, monitors, recovers, and retries each probe execution.
`media_file_probe_task_request` holds the inputs that each file's latest probe request specifies.
The server guards each result with those requested inputs instead of a claim id and a lease.

Another amendment numbers the probe versions in the order in which they shipped (<<later-probe-versions>>).
The keyframe positions shipped first, as probe version 3.
The facts for https://github.com/streamarr/streamarr-server/issues/501[streamarr/streamarr-server#501] are probe version 4, which includes every fact of version 3.
Version 2 is unused.

A further amendment gives each kind of work its own capacity on each worker (<<probe-capacity>>).
A probe never takes a playback slot, so a scan never delays playback.
Each worker grants its own capacities, and the server sends no work beyond them.
The worker lowers its background probe capacity when its job attempts produce too slowly.
That amendment also changes link:0044-encoder-headroom-and-the-preset-scale.adoc[ADR 0044]: the worker, not the server, measures production speed.

The same amendment changes playback of a file without a stored probe outcome (<<playback>>).
The server moves the file's durable probe to the front of the queue and waits, within a configured bound, for the stored outcome.
Playback then starts, instead of returning the not-ready error at once.

A later amendment adds two brakes that work while nothing plays (<<probe-timeout-brake>>).
A probe that reaches the server's probe timeout halves the worker's background probe capacity.
That brake works on every host.
The server's cancel command tells the worker that a probe reached the timeout.
Where the host provides Linux pressure stall information, high IO pressure also halves the capacity.
That brake acts before probes reach the timeout.

Another amendment stops retrying a probe whose worker replies keep breaking the worker contract (<<probe-contract-violations>>).
After three consecutive contract violations for the same probe inputs, the server stores a terminal `probe_error`.
Other temporary failures still retry without a limit.
A scan probes a file with that terminal error again.
A scan does not probe a file again for any other terminal error.

Another amendment adds probe version 5 (<<probe-version-5>>).
Probe version 5 reports each video stream's typed codec profile, level and tier and its color properties.
Probe version 5 also reads the first frames of the chosen video stream.
On the upgrade to probe version 5, the server queues a re-scan itself.
The re-scan runs through the existing scan library operation.
Playback keeps using each file's probe version 4 outcome until the server stores the file's probe version 5 outcome.

== Context

Streamarr learns a media file's technical properties by running ffprobe.
link:0013-stream-decision-architecture.adoc[ADR 0013] describes the pipeline as probe, decide per stream, compose, resolve mode, build command.
Before this decision, ffprobe ran once per stream session.
The result stayed in memory for that session's lifetime.
The `media_file` table stored the filename, path, and size, but no container or stream properties.

Whenever playback started, the server waited for a probe process before it decided how to transcode the file.
The server read the probe result from memory to make that decision.
The server also used the result to build the quality ladder and playlists.
The server read the same result to track watch progress.
The server also used the result to decide when the session expired.

Container and stream properties belong to the media file.
The server can collect and store those properties when it processes the library.
Playback and library views can then read the stored properties.
The server can probe the file again in the background when needed.

Bulk scans called the file processors directly.
The watcher created per-file tasks but processed files inline.
`FileProcessingTaskCoordinator` provided methods to claim tasks and recover expired claims.
No dispatcher called those methods in production.

link:0033-transcode-worker-is-a-separate-service.adoc[ADR 0033] removes FFmpeg from the server.
This ADR first moves probing into library processing.
It also defines the result that workers will later produce.

Each stored probe outcome records the probe version that produced it.
Probe versions 1 and 3 describe each video stream by its codec, size, frame rate and bitrate.
With those facts alone, the transcode decision cannot tell an 8-bit stream from a 10-bit stream.
The transcode decision also cannot tell an SDR stream from an HDR stream.
The transcode decision cannot compute the codec string that the playlist's `CODECS` attribute must carry for a stream copy.
The transcode decision also cannot tell which frame rate an encode should use when a file's declared rates disagree.
Probe version 4 adds the missing facts for the playback capabilities epic, https://github.com/streamarr/streamarr-server/issues/399[streamarr/streamarr-server#399].
Probe version 4 also adds each file's chapters, which a future chapter menu uses.
Probe version 4 describes dynamic range in the vocabulary of link:0036-video-contracts-share-vocabulary-and-dynamic-range-facts.adoc[ADR 0036].
Probe version 4 reads no frames, so probe version 4 cannot report HDR10+ or a Dolby Vision RPU as absent.
Probe version 5 reads the first frames of the chosen video stream and adds typed codec and color facts.

== Decision

Persist each media file's probe result in two tables.
A probe step in the file-processing pipeline produces the result.
Playback consumers read the stored data.

=== What the database stores

`media_file_container_info` holds one row per media file.
Each row stores the container format name, duration, and total bitrate.
The row also stores a snapshot of the source file's size and modification time.
Each row also stores `probe_version` and an optional typed `probe_error` code.

`media_file_stream_info` holds one row per stream.
Each row stores the stream type, index, codec, width, height, frame rate, channels, and bitrate.
The row also stores the language and the default and forced flags.
Probe version 4 adds the stream facts listed in <<probe-version-4,the probe version 4 section>>.
Probe version 4 also reports the container's chapters.
Probe version 5 adds the stream facts listed in <<probe-version-5,the probe version 5 section>>.
The database stores no `MediaFileProbePropertyIssue`.
The server derives each issue from the stored facts, as ADR 0036 decides.
https://github.com/streamarr/streamarr-server/issues/546[streamarr/streamarr-server#546] decides how the server stores the chapters.
The tables correspond to ffprobe's `format` and `streams` sections.
Container properties and `probe_error` are nullable.
The media file reference, source size, modification time, and `probe_version` are required.

A missing container row means the database holds no completed probe outcome.
A row without `probe_error` records a successful probe, even when some properties are unknown.
A row with `probe_error` records a terminal error.
A terminal error is usually a media error.
A terminal error can also record that the worker's replies broke the contract three times in a row (<<probe-contract-violations>>).
The database stores no stream rows or container properties for that outcome.
Both outcomes retain the source snapshot and `probe_version`.
The server continues to use `media_file.status` when it matches and enriches files.
The server adds no probe status values.

Store typed columns without a raw ffprobe JSON column.
Workers must return the complete result through ADR 0018's typed contract, which does not send JSON.
Derive the playback `MediaProbe` from the stream rows rather than storing summary fields on the container row.
The derived `MediaProbe` uses the same streams as the FFmpeg command.
Those are the chosen video stream and the first audio stream (`0:a:0`).
The chosen video stream is the first video stream that is not an attached picture, such as embedded cover art.
Before probe version 4, the transcode decision read the first video stream (`0:v:0`) instead.
That first video stream can be cover art.
Each transcode job names the chosen video stream's index.
FFmpeg therefore maps the same stream that the transcode decision read.
If the server instead used the streams flagged as default, it could authorize copying one audio codec while FFmpeg copies another.

The term "metadata" is reserved for descriptive data from TMDB.
Examples include `library_metadata` and the `METADATA_NOT_FOUND` status.

=== How probes run and scans finish

A shared library collaborator checks whether a file needs a probe when a scan or the watcher processes the file.
Call the collaborator before `LibraryManagementService.processFile` returns, even when the file is already marked `MATCHED`.
The collaborator schedules required probes whether or not the server can match and enrich the file.
Keep the existing code paths that match and enrich files.
Rename the existing `LibraryManagementService.probeFile` method to `findOrCreateMediaFile`.
That method finds or creates the media file row.
The method does not run ffprobe.

The probe dispatcher is a db-scheduler task with at most one execution per media file.
Scans, watcher events, and playback requests use the same enqueue operation.
The enqueue operation saves the requested inputs in `media_file_probe_task_request`, which holds one row per media file.
The same transaction schedules the file's execution when none exists.
If a pending execution has different inputs, the enqueue operation replaces those inputs.
If the request specifies the same inputs, the pending execution keeps its scheduled time.
If the execution is running, the enqueue operation changes only the saved request.
The running attempt compares its inputs with the saved request when it completes.
The dispatcher runs the probe step without matching or enriching the file again.
The watcher no longer creates, completes, or fails probe tasks while it processes files inline.
The shared collaborator schedules the probe tasks.
The dispatcher runs those tasks.

A scan records the source snapshot and probe version that it requests for each file.
Together, the snapshot and version are the requested inputs.
If a file's stored outcome already matches those inputs, the scan counts that outcome at once.
In that case, the file needs no new probe request.
A terminal error from contract violations is the exception, as <<probe-contract-violations>> describes.
If the source is removed before the scan reads its snapshot, the scan requests no probe task for that file.
If the scan cannot enqueue a probe, the scan fails as link:0027-library-operations-are-durable-jobs.adoc[ADR 0027] describes.

Before a scan can complete, it must finish listing the library.
The scan must also finish attempting to match and enrich each file.
Each probe that the scan requested must also have one of these results:

* The database holds a successful probe result for the requested inputs.
* The database holds a terminal error for the requested inputs.
* The dispatcher has recorded why an attempt at the requested inputs failed.
The attempt must have finished after the scan requested the probe.

A failure recorded before the request belongs to an earlier attempt.
The scan requests an immediate retry.
The scan waits for the new attempt.
When a previously unreadable share becomes readable, a new scan therefore retries the probes that failed.
A successful outcome for the current snapshot and probe version shows that the file is ready for playback.
The scan does not start a test stream.
The scan also waits for its required artwork, as https://github.com/streamarr/streamarr-server/issues/418[issue #418] describes.

The scan stops waiting for a probe in three cases:

* Later inputs replace the inputs that the scan requested.
* The database already holds an outcome from a newer probe version for the same source.
* The media file or source is removed.

The watcher supplies later inputs in response to a file event.
The dispatcher supplies later inputs when it observes a change.
Probes for those later inputs can continue after the scan ends.
A probe has no result while it waits for a busy worker.
A canceled attempt also has no result.
In both cases, the scan keeps waiting.
Once the dispatcher records a failure that counts for the scan, the scan does not wait for further retries.
The scan tracks only its own probe requests.
Pending probes for other libraries and later requests for the same files do not delay the scan.

db-scheduler can run probes after the server restarts.
The scan therefore reads stored results at a configured interval rather than waiting for an in-process signal.
Streamarr adds no setting that disables the probe dispatcher.
Keep the db-scheduler starter's `db-scheduler.enabled` property on in deployments.
The scheduler that the starter creates also records each probe request in the transaction that saves the requested inputs.
If that transaction rolls back, no execution remains for the request.
Tests turn the starter off.
Tests supply a scheduler built the same way.
Tests start that scheduler only when they need to run tasks.

The server reads the result tables and probe requests to decide whether a scan can complete.
The server never reads db-scheduler's table for that decision.
If the scan cannot read those results or save a result of its own, the scan fails as ADR 0027 describes.
The dispatcher saves probe failures.
If the dispatcher cannot save the failure reason, the same transaction also fails to schedule the retry.
After db-scheduler detects that the execution is dead, it runs the attempt again.
The scan keeps waiting until the dispatcher records a result.

link:0026-mutation-payloads-and-error-channels.adoc[ADR 0026] and ADR 0027 define how the library's status changes while a scan runs.
The library stays `SCANNING` while the scan waits for required results and runs ADR 0027's finishing steps.
If a ServerAdmin stops the scan, the library changes to `STOPPING`.
The server follows ADR 0027's stop rules.
The server lets admitted tasks finish their foreground steps.
The server then restores the status that the library had before the scan began.
The server does not wait for probes or background artwork when it stops the scan.
That work keeps running.
Even after a scan completes, some files may not be ready for playback.
The scan log counts ready files, terminal errors, recorded failures, and probes that later work replaced.

=== The probe step

The dispatcher runs in the background.
db-scheduler picks due executions and runs the probes.
db-scheduler runs an execution again after it detects that the execution is dead.
A file's execution ends when the database holds an outcome for the requested source snapshot and `probe_version`.
The execution also ends when the media file or its source is removed.
Before an attempt runs ffprobe, it checks again whether the file needs a probe.
The dispatcher probes an unchanged source without waiting for a quiet period.

If the probe succeeds, the probe returns the complete container-and-stream result.
For video streams, the result includes width, height, and frame rate.
The result includes bitrate for any stream that reports a bitrate.
Probe version 4 adds the facts listed in <<probe-version-4,the probe version 4 section>>.
Probe version 5 adds the facts listed in <<probe-version-5,the probe version 5 section>>.
If the probe encounters a terminal media error, the probe returns a typed error.
Replace `MediaProbe` as the probe's return type.
Derive `MediaProbe` from the complete result for playback consumers.
Extend the parser to retain the per-stream dimensions, frame rate, and video bitrate that today's `StreamInfo` omits.
The server first ran ffprobe itself.
Under ADR 0033, the worker runs ffprobe and returns the result through the same contract.

=== Probe version 4 records the facts that playback needs

Streamarr computes facts at probe time wherever it can.
Playback then reads those facts instead of computing them.
Probe version 4 adds these facts to a successful outcome:

* The chosen video stream, which the transcode decision and the frame-rate rule read.
* The dynamic range of each video stream, as a `VideoDynamicRange`.
The probe fills the `VideoDynamicRange` from each stream's headers and configuration records, as the probe version 4 section of ADR 0036 decides.
* The bit depth and chroma subsampling of each video stream.
* The rotation of each video stream, which the probe reads from the stream's display matrix.
* The frame-rate rule's inputs and the output frame rate that the rule chose, as <<output-frame-rate,the next section>> describes.
* The end time of each video and audio stream, where the container header states that end time.
https://github.com/streamarr/streamarr-server/issues/511[streamarr/streamarr-server#511] uses the end times to find a stream that ends early.
* The sample rate of each audio stream.
The MP3 copy rule needs the sample rate, because the fMP4 muxer refuses MP3 below 16 kHz.
* The profile name of each audio stream, kept as ffprobe prints it, such as `Dolby Digital Plus + Dolby Atmos` or `DTS-HD MA`.
https://github.com/streamarr/streamarr-server/issues/503[streamarr/streamarr-server#503] derives the `CHANNELS` attribute of an E-AC-3 Atmos rendition from the profile name.
The codec string never comes from the profile name.
* The container cropping of each video stream, which a Matroska `PixelCrop` element or an MP4 `clap` box carries.
The width and height stay the size before cropping.
The quality ladder and the playlist's `RESOLUTION` use the size after cropping, as they use the size after rotation.
* The HDR10 static metadata that the container declares for each video stream.
The HDR10 static metadata is the mastering display color volume and the content light level.
The worker reads both from the stream side data of the same ffprobe run.
An MP4 `mdcv` or `clli` box or the Matroska mastering elements carry that side data.
The values use the units of the HEVC SEI messages with payload types 137 and 144.
https://github.com/streamarr/streamarr-server/issues/396[streamarr/streamarr-server#396] builds those SEI messages from the stored values and writes them into the `hvcC` record of an HDR10 copy.
Every job attempt of that variant then writes the same initialization segment.
Some streams carry the values only in the SEI messages of their HEVC bitstream.
Those streams report no static metadata, because probe version 4 reads no frames.
A missing value therefore does not mean that a PQ stream is PQ10.
Probe version 5 reads those values from the first frame, or from the SEI messages of the first packets (<<probe-version-5>>).
The static metadata is not the raw color signaling.
Probe version 5 reports the transfer, primaries, matrix and range of each video stream.
* The container's chapters, with each chapter's start time, end time and title.
The chapter times use the timeline of the keyframe positions.
A future chapter menu and the markers of https://github.com/streamarr/streamarr-server/issues/285[streamarr/streamarr-server#285] use the chapters.
The worker reads the chapters with ffprobe's `-show_chapters` option.
* The title, the handler name and the hearing-impaired flag of each audio and subtitle stream.
https://github.com/streamarr/streamarr-server/issues/503[streamarr/streamarr-server#503] names each audio rendition by its title, by its handler name or by its language.
https://github.com/streamarr/streamarr-server/issues/60[streamarr/streamarr-server#60] names each subtitle rendition the same way.
https://github.com/streamarr/streamarr-server/issues/60[streamarr/streamarr-server#60] also marks a subtitle rendition as SDH when the stream's hearing-impaired flag is set.
The worker reads the title from the `title` tag first, then from the MP4 `name` tag.
The worker takes the first of these tags whose value is not blank.
The worker compares tag names without regard to case.
FFmpeg's MP4 muxer writes a stream's title into the track's `name` atom, so ffprobe reports that title as `name`, not as `title`.
The worker reports the `handler_name` tag as a separate fact and never changes its value.
A Matroska `HANDLER_NAME` tag counts as `handler_name`.
The worker never decides whether a handler name is generic.
The server decides which handler names are generic when the server names a rendition, as link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043] describes.
The hearing-impaired flag is ffprobe's `hearing_impaired` disposition.
The worker reports the flag as true or false on every audio and subtitle stream.
False means only that the container does not mark the stream.
A title or a handler name holds at most 512 bytes of UTF-8.
The worker leaves a longer value out and never shortens it.
The titles and handler names of one result take at most 16,384 bytes in their protobuf encoding.
When the titles and handler names would take more, the worker reports neither and marks both as omitted.
The server accepts at most 128 KiB in one session message, so the two limits keep the titles and handler names from closing the worker's session (https://github.com/streamarr/streamarr-server/issues/554[streamarr/streamarr-server#554]).
Without the second limit, one video stream and 256 subtitle streams with 512-byte titles took 139,438 bytes.
In the library sample, the titles of one file took at most 1,727 bytes.
Video streams report none of these three facts, because nothing reads a video stream's title, handler name or flag yet.
* The exact codec string of every video and audio stream, in the form that RFC 6381 defines.
The probe computes the codec string from the stream's decoder configuration record.
Depending on the codec, that record is `avcC`, `hvcC`, `av1C`, `dvcC` or `dvvC`, or `esds`.
AV1 in an IVF or raw OBU (open bitstream unit) file has no `av1C`.
For such a file, the probe parses the AV1 stream's sequence header instead.
The probe never derives the codec string from ffprobe's named profile and level.
Because the probe stores the exact codec string, the playlist never waits for a produced initialization segment.
A sample entry is the four-character code, such as `hvc1`, `hev1` or `avc1`, that names a video stream's coding format in the initialization segment.
A video codec string names the sample entry that a stream copy of that stream will carry.
The worker alone holds the tag rule, which picks a copy's sample entry.
https://github.com/streamarr/streamarr-transcode-worker/issues/18[streamarr/streamarr-transcode-worker#18] changes the tag rule.
The changed tag rule writes a `dvh1` sample entry as `hvc1`.
The changed tag rule also writes a `dva1` sample entry as `avc1`.
Probe version 4 includes the changed tag rule.
Probe version 4 therefore stores each copy's final codec string, after those rewrites.
The stored codec string names the sample entry that the copy really carries.
Any later change to the tag rule increases the probe version.
The re-scan that the server queues on the upgrade to the new probe version then refreshes the stored codec strings.
link:0013-stream-decision-architecture.adoc[ADR 0013] decides how the playlist uses the codec string.

*Why:* The probe reported neither dynamic range nor bit depth.
The server therefore copied HDR sources to clients that never declared HDR.
The server also copied 10-bit H.264 sources to every client.
ADR 0013 records the player measurements behind these findings.
The playlist used fixed codec strings.
Those strings matched only 6 of 59 video copies.
On every rotated source, the server computed a 1920x1080 output size for the quality ladder, but FFmpeg wrote 608x1080.
The codec level and the playlist's `RESOLUTION` were therefore wrong.
A file whose first video stream is cover art fails to encode.
Codec strings computed from the decoder configuration record matched the copy's initialization segment for 54 of 59 video copies.
Those codec strings matched all 50 H.264 and HEVC copies.
Those codec strings also matched 42 of 42 audio copies.
The 5 misses were AV1 in IVF or raw OBU files.
The measurement did not parse the sequence headers of those files.
ffprobe's named profile and level matched only 41 of the 59 video copies.
The measurements are in <<evidence-stream-facts>>.
The worker reports every handler name, because the list of generic handler names is open-ended.
A rule in the worker would need a new probe version for each fix, and every file would then need a new probe.
For example, a rule that treats a name as generic when the name ends with "Handler" would keep "ISO Media file produced by Google Inc." as a track name.
The server can fix its own rule without a new probe.
link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043] holds the library sample's handler names, which test the server's rule.
The hearing-impaired flag comes from the same ffprobe run as the other version 4 facts (<<evidence-hearing-impaired>>).
So https://github.com/streamarr/streamarr-server/issues/60[streamarr/streamarr-server#60] marks SDH renditions without a later probe version.

[[probe-version-5]]
=== Probe version 5 reads the first frames of the chosen video stream and reports typed codec and color facts

Probe version 5 reports every fact of probe version 4.
https://github.com/streamarr/streamarr-server/issues/394[streamarr/streamarr-server#394] adds probe version 5.
Probe version 5 adds these facts to a successful outcome:

* The codec profile, codec level and codec tier of each video stream, as typed values.
The probe reads those values from the stream's decoder configuration record or sequence header.
The probe never maps ffprobe's profile name.
A codec profile that the worker contract does not name is `UNSPECIFIED`.
The codec level is absent when the probe cannot read a level.
Each audio stream still reports only its profile name, as ffprobe prints it.
* The color primaries, transfer characteristics, matrix coefficients and color range of each video stream.
Each value of the primaries, the transfer and the matrix names one ITU-T H.273 code point.
An enum value's number in the worker contract need not equal its H.273 code point, as ADR 0036 records.
A value that the worker contract does not name is `UNSPECIFIED`.
* Whether the probe read the first frames of each video stream.
The probe reads the first 3 frames of the chosen video stream, or fewer when the stream holds fewer.
The probe reads no frame of any other stream.
A read that keeps 1 or 2 frames counts as cut short, even when the stream holds no more, and reports no frame feature as `ABSENT`, as ADR 0036 decides.
When no read decodes a frame, because every read fails or because even the read of 192 packets decodes none, the probe reports that it did not read the stream's first frames.
Only the HDR10+, observed RPU and Dolby Vision facts of such a stream keep their probe version 4 meaning, so it reports no frame feature as `ABSENT`, and a present Dolby Vision gives no first RPU header and an unspecified RPU placement.
Its compatible base follows the probe version 5 rules, as ADR 0036 decides.
* The HDR10+ and Dolby Vision RPU facts that the first frames show, as the probe version 5 section of ADR 0036 decides.
For H.264 and HEVC, the probe also parses the NAL units of the packets that hold those frames, because FFmpeg's decoders drop or ignore some RPUs.
The probe also reads the SEI messages of those packets and of the stream's extradata, because FFmpeg loses some HDR10+ and static metadata messages.
H.264 streams therefore report HDR10+ as present or absent, as HEVC streams do.
FFmpeg's AV1 decoders drop the RPUs, the frames and the rest of the packets whose metadata OBUs they cannot parse, and never apply the metadata OBUs of the extradata.
For AV1, the probe therefore reads the metadata OBUs of the extradata and of those packets.
The probe reads extradata in each form that FFmpeg's demuxers give: an `avcC`, `hvcC` or `av1C` record, Annex B extradata, and the bare OBUs of AV1 in IVF or a raw OBU file.
AV1 streams therefore report HDR10+, RPUs and Dolby Vision as present or absent, as H.264 and HEVC streams do.
Those facts include the fields of the first RPU header that tell the Dolby Vision profile.
An HEVC NAL unit of type 62 counts as an RPU only on layer 0 with TemporalId 0, where FFmpeg's HEVC decoder reads an RPU, as ADR 0036 decides.
The walk skips the NAL units that FFmpeg's NAL unit splitter drops before its decoders see them, such as a NAL unit whose `forbidden_zero_bit` is 1, as ADR 0036 lists.
Those facts also include the RPU placement: whether each RPU follows its own picture, whether every RPU starts its sample, or whether the first packets cannot tell, as ADR 0036 decides.
* Whether the first packets of the chosen video stream carry presentation times.
The probe asks ffprobe for each packet's presentation time in its read of the packets that the NAL unit walk covers.
ffprobe's JSON leaves out the presentation time of a packet to which the demuxer gives none.
The fact is true when every packet that the read printed has a presentation time, and false when at least one has none.
The fact is absent when the probe read no packets: on every stream but the chosen video stream, on a chosen video stream whose codec is not H.264, HEVC or AV1 or whose first frames the probe did not read, and when that read fails or prints no packet.
The server refuses a video stream's fact as a contract violation unless the probe read that stream's first frames and its codec is H.264, HEVC or AV1.
link:0013-stream-decision-architecture.adoc#reshape-rpus-starting-samples[ADR 0013] decides how the worker's RPU move uses the fact.
* The mastering display of the first frame of the chosen video stream, when the container declares no mastering display.
The content light level of that first frame, when the container declares no content light level.
For H.264 and HEVC, when the first frame carries no value either, the value of the first SEI message that carries it and is not nested.
For AV1, when the first frame carries no value either, the value of the first mastering display or content light level metadata OBU without an extension byte.
The values keep the units of the probe version 4 static metadata.
* Whether each video stream carries, or may carry, a static metadata value that the probe left absent.
That includes a Matroska MasteringMetadata element that FFmpeg's Matroska demuxer drops because neither its primaries nor its luminance are complete.
That also includes each value that no source gives when the probe cannot read the Matroska track's Colour element, for every codec.
That also includes a value that the probe cannot rule out, as ADR 0036 decides, such as a value that an SEI NAL unit or an OBU that the probe could not delimit may hold.
A stream with such an omitted value is never PQ10.
* The content light level of the chosen video stream's Matroska track when the track's MaxCLL or MaxFALL element is 0 or missing.
ffprobe reports a Matroska light level only when both elements are nonzero.
When ffprobe reports no light level, the probe reads the two elements itself.
A track that holds either element reports both values, with 0 for an element that the track does not hold.

The server stores every one of these facts with the probe outcome.
The server stores no `MediaFileProbePropertyIssue`.
The server derives each issue from the stored facts when the server decides, as ADR 0036 decides.
A fix to the rule that derives an issue therefore needs no new probe version.

The upgrade to probe version 5 keeps every probe version 4 outcome.
The server can still read a probe version 4 outcome, because probe version 5 does not change how the server reads a probe version 4 fact.
On the upgrade, the server queues a re-scan itself, as <<upgrade-rescan,the section on source changes and probe versions>> describes.
The re-scan runs through the existing scan library operation and the durable probe jobs.
Playback keeps using each file's probe version 4 outcome until the server stores the file's probe version 5 outcome.
A probe version 4 outcome stores no codec profile.
ADR 0013 refuses a copy of an `UNSPECIFIED` codec profile only for an outcome of probe version 5 or later.

*Why:* A probe that reads no frames cannot report HDR10+ or a Dolby Vision RPU as absent.
Some streams carry their HDR10 static metadata only in their HEVC bitstream.
Probe version 4 therefore could not tell HDR10 from PQ10.
A Dolby Vision profile 5 stream without a configuration record names its profile only in its RPUs.
FFmpeg's HEVC decoder ignores an RPU that is not the last NAL unit of its sample, so the frames alone can hide the RPUs of a malformed profile 5 stream.
FFmpeg also loses the HDR10+ and static metadata messages that follow a rejected SEI message, so the frames alone can make an HDR10 stream look like PQ10.
FFmpeg's AV1 decoders lose metadata OBUs in the same way, so the frames alone can also hide an AV1 stream's HDR10+, RPUs and static metadata.
https://github.com/streamarr/streamarr-server/issues/395[streamarr/streamarr-server#395] compares the codec profile and level with what a client declares, so streamarr/streamarr-server#395 needs typed values.
The measurements are in <<evidence-frame-facts>>, <<evidence-static-hdr>> and <<evidence-fate-sweep>>.

[[output-frame-rate]]
=== The probe job chooses the output frame rate once per file

The output frame rate is the rate at which every encode of the chosen video stream runs.
The frame-rate rule chooses the output frame rate.
The worker's probe job runs the frame-rate rule on the chosen video stream.
link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] defines the frame-rate rule.
This ADR decides only where the rule runs and what the outcome keeps.
The probe job reports the rule's inputs and the rate that the rule chose.
The inputs are the declared rates, the field order, the time base and Matroska's statistics tags.
When the rule scans packets, the inputs also include three scan results.
Those results are the motion rate that the scan measured, the number of frames that the scan read, and the number of seconds that the scan covered.
The motion rate is the frame rate at which the video's motion actually runs.
The outcome stores those inputs and the output frame rate.
The outcome stores the output frame rate as an exact fraction, such as 24000/1001, never as a decimal.
The database, the transcode job and the worker's FFmpeg argument all carry the fraction.
The server passes the stored rate to every job attempt.
Every attempt of every stream session therefore encodes the file on one frame grid.
A frame grid is the sequence of output frame times that an encode produces.
Neither the server nor a job attempt computes the rate again.
When the rule refuses to choose a rate, the probe still succeeds.
The outcome then holds no output frame rate.
In that case, the server leaves out each variant that would encode the file's chosen video stream.
The server refuses the stream session only when every variant would encode that video stream, as https://github.com/streamarr/streamarr-server/issues/446[streamarr/streamarr-server#446] describes.

*Why:* In a 300-file library sample, the rule chose the rate of 294 files from their declared rates alone.
The other 6 files needed a packet scan over 30 s of media.
Each of those scans read 8–113 MB.
Each of those scans took 58–336 ms when the file was already in the operating system's cache.
Because the probe job runs the rule, the worker pays the scan cost once per file rather than in every job attempt.
A job attempt that computed its own rate could disagree with an earlier attempt.
For example, a worker upgrade could change the rule between the two attempts.
A junction is the boundary where a replacement attempt's media meets the earlier attempt's media.
At the rule's rates, 46 of 46 junctions carried the same source frame in both attempts.
The comparison covered 20,934 output frame positions.
The measurements are in <<evidence-frame-rate>>.

[[probe-limits]]
=== ffprobe reads up to 200 s or 1 GB and does not scan for every program map table

The worker runs ffprobe with `-analyzeduration 200M -probesize 1G -scan_all_pmts 0` for probe version 4 and later.
`-analyzeduration 200M` lets ffprobe analyze up to 200 s of media.
`-probesize 1G` lets ffprobe read up to 1,000,000,000 bytes.
A program map table lists the streams of one program in an MPEG-TS file.
`-scan_all_pmts 0` stops ffprobe from scanning for every program map table.
An MPEG-TS probe can then stop once every stream has its parameters.
Without this option, an MPEG-TS probe reads to those limits.
The limits apply to the probe only.
A job attempt's FFmpeg input keeps FFmpeg's defaults.

*Why:* By default, ffprobe stops after 5 s of media or 5 MB.
In the 300-file library sample, the default stop missed the width and height of 334 PGS subtitle streams in 49 files.
PGS is the Blu-ray image subtitle format.
The first packets of those 334 streams came after the default stop.
The limits filled in the width and height of 319 of those streams.
The limits changed no video or audio field in any file.
No playback path reads subtitle dimensions yet.
With the limits, ffprobe read more of 66 of the 300 files.
The median extra read was 189 MB.
The largest extra read was 1.05 GB.
Each file pays the extra read once.
With the limits but without `-scan_all_pmts 0`, every MPEG-TS probe read to a limit.
By default, ffprobe scans for every program map table.
The 14 transport streams without PGS subtitles read 66–1,053 MB.
Their results did not change.
With `-scan_all_pmts 0`, all 19 transport streams gave the same results as with the limits alone.
The 14 transport streams without PGS subtitles then read 0.4–1.9 MB.
The measurements are in <<evidence-probe-limits>>.

[[keyframe-positions]]
=== The server learns where the source's keyframes are before it offers a stream copy

A keyframe position identifies one keyframe in the chosen video stream.
Each stored keyframe position keeps both the keyframe's presentation time and the keyframe's decode time.
The probe reads the keyframe positions from the source container's own index when the container has one.
For MP4 and MOV, that index is the sync-sample table.
For Matroska, that index is the Cues element.
The probe trusts a container index only when the probe can read the last keyframe that the index lists.
A durable background step finds the keyframe positions of every other source.
In that step, a worker scans every packet of the chosen video stream.
The step runs for MPEG-TS files, which have no such index.
The step also runs for AVI files.
The step also runs for Matroska files whose Cues are sparse or missing.
The step also runs for a file whose index lists a last keyframe that the probe cannot read.
Such a file gets the same packet scan as a file without a usable index.
A stream copy's media playlist therefore never advertises media segments past the source's real end.
link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] decides what happens when a copied variant still runs short.
Like the probe step, the keyframe step survives a server restart.
Stored keyframe positions are probe facts.
The <<probe-version-rules,probe version rules>> therefore apply to stored keyframe positions.
The server offers a stream copy only after it knows the source's keyframe positions.
Until the server knows those keyframe positions, the server encodes the video.
The server applies this keyframe condition for a stream copy from probe version 3, which stores keyframe positions.
https://github.com/streamarr/streamarr-server/issues/66[streamarr/streamarr-server#66] adds probe version 3.
Before probe version 3 takes effect, the server copies the video under ADR 0013's interim copy rule.
A stream copy's media playlist advertises the real duration of each media segment.
The keyframe positions determine those durations.
link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] defines how a job attempt seeks to a keyframe position.

*Why:* A stream copy's segment boundaries depend on the source's keyframes.
Without keyframe positions, the playlist advertised the same fixed duration for every stream-copy segment.
A stream-copy seek to a media segment that held no source keyframe failed with `SKIPPED_SEGMENT_NUMBER`, as https://github.com/streamarr/streamarr-server/issues/66[streamarr/streamarr-server#66] describes.
A container index already lists the keyframes.
The probe therefore needs no packet scan for a source whose container has an index.
A truncated file can keep an index that lists keyframes past the file's real end.
A keyframe's presentation time can lie after the keyframe's decode time.
A seek that starts reading at a keyframe needs the keyframe's decode time.

=== File events and quiet periods

The server waits for a quiet period only after it observes a file change.
The watcher groups repeated events for a file.
The watcher waits until the events stop before it enqueues a probe request.
When the dispatcher reads a source snapshot, either before or after the probe, it compares that snapshot with the requested snapshot.
If the snapshots differ, the dispatcher records the observed snapshot.
The dispatcher then reschedules the probe one quiet period later.
The dispatcher does not probe the changed source at once.
Each time the dispatcher observes another change, it moves that deadline.
The watcher and the dispatcher use the same quiet period.
Neither wait occupies a scheduler probe slot or reserves a worker.
The dispatcher can probe other files while the changed file waits.

Bulk scans do not impose a quiet period.
A scan requests a probe for an unchanged file that needs one.
The dispatcher probes that file without waiting.
The scan requests the probe using the size and modification time from the library listing.
The scan does not read the source again when it makes the request.
If the source becomes unreadable after the scan lists the file, the probe attempt fails but the scan does not.
A probe requested because `probe_version` changed runs without waiting for a quiet period.

A new request replaces a pending probe's inputs but does not move the scheduled time earlier.
One exception applies to requests from a scan or from the code that discovers files.
If the probe's last attempt has a saved failure, such a request runs the probe at once.
That request also restarts the probe's backoff.
Use the saved failure to decide whether to retry at once.
Do not use db-scheduler's failure count.
db-scheduler keeps the count when the probe waits for a busy worker.
db-scheduler resets the count when a request replaces the pending probe's inputs.
The dispatcher saves no failure for a canceled attempt, so a new request keeps that probe's backoff.
A playback request also keeps the probe's backoff.

If the dispatcher observes a source change during an attempt, the probe keeps its quiet period.
A newer request that arrived during the attempt does not shorten that period.
A request does not record whether the caller waited for the file to go quiet.
The request therefore cannot shorten the quiet period.
The watcher's own quiet period usually ends after the dispatcher's deadline, because the dispatcher's last observation precedes the file's last change.
A retry after a transient failure waits only for its backoff.
If a virtual thread waits inside a claimed probe job, the job still occupies a scheduler slot.
Schedule the probe for a later time so the wait happens before the dispatcher claims the job.

Even after a quiet period or a successful probe, a file may still be copying.
For example, ffprobe can successfully read a faststart MP4 or MKV before the file finishes copying.
Source snapshots and the probe version protect saved results instead.
The dispatcher saves an outcome only if both source snapshots match the requested snapshot.
Those are the snapshots read before and after the probe.
The requested `probe_version` must also be current.
When the server later observes a change, the server replaces the requested inputs.
The server then deletes the stored success or terminal error.
The server schedules a fresh probe for the changed source.
The server does not infer that a copy has finished from the file's age.

[[probe-version-rules]]
=== Source changes and probe versions

When a scan or the watcher processes a file, compare the file's size and modification time with the stored snapshot.
When the source snapshot differs, delete the stored outcome and its stream rows and schedule a new probe.
Playback cannot use the cached result until the server records a new outcome.

When `probe_version` increases, scans and the watcher can schedule background probes to refresh older outcomes.
Playback can still use an older successful result if the server can safely interpret the result and the source snapshot still matches.
Keep the old result until the server atomically saves the new result.
If required fields change, or the server changes how it interprets those fields, the migration must invalidate incompatible outcomes.
The migration must delete the affected container and stream rows.
The migration must also document that playback remains restricted until the server rebuilds those rows.
Apply the same rule when correcting codec data or data that determines which streams the server selects, even if no column is added.
Increase `probe_version` whenever a probe column is added so the server can detect outdated outcomes when it processes files.
Skip probing while the stored success or terminal error matches the source snapshot and requested version.
A scan still probes a file whose terminal error comes from contract violations (<<probe-contract-violations>>).
Use the same scheduling path to refresh older terminal errors and older successful results.

[[upgrade-rescan]]
When an upgrade needs new probe data, the server queues a re-scan itself.
The re-scan reuses the existing scan library operation and the durable probe jobs.
Streamarr adds no separate backfill mechanism.
A ServerAdmin does not have to start the re-scan.
The upgrade to probe version 4 deletes the version 1 and version 3 outcomes before the re-scan, as <<probe-version-4-migration,the section on the version 4 migration>> describes.
On every upgrade to a probe version after version 4, each file's older outcome stays playable wherever the server can still read that outcome.
The older outcome stays playable until the server stores the file's new outcome.
Upgrades of production instances also keep older readable outcomes playable.
The upgrade path must stay clear and clean, so that production instances upgrade gracefully.

[[probe-version-4-migration]]
=== Probe version 4 deletes version 1 and version 3 outcomes, and the server queues a re-scan

The migration to probe version 4 deletes every stored version 1 and version 3 outcome and its stream rows.
The migration also deletes the keyframe positions that a version 3 outcome stores.
The server cannot read version 1 and version 3 outcomes correctly.
Version 4 changes how the server interprets an outcome.
In that case, the rules in <<probe-version-rules,the section on source changes and probe versions>> require the migration to delete incompatible outcomes.
A version 1 or version 3 outcome would read as an `UNSPECIFIED` dynamic range.
The server would then copy an HDR file or encode that file without tone mapping.
Such an outcome does not name the chosen video stream.
The transcode decision would then read the first video stream, which may be cover art.
Deleting the version 1 and version 3 outcomes is a breaking change.
Streamarr accepts that breaking change only while Streamarr has no production instances.
On the upgrade to probe version 4, the server queues a re-scan itself, as <<upgrade-rescan,the section on source changes and probe versions>> describes.
The re-scan probes the files of every library again.
The re-scan requests a probe for every file without a current outcome.
Until a file's probe stores an outcome, a playback request for that file moves the file's probe to the front of the queue and waits for the outcome, as <<playback,the Playback section>> describes.

*Why:* Streamarr has no production instances.
No installation therefore loses playback that it relies on.
If the server kept version 1 or version 3 outcomes, playback would make the decisions that probe version 4 exists to prevent.
Playback would keep making those decisions until the re-scan refreshed each file.

[[later-probe-versions]]
=== Each change that adds probe facts adds its own probe version

Each change that adds probe facts increases the probe version when that change merges.
Each probe version reports every fact of the versions before it.
The probe versions are numbered in the order in which they ship:

* Probe version 1 reports the container's format, duration and bitrate.
It also reports each stream's codec, language, size, frame rate, channels, bitrate and flags.
* Probe version 3 adds the keyframe positions of the chosen video stream, as <<keyframe-positions,the keyframe section>> describes.
https://github.com/streamarr/streamarr-server/issues/66[streamarr/streamarr-server#66] adds the keyframe positions.
* Probe version 4 adds the facts that <<probe-version-4,the probe version 4 section>> lists.
https://github.com/streamarr/streamarr-server/issues/501[streamarr/streamarr-server#501] adds those facts.
Probe version 4 also reports the keyframe positions of version 3.
* Probe version 5 adds the facts that <<probe-version-5,the probe version 5 section>> lists.
https://github.com/streamarr/streamarr-server/issues/394[streamarr/streamarr-server#394] adds those facts.

Probe version 2 is unused.
This ADR first gave version 2 to the facts for streamarr/streamarr-server#501.
The keyframe positions were ready first, so they shipped as version 3.
No server requests probe version 2, and no worker advertises it.

A change after probe version 4 does not add its facts to probe version 4.
A change after probe version 5 does not add its facts to probe version 5.
A later probe version adds caption detection: whether the video carries CEA-608 or CEA-708 captions.
The probe detects the captions by decoding keyframes.
https://github.com/streamarr/streamarr-server/issues/505[streamarr/streamarr-server#505] adds the caption detection.

Probe version 4 already reports the title, the handler name and the hearing-impaired flag of each audio and subtitle stream.
https://github.com/streamarr/streamarr-server/issues/503[streamarr/streamarr-server#503] and https://github.com/streamarr/streamarr-server/issues/60[streamarr/streamarr-server#60] read those facts and leave the probe version unchanged.
The titles and handler names are stream tags, and the hearing-impaired flag is a stream disposition.
The probe reads all three in the same ffprobe pass as every other version 4 fact.
Caption detection stays in a later probe version, because caption detection decodes the video's keyframes.
The ADR that owns each fact decides how the server uses that fact.
This ADR and link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] decide how the server uses keyframe positions.
ADR 0037 and link:0043-audio-tracks-and-text-subtitles-are-hls-renditions.adoc[ADR 0043] decide how the server uses stream end times.
ADR 0043 decides how the server uses stream titles, handler names, hearing-impaired flags and caption detection.
On the upgrade to each probe version, the server queues a re-scan and keeps older readable outcomes playable, as <<upgrade-rescan,the section on source changes and probe versions>> describes.

[[decision-probe-task-protocol]]
=== How the server checks requested inputs and saves results

db-scheduler owns each probe execution.
db-scheduler picks a due execution, keeps a heartbeat while the execution runs, and runs a dead execution again.
Streamarr adds no claim id or lease of its own.
The execution's data records the source snapshot and `probe_version` that the attempt expects.
`media_file_probe_task_request` records the inputs that the latest request specifies.

Read the source snapshot before and after probing.
Discard the result and reschedule the task if the snapshot changes during the probe.
Compare snapshots for equality.
File size and modification time do not establish which attempt is newer.

Publish an outcome in one transaction.
The transaction first locks the media file row.
The transaction then verifies that the attempt's snapshot and version match the inputs in `media_file_probe_task_request`.
The transaction also verifies that the database holds no outcome from a newer probe version for the same snapshot.
That transaction then replaces the container outcome and stream rows.
Check the requested inputs and publish the outcome atomically in the same transaction.
Do not check the requested inputs first and then write without guarding the write.

When an attempt finishes, the server removes or reschedules the execution in another transaction.
That transaction also locks the media file row and reads the requested inputs.
If no request remains, the server removes the execution.
If a newer request replaced the attempt's inputs, the server reschedules the execution with the requested inputs.
An attempt whose inputs a newer request replaced therefore cannot publish an outcome or remove the execution.

A request saves new inputs under the same row lock.
In that transaction, the server replaces the saved inputs and deletes a stored outcome whose snapshot differs.
db-scheduler keeps one execution per media file, so the requested inputs replace obsolete ones rather than adding a second execution.
If an execution already exists when the server enqueues a request, the saved request still preserves any input change that the server detected.
Run file I/O and probing outside database transactions.

=== Transient failures

Retry probes after temporary storage errors.
After ADR 0033, also retry probes when the worker is unavailable or the worker session is lost.
db-scheduler stores the next retry time on the file's execution.
The server writes no terminal `probe_error` for these failures.
The failure handler stores the reason on the file's probe request, `media_file_probe_task_request`, in the transaction that reschedules the retry.
The handler stores the reason only if the failed attempt used the inputs that the probe request still specifies.
If a newer request replaced those inputs while the attempt ran, the handler stores no failure reason.
In that case, the handler retries the newly requested inputs at once.
The failed attempt tells the server nothing about those new inputs.
If no probe request remains, for example because the media file was deleted during the attempt, the handler removes the execution.
Use the item failure reasons from https://github.com/streamarr/streamarr-server/issues/417[issue #417]:

* Store `SOURCE_INACCESSIBLE` when the worker reports `PROBE_FAILURE_SOURCE_UNAVAILABLE` or the server cannot read the source attributes.
For example, the worker reports `PROBE_FAILURE_SOURCE_UNAVAILABLE` when a share is unmounted or the worker cannot read a file.
* Store `MISCONFIGURED` when the worker reports `PROBE_FAILURE_UNSUPPORTED_VERSION` or replies for another probe version.
Also use this reason when no connected worker can read the source namespace at the requested version.
* Store `TEMPORARY` when the worker reports `PROBE_FAILURE_EXECUTION_FAILED`.
Use the same reason when a worker is lost, unreachable or missing.
Also use `TEMPORARY` when a reply breaks the worker contract or an unexpected exception occurs.
After three consecutive contract violations, the server stops retrying the probe, as <<probe-contract-violations>> describes.

A canceled attempt, including `PROBE_FAILURE_CANCELLED`, did not finish.
Retry the probe with backoff and do not record a failure reason, just as when the probe waits for a busy worker.
A worker that reports `PROBE_FAILURE_NO_FREE_CAPACITY` refused the probe before ffprobe started.
The server treats that refusal as a wait for a busy worker and records no failure reason (<<probe-capacity>>).
Do not store a retryable failure as a terminal `probe_error`.
The server does not retry a terminal error while the source and probe version stay the same.
An unreadable source may become readable again.
The one exception is a probe whose replies broke the contract three times in a row (<<probe-contract-violations>>).
A scan still probes a file with that terminal error again.
Do not store the failure reason in `item_result`, because that table keys results by movie or series rather than by media file.
Clear the failure reason when the server stores an outcome for the requested inputs or a request replaces those inputs.
Keep the reason when a request specifies the same inputs again.
When the dispatcher finds that the source no longer exists, it deletes the probe request instead of rescheduling it.
When a probe needs a retry, db-scheduler reschedules the file's execution.
db-scheduler picks the execution again when the retry is due.
Use capped backoff without requiring a file change or version bump.
Keep one execution per media file during retries.
Schedule retries without holding a database transaction across the delay.

[[probe-contract-violations]]
=== Three consecutive contract violations stop a probe's retries

A contract violation is a worker reply that breaks the worker contract.
For example, a reply can carry a result without an outcome.
A reply can also list keyframe decode times that do not increase.

After three consecutive contract violations for the same probe inputs, the server stops retrying the probe.
The server then stores a terminal `probe_error` that names the contract violation.
The terminal error tells a ServerAdmin that the worker, not the file, is at fault.
After the first and the second contract violation, the probe retries with capped backoff, as the section on transient failures describes.
The count covers only attempts at the same probe inputs.
A request that replaces those inputs starts the count again.
Any other recorded failure between two contract violations also starts the count again.

Other `TEMPORARY` failures keep retrying with capped backoff and no limit.
For example, the server keeps retrying when a worker is lost, unreachable or missing.
An unrecognized failure value from a newer worker is not a contract violation.
That failure value stays retryable and has no limit.

Some contract violations break the worker session rather than one reply.
An oversized message for one probe's result is an example.
When the server can tie such a violation to one probe, the violation counts toward that probe's limit.
When the server cannot tie the violation to one probe, the server ends the worker session.
The probe then fails as an ordinary retryable failure, as when a worker is lost.

A changed source and a new probe version retry a stopped file, as they retry every terminal error.
Unlike other terminal errors, a scan also retries a file that contract violations stopped.
A ServerAdmin's scan retries the file.
Scheduled scans also retry the file once https://github.com/streamarr/streamarr-server/issues/480[streamarr/streamarr-server#480] ships.
The scan deletes the terminal error in the transaction that saves the scan's probe request.
The scan then waits for a result, as for any probe that the scan requests.
The new attempts start the count of contract violations again.
A playback request does not retry a stopped file, as <<playback>> describes.

The server counts every contract violation in a metric tagged by cause.
A ServerAdmin can therefore see contract violations before any file stops.

*Why:* The same file and the same worker give the same broken reply on every attempt.
A retry therefore cannot fix a contract violation.
Only a worker fix can.
Before this amendment, the server retried a contract violation forever.
The backoff started at 5 s and doubled up to 300 s.
Once the backoff reached 300 s, each retry cost a worker probe and a database write every five minutes.
The broken reply never succeeded.
A keyframe packet scan on a real library reached 17 consecutive identical failures.
Keyframe packet scans already stop after three failed scans.
https://github.com/streamarr/streamarr-server/pull/646[streamarr/streamarr-server#646] counts contract violations toward that limit.
Probes use the same limit of three.
A rare transient corruption breaks only one reply.
The next attempt then succeeds.
Three attempts therefore stop only a reply that keeps breaking.
A worker fix that keeps the probe version changes neither the source nor the version.
A scan is therefore how a worker fix reaches a stopped file.

[[probe-capacity]]
=== Each worker grants a separate capacity for each kind of work, and playback comes first

A worker runs four kinds of work:

* A job attempt produces one variant of a stream session for playback.
* A playback probe is a probe that a playback request waits for, as <<playback>> describes.
* A background probe is any other probe that reads ffprobe's facts, such as a probe that a scan requested.
* A keyframe packet scan scans every packet of the chosen video stream, as <<keyframe-positions>> describes.

A capacity is the number of items of one kind that a worker accepts at once.
Each worker grants a separate capacity for each kind of work.
The playback slots are the capacity for job attempts.
The other three capacities are the playback probe capacity, the background probe capacity and the keyframe packet scan capacity.
The server sends a worker an item only while the worker's capacity for that kind of item has a free unit.
The server never sends an item beyond a granted capacity.
The server decides only the order in which queued work goes out.
Playback probes go first.
Background probes go next.
Keyframe packet scans go last.
Each probe request names the probe's kind, so the worker knows which capacity the probe uses.
A probe never takes a playback slot, and a job attempt never takes a probe's capacity.

A worker can lower a capacity at any time during the worker's session.
Work that already runs keeps running when a capacity drops below that work.
The server learns of a lower capacity only when the worker's message arrives.
A probe that the server sent before that message can therefore arrive beyond the lower capacity.
The worker refuses such a probe with `PROBE_FAILURE_NO_FREE_CAPACITY` before ffprobe starts.
The server treats that refusal like a busy worker.
The probe stays queued without a failure.
Any worker with a free unit of the right capacity can then take the probe.

*Why:* The worker alone can see the worker's host.
The worker alone sees the other services on the host, the host's disks and the cores that the worker's own job attempts use.
The server sees viewers, but the server cannot see a worker's host.
A worker that grants capacity also fits workers of different sizes.
A 72-core host, a 4-CPU Kubernetes pod and a GPU node each grant what each one can run.
The server adds up the capacities and needs no knowledge of each host.
A capacity for each kind of work keeps urgent work from waiting behind work that the worker already accepted.
Temporal's workers keep a separate slot pool for each task type in the same way, and Kubernetes' API Priority and Fairness keeps separate limits for each priority level.

==== Playback slots

The playback slots stay fixed for the worker's session.
A worker setting sets the playback slots.
https://github.com/streamarr/streamarr-server/issues/499[streamarr/streamarr-server#499] replaces the fixed count with measured encoder headroom, as link:0044-encoder-headroom-and-the-preset-scale.adoc[ADR 0044] decides.

==== Playback probe capacity

The playback probe capacity is 2 on every worker.
The playback probe capacity stays fixed for the worker's session.
The worker never lowers the playback probe capacity.
A playback probe can also use a free unit of the background probe capacity.
A background probe never uses the playback probe capacity.
A playback probe therefore never waits behind a background probe, behind a keyframe packet scan or behind a lowered background probe capacity.
No probe holds a particular unit.
The server and the worker each count the playback probes and the background probes that run.
Both compute the background units in use with the same formula: the background probes, plus the playback probes beyond the playback probe capacity.
The server counts a probe until the probe's result arrives, so the server's counts never fall below the worker's counts.
The worker therefore accepts every probe that the server sends while no capacity drops.
The server measures how long each playback probe waits for a free unit.

*Why:* Two units cover two viewers who start unprobed files at the same moment.
A probe that held the unit it arrived on would let the two sides disagree.
The server learns that a probe ended only when the probe's result arrives.
Until then, the worker can place the next playback probe on a playback unit that the server still counts as used.
The server would then count a free background unit that the worker has filled, and the worker would refuse a background probe although no capacity dropped.
Other systems reserve similarly small pools: Apache Flink reserves 2 buffers for each channel, and PostgreSQL reserves 3 connections for superusers.
A playback probe that waits for a free unit shows that 2 units are too few.

==== Background probe capacity

The worker adapts the background probe capacity while the worker runs.
The background probe capacity is an additive-increase, multiplicative-decrease limit, `AIMDLimit` from Netflix's concurrency-limits library.
The sections below call the background probe capacity the limit.
The limit starts at 4.
The limit never falls below 1.
The limit never rises above the processor count of the worker's JVM.
In Kubernetes, the deployment example sets that processor count from the worker container's CPU request.
When a probe ends that used a background unit, and at least half of the limit was in use, the limit grows by 1.
The limit does not grow while a judged job attempt produces below the floor.
A brake halves the limit.
Three brakes exist: the brake for job attempts, the brake for timed-out probes and the brake from pressure stall information.
After a brake, the limit does not grow for 30 s.
A worker setting holds the background probe capacity at a set value.
That setting stops the limit from adapting and turns every brake off.
The worker reports whether the worker's background probe capacity adapts or stays fixed.

*Why:* The limit uses the whole host while nothing plays.
A fixed reserve of cores for playback would waste those cores while nothing plays.
A fixed reserve also could not protect a software encode that needs more cores than the reserve holds.
Netflix's PlayAPI gives work that users start the first share of its capacity, and prefetch runs only on capacity that remains.
The 30 s pause after a brake keeps the limit from swinging up and down against a long encode.
LinkedIn's Hodor waits in the same way before it raises a limit again.

==== The brake for job attempts

The brake for job attempts protects the production speed of the worker's job attempts.
Production speed is the number of media seconds that a job attempt produces per second of wall-clock time, as ADR 0044 defines it.
The worker measures each job attempt's production speed from the attempt's own media segments.
The worker averages the production speed over the media segments that the attempt finished in the last 15 s of wall-clock time.
The average always covers at least the attempt's last 2 media segments, even when those segments finished more than 15 s ago.
The average is the media seconds of those segments divided by the seconds that the worker took to produce them.
The worker judges an attempt only after the attempt's media segments have taken 15 s of production time in total.
The brake applies when a judged attempt's average falls below 2.10× real time.
While the average stays below 2.10×, the brake applies again once in each further 15 s.
A brake for a slow attempt waits until 15 s have passed since the previous brake, whatever applied it.
Every job attempt counts, including a stream copy and a remux.
The brake also applies once when a job attempt starts, before the worker can judge that attempt.

A media segment's production time runs from the end of the attempt's previous media segment until the worker finished the segment.
The first media segment's production time runs from the moment the worker started FFmpeg.
The production time leaves out every wait in which the worker held FFmpeg back until an earlier segment's upload was accepted.
This includes a wait for the worker's segment memory, which other job attempts' uploads also hold.
The worker measures production times on a monotonic clock, so a correction of the host's clock cannot apply the brake.
The worker reports each media segment's production time with the segment's upload.
The server takes each job attempt's production speed from those reports.
One measurement therefore serves both the brake and ADR 0044's headroom.

*Why:* The brake for job attempts measures harm to playback, not how busy the host is.
The production time leaves out waits for uploads, because probes do not slow an upload.
A slow network or a server that holds back a producer, as https://github.com/streamarr/streamarr-server/issues/55[streamarr/streamarr-server#55] plans, would otherwise apply the brake.
ADR 0044's headroom needs the encoder's speed for the same reason.
Slow production catches a contended CPU and a contended disk alike.
Google's CPI² and LinkedIn's Hodor also act on harm to the work that matters.
The window is a span of time, not a number of segments, because media segments differ in length.
A merged-slot segment under link:0037-worker-delivers-fmp4-segments-from-ffmpeg-stdout.adoc[ADR 0037] can span several 3 s slots.
The window of 15 s lets the brake act before a player's buffer of about 30 s runs out.
Raw production speed of each media segment varies too much to act on.
Livepeer had to smooth the same measurement.
The first media segments of an attempt are slow for reasons other than contention, such as FFmpeg's startup and the source seek.
2.10× is ADR 0044's speed floor at 3 s segments, the floor of the neediest player.
The server does not compute a floor for each stream session yet.
A fixed 2.10× therefore lowers the background probe capacity during some playback that keeps its own floor.
That error slows a scan but never risks playback.
The brake at the start of an attempt clears probes from the host while a viewer waits for the first media segment.
The probes that run then finish within seconds, so the brake takes effect almost at once.

[[probe-timeout-brake]]
==== The brake for timed-out probes

The server ends every probe that has not finished within the probe timeout.
The probe timeout is a server setting.
The default is 60 s.
The server alone owns the probe timeout.
When the server ends a probe, the server sends the worker a cancel command.
The cancel command says why the server ended the probe.
The reason is the probe timeout, a server shutdown or another reason.
The server retries a timed-out probe later, as the section on transient failures describes.

A probe that the server cancels for the probe timeout applies a brake, which halves the limit.
Both a background probe and a playback probe apply that brake.
A cancel command with the server shutdown reason or another reason never applies a brake.
A keyframe packet scan has a timeout of its own and applies no brake.
Only a probe that started after the latest brake can apply the next brake for a timed-out probe.
A probe that started before the latest brake applies no brake when the probe times out.
A brake for a timed-out probe also waits until 15 s have passed since the previous brake, whatever applied that brake.
After that brake, the limit does not grow for 30 s, as after every brake.
A probe that ended at the probe timeout never grows the limit.
At the limit's floor of 1, a probe that reaches the timeout cannot lower the limit further.
That probe fails like any other timed-out probe.
The server retries the probe later.
The brake for timed-out probes works while no job attempt runs.
The brake for timed-out probes works on every host and needs no extra privilege.

*Why:* A busy disk can stop every probe from finishing.
The brake for job attempts cannot see a busy disk while nothing plays.
A RHEL 8 host showed the failure.
A library manager gave every movie file of a library a new path.
A scan then had to probe most of the library again.
Nothing played.
Another media server on the same host read the same files at the same time.
The limit stayed at 72, the host's core count.
Between 65 and 73 probes ran at once.
The worker logs a probe summary each minute.
Over eight minutes, the average probe time in those summaries rose from 1.4 s to 60 s.
In the last observed minute, all 69 probes that ended had reached the 60 s probe timeout.
The server recorded 207 probe timeouts in about 6 minutes.
The ffprobe processes waited for the disk in uninterruptible sleep.
No brake applied, because no job attempt ran.
Three days earlier, a cold scan of the same library took 2 to 3 s per file.
Only 12 of that scan's probes reached the timeout.

The probes did no useful work.
A probe that reaches the timeout discards every byte that the probe read.
The server retries each timed-out probe, so the retries keep the disk as busy as before.
The number of finished probes fell to zero while the limit stayed at its maximum.
Networks call this failure congestion collapse.
TCP avoids congestion collapse with the rule that the limit already follows.
TCP halves its congestion window when the network loses a packet.
TCP then grows the window by one step at a time.
A probe that reaches the timeout corresponds to a lost packet.
One slow file that times out alone halves the limit once.
The other probes keep finishing, so the limit grows back after the 30 s pause.
When many probes reach the timeout together, the host is the cause, not the files.

TCP also halves the window only once for each window of data in flight.
RFC 5681 describes that rule.
When the first probe times out, many other probes may already be running.
The first brake cannot help the probes that started before the brake.
Those earlier probes keep reaching the timeout for up to 60 s after the first brake.
With only the 15 s wait between brakes, the earlier probes would apply about 4 more brakes and lower a limit of 72 to about 2.

A playback probe that times out also applies the brake.
A playback probe that waits behind the disk reads of background probes is the worst case, because a viewer is waiting.
A playback probe uses the playback probe capacity, which stays fixed.
The brake therefore lowers the background probe capacity, because background probes load the disk.

The server owns the timeout.
The reason in the cancel command is therefore the only way the worker learns of a timeout.
A server shutdown says nothing about the host.
A cancel command with the shutdown reason therefore never applies a brake.
The brake for timed-out probes reacts only when a probe reaches the timeout.
With the default setting, a probe reaches the timeout 60 s after the probe starts.
Pressure stall information gives an earlier signal where the host provides it.

==== The brake from pressure stall information

Linux pressure stall information reports the share of time in which tasks waited for a resource.
The file `/proc/pressure/io` reports that share for IO, such as disk reads.
The `full` line of that file reports the share of time in which every task that had work to do waited for IO at once.
The worker reads the host-wide file `/proc/pressure/io`.
The worker applies a brake while the kernel's 10 s average of the `full` line stays above a threshold.
The brake from pressure counts IO pressure only, not CPU pressure or memory pressure.
https://github.com/streamarr/streamarr-transcode-worker/issues/104[streamarr/streamarr-transcode-worker#104] picks the threshold from a measurement on a host that provides pressure stall information.
A brake from pressure waits until 15 s have passed since the previous brake, whatever applied that brake.
When the file is missing or unreadable, the worker reports that the brake from pressure is unavailable.
The brake for job attempts and the brake for timed-out probes still apply on such a host.
The file is missing on RHEL 8 unless the kernel boots with `psi=1`.
Other kernels can also turn pressure stall information off.
Sandboxed container runtimes such as gVisor or Kata Containers can also lack the file.

*Why:* IO pressure rises as soon as tasks wait for the disk.
A probe reaches the timeout much later.
The pressure is the time that tasks lost while they waited.
The pressure therefore measures harm to work on the host, not how busy the host is.
Linux provides pressure stall information from kernel 4.20.
The brake from pressure therefore cannot be the only brake for a busy host.

The worker reads the host-wide file because other services' disk stalls also slow probes and playback.
Linux does not give each container its own `/proc/pressure`.
An unprivileged container or Kubernetes pod therefore reads the whole host's values.
In a Docker container, `/proc/pressure/io` matched the counters of the host virtual machine.
The container's own cgroup `io.pressure` read 0.
The cgroup file counts only the stalls of the worker's own tasks.

The brake counts IO pressure only, because background probes already run at the lowest CPU priority.

==== Keyframe packet scan capacity

The worker sets the keyframe packet scan capacity to 0 while the worker runs any job attempt.
The keyframe packet scan capacity returns to 1 once no job attempt has run on the worker for 30 s.

*Why:* A keyframe packet scan reads a whole file, and a file can take tens of seconds to scan.
CPU priority does not protect disk reads.
On another media server, a user ran the generation of seek thumbnails at idle CPU priority, and playback from a 7200 RPM disk still failed.
Pausing a scan costs only time.
After the scan finishes, playback can copy the file's video instead of encoding it.

==== CPU priority

The worker runs background probes and keyframe packet scans at the lowest CPU priority, nice 19.
The worker runs playback probes at normal CPU priority.

*Why:* The kernel then gives the worker's job attempts the CPU first, before any brake has measured anything.
A process needs no privilege to lower its own priority.
The priority applies only inside the worker's container.
The priority therefore does not protect playback from other services on the same host.

==== The server's part

The server dispatches as many probes at once as the connected compatible workers grant in total.
db-scheduler still picks, monitors, recovers and retries each probe execution.
The server sets no fixed probe limit of its own beside the granted capacities.
A probe that finds no free unit of the right capacity stays pending without a failure, as the section on how probes run describes.
The worker contract carries each capacity, the probe's kind and each media segment's production time.
https://github.com/streamarr/streamarr-server/issues/578[streamarr/streamarr-server#578] changes the server and the worker contract.
https://github.com/streamarr/streamarr-transcode-worker/issues/93[streamarr/streamarr-transcode-worker#93] changes the worker.
The brake for timed-out probes needs a change to the server and to the worker contract.
The cancel command must say why the server ended the probe.
https://github.com/streamarr/streamarr-server/issues/632[streamarr/streamarr-server#632] adds that reason to the server and to the worker contract.
https://github.com/streamarr/streamarr-transcode-worker/issues/104[streamarr/streamarr-transcode-worker#104] adds the brake for timed-out probes and the brake from pressure stall information to the worker.

This amendment defers the following work:

* A brake from held segment requests.
A held segment request is a viewer's request for a media segment that does not exist yet.
Only the server sees held segment requests.
The worker would need a new message from the server.
* A speed floor for each stream session.
https://github.com/streamarr/streamarr-server/issues/499[streamarr/streamarr-server#499] computes that floor.
The server can then send each job attempt's floor with the attempt.
* A limit on how far a job attempt runs ahead of the viewer.
https://github.com/streamarr/streamarr-server/issues/55[streamarr/streamarr-server#55] covers that limit.

[[playback]]
=== Playback

A playback request for a file without a usable probe outcome moves that file's durable probe to the front of the queue.
The server publishes `MediaFileProbeRequested(mediaFileId)` in `services.events.library`.
The library listener uses the shared enqueue operation, so the file keeps one execution.
The probe dispatcher then picks that execution before every other due execution that has not started.
The dispatcher sends the execution as a playback probe, which uses a worker's playback probe capacity (<<probe-capacity>>).
db-scheduler still picks, monitors, recovers and retries the execution.
If the file's probe is already running, the server starts no second probe.
The playback request then waits for the running probe, even when the running probe is a background probe.
The playback request cancels no running probe of another file.
Moving the execution to the front does not shorten a quiet period or a retry backoff.

*Why the request waits for a running background probe:* The running probe has already done part of the file's work.
A second probe would start from the beginning.
A probe mostly waits for the source's disk, and a second probe would wait for the same disk.
The running background probe's low CPU priority matters only while the CPU is busy.

The playback request then waits for the stored outcome, up to a configured bound.
The wait ends as soon as the server stores the outcome for the requested inputs.
The wait holds no database transaction or connection.
A successful outcome starts playback.
A terminal `probe_error` returns that error as a typed mutation payload error, per ADR 0026.
Two playback requests for the same file wait for the same probe.

The playback request returns the typed not-ready error, `MediaFileProbeNotReadyError`, in three cases:

* The bound passes before the server stores an outcome.
* No compatible worker is connected.
The request returns at once, without waiting for the bound.
* The attempt fails with a retryable reason.
The probe keeps its backoff, and the request does not wait for the retry.

In each of these cases the probe stays at the front of the queue.
The probe runs once a compatible worker connects and the probe's retry time arrives.
A later playback request therefore finds the outcome sooner.
https://github.com/streamarr/streamarr-server/issues/579[streamarr/streamarr-server#579] changes playback this way.

If a file has a stored terminal `probe_error`, a playback request returns that error as a typed mutation payload error.
The server does not enqueue another task for that file.

When this change first ships, no production installations need to migrate.
Scans and the watcher use the shared enqueue operation to request probes when an outcome is missing or outdated.
When an upgrade needs new probe data, the server queues a re-scan itself, as <<upgrade-rescan,the section on source changes and probe versions>> describes.
Streamarr adds no separate backfill mechanism, such as the one that https://github.com/streamarr/streamarr-server/issues/344[streamarr/streamarr-server#344] proposed.
streamarr/streamarr-server#344 stays closed as not planned.
Playback continues to use compatible older successful results while those probes run.

Integration tests verify that scans and watchers can enqueue probes concurrently.
The tests verify that already-matched files receive probes when needed.
The tests also verify that a scan fails if the scan cannot enqueue a probe.
The tests also verify that playback can use a compatible stored result while a probe refreshes that result.
Tests keep a library `SCANNING` while a probe waits for a busy worker.
The tests then let the scan complete after a stored outcome, a recorded failure, or a removed source.
Another test replaces a running attempt's inputs with a new scan request.
The running attempt fails, and the source then becomes unreadable.
The test verifies that the scan can still complete.
Tests also replace the requested inputs while an attempt runs.
The earlier attempt must not publish an outcome.
The earlier attempt must not remove the file's execution.
The file's execution must then carry the newly requested inputs.

This ADR defers the following work:

* Expose container and stream info in GraphQL, for example to display codec badges.
* Add a mutation that lets a ServerAdmin request another probe.
* Hash file contents to detect changes.
The source snapshot currently uses file size and modification time.
* Select streams other than the chosen video stream and the first audio stream.
The code that decides how to transcode would need the selected stream indices.
The worker contract and command builder would also need those indices.
* Report typed codec profiles of audio streams.
Probe version 5 keeps only each audio stream's profile name, as ffprobe prints it.
* Read the frames of video streams other than the chosen video stream.

== Consequences

* When playback starts, the server no longer spawns a probe process.
Playback still needs FFmpeg to remux or transcode into HLS (link:0007-transcode-first-with-smart-remux.adoc[ADR 0007]).
Every playback session needs a job attempt.
After ADR 0033, a worker produces the media.
* Playback consumers use a `MediaProbe` derived from stored rows instead of a probe process result.
* The server adds two entities: `MediaFileContainerInfo` and `MediaFileStreamInfo`.
The server maps the complete probe result to rows in those tables.
* Playback waits, within a configured bound, for a probe that the playback request moved to the front of the queue.
Playback exposes typed errors for unavailable probe data and recorded terminal errors.
The server continues to retry transient failures in the background.
db-scheduler runs the probe executions and stores when each execution should retry.
Before the server publishes a result or ends an execution, the server rejects an attempt whose inputs a newer request replaced.
* Bulk scans probe unchanged files without a per-file quiet period.
Probe requests therefore reach workers sooner, so more probes may have to wait for a busy worker.
Release this behavior with https://github.com/streamarr/streamarr-server/issues/414[issue #414], which keeps probes pending while compatible workers are busy.
* Unless a scan stops or fails, the scan waits for a result from each probe that the scan requested.
During a large first scan, the library stays `SCANNING` while required results are missing.
Workers must produce probe outcomes, or the dispatcher must record why attempts failed.
The scan keeps waiting while probes wait for busy workers.
If no worker is connected, the scan can complete once the dispatcher records each attempt's failure.
Whether a file is ready for playback still depends on the stored probe outcome.
* Each new probe column requires a higher probe version.
When the server processes a file, it schedules a background probe to refresh an outdated outcome.
When an upgrade needs new probe data, the server also queues a re-scan of every library.
After ADR 0033, a worker runs the probe.
Playback can use a compatible outcome while the probe runs.
If a migration invalidates an incompatible outcome, playback cannot use the file until the server records a new outcome.
* ADR 0013's pipeline reads its probe input from rows.
The pipeline itself is unchanged.
* After the upgrade to probe version 4, no file has a usable outcome until a scan or a playback request probes the file again.
The server queues a re-scan itself on the upgrade to probe version 4.
* A full scan under probe version 4 reads more of each library.
The re-scan on the upgrade to probe version 4 is such a full scan.
For a library of 23,210 video files, a version 1 scan reads about 21 GB.
The probe limits of version 4 read an estimated 570 GB more.
The 95 % interval for that extra amount is 270–990 GB.
At 110 MB/s, the extra 570 GB takes about 86 minutes to transfer.
About 2 % of files also need the frame-rate rule's packet scan over 30 s of media.
* A source whose container has no usable keyframe index plays through an encode until its keyframe step finishes.
A source whose index lists a last keyframe that the probe cannot read also plays through an encode until its keyframe step finishes.
That step reads the whole file once.
* The upgrade to probe version 4 deletes the keyframe positions that version 3 stored.
Each source without a usable container index then needs its keyframe step again.
* Probe version 4 leaves four known gaps.
First, `-scan_all_pmts 0` could omit the streams of a later program in a multi-program transport stream.
The library sample held no multi-program transport stream.
Second, 15 PGS subtitle streams in 7 of the 300 sampled files still had no size.
None of the packets of those streams fell within 200 s or 1 GB.
Third, a Dolby Vision profile 5 stream in MPEG-TS without the Dolby Vision descriptor reads as `UNSPECIFIED`.
Fourth, a stream that carries its HDR10 static metadata only in its HEVC bitstream reports none.
Every HEVC stream in MPEG-TS or in a raw HEVC file works this way.
Probe version 5 closes the third gap and the fourth gap.
Probe version 5 identifies such a profile 5 stream from its first RPU header.
The third gap stays open for such a stream when no read decodes a frame of it, because the probe then finds no RPU header (link:0013-stream-decision-architecture.adoc#record-less-profile-5-without-frames[ADR 0013]).
Probe version 5 reads such static metadata from the first frame, or from the SEI messages of the first packets.
* The re-scan on the upgrade to probe version 5 probes every file again.
Each of those probes reads the first frames of the chosen video stream.
Each file keeps its probe version 4 decisions until the server stores the file's probe version 5 outcome.
* Probes and job attempts no longer compete for a worker's slots.
Before this amendment, probes shared the playback slots, and a worker defaulted to one slot.
A cold scan of about 1,800 movies on a 72-core host then spent about 20 minutes probing, at about 1.6 files per second.
About 90 % of the host's CPU stayed idle during that scan.
A large first scan now probes as fast as the worker's cores and storage allow.
* While nothing plays, background probes can load every core of the worker's host.
The brake for job attempts protects only the worker's own job attempts.
Another service on the same host, such as another media server, competes with the probes.
The brake for timed-out probes lowers the background probe capacity once probes stop finishing within the probe timeout.
Where the host provides pressure stall information, the brake from pressure lowers the capacity sooner.
Until a brake applies, the probes can still slow the other service.
An operator who runs such a service on the host can still hold the background probe capacity at a set value with the worker setting.
* A scan runs more slowly while the worker plays, because the brake for job attempts lowers the background probe capacity.
Keyframe packet scans wait until playback ends.
* The worker contract carries a production time with each media segment's upload.
ADR 0044's headroom takes production speed from those reports instead of from arrival times at the server.
* A file whose worker replies keep breaking the contract stops after three attempts with a terminal error.
The file stays unplayable until a scan, a changed source or a new probe version retries the file.
A worker fix that keeps the probe version reaches such a file only through a scan.
A transient corruption that repeats three times in a row also stops a file.
The next scan then retries that file.
* The server no longer spends a worker probe and a database write every five minutes on a reply that never succeeds.

== Rejected Alternatives

* Let playback run an ad hoc probe outside the durable queue when no stored outcome exists.
The ad hoc probe would duplicate the queued probe of the same file.
The ad hoc probe would also bypass db-scheduler's retries and the workers' probe capacity.
Playback instead moves the file's queued probe to the front and waits for the stored outcome.
* Return the not-ready error at once and let the client retry.
The viewer would press play again until a scan's probe reached the file, which can take many minutes in a large library.
* Store raw ffprobe JSON beside the typed columns.
The server would store the same facts twice, while playback and the worker contract would still use typed fields.
* Store summary columns on the container row.
The server would duplicate stream properties and have to keep both copies consistent just to avoid reading the stream rows.
* Store probe outcomes in `media_file.status`.
Matching and probing can succeed or fail independently, so one status cannot preserve both outcomes.
* Add nullable probe columns to `media_file`.
Those columns alone would not distinguish a file that has never been probed from a file whose probe returned unknown values.
* Name the tables `media_analysis`, `media_file_analysis`, or `media_file_metadata`.
In this schema, "media" means the collectable.
"Analysis" names the step rather than the row.
"Metadata" describes data from TMDB.
* Replace ffprobe with a Java library.
Streamarr would need to verify that the library supports MKV, HEVC, Dolby Vision, and audio channel layouts as well as ffprobe does.
* Complete a scan as soon as the server enqueues the probe requests.
The scan would report that it had finished while most files still had no probe result.
* Wait for probes to send in-process signals.
db-scheduler may run a probe after the server restarts or through a path that sends no signal.
The database already records the result.
* Allow deployments to disable the probe dispatcher.
ADR 0027 permits only one active server, so no other server would run the probes.
Scans would never finish, and new files would never become playable.
* Add a second scheduler client to record requests while the starter is off.
Deployments keep the starter on.
The two clients could differ in how they join the transaction that requests a probe.
* Store retryable probe failures as a terminal `probe_error`.
The server would not retry those failures while the source and probe version stayed the same.
* Keep retrying a contract violation forever.
Each retry costs a worker probe and a database write every five minutes.
A broken reply never succeeds.
* Store a terminal `probe_error` on the first contract violation.
A rare transient corruption would then stop a file that a retry would fix.
* Retry a file that contract violations stopped when a different worker build connects.
The worker reports no build identity.
A scan already lets a worker fix reach the file.
* Count an attempt that waits for a busy worker or has been canceled as a failure.
The scan would count files that no worker had finished probing.
* Wait for every retry after an attempt fails.
A file on an unreadable share would keep the scan open indefinitely.
* Retry the failed attempt's inputs after a newer request has replaced those inputs.
If the attempt fails before it compares the source snapshot, the attempt never reaches the new inputs.
The scan would wait indefinitely for a result at those inputs.
* Count a failure that was recorded before the scan requested the probe.
After a share becomes readable again, a new scan would report the old failure while the probe waited for its retry time.
* Use db-scheduler's failure count to decide whether a scan should retry a probe at once.
db-scheduler keeps the count when a probe waits for a busy worker, so a new scan would run that probe too soon.
db-scheduler resets the count when a request replaces a pending probe's inputs.
A scan that requests new inputs would therefore wait for the retry time even if the earlier attempt had failed.
* Read the source again when a scan requests a probe.
If the source became unreadable after the scan listed the file, the whole scan would fail instead of just the probe attempt.
* Retry a failed file on each scan without saving why the probe failed.
An administrator could not see why the file never became playable.
* Delete the probe version 4 outcomes on the upgrade to probe version 5, as the upgrade to probe version 4 deleted older outcomes.
The server can still read every probe version 4 outcome.
Playback of every file would stop until the re-scan stored the file's probe version 5 outcome.
* Keep version 1 and version 3 outcomes usable while the re-scan refreshes them to probe version 4.
Those outcomes would read as an `UNSPECIFIED` dynamic range.
Until the re-scan refreshed an HDR file's outcome, the server would copy that file or encode it without tone mapping.
* Tell the ServerAdmin to run a scan after an upgrade, instead of having the server queue the re-scan.
Playback would stay restricted until a ServerAdmin read the release notes and started the scan.
* Add a separate backfill mechanism that probes outdated files outside a scan, as https://github.com/streamarr/streamarr-server/issues/344[streamarr/streamarr-server#344] proposed.
The scan library operation and the durable probe jobs already request, run and retry every probe that a file needs.
The re-scan that the server queues on an upgrade reuses both.
* Take the first video stream (`0:v:0`) as the stream the transcode decision reads.
A file whose first video stream is cover art fails to encode.
* Take a stream copy's codec string from ffprobe's named profile and level.
Those names lose the H.264 constraint flags.
Those names also lose the HEVC compatibility flags, tier and constraint byte.
Codec strings built from those names matched 41 of 59 video copies.
* Read a stream copy's codec string from the copy's first produced initialization segment, and make the multivariant playlist wait for that segment.
Playback start would wait for a job attempt to produce the initialization segment.
* Keep ffprobe's default limits until the server delivers subtitles.
Raising the limits later would need another probe version and another re-scan of every library.
* Run ffprobe with the 200 s and 1 GB limits but keep its default scan for every program map table.
Every MPEG-TS probe then read to a limit.
The 14 transport streams without PGS subtitles read 66–1,053 MB.
Their results did not change.
* Apply the same limits to a job attempt's FFmpeg input.
FFmpeg analyzes the start of the file before it seeks.
With the limits, an input that seeks into one MPEG-TS source read 220 MB instead of 8.8 MB.
That input also opened 0.5–0.9 s later.
* Have the probe report the facts behind the HEVC tag and have the server apply the tag rule.
The tag rule would then live in two places, the worker and the server.
* Add caption detection to probe version 4.
Caption detection decodes the video's keyframes.
Every version 4 fact comes from the headers and tags of one ffprobe pass.
Probe version 4 would then wait for a change that decodes frames before https://github.com/streamarr/streamarr-server/issues/501[streamarr/streamarr-server#501] could play HDR and 10-bit sources as SDR.
* Leave the stream titles to a later probe version.
Every library would then need a second re-scan before https://github.com/streamarr/streamarr-server/issues/503[streamarr/streamarr-server#503] and https://github.com/streamarr/streamarr-server/issues/60[streamarr/streamarr-server#60] could name their renditions.
The titles come from the same ffprobe pass as the other version 4 facts.
* Have the worker decide which handler names are generic, and report a handler name as the title only when the name is not generic.
The list of generic names is open-ended.
Each fix to the worker's rule would need a new probe version, and every file would then need a new probe.
A rule that treats a name as generic when the name ends with "Handler" would keep "ISO Media file produced by Google Inc." as a track name.
Reporting every handler name adds bytes to the result, so the handler names count toward the 16,384-byte limit together with the titles.
* Leave the hearing-impaired flag to a later probe version.
Every library would then need a second re-scan before https://github.com/streamarr/streamarr-server/issues/60[streamarr/streamarr-server#60] could mark SDH renditions.
The flag comes from the same ffprobe run as the other version 4 facts.
* Give the facts for https://github.com/streamarr/streamarr-server/issues/501[streamarr/streamarr-server#501] probe version 2 after probe version 3 has shipped.
The server compares probe versions by number.
A version 3 outcome would then count as newer than a version 2 outcome, although the version 3 outcome lacks the facts of version 2.
* Scan every packet of every file to find its keyframe positions.
The scan would read whole files whose container index already lists the keyframes.
* Read keyframe positions only from Matroska Cues.
MP4, MOV, MPEG-TS and AVI sources would have no keyframe positions.
The server could then never copy those sources.
* After the probe version that stores keyframe positions takes effect, offer a stream copy before the server knows the source's keyframe positions.
A seek to a media segment without a source keyframe would fail.
The playlist would also advertise durations that the copy does not have.
* Compute the output frame rate at session start or in each job attempt.
Each attempt that needed a packet scan would read the file again.
Attempts that run different versions of the rule could encode on different frame grids.
* Keep one shared slot pool for probes and job attempts.
While a probe held the only slot, playback waited for the scan.
More shared slots would speed up probes, but the extra slots would also admit encodes that the CPU cannot run at speed, as link:0019-recoverable-jit-hls-segment-delivery.adoc[ADR 0019] observed.
* Keep a fixed server-wide probe limit.
The server does not know how many cores each worker has.
A fixed limit leaves a large worker idle and overloads a small worker.
* Let the server compute each worker's probe capacity.
The server cannot see the worker's host, such as another service or a busy disk.
The server would also have to know the size of every worker.
* Keep one probe capacity for every kind of probe and order the probes by priority.
A keyframe packet scan or a background probe that a worker already accepted would then hold the capacity that a playback probe needs.
A playback probe that skipped the capacity would arrive at a worker that granted no room for the probe.
* Refuse keyframe packet scans during playback instead of granting a keyframe packet scan capacity of 0.
The server would keep sending scans to a worker that plays, and each scan would come back refused.
With several workers, the scans would keep going to the worker that plays while another worker sits idle.
* Size the background probe capacity at the worker's cores minus 3.
The 3 reserved cores would sit idle while nothing plays.
A software encode at 4K can need more than 3 cores, so the reserve would not protect that encode either.
* Use Gradient2 or hill climbing on probe throughput as the limit.
Gradient2's defaults suit services with hundreds of requests in flight, not ffprobe on one host.
Hill climbing needed noise handling and about ten interacting parameters in the .NET thread pool.
* Brake on probe latency.
Probe latency depends on each file, and probe latency measures probes, not harm to playback.
A probe that reaches the probe timeout is not a measure of latency.
That probe failed, and the server retries the probe from the beginning.
* Put the probe's deadline in the probe request, and let the worker end the probe at that deadline.
Two clocks would then enforce one deadline.
* Treat every cancel of a probe as a timeout.
The brake would then apply at every server shutdown or restart.
* Let every probe that reaches the timeout apply a brake.
Only the 15 s wait between brakes would space those brakes out.
The probes that started before the first brake would then apply about 4 more brakes and lower a limit of 72 to about 2.
* Read the worker's own cgroup `io.pressure` for the brake from pressure.
That file misses the disk stalls of other services on the host.
* Count CPU pressure in the brake from pressure.
Background probes already run at the lowest CPU priority.
* Read pressure through the kubelet API.
Kubernetes publishes pressure stall metrics there, as KEP-4205 describes.
Those metrics are stable in Kubernetes 1.36.
The kubelet reads the same kernel files.
Every operator would have to grant the worker a service account with RBAC access to node statistics.
The worker would also need node discovery and a code path for Kubernetes only.
The API adds information only inside sandboxed runtimes.
The brake for timed-out probes already covers those runtimes.
* Rely on pressure stall information alone to brake while nothing plays.
Hosts without pressure stall information, such as RHEL 8 by default, would then have no brake for a busy disk.
* Rely on the operator to set a fixed background probe capacity on a shared host.
The operator learns that the capacity is too high only after the probes have stopped finishing.
* Measure production speed on both the server and the worker.
Two measurements of one quantity can disagree, and each needs its own code and tests.
* Brake against each player's own speed floor in this change.
The server does not compute those floors yet.
Building them here would pull ADR 0044's player rules into probe capacity.
* Start a second, normal-priority probe when a playback request finds the file's background probe running.
The second probe would start from the beginning and wait for the same disk.
The running probe usually finishes first.
* Give the worker the Linux capability to raise a running probe's CPU priority.
Every operator, in Docker Compose and in Kubernetes, would have to grant that capability.

The second subtitle stream, without the flag, reported 0.
* An MP4 file kept the flag on its audio stream and on its first subtitle stream.
FFmpeg's MP4 muxer wrote a `kind` box with the scheme `urn:mpeg:dash:role:2011` and the value `caption` into each flagged track.
ffprobe reported that box as both `hearing_impaired` and `captions`.
An MP4 file whose streams had only the `captions` disposition reported `hearing_impaired` as well.
* A Matroska file and an MP4 file that FFmpeg remuxed from each other kept the flag.
* A MOV file lost the flag, because FFmpeg's MOV muxer writes no `kind` box.
A WebM file lost the flag, because FFmpeg's WebM muxer never writes `FlagHearingImpaired`.
* An MPEG-TS file kept the flag on its audio stream.
FFmpeg reads the flag from audio type 2 in an ISO 639 language descriptor, and from the DVB subtitling types 0x20 to 0x25.
* FFmpeg's MP4 demuxer reads no other box for the flag.
So ffprobe reports no flag for a track that only the media characteristics of Apple tools mark as SDH.

[[evidence-frame-rate]]
=== Output frame rate

* The measurements checked the rule on 1,622 video streams.
Those streams came from the library sample, from 1,253 files in FATE (FFmpeg's automated test suite), and from 69 local test sources.
* The rule chose the rate of 294 of the 300 library files from their declared rates alone.
* The packet scan over 30 s of media read 8–113 MB on the other 6 files.
Each scan took 58–336 ms when the file was already in the operating system's cache.
At 110 MB/s, the largest scan would take about 1 s.
* The rule refused 3 test-suite streams and no library file.
* At the rule's rates, 46 of 46 junctions between a first attempt and a replacement attempt passed.
All 20,934 compared output frame positions carried the same source frame and checksum in both attempts.

[[evidence-probe-limits]]
=== ffprobe limits

* Without the limits, ffprobe stops after 5 s of media or 5 MB.
For MPEG-TS, the media limit is 7 s.
* The limits changed what ffprobe reported for 50 of the 300 files.
Every change was on a subtitle stream.
49 files gained the width and height of 319 PGS subtitle streams.
In 50 files, subtitle streams gained a start time at their first packet.
The same subtitle streams lost the stream duration that FFmpeg had copied from the container.
* The limits added or dropped no stream.
Video size and pixel format, audio sample rate and channels, durations, bitrates, `r_frame_rate` and `avg_frame_rate` were identical in all 300 files.
* With the limits, ffprobe read more of 66 files.
The median extra read was 189 MB.
The largest extra read was 1.05 GB.
Without the limits, ffprobe read about 5 MB of each file.
The extra CPU time had a median of 0.2 s and a maximum of 4.6 s.
At 110 MB/s, the extra transfer per affected file would have a median of 1.7 s and a maximum of 9.5 s.
* The 66 files were all 19 MPEG-TS and M2TS files, 45 Matroska files whose PGS subtitle streams had no packet in the first 5 MB or 5 s, and 2 Matroska files with an attachment of unknown type.
* ffprobe sets `scan_all_pmts` by default.
That default disables the early stop for MPEG-TS.
With `-scan_all_pmts 0`, the 19 transport streams gave results identical to the limits alone in every compared field.
The 14 transport streams without PGS subtitles read 0.4–1.9 MB.
Without the limits, those 14 transport streams read 1.6–5.7 MB.
* With the limits, 15 PGS streams in 7 files still had no size.
For the 2 files with an attachment of unknown type, ffprobe read 200 s of media and reported nothing new.
* One measurement used an FFmpeg input that seeks into one MPEG-TS test source.
The limits raised the bytes read before the seek from 8.8 MB to 220 MB.
The limits also raised the time to open the input by 0.5–0.9 s.
* The library-wide estimate weights each container and category by its size in the library.
Its 95 % intervals come from bootstrap resampling.
