= ADR 0059: Releases Stay Draft Until Their Notes Are Curated

== Status

Accepted

Amends the publication gate in link:0034-release-please-owns-maven-release-versions.adoc[ADR 0034].

== Context

Streamarr releases need an editorial summary of user-visible changes, like the server's notes for `v0.0.10`.
Release Please regenerates the open release PR and changelog as commits reach `main`, so manual edits to that generated output do not survive later updates.
Freezing the release PR would stop automatic version and changelog updates and work against the required current base.
ADR 0034 chose immediate publication after merging the release PR, leaving no protected editing stage before the notes become public.

== Decision

Every Streamarr repository using Release Please uses its native draft GitHub releases as the editorial stage.
The current consumers are the server and transcode worker.
Set `draft: true` and `force-tag-creation: true` for each released package in its repository's Release Please configuration.
Merging the stable release PR records the stable POM version, creates the tag at that merged revision, and creates an unpublished GitHub release with generated notes.
The tag exists immediately, even while the release is a draft, so subsequent version calculations have a fixed baseline.
The maintainer edits the draft GitHub release body, then explicitly publishes that release.
The draft release body owns the curated summary; `CHANGELOG.md` remains the generated commit-level record.
Normal Release Please runs process the merged PR once and then advance to the next snapshot; they do not regenerate the processed release's edited body.
A rerun after a partly failed release run finds the release it already created and completes the run without creating another.

Publishing the stable GitHub release starts the existing image publisher.
The publisher still requires a published release, validates the stable tag and matching POM, and builds the exact tagged revision for both architectures.
Creating a tag, creating a draft, or editing notes does not start stable image publication.
Main CI continues publishing commit and snapshot images independently.
Manual image retries continue to reject unpublished drafts.

Release Please retains ownership of versions, tags, the release PR, and the next snapshot.
Keep the official action, pinned shared workflows, release App, and required checks from ADR 0034.
Repositories that do not use Release Please retain their existing release processes.

== Consequences

A release now has two maintainer actions: merge the release PR to fix its contents, then publish the draft after curating its notes.
Development and snapshot preparation can continue while the draft is being edited without moving the release tag or changing its summary.
The curated GitHub notes may differ from the generated changelog and do not get copied back into it.
The Git tag is visible before the GitHub release and release images are published.
No preservation label, custom Release Please runner, or note synchronization job is needed.

== Rejected Alternatives

* Keep immediate publication and edit the published notes afterward — exposes the generated notes before editorial review.
* Freeze the release PR with a label — stops regeneration of versions and changelogs and requires manual branch maintenance.
* Restore notes from a separate file or comment after each update — adds synchronization and stale-summary handling that the native draft stage avoids.
* Use commit overrides for the whole summary — useful for individual changelog corrections, but does not express a freely curated release-wide narrative.
