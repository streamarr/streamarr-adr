= ADR 0028: Credential Attempts Are Journaled and Throttled in PostgreSQL

== Status

Proposed

== Context

link:0016-authentication-mechanisms-and-session-security.adoc[ADR 0016] requires online credential guessing to be throttled.
The first implementation kept sliding-window budgets in each server process for login, authenticated Account-password verification, Profile PINs, invitation codes, password-reset codes, manager-invitation codes, and device-pairing codes.
Those independent budgets disagree as soon as requests reach more than one server instance, and a restart erases their state.

Streamarr needs one admission decision across instances without holding a database transaction open while Argon2 or another credential verifier runs.
Operators may eventually want configurable policy and IP-based controls, but neither is required to make the current behavior horizontally correct.
IP addresses remain useful evidence even when the application does not use them to reject traffic.

== Decision

Every request that reaches credential verification reserves an attempt in PostgreSQL before verification and completes it as `FAILED` or `SUCCEEDED` afterwards.
Transport-validation failures and policy-blocked requests do not create rows.
An unexpected process or verifier failure leaves the reservation pending until it becomes abandoned.

The `credential_attempt` journal stores:

* a UUID id and `credential_kind`;
* nullable `account_id`, `profile_id`, and polymorphic `credential_id` target identifiers;
* an `INET` client address;
* `attempted_at`; and
* nullable `completed_at` and `result` (`FAILED` or `SUCCEEDED`), which are both null or both populated.

The journal has no foreign keys to Accounts, Profiles, or credential rows because security history must survive deletion of those subjects.
It stores no email, PIN, public code id, code, password, digest, or hash.
Unresolved emails and codes produce a failed row with null target identifiers and are not subject-throttled.

`CredentialKind` is one of `ACCOUNT_LOGIN`, `ACCOUNT_PASSWORD_VERIFICATION`, `PROFILE_PIN`, `ACCOUNT_INVITATION_CODE`, `PASSWORD_RESET_CODE`, `PROFILE_MANAGER_INVITATION_CODE`, or `DEVICE_PAIRING_CODE`.
`ACCOUNT_PASSWORD_VERIFICATION` means checking an authenticated Account's current password for reauthentication or password change; it does not mean password reset.

Policy is a sealed `CredentialAttemptPolicy` with `Unlimited` and `Limited` variants.
`Limited` contains a positive maximum-failure count, failure window, and throttle duration; both durations are positive and no longer than 24 hours.
A provider selects policy by credential kind.
The standard provider applies five failures in 15 minutes followed by a 15-minute lockout to every kind.
`Unlimited` is supported but is not the default, records every attempt, and never rejects admission.
Policy is code in this increment, not YAML, a database settings row, or an administrative API.

A limited, resolved target follows this admission protocol:

* failures completed at or before its latest success are ignored;
* the first five failures are admitted, and completion of the fifth begins the full lockout;
* fresh pending reservations consume capacity so concurrent verifiers cannot overrun the limit;
* a pending reservation is abandoned after five minutes; and
* a blocked request creates no row, so rejected traffic cannot prolong the lockout or amplify storage.

Reservation and completion each run in a short `REQUIRES_NEW` transaction.
A bounded transaction-scoped PostgreSQL advisory lock derived from credential kind and known target identifiers serializes the target's admission decisions across instances.
No transaction or advisory lock spans Argon2, PIN hashing, code comparison, or another verifier.
Database and lock failures fail closed as service unavailable rather than being reported as a credential mismatch or success.

The application keeps the public throttling contracts that already exist, including HTTP 429 responses and device-pairing `Retry-After`.
Driving adapters resolve the request's client address from the trusted-proxy-aware servlet request and pass it explicitly through commands; application services do not import servlet, HTTP, GraphQL, or DGS types.
The address is observational only, is exposed through no API, and has no index or admission policy.
A success resets only its credential target's failure sequence.
The firewall owns volumetric and IP-based enforcement.

Attempts are retained for 30 days.
A scheduled database deletion removes older rows, while successful attempts remain until retention and reset a target's failure sequence logically rather than by deleting history.

Explicitly deferred:

* persisted or UI-editable throttle policy;
* IP-based admission, IP indexes, subnet policy, and privacy-preserving address transforms; and
* configurable retention and abandoned-reservation timeouts.

== Consequences

* Credential admission is consistent across server instances and survives process restarts.
* Every verifier depends on PostgreSQL availability; failing closed can temporarily refuse valid credentials when the database or advisory lock is unavailable.
* Pending reservations bound concurrent guessing without holding scarce database resources across expensive verification.
* The append-oriented journal supports future policy changes and investigation without making current admission depend on IP.
* Thirty-day IP retention creates an explicit privacy and cleanup obligation.
* The journal grows by one row for every admitted credential verification, including successes and unresolved failures.
* The in-memory login, credential-guess, device-guess, and sliding-window throttle implementations and their YAML limits are removed.

== Rejected Alternatives

* Keep per-instance in-memory budgets — limits diverge across replicas and disappear on restart.
* Store only the last attempt or a mutable counter — policy changes would lose the event history needed to evaluate a different window or distinguish pending, failed, and successful attempts.
* Use the security audit log — credential admission has different write volume, retention, target, pending-reservation, and privacy requirements.
* Hold a transaction across credential verification — Argon2 latency would hold a connection and lock across expensive work.
* Enforce IP limits now — self-hosted deployments often share a proxy address, application IP policy has not been requested, and the firewall already owns volumetric protection.
* Persist policy now — no production compatibility requirement or settings UI needs it yet; the sealed provider keeps the policy boundary explicit without speculative schema.
